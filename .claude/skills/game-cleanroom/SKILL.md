# 게임 클린룸 제작 스킬

게임 1개 = 클린 세션 1개 체제의 실행기. **단일 원본은
`docs/standards/game-cleanroom-pipeline.md`** — 이 스킬은 그 문서를 로드해 실행하는
오케스트레이터다. 품질 게이트·프롬프트 문구를 여기서 재작성하지 않는다 (드리프트 방지).

## 절차

### 0. 단일 원본 로드
`docs/standards/game-cleanroom-pipeline.md` 를 읽는다. 이 문서의 "마스터 프롬프트" 블록과
"통합 절차" 절이 이후 모든 단계의 지시서다.

### 1. 슬롯 채우기
사용자 인자에서 추출한다. 모자란 슬롯은 아래 기본값으로 채우고, 장르가 아예 없을 때만 묻는다.

| 슬롯 | 기본값 |
|---|---|
| ⟨장르/컨셉⟩ | (필수 — 없으면 질문) |
| ⟨벤치마크⟩ | 장르 대표작 중 32비트 세대 이상 명작을 스스로 지정하고 명시 |
| ⟨콘텐츠 깊이⟩ | 문서의 슬롯 작성 예에서 장르에 맞는 것 |
| ⟨slug⟩ | 영문 kebab-case 로 직접 작명 |
| ⟨해상도⟩ | "1440p급 캔버스 또는 그에 준하는 밀도" |
| ⟨타겟 방향⟩ | **세로(1080×1440 계열)가 기본**. 가로가 꼭 필요한 장르만 가로 전용으로 선언하고 근거를 적게 한다 — 16:9 가로 캔버스는 세로 폰에서 자동 실패다 (문서 G5-2) |
| ⟨장르 프리셋⟩ | `--preset <이름>` 또는 컨셉에서 장르 추론. **문서의 "장르 프리셋" 절 블록을 통째로 프롬프트에 붙인다** |
| ⟨진행 모드⟩ | **수직 슬라이스 우선** (문서의 "진행 모드" 절). 사용자가 "끝까지 완성"을 명시했을 때만 무중단 완주 |

### 1.5 장르 프리셋 적용 (2026-08-16 신설 — 필수)
사용자가 "이런 느낌의 게임" 이라고 컨셉만 줘도 그 장르의 **필(feel) 규약이 수치로** 실려
나가야 한다. 문서의 **"장르 프리셋"** 절에서 해당 프리셋 블록을 찾아 **그대로 프롬프트에
붙인다** (카메라 스케일 / 액터 충돌 규약 / 응답성 수치 / 시점 / 필수 기술 체계 / 규모).

- `--preset arcade-beltscroll` — 고속 아케이드 벨트스크롤 (검증됨)
- 프리셋이 없는 장르면: 6축 게이트만으로는 **체감**을 못 잡는다는 것을 전제로,
  그 장르의 필 규약을 사용자와 1회 확인한 뒤 새 프리셋으로 문서에 박는다
- 근거: `ashen-warband` 1차는 6축 전 축 통과에도 사용자 플레이에서 하한 미달 —
  원인은 그래픽이 아니라 장르 필(캐릭터 과대·평면 협소·시체 블로킹·느린 발동·미끄러짐)

### 2. 제작 모드 결정
- **이 세션이 새로 열린 클린 세션이면 (기본)**: 마스터 프롬프트를 자기 임무로 삼아 직접
  수행한다. 클린룸 하드 룰을 스스로에게 적용한다 — 다른 게임 폴더·`lib/`·게임 문서를
  열람하지 않는다 (파이프라인 문서 자체는 예외).
- **사용자가 "위임"/"서브세션"을 명시했으면**: Agent 로 클린룸 세션을 기동한다.
  프롬프트 = 마스터 프롬프트 전문(슬롯 채운 것). 백그라운드로 두고 완료 보고를 기다린다.

### 2.5 진행 체크포인트 (디폴트 — 2026-08-15 피드백 반영)
**극초반 수직 슬라이스만 먼저 완성 → 사용자 체크 → 반영 후 완주**가 기본 흐름이다.
슬라이스 = 핵심 조작 전부 + 대표 적 2~3종 + 이펙트/사운드/아트 문법 최종본 + 벤치마크
나란히 비교표. 슬라이스 품질이 전체의 상한이므로 하한 판정을 여기서 끝낸다.
사용자가 "끝까지 완성"을 명시적으로 지시한 경우에만 중간 체크 없이 묻지 않고 완주한다.

### 3. 품질 게이트 집행
문서의 ★품질 게이트 5축(아트/게임필/콘텐츠/사운드·UI/조작)이 완성의 정의다.
- **벤치마크 = 하한선.** 그래픽/애니메이션/해상도 활용/이펙트/조작감/연출 6축 비교표에서
  전 축 "동급 이상"이어야 완성이다. 미달 축은 "미완 명시"가 아니라 **개선 반복** 대상.
  (nova-strike 1차 실측: 이 강제가 없어 벤치마크 대비 30점 평가 — 재발 금지)
- 미달 상태로 "완성" 을 선언하지 않는다. 비주얼 반복 3회+ 는 회차별 점검축 기록과 함께.
- 검증은 실제 KeyboardEvent 만 인정, 콘솔 에러 0, 60fps 수치 보고.
- **★ 모바일 두 방향 실측 없이 완성 선언 금지** (2026-08-24 — 가장 자주 실패한 축).
  같은 세션에서 CDP 디바이스 에뮬레이션으로 **세로 390×844 · 가로 844×390** 을 둘 다 재고,
  문서의 "모바일 두 방향 감사" 표를 채운다. 크기는 **레터박스 배율을 포함한 CSS px** 로 —
  논리 좌표로 재면 전부 통과처럼 보인다. 데스크톱만 보고 완성을 선언한 결과가
  **50여 종 공통 결함**이다
- 이미지/캡처는 절대 대화(컨텍스트)로 통과시키지 않는다 — 문서의 업로드 서버 스니펫 사용.

### 4. 완성 후 — 플랫폼 통합
게임 완성 선언 **이후에만** 문서의 "통합 절차" 를 수행한다 (이 시점부터 클린룸 열람 제한
해제): **rank.js + platform.js 배선(순서 중요 — rank.js 가 앞)** → **모바일 배선**(가상패드 게임은
`lib/touch.js` + 3-part 한글 라벨, 네이티브 터치 게임은 그 판단을 문서에 명시) →
**`scripts/lint-game-mobile.py <slug>` 통과** → 썸네일(업로드 서버 방식) →
**V시드(`supports_mobile` · `orientation` 포함)** + Testcontainers 검증 →
game/CLAUDE.md 행 → 커밋 → 푸시는 사용자에게 1회 확인 → 배포 후 portal-fe 재빌드.

- `supports_mobile=1` 은 **약속**이다 — 두 방향 실측을 통과한 뒤에만 켠다
- 가로 전용 게임은 `orientation=LANDSCAPE` 를 채운다 (자동 가로 전환의 유일한 근거)

### 5. 최종 보고
문서의 "최종 보고 양식" 그대로. 미달 축 은폐 금지 — 벤치마크 대비 자평에 정직하게 적는다.

## 주의
- **모바일이 1순위 타겟이다** — 데스크톱에서 좋고 모바일에서 나쁘면 실패. 반대는 허용.
  문서의 전역 가드레일 **G5** 전문을 프롬프트에 함께 붙인다 (프리셋과 같은 취급)
- **새 런타임 기술(WASM/WebGL/Worker 등)은 문서의 "기술 도입 게이트"를 통과해야 한다** —
  측정 없이 도입 금지, 사다리 아랫단 우선, 빌드 스텝 도입은 최후.
  **비2D(3D 지향·물리 헤비) 신작은 같은 절 §8 로 유니티/캔버스를 먼저 판정**한다
- 파이프라인 문서와 이 스킬이 충돌하면 **문서가 이긴다** — 문서를 고치고 스킬은 얇게 유지
- 실측 함정 목록(문서 내)은 매 제작마다 갱신 후보다 — 새 함정을 발견하면 문서에 추가할 것
