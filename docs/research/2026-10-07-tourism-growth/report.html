조사일: 2026-10-07 · 상태: 의사결정용 제안 · 대상: https://place.1989v.com/ 운영 화면·HTTP 응답·현재 작업 트리·공식 외부 자료를 교차 확인했다. 서비스 구현이나 배포를 변경하는 문서가 아니다.

1. 판단: 데이터의 양에서 ‘방문 결정을 돕는 정보’로

추천 방향은 한국 여행에 특화된 ‘조건별 관광지 발견 + 믿을 수 있는 방문 정보 + 저장·공유’ 서비스다. 세계 전체 관광지 확장보다, 한국의 몇 개 지역에서 방문 결정을 가장 잘 돕는 경험을 먼저 만든다. 글로벌 사이트는 범위를 그대로 따라갈 대상이 아니라 정보 설계의 벤치마크다.

현재 서비스는 지도 검색만 있는 초기 제품이 아니다. 한·영 정보, 관광지 상세, 지역별 탐색, 무료·주차·반려동물·접근성 필터, 찜, 주변 장소, 행사, 날씨, 영상, 외부 여행 상품 링크까지 있다. 핵심 문제는 기능 부족보다 우선순위·정보 정제·신뢰·검색 유입 후의 행동 연결이다.

바로 결정할 세 가지:

  1. 첫 사용자: 우선 국내 자유여행자의 ‘주말/당일 여행지 고르기’를 90일 가설로 삼는다. 외국인 대상 서울 핵심 명소는 별도 소규모 실험으로 검증한다. 타깃을 확정한 사용자 답변은 없으므로 이는 제안이다.
  2. 첫 상품 가치: “어디가 유명한가”에 더해 “내 조건에 맞고, 방문 전에 무엇을 확인해야 하는가”를 답한다. 무료·주차·동반 조건이라는 기존 자산을 활용한다.
  3. 첫 투자: 화면 재배치와 신뢰 정보 → 지역·상황별 편집 콘텐츠 → 공유·유통 → 검증된 범위 확대 순서다. 전면 프레임워크 교체와 자체 예약 엔진은 후순위다.

운영 화면에 있는 필터·주변 탐색·행사 등 일부가 현재 로컬 파일보다 확장되어 있었다. 따라서 운영에서 확인한 기능을 우선하며, 로컬에 없다는 이유로 운영에도 없다고 판정하지 않았다. 작업 트리는 다른 변경이 다수 있어 분석 산출물만 별도 디렉터리에 작성했다.

스크린샷·모바일 에뮬레이션 도구는 자동 승인 검토에서 거절되었다(approval policy is never). 픽셀 단위 시각 검수와 모바일 평가를 완료했다고 주장하지 않는다. 초기 Python 기본 HTTP 클라이언트는 403/1010을 받았으나 일반 브라우저와 curl은 정상 응답했다. 이것만으로 Googlebot 차단을 단정할 수 없다.

증거: HTTP 기본 표본, 상세 후반 표본, 사이트맵 항목 집계, 운영 UI 관찰 기록. HTTP의 textChars는 title 등을 포함한 단순 텍스트 추출 길이이며 본문 품질 점수가 아니다. xRobots는 헤더 미수집으로 판정하지 않는다.

3. 현재 서비스: 유지할 강점과 실제 마찰

이미 있는 강점

  • 탐색 기반: 지도/목록, 지역 드릴다운, 내 주변, 자연·역사·문화·레포츠·행사·코스, 지도 위 음식·쇼핑·숙박.
  • 조건 필터: 무료입장, 주차, 반려동물, 휠체어·엘리베이터·장애인 화장실 등. “정보가 있는 곳만 거릅니다”라는 한계 안내도 있다.
  • 방문 보조: 경복궁 상세에 사진 7장, 이용시간·휴무·요금·주차, 주변 탐색, 지역 날씨·대기질·혼잡도 탭, 영상, 외부 링크가 있다. 탭 존재와 각 데이터 정확성은 다른 문제다.
  • 재방문 기반: 카드 찜과 /favorites 진입이 있다. 찜 기능을 새로 만들라는 권고는 부정확하다.
  • 검색 기반: 원본 HTML 본문, 고유 title/description/canonical, 지역 링크, 한·영 허브/지역 hreflang, BreadcrumbList, TouristAttraction, 행사 Event, 분할 사이트맵.

근거: 국문 홈, 영문 홈, 경복궁 상세, 서울 지역.

관찰 → 사용자 영향 → 개선

관찰 해석/영향 가설 권고
홈 상단에 유형·시설·서울 25개 구 선택이 연속 노출. 첫 카드 y=441px 탐색 시작 전 선택 부담, 작은 화면에서는 더 클 가능성 지역 1개 + 주요 테마 + ‘필터’로 압축. 선택한 조건만 항상 노출
카드가 주소와 긴 역사/설명 발췌 중심 여러 후보의 차이와 적합성을 비교하기 어려움 ‘추천 이유 1줄 + 확인된 실용 속성 2~3개’로 재편
경복궁의 긴 역사 설명 다음에 이용 안내 당일 방문자가 필요한 요금·휴무를 늦게 찾음 제목·사진 → 방문 요약 → 길찾기·저장 → 설명·주변 순서

영문 서울 필터에 Credit cards·Stroller·Pets 0건 ‘불가능’과 ‘정보 없음’을 혼동할 수 있음 0건 선택의 설명, 확인된 데이터 범위 표시, 조건 완화 제안
‘오늘 정기휴무 아님’/‘Not closed today’ 영문은 현재 영업 중으로 읽힐 가능성 ‘정기휴무 기준’ 표시. 특별휴무·영업시간 미검증이면 ‘Open now’ 금지
주변 장소에 광화문·건청궁 모두 6m 표시 원천 대표 좌표의 중복 가능성, 이동거리로 오해 ‘직선거리·대표 좌표’ 표시, 입구 좌표/도보 시간은 별도 검증
로컬 FavoriteButton은 비로그인 시 apex 로그인 이동 첫 저장에 서비스 맥락 이탈 가능성 게스트 로컬 저장 후 동기화 제안. 운영 완주를 먼저 확인
지역 원본 HTML은 제목·소개·행정구역·명소 링크 중심 지역 고유의 여행 판단 정보가 적음 일정 길이·여행 목적별 추천과 편집 근거를 추가

관찰된 UI 문제와 전환 저하의 인과관계는 아직 사용자 실험으로 검증되지 않았다. 카드에 즉시 임의 평점·소요시간·혼잡도를 채워 넣는 방식으로 해결하지 않는다.

4. 글로벌 벤치마크 6개

대중적 글로벌 서비스와 전문 발견형 서비스를 역할별로 선정했다. 아래 순서는 방문자 수 순위가 아니다. 트래픽/시장점유율은 이번 조사에서 검증하지 않았다. 동일한 서울 목적지 페이지를 우선 비교했다.

서비스·역할 공식 페이지에서 확인한 구조 K-관광과의 차이 가져올 패턴과 비용
Tripadvisor — 후기 기반 선택 명소 순위, 평점·리뷰 수, 여행자 의견, 지도, 체험 연결 K-관광은 공식 정보 중심으로 확인된 여행자 검증 신호가 약함 초기에는 ‘왜 추천하는지’ 편집 근거부터. 자체 리뷰는 신고·조작 방지 운영 비용 필요
Google Maps — 장소 저장과 실행 장소 리스트 생성·저장·공유·팔로우 단건 찜 이후 동행자와 함께 고르는 경험을 더 키울 여지 게스트 저장, 이름 붙인 목록, 공유 링크, 지도 앱 인계. 지도 자체 재구현은 불필요
Lonely Planet — 편집형 여행 안내 명소 외 방문 시기·교통·무료 활동·동네·당일 여행 가이드, 저자 현재 지역 페이지는 장소 목록 중심 지역당 ‘처음 가는 사람의 선택 기준’과 현장 팁. 꾸준한 검수 필요
Atlas Obscura — 취향 기반 발견 숨은 장소의 이야기, 테마, 지도, 가고 싶은/다녀온 곳 활동 현재 넓은 분류와 원천 소개에서 발견의 이유가 약함 ‘서울 오래된 골목’, ‘비 오는 날 박물관’ 같은 선명한 편집 관점
GetYourGuide — 의도별 활동 선택 관심사, 가족/커플/휠체어 접근성, 비 오는 날·야간·숨은 명소, 목적지 가이드 기존 시설 필터를 여행 상황과 연결할 여지 실제 속성으로 뒷받침한 상황별 진입. 투어 재고·예약 운영은 별도 사업
Klook — 목적지에서 상품 실행까지 명소·체험·교통 묶음, 이용 가능일·취소 조건·가격·평점 현재 상품 검색 링크는 있으나 선택한 장소와 상품 관계 설명이 약함 검증된 상품만 문맥 연결하고 외부 이동 명시. 가격/재고 동기화 비용 고려

출처: Tripadvisor 서울, Google Maps 리스트 도움말, Lonely Planet 서울, Atlas Obscura 서울, GetYourGuide 서울, Klook 서울.

국내 직접 비교도 필요하다. 대한민국 구석구석은 공식 명소, 추천 기사, 여행 정보를 제공한다. 같은 공공데이터를 더 많이 보여주는 것만으로 차별화하기는 어렵다는 판단이다. K-관광의 차이는 ‘조건 비교의 속도’, ‘정보 근거의 명확성’, ‘실제로 쓸 저장·공유 경험’에서 만들어야 한다.

5. UI/UX 개선안

화면 구성 상세 보완: 탐색 플로우·카드·지도·상태별 상세 설계와 직접 조작하는 HTML 스켈레톤을 함께 볼 수 있다. HTML은 검토용 예시 데이터로 동작하며 실제 지도·예약·공개 공유에 연결되지 않는다.

검색 품질: 경복궁, Gyeongbokgung, 궁궐, 제주 무료, 비 오는 날 서울 등 30개 평가 질의를 만든다. 지원하지 않는 자연어 조건은 해석했다고 가장하지 않고 사용 가능한 필터로 안내한다. 잘못된 지역·동명이인·별칭·오타·0건을 별도로 평가한다.

C. 저장·공유: 기존 찜에서 작은 여행 계획으로

제안 흐름은 검색 → 후보 3곳 저장 → 목록 이름 설정 → 링크 공유 → 동행자 열람 → 길찾기다. 게스트 저장은 로컬 브라우저 범위임을 알려주고 로그인 시 계정에 합친다. 공유 목록은 사용자가 명시적으로 공유할 때 생성하며, 기본 공개 SEO 페이지로 만들지 않는다.

첫 버전은 후보 목록과 간단한 메모면 충분하다. 경로 최적화·실시간 협업·AI 일정 자동 생성은 실제 저장/공유 사용을 확인한 다음 결정한다.

D. 시각·접근성 원칙

사진이 목적지를 설명하고 타이포그래피가 정보 중요도를 드러내도록 한다. 새 브랜드 팔레트를 즉흥적으로 추가하기보다 root DESIGN.md의 k-heritage 관련 토큰과 기존 컴포넌트를 우선 사용한다. 지도 위 텍스트, 사진 위 라벨, 버튼 상태의 명도 대비는 실측한다.

모바일 검증 계획: 390px·360px·320px, 목록/지도 전환, 필터 시트 열고 닫기, 뒤로 가기 시 검색 조건·스크롤 복원, 키보드 노출, 느린 네트워크, 지도 실패 폴백. 이미지 대체 텍스트는 장식인지 정보 전달인지 구분하고, 지도 없이도 목록과 주소로 탐색 가능하게 한다. 이번 조사에서 모바일 검증을 수행한 것은 아니다.

E. 화면별 구성과 지도 비율 — 상세 보완

화면 데스크톱 제안 모바일 제안 핵심 상호작용
탐색 시작 검색 + 지역/상황별 작은 추천 묶음 검색과 지역 선택을 먼저 노출 추천 선택 시 조건이 보이는 검색 결과로 이동
검색 결과 1200px 이상에서 목록 약 46% / 지도 약 54% 한 열 목록을 기본으로 지도 전환 카드·핀 선택 동기화, 필터 결과 일치
필터 그룹별 다이얼로그 바텀시트 또는 전체 화면 초안 수정 후 적용, 취소 시 기존 조건 유지

비율은 고정 규칙이 아니라 시안에서 비교할 시작값이다. 넓은 지도와 좁은 목록은 위치 이해에는 유리하지만 정보 비교를 어렵게 한다. 사진 그리드는 발견에 유리하지만 위치 관계를 별도로 확인해야 한다. 그래서 검색에는 병렬 배치, 첫 발견에는 카드 묶음, 모바일에는 한 번에 하나의 작업을 선택했다.

관광지 카드는 장소명·지역·선택 이유·확인된 방문 조건·저장을 보여준다. 예약 상품 카드는 판매하는 옵션·제공업체·포함사항·가격의 기준·취소 조건·외부 판매처 이동을 보여준다. 장소 정보와 구매 상품을 같은 목록의 같은 카드로 섞지 않는다.

지도는 결과 집합의 다른 표현이다. 핀 클릭은 해당 카드 선택, 카드의 지도 선택은 핀 강조로 이어진다. 상세 진입은 별도 행동으로 두어 핀을 확인할 때마다 화면이 바뀌지 않게 한다. 지도 범위가 바뀌면 명시적인 ‘이 지역에서 다시 검색’으로 적용하며, 거리는 직선거리와 이동시간을 구분한다.

시안에는 정상·로딩·0건·오류 상태를 포함한다. 자동완성의 키보드 동작, 한글 입력 조합, 필터 취소, 상세에서 돌아왔을 때 선택과 스크롤 복원은 배치만큼 중요한 검토 항목이다. 전체 상태 규칙과 카드 구조는 화면 구성 상세안에 있다. HTML 시안의 반응형 검증과 운영 사이트의 모바일 검증은 별개다.

6. 콘텐츠·데이터 확장 전략

단계적으로 넓힐 범위

  1. 서울·부산·제주 × 2개 상황, 편집 페이지 6개: 팀이 실제 검수할 수 있는 지역부터. 콘텐츠 예산이 작으면 서울 2개부터 시작한다.
  2. 핵심 상세 30개: 원문 정제, 방문 요약, 공식 링크, 출처/시각, 사진·언어 품질을 검수한다.
  3. 영문 서울 핵심 10개: 영문 데이터의 현지명·교통·결제·예약 안내를 검증한다. 성공한 한국어 글을 기계번역해 전량 발행하지 않는다.
  4. 성공한 조건/지역만 확대: 검색 노출보다 저장·길찾기·수정 제안 등 실제 사용까지 확인한다.

11. 실행 전에 남은 결정

  • 국내 여행자 중심인지, 방한 외국인 중심인지. 후자라면 영문 정보 정제·교통/결제 안내·언어 쌍 연결이 P0로 올라간다.
  • 실제 Search Console 권한/현황과 28일 유입 데이터. 미색인 원인을 현재 공개 표본만으로 단정할 수 없다.
  • 주당 콘텐츠 검수 시간과 처음 집중할 지역. 운영 여력이 30곳을 감당하지 못하면 10곳으로 줄인다.
  • 현재 배포된 소스 버전/브랜치. 운영과 로컬 차이를 정리한 뒤 구현 범위를 확정한다.
  • 게스트 저장과 공유 공개 범위, 오류 제보 검토 담당자.

다음 구현의 작은 범위 제안: ‘홈 필터 압축 + 경복궁 상세 방문 요약 + 영문 카드 정제’의 시안/명세를 먼저 확정한다. 그다음 지정된 Codex 구현 에이전트로 구현·검증하고, 결과를 본 뒤 지역 가이드와 저장·공유로 넓힌다.
