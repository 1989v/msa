## 1. 무엇을 만드는가

커피 사는 사람 정하기, 순서 정하기에 쓰는 **카드 뽑기 도구**.
참가자 수만큼 카드를 엎어 놓고 한 명씩 뒤집는다.

실력 게임이 아니라 도구다. 그래서 1급 목표가 재미가 아니라 **공정성과 그 증명**이고,
재미는 "결과가 나오기까지 지켜보게 만드는 연출" 로 만든다.

**이 게임의 심장은 남은 확률이다.** 여섯 장 중 한 장일 때는 아무렇지 않다가 두 장 남으면
손이 떨린다. 그래서 확률은 HUD 구석의 작은 숫자가 아니라 판 위쪽의 **큰 글자**로 두고,
오를수록 노랑에서 빨강으로 가며, **심장 박동 소리가 같은 값을 따라 빨라진다**
(72 → 158 BPM). 화면을 안 보고 있어도 조여드는 게 들려야 한다.

## 2. 사행성 가드레일 (프리셋 1절 — 앞선 두 산출물과 동일)

- 돈·포인트 입력란이 **없다**. 배당·당첨금·베팅 표현을 쓰지 않는다
- 결과를 미리 정해 두고 연출만 재생하지 않는다 (§3 재현)
- 참가자 이름은 기기 밖으로 나가지 않는다 → `PlatformAdapter` 미부착, 랭킹 없음, `sdk_integrated=0`

## 3. 공정성 — 이 게임에서 의심받는 건 딱 하나다

### 먼저 뽑는 게 불리한가 — 아니다, 그리고 그게 반직관이다

k 번째 사람이 걸릴 확률:

```
(n−1)/n · (n−2)/(n−1) · … · (n−k+1)/(n−k+2) · 1/(n−k+1) = 1/n
```

앞이 전부 약분된다. **남은 카드가 줄어 확률이 오르는 것과, 자기 차례까지 갈 확률이 줄어드는
것이 정확히 상쇄된다.** 사람들이 가장 자주 틀리는 직관이라, 이 게임은 그 직관을 화면에서
보여 주고(확률이 실제로 오르는 것을 매 판 본다) 수치로 반박한다.

실측 (n=6, 각 4,000판):

| 고르는 방식 | 차례별 걸림 수 | χ² | 임계값(α=.05, df=5) |
|---|---|---|---|
| 왼쪽부터 | 663 / 670 / 707 / 647 / 640 / 673 | **4.18** | 11.07 |
| 아무거나 | 653 / 689 / 666 / 689 / 643 / 660 | **2.68** | 11.07 |

**고르는 방식도 결과를 바꾸지 않는다.** 이걸 따로 잰 이유는 "왼쪽부터 뽑으면 손해" 같은
말이 실제로 나오기 때문이다 — `Deck.simulate()` 가 고르는 방식을 인자로 받는 건 그래서다.

### 출발 위치가 결과를 정하지 않는다 — 장르 공통 하한선

| 방식 | ρ (뽑는 차례 ↔ 결과) | 통과선 |
|---|---|---|
| 순서 정하기 | **−0.011** | \|ρ\| < 0.1 |
| 한 명이 걸린다 | **−0.008** | \|ρ\| < 0.1 |

각 2,500판 × 6명 = 15,000 표본. `dev.startBias(runs, n, mode)`.

> 앞선 두 산출물과 대조하면 이 장르의 성질이 드러난다. 구슬 레이스는 출발 자리를 한 줄로
> 세우면 ρ −0.27 이었고 **한 통에 담아 쏟아** 지웠다. 사다리는 12명에서 0.641 이었고
> **아래 항목을 섞어** 지웠다. 카드 뒤집기는 **처음부터 0** 이다 — 카드가 이미 섞여 있고
> 자리에 아무 의미가 없기 때문이다. 같은 하한선을 서로 다른 이유로 통과한다.

### 재현

무작위는 시드 하나(`mulberry32`, 시드는 `crypto.getRandomValues`)에서만 나온다.
**뒤집는 순간에 결과를 고르는 코드가 없다** — 카드 배치는 `start()` 에서 끝났고,
그 뒤로는 적혀 있는 것을 읽을 뿐이다. **실측: 재현 불일치 0** (10판).

"미리 정해 두고 연출만 재생" 과 헷갈리기 쉬운데 차이는 **무엇을 정해 두느냐**다.
카드 배치를 정해 두는 건 덱을 섞어 엎어 두는 것과 같다 — 어느 카드를 뽑느냐가 결과를 바꾼다.
결과를 정해 두는 건 누가 뽑든 답이 같다는 뜻이고, 그건 이 게임이 하지 않는다.

### 끝나면 남은 카드를 전부 깐다 — 이게 증명 장면이다

걸림이 나오면 뒤 사람들은 뽑지 않는다. 그대로 끝내면 **안 뒤집은 카드에 뭐가 있었는지
아무도 모르고**, "사실 전부 걸림 아니었냐" 를 반박할 방법이 없다. 그래서 결과 화면 전에
남은 카드를 0.1초 간격으로 한 장씩 깐다(누르면 건너뛴다). 안 뽑힌 카드는 흐리게 그려
결과에 관여하지 않았음을 구분한다.

## 3-a. 장르 인계 — 허브가 뽑아 준 판으로 바로 시작한다

허브의 「랜덤으로 돌리기」가 이 게임을 뽑으면 참가자·방식이 이미 정해진 상태로 넘어온다.
부팅 때 `GameParty.take('card-flip')`(`games/lib/party.js`) 한 줄로 받아 준비 화면을
건너뛴다. 넘어오는 방식은 `'last'`(→ 한 명이 걸린다) / `'order'`(→ 순서 정하기) 둘뿐이다.
**'여러 명 뽑기' 는 인계 대상이 아니다** — 몇 명인지가 따로 필요해 허브가 대신 정해 줄 수 없다.

## 4. 화면·조작 실측치

| 항목 | 값 |
|---|---|
| 캔버스 | 1080 × 1440 (세로) |
| 카드 배치 | n별 열 수 고정표 (2→2, 6→3, 12→4열), 마지막 줄은 가운데 정렬 |
| 카드 크기 | 상한 300px, 판 크기에 맞춰 축소 (n=12 에서 185 × 263) |
| 터치 타깃 | 414 × 896 에서 카드 한 장 **108.3 × 153.7 CSS px** (하한 44px) |
| 뒤집기 | 0.42초 (가로 눌림 + 들어 올림), 절반에서 앞뒤 교체 |
| 프레임 | 120fps |
| 콘솔 | 0 (직접 URL 진입 시 AudioContext 경고만 — 허브 경유는 부모 클릭이 활성화를 물려준다) |

**가상패드(lib/touch.js)를 붙이지 않는다** — 카드를 직접 눌러야 하는데 패드가 판을 가린다.
sum-trail·hoop-order·pixel-logic 과 같은 판단이다.

**색만으로 구분하지 않는다** — 걸림/통과/번호는 색·글자·도형이 전부 다르다
(붉은 X / 초록 체크 / 파란 숫자).

## 5. 검증

| 항목 | 결과 |
|---|---|
| 죽은 입력 감사 | **57칸(3씬 × 19키) 전수 통과** (`dev.audit()`) |
| 재현 | 불일치 0 / 10판 |
| 균등성 | χ² 4.18 · 2.68 (임계 11.07) |
| 출발 편향 | ρ −0.011 · −0.008 (통과선 0.1) |
| 자동 완주 | `dev.autoplay(n, mode)` — 판이 안 끝나는 상태 0 |
| fps | 120 |

> 감사가 실제로 잡은 것: **준비 화면에서 '뒤로' 키 3종(P·C·L)이 죽은 칸**이었다.
> 같은 문구를 다시 띄우기만 해서 두 번째부터는 반응이 없는 것처럼 보였다. 소리를 붙여 고쳤다.
> 감사 신호에 `toast.t` 를 넣어 통과시키는 쪽이 쉬웠지만 그러면 감사가 무력해진다 —
> **감사를 느슨하게 하지 말고 입력을 고친다.**
