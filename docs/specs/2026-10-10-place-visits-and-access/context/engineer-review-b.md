## 1. Test Strategy

### T1 (상) 「많이 저장한 곳」·「많이 누른 곳」 절의 숨김 판정이 정렬 응답으로는 성립하지 않는데, 이를 잡을 테스트가 없다 — 체크 1·5
- 근거: 절 규칙은 「상위 6, 항목이 3 미만이면 숨긴다」(spec.md:58, :65)이다. 그런데 정렬 규칙은 「값 없는 문서는 뒤」(tasks.md:43)다. `size=6` 질의는 그 시군구에 관광 분류 문서가 6곳 이상이면 늘 6건을 돌려준다. 그러면 절이 숨지 않고, 찜 0인 관광지가 「많이 저장한 곳」에 들어간다.
- 클릭도 같다. `uniqueClickers14d` 는 하한 미만 값도 색인에 실린다. 재색인이 전 관광지를 적재하고(`AttractionApiReindexTasklet.kt:384-398`), 렌더러 테스트도 `min - 1` 값을 가진 문서를 쓴다(`AttractionPageRendererTest.kt:388`). 따라서 `sort=clicked` 상위 6에는 1~4명이 누른 곳이 섞인다. 하한 5(spec.md:64)를 어긴다.
- 수정안: SR-3.4·SR-4.2 에 「질의는 `savedCount ≥ SAVED_MIN` / `uniqueClickers14d ≥ FREQUENTLY_CLICKED_MIN` 인 문서만 거른다(검색 API 에 `minSaved`·`minClickers` 필터 또는 `sort` 값이 그 필터를 함께 건다)」를 넣는다. 테스트는 두 층에 둔다. `SearchAttractionServiceTest` 에서는 하한 미만 문서와 값 없는 문서가 응답에 없어야 한다. `RegionPage.test.tsx` 에서는 응답 6건 중 하한 이상이 2건이면 절이 없어야 한다.

### T2 (상) 원천 파일의 열 이름·형식 변화를 감지하는 테스트가 없다 — 체크 5
- 근거: 실패 조건은 「받기 실패·0행」뿐이다(spec.md:69, tasks.md:56). 열 이름이 바뀌면(예: `위도`→`WGS84위도`) 파서는 행을 그대로 만든다. 다만 좌표가 비어 모든 행이 `valid_coord=false` 가 되고(spec.md:70), 「통째로 교체」(spec.md:69)가 정상 행을 무효 행으로 바꾼다. 다음 계산에서 `attraction_access` 가 전부 빈다. 0행이 아니라서 Job 은 성공한다.
- 원천 열이 하나 **늘어도** 문제다. 고정 컬럼 매핑이 그 열을 조용히 버린다. 그러면 3규칙 ①(spec.md:69, CLAUDE.md 「원천 필드는 전부 적재」)을 어긴다.
- 수정안: SR-5.2 에 다음을 더한다. 테스트(5.1)에는 「열 이름 바꾼 표본 → 예외, `place_client.put_*` 미호출」 「열 하나 더한 표본 → 예외」 「무효 비율 초과 → 예외」를 더한다.
  - 원천마다 `EXPECTED_COLUMNS`(TG0.1 원문 그대로)를 둔다. 헤더 집합이 다르면(빠짐·늘어남 모두) 적재 전에 Job 을 실패시킨다.
  - 무효 좌표 비율 상한(예: 5%)과 행 수 변동 상한(이전 대비 ±20%)을 넘어도 실패시킨다. 「이전 행을 지우지 않는다」 규칙을 그대로 따른다.

### T3 (상) 회귀 주입 세 건 중 둘은 지금 테스트 설계로는 빨간불이 보장되지 않는다 — 체크 1·5
- `SAVED_MIN` 2 주입(tasks.md:72): FE 쪽은 리터럴 단언(tasks.md:22)이 잡는다. 그런데 그 단언은 「검사 안의 사본」이라 경계 동작(2명이면 안 보이고 3명이면 보임)을 재지 않는다. 서버 쪽 `SAVED_MIN` 은 기존 선례처럼 테스트가 상수 이름으로 경계를 만들면(`AttractionPageRendererTest.kt:380` `val min = AttractionClickSignal.MIN_SAMPLE`) 상수를 낮춰도 초록이다. 어느 사본을 낮췄을 때 무엇이 빨개지는지 스펙에 없다.
- 「직선거리」 문구 빼기: 테스트(tasks.md:67)가 기대 문자열을 `visitSignals.ts` 상수로 조립하면, 상수를 비웠을 때 기대값도 같이 비어 초록이다.
- 수정안
  - 경계 테스트는 **리터럴 고정값**으로 쓴다. 찜 2·3, 클릭 4·5, 거리 999m·1000m를 쓰고, 기대 문구도 리터럴(「직선거리 1.0km」)로 쓴다. 이 규칙을 1.1·3.3·4.1·4.2·4.4·6.2 에 명시한다.
  - 6.7 은 사본마다 따로 주입한다(FE `SAVED_MIN`, search/domain `SAVED_MIN`, batch 가 wishlist 에 넘기는 `min`). 각 주입의 빨간 테스트 이름을 `regression-injection.md` 에 적는다.
  - 주입은 **컴파일·tsc 를 통과하는 회귀**여야 한다. congestion 정렬 주입은 `tsc` 통과를 먼저 확인한 뒤에 게이트 빨간불을 기록한다(구문 오류 빨간불은 증거가 아니다).
  - T2 의 헤더 검사도 주입 대상에 넣는다(검사 한 줄을 지우고 5.1 이 빨개지는지 본다).

### T4 (중) FE↔서버 하한 대조 테스트의 「선례」가 코드에 없다 — 체크 3
- 근거: spec.md:45 와 tasks.md:24 는 「선례대로 FE 테스트가 서버 상수 파일을 읽어 대조」한다고 쓴다. 그러나 `FREQUENTLY_CLICKED_MIN` 은 주석으로만 연결되어 있다(`placeAttributes.ts:285-287`). portal-fe 에서 `MIN_SAMPLE`·`AttractionClickSignal` 을 읽는 테스트가 없다(grep 0건).
- 수정안: 1.3 을 「새로 만든다」로 고친다. 테스트는 Kotlin 상수 파일을 `readFileSync` 로 읽어 `const val SAVED_MIN = (\d+)` 를 뽑아 FE 값과 대조한다. 기존 클릭 하한 쌍도 같은 테스트에 넣는다. 정규식이 0건이면 실패하게 해서, 이름이 바뀌어 조용히 통과하는 일을 막는다.

### T5 (중) 금지어·「방문자」 검사가 서버 렌더 문구를 보지 않는다 — 체크 1
- 근거: 1.1 은 `visitSignals.ts` 문구 객체만 순회한다(tasks.md:19-20). 서버 렌더는 Kotlin 에 자기 문구를 갖는다(spec.md:45, :85). 렌더러 쪽에 「인기」나 사이트 클릭의 「방문자」가 들어가도 아무 테스트도 잡지 않는다.
- 수정안: 4.4·6.3 에 「렌더러 출력 HTML 에 금지어 없음, 사이트 근거 줄에 `방문자` 없음」 단언을 더한다. 또는 1.4 grep 게이트 대상에 `AttractionPageRenderer.kt` 의 문자열 리터럴을 넣는다.

### T7 (중) CDP 검증이 데이터가 없는 지금 성립하지 않는다 — 체크 4
- 근거: spec.md:104 는 「세 근거가 각각 나오는지」 DOM 텍스트로 확인한다고 쓴다. 찜 ≥3·클릭 ≥5 를 넘는 관광지는 거의 없을 것이다(Q8, tasks.md:14 — 측정 전). 클릭 분포는 TG0 에서 재지도 않는다.
- 수정안: TG0.5 에 클릭 분포를 더한다. 「`uniqueClickers14d ≥ 5` 관광지 수, 그런 곳이 3곳 이상인 시군구 수」를 재고, 재색인 로그 줄(`AttractionApiReindexTasklet.kt:393`)이 이미 앞의 수를 낸다. CDP 대상은 「근거가 있는 표본 페이지」와 「근거가 없는 페이지(절 숨김 확인)」 둘로 나눠 미리 정한다. 표본이 0이면 그 근거는 컴포넌트 테스트로만 확인했다고 기록한다.

### T8 (하) 테스트 파일 이름 — 체크 6

## 2. Domain

### D1 (상, BLOCK) 「방문자」 용어가 스펙 안에서도, 용어집과도 어긋난다 — 체크 3·5
- 스펙 결정: 「방문자」는 `KTO_REGION_VISITORS` 에만 쓴다(spec.md:43).
- 위반 ①: 바로 다음 줄 예시가 「이 사이트 방문자 클릭(같은 사람은 한 번)」이다(spec.md:44). 1.1 테스트(「`SITE_CLICKS` 문구에 방문자 없음」, tasks.md:20)를 그대로 쓰면 스펙 예시가 실패한다.
- 위반 ②: 용어집은 `uniqueClickers14d` 를 「최근 14일 … 고유 방문자 수」로 정의한다(search/glossary.md:77). 코드 주석·로그도 「고유 클릭 방문자」다(`AttractionApiReindexTasklet.kt:378, 389`).
- 사람 판단: 사이트 쪽 행위자를 부를 말(예: 「이용자」·「사람」)을 정한다.
- 수정안: spec.md:44 예시를 고친다. search/glossary.md:77 정의를 「고유 클릭 이용자(사람) 수」로 바꾼다. 「방문자 = 관광공사 이동통신 추정치」 행을 place 용어에 새로 둔다(D2). 코드 식별자(`visitor_id`)는 그대로 둔다.

### D2 (중) place BC 에 용어집이 없고, 새 용어가 정의되지 않았다 — 체크 2·3
- 근거: `docs/context-map.md` 의 BC 표(18-38행)에 place 가 없다. `place/glossary.md` 도 없다. 스펙이 새로 들인 말은 근거(`KTO_REGION_VISITORS`·`SITE_SAVES`·`SITE_CLICKS`), 근거 줄, 다 받은 달, 타지 방문자(외지인+외국인), 가는 법, 직선거리, 「많이 저장한 곳」/「많이 누른 곳」이다. search 용어집에는 「방문 요약」·「배지 줄」(search/glossary.md:92, :94)이 있다. 새 「근거 줄」이 배지 줄과 어떻게 갈리는지도 정의가 없다.
- 수정안: 구현 뒤 `/hns:glossary` 로 place 용어집을 만들고 context-map 에 한 줄 넣는다. 그 전까지는 spec 에 짧은 용어 표를 둔다(근거 줄 ≠ 배지 줄: 배지 「많이 클릭한 곳」은 그대로 두고, 근거 줄은 출처 문장이다).

### D3 (중) 「저장」과 「찜」이 한 근거를 두 이름으로 부른다 — 체크 3·5
- 근거: 단추 문구는 「찜하기」(`FavoriteButton.tsx:33`)이다. 스펙의 근거 이름·근거 줄도 「찜」이다(spec.md:42, :58-59). 그런데 절 제목과 필드는 「많이 저장한 곳」·`savedCount`·`SITE_SAVES`(spec.md:54, :56)이다. 사용자는 자기가 누른 「찜」과 「저장」을 같은 것으로 연결하지 못할 수 있다. wishlist 용어집에는 「Bookmark」가 `Avoid` 로 올라 있다(wishlist/glossary.md:26).
- 수정안: 화면 문구를 「많이 찜한 곳」으로 맞춘다. 코드 이름(`savedCount`)을 남기려면 용어집에 「저장 = 찜(wishlist 항목) 수」 대응을 적는다. 참고로 wishlist 용어집은 아직 `productId` 시절 정의라(wishlist/glossary.md:10-28) 다형 대상(ADR-0074)으로 갱신이 필요하다. 이번 스펙 범위는 아니고 보고만 한다.

### D4 (중) 「이 관광지」 찜 수의 단위가 언어별 문서다 — 체크 5·6
- 근거: 찜 키는 언어별 문서 id(`targetKey={attraction.id}`, `AttractionPage.tsx:361-362`, `PlacePage.tsx:2001`)이다. 같은 장소의 국문·영문 찜이 따로 센다. 영문 상세는 하한 3을 거의 넘지 못한다.
- 수정안: spec SR-3 에 「`savedCount` 는 문서 id 단위이고 국·영을 합치지 않는다」를 명시한다(또는 짝 판정으로 합친다고 정한다). 근거 줄의 「이 관광지」 대상 칸이 이 정의를 따른다.

### D5 (하) 역·정류장 참조가 통째로 교체되는 표의 대리키를 가리키면 끊긴다 — 체크 6·8
- 근거: `attraction_access` 는 「stop 참조」를 갖는다(spec.md:71). 원천 표는 기준일마다 통째로 교체된다(spec.md:69). 대리키 FK 라면 교체 순간 참조가 끊기거나 다른 정류장을 가리킨다.
- 수정안: 참조를 원천 자연키로 정한다(철도 역사 코드, 버스 `도시코드 + 정류장번호`). 화면에 쓰는 이름·노선은 `attraction_access` 에 사본으로 싣는다. 이렇게 하면 원천 교체와 access 교체 사이 순간에도 화면이 성립한다.

### D6 (하) access 불변식을 서버가 강제하는지 정해지지 않았다 — 체크 6
- 근거: 「역 2,000m·정류장 500m, 종류당 2곳」(spec.md:76)은 파이썬 순수 함수에만 있다. place 내부 PUT(spec.md:77)은 받은 그대로 저장한다.
- 수정안: PUT 이 `rank ∈ {1,2}`, `distance_m ≤ 종류별 상한` 을 검증하고 어긋나면 400 으로 거부하게 한다(5.4 테스트 한 줄). 규칙의 원본은 한 곳(ingest 상수)이라고 적는다.

## 3. Usecase

### U1 (상) 「많이 저장한 곳」·「많이 누른 곳」 주 흐름이 하한을 어긴다 — 체크 2·5
- T1 과 같은 결함을 사용자 흐름 쪽에서 본 것이다(spec.md:58, :65, tasks.md:43). 시군구 페이지에 찜 0·클릭 1명인 관광지가 「많이 … 한 곳」으로 나간다. 그러면 「근거마다 이름이 근거를 말한다」(SR-1)가 틀린 말이 된다. 수정안은 T1 과 같다.

### U2 (상) 버스정류장이 BIS 미연계 군에서 빠지면 「정류장이 없다」로 읽힌다 — 체크 5
- 근거: 원천에는 BIS 연계 지자체만 담긴다(spec.md:34). 범위 밖이면 행이 없다(spec.md:76). 절은 항목이 없을 때만 숨는다(spec.md:81). 그래서 역만 있는 관광지는 역만 보이고, 사용자는 근처에 버스가 없다고 읽는다. 군 지역은 철도가 드물어 절 전체가 숨는 경우가 많다. 그 경우 「자료 없음」과 「주변에 없음」을 가를 수 없다.
- 수정안: 버스 원천의 `도시코드·관리도시명`으로 「자료가 있는 지역」 집합을 만든다. 관광지 시군구가 그 집합 밖이면 버스 칸에 「이 지역은 버스정류장 위치 자료가 없습니다」를 낸다(영문 「No bus stop data for this area」). 매핑 방법(도시코드 ↔ 시군구 코드, 없으면 「관광지 10km 안에 유효 정류장이 하나도 없음」을 미연계로 판정)은 TG0 에서 정한다. 테스트는 6.2 에 「미연계 지역 → 안내 문구, 연계 지역 범위 밖 → 버스 줄 없음」 두 사례로 둔다.

### U3 (중) 「직선거리」 표기와 도보 시간 미계산 — 기대와의 차이를 줄이는 장치가 덜 됐다 — 체크 5
- 판단: 도보 시간을 내지 않는 결정(spec.md:82)은 근거가 분명하고 옳다. 다만 세 가지가 기대를 어긋나게 한다.
  - 역 반경 2,000m(spec.md:76)를 「가는 법」이라는 제목 아래 보이면, 「직선거리 1.9km」도 걸어갈 수 있는 역처럼 읽힌다. 실제 도보는 2.5km를 넘기 쉽다. 수정안: 절 제목을 「가까운 역·정류장」으로 하고, 구글 지도 대중교통 길찾기 링크를 그 절의 첫 행동으로 둔다. 또는 역 반경을 1,000~1,500m로 줄인다(Q8 에 선택지로 올린다).
  - 표기 「{역명}역」(spec.md:81): 원천 역명이 이미 「…역」으로 끝나면(예: 서울역) 「서울역역」이 된다. 수정안: 원천이 「역」으로 끝나면 붙이지 않는다. 6.2 에 사례를 넣는다.
  - 환승역 중복: 역사 정보는 노선별 행이라 같은 역이 여러 행이다. 「가까운 순 2곳」(spec.md:76)이 같은 역의 두 노선으로 채워질 수 있다. 수정안: 역명(+좌표 근접)으로 묶어 한 역에 노선을 「1·4호선」처럼 합친다. 5.2 테스트에 사례를 더한다.

### U4 (중) access 「관광지 단위 통째 교체」의 빈 결과·부분 실패 흐름이 없다 — 체크 2·3
- 근거: 범위 안에 없으면 행을 만들지 않는다(spec.md:76). 결과는 관광지 단위로 교체한다(spec.md:77). 그러면 이번 회차에 결과가 0인 관광지(정류장 폐지, 좌표 수정)는 보내지 않으므로 옛 행이 남는다. 또 버스 20.6만 행을 5,000행 묶음으로 보내는데(spec.md:71), 중간 묶음이 실패하면 「통째로 교체」가 반만 된 상태로 남는다.
- 수정안: ① access 는 계산 대상 전 관광지를 보낸다(빈 목록 = 지움). 또는 회차 id 를 찍고 마지막에 옛 회차를 지운다. ② 원천 표는 「회차 id(기준일)로 새 행 적재 → 전부 성공하면 활성 회차 전환 → 옛 회차 삭제」 순서로 교체한다. 부분 실패면 활성 회차가 그대로다. 5.4 테스트에 「3번째 묶음 실패 → 조회는 옛 회차」를 넣는다.

### U5 (중) 시도 순위의 경계 사례가 정해지지 않았다 — 체크 3·5
- 세종(36)은 시군구가 없다. 제주는 2개뿐이다. 「상위 10」 절이 빈 절이 되거나 1~2행짜리가 된다. 수정안: 시군구 3개 미만 시도는 절을 숨긴다(다른 절의 「3 미만 숨김」과 같은 규칙).
- 「다 받은 달」은 시도 안 모든 시군구가 그 달을 다 받았을 때로 정의한다. 시군구마다 판정하면 일부만 받은 시군구가 낮은 순위로 섞인다(spec.md:48).
- 다 받은 달이 아직 없으면(첫 적재 직후) 절을 숨긴다. 레디스가 비었을 때 다시 계산할지 빈 응답을 줄지 정한다(spec.md:49 는 write-through 만 말한다).

### U6 (중) 「외지인+외국인」 순위의 의미 확인이 필요하다 — 체크 1
- 근거: 현지인을 빼는 이유를 「생활 이동이 섞여」라고 썼다(spec.md:48). 하지만 외지인에도 통근·통학이 섞이면 서울 시도 페이지 상위가 업무 지구(중구·강남구)가 된다. 그러면 「타지 방문자가 많은」 순위가 관광 신호로 읽히지 않는다.
- 수정안: 원천 정의(관광공사 빅데이터의 외지인 산정에서 일상 이동을 빼는지)를 data-sources 본문에 인용한다. 「기준 보기」에 그 정의를 한 줄로 단다. 빼지 않는 정의라면 근거 줄에 「통근 포함」을 밝힌다. TG0 에 서울·부산 실제 상위 10을 뽑아 보는 단계를 더한다.

### U7 (중) 상세의 시군구 방문자 줄이 사용자에게 주는 정보가 적다 — 체크 1
- 근거: 「이 관광지가 있는 {시군구}의 {월} 타지 방문자 약 N명 — 관광지 하나의 값이 아닙니다」(spec.md:51)는 같은 시군구 관광지 수백 곳에 같은 숫자로 붙는다. 공개 지연 30일과 다 받은 달 규칙 때문에 보이는 달은 늘 1~2달 전이다(data-sources.md:238, :243). 부정문으로 끝나는 근거 줄은 사용자가 무엇을 판단할 수 있는지 알려 주지 않는다.
- 수정안(택1): ① 상세에서는 빼고 시도 순위·지역 페이지 추이로 연결하는 링크 한 줄(「{시군구} 방문 추이 보기」)만 둔다. ② 남기면 같은 시도 안 순위(「{시도} 시군구 중 3위」)처럼 비교 정보를 붙인다. 어느 쪽이든 사용자 확인 항목(Q10)으로 올린다.

### U8 (하) 전제·사후 조건 표기 — 체크 3
- spec.md:96 「주 2회 파일 받기」와 spec.md:68 「주 1회」가 어긋난다(아마 「주 1회 · 파일 둘」). 고친다.
- Q8 의 「절은 두되 숨김 상태로 배포」(open-questions.yml:44)는 절이 이미 「3 미만이면 숨김」으로 스스로 숨으므로 따로 스위치를 둘 필요가 없다(YAGNI). 「데이터 규칙으로 숨는다」로 바꾼다.
