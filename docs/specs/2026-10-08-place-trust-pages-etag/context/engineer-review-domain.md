## Findings

### D1. 바닥글 라벨 「소개」가 기존 화면의 「사이트 소개」와 다르다 (REVISE · 항목 3·5)
- 스펙: `spec.md:19` 「소개 /about · 연락처 /contact · 개인정보처리방침 /privacy · 데이터 출처 /data-sources」.
- 기존: 런타임 바닥글 `portal-fe/src/components/Footer.tsx:50-52` 은 「사이트 소개」, 페이지 제목 `portal-fe/src/seo/copy.mjs:994` · `AboutPage.tsx:34` 도 「사이트 소개」, 연락처 본문 `ContactPage.tsx:71` 도 「사이트 소개」.
- 결과: 초기 HTML 바닥글과 하이드레이션 뒤 바닥글이 같은 대상을 다른 이름으로 부른다.
- 수정안: SR-2.1 의 라벨을 「사이트 소개」로 바꾼다. 순서도 런타임 바닥글(`Footer.tsx:47-55`: 개인정보처리방침 · 사이트 소개 · 연락처)에 데이터 출처를 덧붙인 순서로 맞추거나, 반대로 런타임 쪽을 스펙 순서로 바꾸는 것을 SR-2.3 에 명시한다. 한 순서로 통일하면 SR-2.2 패리티 단언에 런타임 바닥글도 같은 리터럴을 쓸 수 있다.
- 「데이터 출처」라는 페이지 명칭 자체는 `AboutPage.tsx:75` h2, `copy.mjs:996` 설명문, `ContactPage.tsx:71` 과 일치한다 — 문제없음.

### D2. 「라이선스 문자열이 대장과 같다」의 비교 규칙이 없어, 그대로 구현하면 내부 표기가 공개 페이지로 나간다 (REVISE · 항목 6)
`spec.md:15` 는 각 행의 라이선스 문자열이 대장과 **같다**고만 한다. 대장 §1 라이선스 열에는 공개 문구로 쓸 수 없는 값이 섞여 있다.

| 대장 위치 | 라이선스 열 원문 | 그대로 공개하면 |
|---|---|---|
| `data-sources.md:69-77` | `〃` (9행) | 페이지에 「〃」가 찍힌다. 표 정렬이 바뀌면 뜻이 바뀐다 |
| `data-sources.md:75-77` | `〃 (행마다 \`cpyrhtDivCd\`)` | 코드 필드명이 공개 문구가 된다 |
| `data-sources.md:84-85,87-88,90` | `**…**` 굵게 | 마크다운 기호가 남거나, 벗기는 규칙이 테스트마다 다르다 |
| `data-sources.md:88` | `공공누리 제3유형으로 취급 (포털 표기 미확인 — 같은 기관 대기오염정보 기준)` | 내부 판단 메모가 공개 고지가 된다 |
| `data-sources.md:89,97` | 데이터 열 `**행정구역(법정동)**`, `**주유소·유가**` | 「데이터 집합 ==」 비교가 굵게 표기 때문에 어긋난다 |

수정안: SR-1.4 에 정규화 규칙을 한 줄로 고정한다.
1. `〃` 는 바로 위 행의 값으로 풀고, 꼬리의 괄호 보충(`(행마다 …)`)은 정규화 뒤 별도 비고 열이나 각주로 보낸다.
2. `**`·백틱을 벗긴 뒤 비교한다. 데이터 열도 같다.
3. 괄호 안 내부 메모(`포털 표기 미확인 …`)를 공개할지 정한다. 결정 ②가 「라이선스 열」 공개라 원문을 다 내는 해석도 가능하지만, 공개한다면 그것도 명시한다.
4. 정규화 함수는 게이트와 페이지 상수 생성(수작업이라도) 양쪽의 기준이 되도록 테스트 파일 안에 하나만 둔다.

### D3. 같은 라이선스를 「KOGL」과 「공공누리」 두 이름으로 공개하게 된다 (REVISE · 항목 3)
- 대장: `data-sources.md:92` 참가격은 「KOGL 제1유형」, 나머지(`:84-89`)는 「공공누리 제n유형」. KOGL 은 공공누리의 영문 약칭이라 같은 라이선스다.
- 같은 유형의 띄어쓰기도 갈린다: `:78-83,97` 「이용허락범위 제한 없음」 vs `:91` 「이용허락범위 제한없음」 vs `:92` 「제한없음」.
- 「대장 표기 그대로」(`spec.md:13`)에 정확 일치 게이트(`spec.md:15`)를 걸면 공개 페이지에 이 혼용이 그대로 고정된다. 사용자에게는 서로 다른 라이선스처럼 보인다.
- 수정안: 대장 수정이 범위 밖(`spec.md:39`)이므로 D2 정규화에 「KOGL → 공공누리」, 「제한없음 → 제한 없음」 매핑을 넣고 페이지는 정규형으로 쓴다. 대장 자체 통일은 후속으로 남긴다.

### D4. 「출처표시 의무가 있으면 그 문구」가 가리키는 대상이 대장 §1 에 없다 (REVISE · 항목 6)
- 스펙: `spec.md:13` 「라이선스(출처표시 의무가 있으면 그 문구)」 + 「대장에 없는 값은 쓰지 않는다」.
- 대장 §1 표에는 라이선스 **이름**만 있고 표기 문구는 없다. 문구는 다른 절에 흩어져 있다: `data-sources.md:100` 「출처: 한국관광공사 TourAPI」, `:261` 에어코리아 「실시간 측정값으로 확정 전 자료」, `:347` 「식품의약품안전처, 한국소비자원 참가격」.
- CC BY 4.0 은 저작자 표시와 함께 라이선스 고지·링크, 변경 여부 표시를 요구한다. GeoNames 는 `normalize_regions.py` 로 가공해 쓰므로 변경 표시 대상이다(`data-sources.md:90`). 공공누리 출처표시도 기관명과 유형 표시가 기본 형태다.
- 수정안: 둘 중 하나를 SR-1.2 에 명시한다.
  - (a) 「그 문구」 = 정규화된 라이선스 열 문자열로 한정하고, 화면별 출처 줄이 실제 표기 의무를 진다고 적는다.
  - (b) 라이선스 종류별 고정 고지(공공누리 유형 링크, CC BY 4.0 라이선스 링크와 「가공함」 표기)를 데이터 값이 아닌 상수로 두고 게이트 비교 대상에서 뺀다. 「대장에 없는 값은 쓰지 않는다」의 예외로 적는다.
- 권고는 (b)다. 공개 출처 페이지가 생기면 CC BY 고지를 거기서 찾게 되는데, 지금 화면 출처 줄(`AttractionPage.test.tsx:209` 「출처: 한국관광공사 TourAPI · GeoNames」)에는 라이선스 표기가 없다.

### D5. TourAPI 행의 「공공누리 (출처표시)」가 대장 §2 의 「행마다 다름, 표본 Type3=변경금지」와 맞지 않는다 (REVISE · 사람 판단)
- 대장 §1 `data-sources.md:68` 「공공누리 (출처표시)」. 대장 §2 `:168` 「공공누리 유형은 행마다 다르다(`cpyrhtDivCd`, 표본은 `Type3` = 출처표시·변경금지)」.
- 결정 ②대로 §1 만 옮기면 공개 페이지는 TourAPI 전체가 출처표시만 요구한다고 읽힌다. 실제로는 변경금지 조건이 붙은 행이 있다.
- 대장 내부의 불일치라 스펙만으로는 고칠 수 없다(대장 수정은 `spec.md:39` 범위 밖). D2 의 「꼬리 보충을 비고로」 규칙을 TourAPI 첫 행(`:68`)에도 적용해 「행마다 공공누리 유형이 다름」을 비고로 다는 정도는 대장에 있는 사실(`:168`)이라 「대장에 없는 값」 금지에 걸리지 않는다. 수용 여부는 사람이 정한다.

### D6. About 요약 축약 시 에어코리아 「확정 전 자료」 고지가 목록 원본에서 빠진다 (REVISE · 경미)
- 현재 `AboutPage.tsx:85` 「한국환경공단 에어코리아 — 대기 실시간 측정 (확정 전 자료)」. SR-1.5(`spec.md:16`)는 이 목록을 요약 3줄로 줄이고, 새 페이지는 §1 세 열만 담아 이 고지가 어디에도 남지 않는다.
- 이 문구는 대장 `data-sources.md:261` 에 화면 표기로 있으니 「대장에 없는 값」이 아니다.
- 수정안: `/data-sources` 의 대기 실시간 측정 행 비고(D2 의 비고 열)에 「실시간 측정값으로 확정 전 자료」를 싣는다고 SR-1.2 에 적는다.

## 요약
- 차단 사유 없음. 페이지 명칭 「데이터 출처」는 기존 화면과 일치한다.
- 고칠 것은 두 갈래다. 하나는 바닥글 라벨을 기존 「사이트 소개」로 맞추는 것(D1)이다. 다른 하나는 「대장 == 페이지」 게이트의 정규화 규칙과 공개 고지 문구의 범위를 스펙에 못 박는 것(D2~D6)이다.

VERDICT: REVISE
