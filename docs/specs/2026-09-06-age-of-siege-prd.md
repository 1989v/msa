## 0. 수직 슬라이스 — 이번에 100% 로 만들 것

**고을 1 · 1판 방어 하나.** 방어 한 판이 처음부터 끝까지 완성품 품질로 돈다.

슬라이스에 **반드시** 들어가는 것:

| | 슬라이스 | 완성작 |
|---|---|---|
| 판 | 1판 방어 1 | 54 (고을 18 × 3판) |
| 영웅 | **1** (광개토대왕) | 12 |
| 슬롯 건물 | **3** (궁방·노대·마름쇠) | 6 |
| 적 | **3** (기병·방패병·궁수) | 24 |
| 보스 | **1** (술통 굴리기) | 6 |
| 고지대 | **2곳** | 스테이지마다 2~4 |

그 외에 슬라이스가 갖춰야 하는 것 — **원근 카메라 · 실시간 조명과 그림자 ·
3열 종대 100기 · 슬롯 가격표와 배치 · 고지대에서 굴리는 바위 · 봉수 연출 ·
가로/세로 레이아웃 · 사운드**. 하나라도 빠지면 하한 판정을 못 한다.

## 1. 화면 축척 — 원근이라 재는 법이 다르다

아이소메트릭의 「시야 폭」이 없다. 카메라 파라미터와 **화면에 찍히는 픽셀**로 잰다.

| 항목 | 값 | 어떻게 재나 |
|---|---|---|
| 카메라 | 원근, 수직 FOV **38°** | 프로젝트 설정 |
| 내려다보는 각 | **54°** | 지면 법선과 카메라 전방의 각 |
| 대상까지 거리 | **32 유닛** (줌 3단: 24 / 32 / 46) | 카메라 ↔ 영웅 |
| **주인공 화면 비율** | **1/9.5** (기본 줌, 화면 짧은 변 기준) | 스크린샷 픽셀 실측 |
| **주인공 CSS px** | 가로 844×390 → **41 px** · 세로 390×844 → **41 px** | 짧은 변이 390 으로 같다 |
| 화면 중앙 지면이 담는 가로 | **47.7 유닛** (가로 844×390) | 화면 좌우 끝에서 지면으로 광선을 쏴 두 점 사이 |

- 참조작 실측이 **1/8.3** 이다(`_ref/ks-가로-01.png`, 왕 150px / 짧은 변 1242). 그보다 조금 작게 잡았다
- **주인공 키는 3.59 유닛**이고 손으로 정하지 않는다 — 위 세 값에서 역산한다(`Spec.HeightForFraction`).
  눌려 보이는 것(cos)만 넣으면 11% 크게 나온다: 부각이 있으면 세운 것의 윗끝이 카메라에 더 가깝다
- 「한 화면이 담는 길」은 처음 42 로 어림했는데, 적어 둔 재는 법대로 재니 **47.7** 이었다(2026-09-06 스캐폴드 실측).
  굽이진 길이라 시작 화면에 실제로 들어오는 길은 **31 유닛**이다
- **41 CSS px 는 조작 대상 하한 28 을 넘긴다.** 캔버스 판본이 19.5px 로 겨우 버티던 자리가 풀린다
- 줌 3단은 유지한다. 최대 축소(46)에서 길의 굽이가 한눈에 읽혀야 한다

## 4. 웨이브 — 「군단 러시」의 숫자

캔버스 판본이 웨이브당 6~20기였고, 그래서 화면이 비어 보였다. **자릿수를 올린다.**

| 웨이브 | 총 마릿수 | 구성 |
|---|---|---|
| 1 | 24 | 기병 24 |
| 2 | 38 | 기병 34 · 궁수 4 |
| 3 | 52 | 기병 42 · 궁수 8 · 방패병 2 |
| 4 | 68 | 기병 52 · 궁수 12 · 방패병 4 |
| 5 | 86 | 기병 62 · 궁수 16 · 방패병 8 |
| 6 | 108 | 기병 76 · 궁수 22 · 방패병 10 |
| 7 | **130 + 보스 1** | 기병 88 · 궁수 28 · 방패병 14 · 보스 |

- **동시 생존 최대 140기.** 성능 예산은 이 값을 전제로 잡는다
- 한 마리씩 **0.28초 간격**으로 내보낸다 — 이 간격이 행렬의 길이를 만든다
- **3열 종대**: 길 중심선과 그 좌우로 번갈아 세운다. 간격은 길 폭에서 뽑는다(`RoadWidth × 0.22`)
  — 숫자를 손으로 적으면 길을 넓힐 때 행렬만 그대로 남아 한 줄로 구불거린다.
  참조작 실측도 3열이고, **행렬이 길을 메우는 것**이 「군단이 밀려온다」의 실체다
- 앞선 놈을 추월하지 못하게 묶는다. 그 한 줄이 곧 행렬이다

## 5. 고지대 기믹 — 이번 전환의 이유 중 하나

**고지대에서 바위를 굴려 행렬을 쓸어버린다.**

| 항목 | 값 |
|---|---|
| 발동 | 고지대 가장자리의 바위를 영웅이 밀거나, 슬롯 건물(투석대)이 민다 |
| 굴러가는 것 | 반지름 **1.6 유닛**, 경사를 따라 가속 |
| 피해 | 닿은 적 즉사(방패병은 2회), 최대 **12기** 관통 |
| 재사용 | 웨이브마다 고지대당 **1회** |
| 보스 | 같은 기믹을 반대로 쓴다 — **술통을 길로 굴려 내려보낸다** |

지형이 장식이 아니라 규칙에 들어가는 자리다.

## 6. 성능·용량 예산

| 항목 | 예산 | 근거 |
|---|---|---|
| 총 전송량 (압축 후) | **≤ 10MB** | 표준 상한 15MB. 절차 메시라 `.data` 가 가벼워 더 조인다 |
| 첫 화면까지 | **≤ 5초** | `archer-outbreak` 이 5.66초로 넘긴 전례가 있다 |
| 화면 삼각형 (폰) | **≤ 120k** | 캐릭터 140기 × 약 200 + 지형 |
| 목표 프레임 | 폰 **45** · 데스크톱 60 · 멈춤 **20** | G7 |
| MSAA · 포스트 | 폰 **0** · **≤4 패스** | G7 |
| DPR 상한 | **2** | G7 |

**측정은 전후 비교로만 읽는다.** 검증 브라우저가 소프트웨어 렌더러라 fps 절대값은 무의미하다.

## 7. 조작

| | 가로 (우선) | 세로 |
|---|---|---|
| 이동 | 왼쪽 절반 떠다니는 가상 스틱 | 같음 |
| 공격 | 자동 (사거리 안) | 같음 |
| 스킬 | 오른쪽 아래 버튼 2 | 같음 |
| 배치 | 슬롯을 탭 → 목록에서 고름 | 같음 |
| 줌 | 핀치 + 버튼 | 같음 |

- 터치 타깃 **≥44 CSS px**, 조작 대상 ≥28, 라벨 ≥11
- 유니티는 `data-fit="0"` 이라 **템플릿이 하단 띠를 직접 계산**한다 (비율 0.28)
- `EventSystem` + `StandaloneInputModule` 을 HUD 와 **같이** 세운다. 없으면 버튼이 조용히 안 먹는다

## 8. 완성 판정 — 이 표를 다 채워야 슬라이스가 끝난다

| 게이트 | 판정 |
|---|---|
| 화면 축척 | 1장 세 수치를 스크린샷 픽셀로 실측, 기준 대비 ±8% |
| 모바일 두 방향 | 가로 844×390 · 세로 390×844 실측 + 스크린샷 |
| 웨이브 | 7웨이브 완주. 마지막 동시 생존 **≥130** 확인 |
| 성능 | 삼각형·전송량·첫 화면 실측값을 6장 표와 나란히 |
| 조명 | 지형에 그림자가 떨어지는가. 태양 방위 ↔ 시작 시야 내적 **양수** |
| 팔레트 연동 | 소스에 하드코딩 hex 리터럴 **0건** |
| 콘솔 | 에러 0 |
| 게이트 자체 | **회귀를 주입해 빨간불을 본 뒤에만** 켰다고 한다 |
| 벤치마크 일치도 | 깨끗한 서브에이전트가 소스와 `_ref/` 를 보고 판정 |
