## 요약

이 스펙은 보안 판단을 회피하지 않는다 — 별칭을 개인정보로 전제하고(SR-2.6), 옵트인·하드삭제를
정하고(SR-2.3), URL 로 이름을 안 넘기고(SR-4.3), 클라이언트 점수를 안 믿는다(SR-7.3).
방향은 맞다.

문제는 **세 개의 보안 주장이 그 주장을 실현할 기제를 지목하지 않은 채 단정형으로 적혀 있다**는 것이다.
지목된 재사용 대상(릴레이·HMAC 토큰)을 실제로 읽으면 그 주장이 성립하지 않는다.

| 주장 | 스펙 | 코드가 말하는 것 |
|---|---|---|
| 누가 뭘 골랐는지 어떤 응답에도 안 실린다 | SR-5.6 | 릴레이의 모든 전달 메시지에 **발신 좌석 번호가 박힌다** (`move()`) |
| 좌석 토큰 없이는 제출이 거부된다 | SR-7.4 | 토큰을 **누가 발급하는지 없다**. 릴레이만 진짜 좌석을 알고, 릴레이는 토큰을 모른다 |
| 채점은 서버가 한다 | SR-7.2 | 서버가 받는 「원자료」가 **클라이언트가 쓴 시각**이다. 산술은 서버가 해도 입력이 공격자 것이다 |

스펙 수정으로 전부 닫히므로 BLOCK 은 아니다. 다만 이대로 태스크를 끊으면 ADR(SR-7.2 가 예고한
「첫 권위 레이어」)에 **거짓 보안 주장이 박제된다.** 아래 M1~M4 를 spec.md 에 반영한 뒤 진행할 것.

## 필수 수정 (M) — 태스크 생성 전에 spec.md 에 반영

### M1. SR-5.6 은 릴레이로는 성립하지 않는다 — 투표의 전송 경로를 정하라

`GameRelayRegistry.move()` 는 두 갈래 모두에서 **발신자의 좌석을 페이로드에 박아** 보낸다.

```kotlin
val out = message("move")
out.put("seat", peer.seat)      // ← 두 갈래 공통. 익명성이 여기서 끝난다
out.set("d", opaque)
// to 가 있으면 그 좌석에게만, 없으면 방 전체에 팬아웃
```

따라서 투표를 릴레이로 보내면 결과는 둘 중 하나다.

- `to` 없이 보냄 → **방 전원이** `{seat: 3, d: "게임슬러그"}` 를 본다.
- `to: 0` (방장에게만) → **방장이** 좌석별 선택을 그대로 본다. SR-5.6 의 「방장 화면에도 집계만」이 정면으로 깨진다.

릴레이는 무권위 팬아웃 장치이고 익명 집계기가 아니다. 집계 주체가 필요하며, 그 주체는
**SR-7 이 이미 세우기로 한 채점 서버**다(같은 JVM 안에 있다 — ADR-0059 폴드).

**spec.md 에 적을 것**
- 투표 제출은 릴레이가 아니라 채점 서버의 HTTP 엔드포인트로 간다. 선택값은 릴레이를 지나지 않는다.
- 서버는 (방·판·좌석)→선택 을 **메모리에만** 들고, 마감 시 집계만 내보낸 뒤 즉시 버린다(SR-9.3 과 같은 규율).
- **진행 중 집계를 공개하지 않는다.** 「3/6 제출」까지만 보이고 득표 수는 마감 후에 한 번에 나온다 —
  실시간 카운트는 제출 순서와 증분을 대조해 누가 무엇을 골랐는지 역산할 수 있다.
- 소수 인원의 구조적 한계를 한 줄로 적는다: 참가자 2~3명이면 집계만으로도 타인의 표가 드러난다.
  기능의 성질이지 결함이 아니지만, 적어 두지 않으면 나중에 버그로 보고된다.

### M2. SR-7.4 좌석 토큰 — 발급자를 정하라. 지금 형태로는 무엇도 막지 못한다

스펙은 「방 입장 때 서버가 (방·좌석)에 HMAC 서명한 토큰을 발급」이라고만 적는다.
**어느 서버인지가 비어 있고**, 그 빈칸이 이 토큰의 가치를 전부 결정한다.

- 릴레이만이 진짜 좌석을 안다(`join()` 이 `indexOfFirst { it == null }` 로 배정하고
  `peer.seat` 에 박는다). 그런데 릴레이는 토큰을 발급하지 않고, `GameRelayWebSocketHandler`
  는 **핸드셰이크에서 헤더를 하나도 읽지 않는다**(경로에서 슬러그만 뽑는다).
- 반대로 HTTP 엔드포인트가 「방 코드 + 좌석 번호」를 받아 토큰을 내주면, 그건 **자칭 사실에 서명해 주는 것**이다.
  공격자는 좌석 0~11 전부의 토큰을 받아 전원 대신 제출할 수 있다. 서명은 위조를 막지만
  **서명 대상이 검증되지 않은 주장이면 서명은 그 주장을 진실로 만들어 주는 도장**이 된다.

**그래서 발급은 릴레이가, 좌석 배정 시점에, 그 피어의 소켓으로만** 내려야 한다.
`join()` 이 이미 `joined` 메시지에 `room`/`seat`/`seats` 를 실어 그 피어에게만 보내므로
거기에 토큰 한 필드를 더하는 형태가 자연스럽다. 채점 서버는 같은 JVM 이라 같은 비밀키로 검증한다.

**토큰이 막는 것과 못 막는 것을 spec.md 에 표로 적을 것** (「HMAC 이니까 안전」으로 끝내지 말 것):

| | 막나 | 조건 |
|---|---|---|
| 관전자의 제출 | ✅ | 좌석을 못 받았으면 토큰이 없다. **단 관전자 정의가 릴레이에 있어야 한다 — F3** |
| 같은 방 다른 좌석 사칭 | ✅ | 좌석 번호가 서명 안에 있고, 발급자가 릴레이일 때만 |
| 방 밖에서의 제출 | ✅ | 방 코드가 서명 안에 있다 |
| 재사용 (다음 판) | ❌ | 방이 게임보다 오래 산다(SR-1.3). **판 식별자를 서명에 넣거나** 제출 시 열린 판인지 검사해야 한다 |
| 좌석 재점유 후 사용 | ❌ | `leaveRoom()` 이 좌석을 `null` 로 비우고 다음 `join` 이 **그 자리를 재배정**한다. 먼저 나간 사람의 토큰이 새 점유자 자리에서 계속 유효하다 → **좌석 점유 세대(epoch)를 서명에 포함** |
| 토큰을 넘겨받은 대리 제출 | ❌ | 소지자 토큰의 성질. 판 단위 만료로 창을 줄이는 것이 상한이다 |
| 원자료 위조 | ❌ | M3 의 영역 — 토큰은 「누가」만 증명하고 「무엇을」은 증명하지 않는다 |

기존 선례 `HmacSessionTokenService`(`InfraComponents.kt:52-77`)를 그대로 쓰되 **키 주입을 확인할 것** —
기본값이 `dev-secret-change-me-in-prod` 다. 파티 좌석 토큰이 그 기본값으로 운영에 나가면 토큰은 장식이다.
스펙에 「비밀키 미주입 시 기동 실패」를 요구로 적는 편이 안전하다(ADR-0078 의 `AUTH_SUBJECT_HASH_KEY` 선례).

### M3. SR-7.2/7.3 「서버가 채점한다」의 실제 경계를 적어라

SR-7.3 은 「점수를 보내지 않고 원자료를 보낸다」로 권위를 확보했다고 본다. 그런데 지정된 원자료가
**7초는 시작·정지 입력 시각, 원그리기는 궤적 점열** — 둘 다 클라이언트가 자유롭게 쓸 수 있는 값이다.
`{start: T, stop: T+7000}` 을 보내면 서버는 만점을 계산한다. 완벽한 원의 점열도 마찬가지다.
서버가 산술을 대신할 뿐, 신뢰 경계는 클라이언트 안에 그대로 있다.

이것은 「고칠 수 있는 버그」가 아니라 **경계를 어디에 그을지의 결정**이다. spec.md 가 골라 적어야 한다.

- **7초 맞추기**: 서버 시계로 재는 형태가 가능하다 — 서버가 판 시작을 스탬프하고, 클라이언트의
  「멈춤」이 도착한 시각을 서버가 잰다. 네트워크 지연이 오차로 들어오지만(수십 ms), 7초 게임의
  변별력은 그보다 크다. 클라이언트 시각을 쓰려면 **왜 쓰는지와 무엇이 뚫리는지**를 함께 적는다.
- **원그리기**: 궤적은 서버가 재현할 수 없다. 여기서 얻을 수 있는 것은 위조 방지가 아니라
  **개연성 검사**다 — 표본 간격의 분포, 사람 손의 떨림 분산, 총 소요 시간. 합성 궤적은 대개
  이 검사에서 걸린다. 「완전한 방어는 없고 캐주얼 조작만 막는다」를 스펙에 명시할 것.
- 두 게임 모두 **거부 사유에 「개연성 위반」을 추가**하고 SR-9.5 카운터에 넣는다.

이 항목이 특히 중요한 이유: SR-7.2 가 이 레이어를 ADR 로 남기겠다고 했다. 경계를 안 적으면
ADR 이 「서버 채점이므로 위조 불가」로 읽히고, 다음 사람이 그 문장 위에 더 무거운 것을 얹는다.

### M4. SR-2 / SR-9 — 제3자의 개인정보라는 점과 보존 숫자가 비어 있다

옵트인·하드삭제·방침 한 줄은 맞는 방향이고 ADR-0078 의 태도와도 맞는다. 두 가지가 빠졌다.

**(a) 정보주체가 사용자 본인이 아니다.** 친구 그룹의 별칭은 **다른 사람의 이름**이고, 그 사람은
동의한 적이 없다. ADR-0078 이 지켜 온 것은 「우리는 실명을 안 받는다」인데, 이 기능이 그 원칙에서
플랫폼이 실명을 저장하게 되는 첫 지점이다 — 그것도 회원 본인이 아닌 사람의 것으로.
SR-2.5 가 `member` 대신 `game_db` 를 고른 것은 **위치를 옮긴 것이지 위험을 줄인 것이 아니다.**
스펙에 남길 것:
- 입력 화면에서 **별명 사용을 권하는 안내**를 한 줄 띄운다(실명을 막을 수는 없으나 기본값을 바꾼다).
- 계정 저장 옵트인 확인 화면에서 「다른 사람의 이름이 서버에 저장된다」를 그대로 말한다.
  이 문장을 못 쓰겠으면 그 기능을 안 하는 게 맞다는 뜻이다.
- 서버 그룹은 **회원 탈퇴 시 함께 즉시 파기**한다(방침 §6 「회원 정보 — 탈퇴 시 지체 없이 파기」와 같은 줄).

**(b) SR-9.2 가 요구하는 숫자가 아직 없다.** 「방침에 적은 숫자와 코드 상수가 같아야 한다」인데
스펙 어디에도 기간이 없다. 그리고 ADR-0077 의 실패 모드가 정확히 이 자리에 있다 —
`blog_post_view` 는 `RETENTION_DAYS = 90` 상수가 있었는데 **호출자가 없어 무기한 누적**했다.
그래서 다음 셋을 함께 적지 않으면 SR-9.2 는 못 지킨다.

1. 숫자 (예: 마지막 사용 후 N일 미사용 시 만료). 「삭제할 때까지」만으로는 방침에 쓸 문장이 안 나온다.
2. 그 숫자를 실제로 지우는 **호출자** — 주 1회 `retention` CronJob 에 스윕을 추가한다(ADR-0077 §2 의 그 CronJob).
3. `PrivacyPage.tsx:238-263` §6 에 행 추가. 현재 항목은 회원 정보 · 댓글/찜/평점 · 방문자 번호 ·
   조회/클릭 90일 · 이력서 열람 1년 다섯 개뿐이라 친구 그룹이 어디에도 안 걸린다.

## 그 밖의 지적 (F)

### F1. 「릴레이 서버 코드 변경 0」(SR-1.1)이 사실이 아니고, 그 오해가 M2 를 낳았다

`isValidSlug` 가 형식만 본다는 것은 맞다. 그러나 SR-1.4(로비 30초 미사용) · SR-1.6(유휴 90초) ·
SR-4.4(자리 픽) · SR-4.5(선착순 중재) · SR-4.6(관전자) · SR-7.4(좌석 토큰) 이 전부 릴레이 변경을 요구한다.

특히 SR-1.4 는 **지금 코드와 정면으로 충돌한다.**

```kotlin
// startDueLobbies — 12석 파티 방은 legacy(2석)가 아니므로 이 조건에 걸린다
val due = rooms.values.filter { !it.legacy && !it.started && nowMs - it.createdMs >= LOBBY_MAX_WAIT_MS }
```

파티 방(seats=12)은 `legacy == false` 라 **생성 30초 뒤 자동으로 `started = true`** 가 되고,
그 순간 `join()` 의 `if (room.started && !room.legacy)` 가 **이후 입장을 전부 ROOM_STARTED 로 거절**한다.
카톡으로 링크를 돌리는 데 30초는 아무것도 아니다 — 초대 링크가 발송 직후 죽는다.
덤으로 `startRoom()` 이 그 시점의 `players`(별칭 배열)를 방송한다.

「서버 변경 0」이라는 전제가 M2 의 「어느 서버가 토큰을 발급하나」를 비워 두게 만들었다.
전제를 고쳐야 나머지가 제자리를 찾는다.

### F2. 방 코드가 유일한 접근 통제다 — 그 방에 실명이 있다

방에 들어오면 `seat` 방송과 `start` 의 `players` 배열로 **전원의 별칭을 받는다.** 즉 6자리 코드는
「실명일 수 있는 이름 12개」를 여는 열쇠다. 코드는 `SecureRandom` 32진 6자리(약 10.7억)라
표적 추측은 비현실적이지만, 구조상 두 가지가 남는다.

- **미지 코드가 방을 만든다.** `roomByCode()` 는 없는 코드면 그 코드로 방을 **생성**한다.
  코드 스캐너는 탐색과 동시에 방 슬롯을 먹고, `MAX_ROOMS = 200` 은 **전역**(모든 게임 공용)이다.
  게이트웨이 `/ws/games/**` 라우트에는 rate limiter 가 없고(`GatewayRouteConfig.kt:320-327` 은
  authFilter 만 건다), 레지스트리의 `peers` 맵에도 연결 수 상한이 없다. 200 방 고갈은 파티뿐 아니라
  **모든 릴레이 게임을 동시에 멈춘다.**
  → 파티 슬러그는 **미지 코드로 자동 생성하지 않는다**(명시적 방 생성만)로 좁히면 스캔이 슬롯을 못 먹는다.
- **링크는 소지자 권한**이다. 링크를 받은 사람은 누구나 좌석을 차지하고 명부를 읽는다.
  좌석이 다 차면 진짜 친구가 못 들어온다. 「링크를 아는 사람 = 방에 들어올 자격」이 이 기능의
  신뢰 모델이라는 것을 Out of Scope 옆에 한 줄로 명시할 것. 방장 승인은 범위 밖이어도 좋지만,
  **적혀 있지 않으면 나중에 사고로 보고된다.**

부수: 초대 링크의 방 코드는 Referer 로 새어 나갈 수 있다. 파티 화면에서 외부 링크(구글맵·광고)를
띄우지 않거나, 입장 후 `history.replaceState` 로 주소에서 코드를 지우는 편이 낫다.

### F3. 관전자(SR-4.6)를 실현할 자리가 릴레이에 없다

`join()` 은 언제나 빈 좌석을 잡는다. 좌석 없이 접속을 유지하는 개념이 릴레이에 없으므로
관전자는 (a) 좌석을 먹거나 (b) 아예 못 본다. (a) 를 고르면 참가자 수가 오염되고
「관전자는 표가 없다」(SR-5.8)를 **클라이언트 선의로만** 지키게 된다 — 신뢰 경계가 아니다.
관전 좌석을 릴레이 개념으로 만들지, 관전은 방 밖(폴링)으로 볼지 정할 것.
M2 의 토큰이 「좌석이 없으면 토큰이 없다」로 관전자 제출을 막는 것은 **이 결정이 선행되어야** 성립한다.

### F4. 자리 픽의 중재자가 없다 (SR-4.5)

「먼저 도착한 쪽이 앉고 나중은 거절」은 권위가 있어야 판정된다. 릴레이는 좌석 번호만 배정하고
**별칭↔좌석 결합은 클라이언트가 `join` 의 `nick` 으로 자칭**한다(`sanitizeNick` 은 제어문자 제거와
16자 절단이 전부). 즉 두 사람이 같은 별칭을 주장할 수 있고, 아무도 아니라고 말할 수 없다.
방장 클라이언트가 중재하면 방장이 명부를 조작할 수 있고, 서버가 중재하려면 릴레이에 상태가 생긴다.
어느 쪽인지 정하고, 「이 결합은 검증되지 않는다」면 그것을 적을 것 — 파티는 대면 상황이라
사회적 계약으로 충분할 수 있다. 다만 그렇다면 **좌석 토큰이 보증하는 것은 「좌석 k」이지
「민수」가 아니다**를 M2 표에 함께 적어야 한다.

### F5. 별칭 렌더링 — `sanitizeNick` 은 HTML 새니타이저가 아니다

릴레이는 제어문자만 거른다. `<img src=x onerror=...>` 는 그대로 통과해 **방 전원의 화면으로 방송된다.**
파티 UI 는 React 라 안전하지만, 별칭은 명부 규약을 타고 캔버스 게임 쪽으로도 넘어간다.
`portal-fe/public/games/lib/` 에는 `innerHTML` 로 목록을 그리는 코드가 실재한다(`rank.js:160` — 여기는
`escapeHtml` 을 거치지만 규율이 파일마다 달라진다). game 호스트에서 XSS 가 성립하면 인증 토큰이
`.1989v.com` 도메인 쿠키이고 **FE 가 읽을 수 있는 값**이라([[anonymous-identity-headers]] — `X-User-Id`
열의 「FE가 값을 아나: 안다」) 피해가 게임 한 곳에서 끝나지 않는다.
→ 스펙에 「별칭은 `textContent`/React 노드로만 그린다. `innerHTML` 경로에 넣지 않는다」를 요구로 넣을 것.
부수로 길이 기준이 갈려 있다 — 규약은 12자(`slice(0,12)`), 릴레이는 16자(`MAX_NICK_LENGTH`). 하나로 맞출 것.

### F6. 제출 입력의 상한이 없다

릴레이는 `MAX_MESSAGE_CHARS = 4096` · 초당 40건으로 스스로를 지킨다. 새로 생기는 **HTTP 채점 경로에는
그런 상한이 스펙에 없다.** 원그리기 궤적 점열은 무제한이면 메모리·CPU 를 그대로 먹는다.
점 개수 상한 · 바디 크기 상한 · 좌석당 제출 빈도를 **숫자로** 적을 것(릴레이가 그랬듯이).

### F7. 감사 로깅이 SR-9.3 과 상충한다 — 의도라면 그렇게 적어라

「판이 끝나면 남기지 않는다」는 개인정보 관점에서 옳다. 대가는 **분쟁의 증거가 없다**는 것이다
(「서버가 내 점수를 잘못 줬다」에 답할 자료가 없다). 파티 게임에는 받아들일 만한 거래지만,
스펙이 그것을 선택으로 적어야 나중에 「로그를 남기자」가 조용히 들어오지 않는다.
보안 이벤트는 SR-9.5 의 사유별 카운터가 대신한다 — **임계 알림**을 한 줄 붙일 것.
서명 불일치가 튀는 것은 공격의 유일한 신호인데, 세기만 하고 아무도 안 보면 없는 것과 같다.

### F8. 방장 권한 — 비율을 정하는 사람이 결과를 기울인다

SR-3.4 의 사람별 비율은 「누가 걸리나」를 직접 움직인다. 방장 승계가 자동(최저 좌석)이라
특정인에게 넘기는 조작은 불가능하고, 대면 상황이라 사회적 통제가 있다. 다만 **설정이 전원 화면에
보여야** 그 통제가 작동한다. SR-6.2 는 판 설정을 시작 메시지에 싣는다고만 하고 **표시 요구가 없다.**
「각 기기가 시작 직전 판 설정(제외자·인원·비율)을 화면에 보여준다」를 요구로 승격할 것.

참여형에서는 더 세다 — 방장이 채점 서버에 명부를 선언하면 서버가 그것을 검증할 방법이 없다.
`game/feature` 는 릴레이와 같은 JVM 이므로(ADR-0059 폴드) **채점 서버는 방·좌석의 진실을
`GameRelayRegistry` 에서 직접 읽어야 한다.** 클라이언트 선언을 받으면 M2 의 토큰을 세워 놓고
그 옆문을 여는 셈이다. (레지스트리에 조회 API 가 없다 — 지금은 `roomCount()`/`peerCount()` 뿐이라
이것도 릴레이 변경 항목이다. F1 참조.)

### F9. `X-Visitor-Id` 는 이 투표의 주체로 맞지 않는다

[[anonymous-identity-headers]] (1989v 볼트, updated 2026-08-28) 가 이 판단의 기준을 준다.
세 식별자의 갈림선은 **게이트웨이가 그 헤더를 자기 값으로 덮어쓰는가**이고, `X-Visitor-Id` 는
서버 발행 + httpOnly 쿠키 왕복이라 **헤더 위조는 불가, 쿠키 조작은 가능**한 중간 등급이다.
그리고 그 페이지가 못 박은 결론이 이 스펙에 그대로 적용된다 — **「어느 쪽도 어뷰징 방어가 아니다.
저장소를 비우면 전부 새 표가 된다.」** 블로그 좋아요에서는 그 대가로 표 수를 함께 노출해 저표본이
스스로 드러나게 했지만, 6인 방의 게임 선정에서는 표 하나가 결과를 바꾸므로 같은 완화가 안 통한다.

구체적으로 세 가지가 안 맞는다.

1. **릴레이 경로에는 그 값이 없다.** 게이트웨이 `VisitorIdFilter` 는 `/ws` 업그레이드 요청에도
   헤더를 심지만(`GatewayRouteConfig.kt:320-327` 로 릴레이가 게이트웨이를 지난다),
   `GameRelayWebSocketHandler.afterConnectionEstablished` 는 **경로에서 슬러그만 뽑고 헤더를 안 읽는다.**
   쓰려면 핸드셰이크 인터셉터로 세션 속성에 옮기는 작업이 따로 필요하다.
2. **필요한 성질이 다르다.** 투표 자격은 「이 방의 이 좌석인가」이지 「이 브라우저인가」가 아니다.
   `X-Visitor-Id` 로는 관전자를 못 거른다(관전자도 `vid` 를 갖는다). SR-5.8 이 그것을 요구한다.
3. **중복 방지도 못 한다.** 쿠키를 지우면 새 표다. 좌석은 방에 12개뿐이라 오히려 **좌석이 더 강한 상한**이다.

→ **투표 주체는 좌석 토큰(M2)으로 한다.** `X-Visitor-Id` 는 쓰더라도 보조 신호이지 주체가 아니다.
「식별자를 늘리지 않는다」는 취지는 좌석 토큰을 쓰면 그대로 지켜진다 — 새 식별자가 아니라
SR-7.4 가 이미 만들기로 한 물건이다.

### F10. 별칭이 로그로 새는 경로 — SR-9.7 을 구현 규칙으로 내려라

「어떤 관측 값에도 안 들어간다」는 선언이고, 지금 코드에 그 선언을 시험하는 자리가 있다.

```kotlin
log.debug { "게임 릴레이 파싱 실패 ${peer.conn.id}: ${e.message}" }
```

파싱 실패 메시지에 원문 조각이 포함되는 설정이면 별칭이 그대로 로그에 앉는다
(Jackson 은 판올림마다 소스 포함 기본값이 달라졌다 — `tools.jackson` 의 현재 기본값을 확인하고,
포함이면 명시적으로 끌 것). 같은 함정이 새로 생기는 곳:

- 채점/그룹 API 의 400 응답이나 예외 로그가 **요청 본문을 에코**하는 형태
- 검증 실패 메시지에 입력값을 넣는 습관 (`"이름이 너무 깁니다: 김철수"`)

「별칭은 로그·메트릭·에러 응답 어디에도 값으로 나가지 않는다. 길이·개수만 남긴다」로 적을 것.

## OQ 에 대한 보안 관점 메모

- **OQ-1 (유휴 90초)** — 코드상 답이 보인다. `sweepIdle` 은 60초에 `ping` 을 보내고 90초에 끊으며,
  **어떤 수신 메시지든 `lastSeenMs` 를 갱신**한다(릴레이는 `ping` 을 받으면 `pong` 을 돌려준다).
  즉 클라이언트 하트비트로 유지된다. 다만 좌석 토큰의 수명이 방 수명에 묶이므로(M2), 방이 끊겼다
  다시 열릴 때 **옛 토큰이 새 방에서 유효하면 안 된다** — 방 식별자에 생성 시각을 섞을 것.
- **OQ-4 (규약 v2)** — 보안 관점의 요구 하나: `roomCode` 를 `localStorage` 에 넣으면 같은 오리진의
  모든 게임 스크립트가 방 입장 권한을 읽게 된다. v1 의 규율(TTL 3분 · 읽으면 삭제)을 v2 에서도
  **방 코드에 대해 특히** 유지할 것.
- **OQ-2 (원그리기 채점식)** — 식을 고를 때 「위조 궤적이 그 식에서 만점을 받는가」를 판정 기준에 넣을 것.
  M3 의 개연성 검사와 함께 정해야 한다.

## 판정

**REVISE** — M1~M4 를 spec.md 에 반영한 뒤 태스크 생성.

되짚을 것 하나. 이 스펙은 「무엇을 지킬 것인가」를 정확히 알고 있다(SR-2.6 · SR-4.3 · SR-5.6 · SR-7.3).
빠진 것은 **그것을 지키는 물건이 무엇인가**다. 릴레이는 좌석 번호를 박아 보내는 팬아웃 장치이고,
HMAC 은 서명 대상이 검증된 사실일 때만 권위가 되며, 클라이언트가 쓴 시각은 서버가 계산해도
클라이언트의 것이다. 세 문장을 스펙에 적어 넣는 것이 이번 REVISE 의 전부다.
