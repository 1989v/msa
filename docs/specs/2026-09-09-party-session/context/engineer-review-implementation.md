# 구현 관점 리뷰 — 파티 세션

스펙이 「기존 코드로 성립한다」고 주장하는 대목을 코드로 대조했다. 결론부터:
**방 자체는 열리지만, 「서버 변경 0」은 성립하지 않는다.** 릴레이의 3석 이상 방에는
30초 강제 마감과 시작 후 입장 잠금이 하드코딩돼 있고, 그 둘이 각각 SR-1.4 와 SR-4(초대 링크)를
직접 깬다. 나머지 주장(결정적 재생·명부 규약 확장·좌석 토큰 선례)은 대체로 사실이나
전제가 하나씩 빠져 있다.

## 반드시 고쳐야 하는 것

### F1 (BLOCK급) — SR-1.4 「로비 30초 강제 마감을 쓰지 않는다」는 클라이언트가 고를 수 있는 게 아니다

`GameRelayRegistry.kt:165-185`

```kotlin
@Scheduled(fixedDelay = 1_000L)
fun tickLobbies() = startDueLobbies(System.currentTimeMillis())

fun startDueLobbies(nowMs: Long) {
    val due = rooms.values.filter {
        !it.legacy && !it.started && nowMs - it.createdMs >= LOBBY_MAX_WAIT_MS
    }
```

`legacy` 는 `capacity == MIN_SEATS`(2)일 때만 참이다(`:86`). 파티 방은 3석 이상이므로
**생성 30초 뒤 예외 없이 `startRoom` 이 돌고 `started = true` 가 된다.** 방장의 의사와 무관하다.

그 결과가 SR-1.4 하나로 끝나지 않는다:

```kotlin
// :233
if (room.started && !room.legacy) {
    send(peer, error("ROOM_STARTED")); return
}
```

**방을 연 지 30초가 지나면 초대 링크로 들어오는 사람이 전부 `ROOM_STARTED` 로 거절된다.**
SR-4(초대·자리 픽)와 SR-6.5(판 시작 뒤 합류해 빨리 감기)가 통째로 성립하지 않는다.
카톡으로 링크를 뿌리고 30초 안에 전원이 들어오는 시나리오는 이 기능의 전제가 아니다.

「릴레이 코드 변경 없이 성립한다」(SR-1.1)와 「30초 마감을 쓰지 않는다」(SR-1.4)는
**동시에 참일 수 없다.** 둘 중 하나를 고쳐야 한다.

### F2 (BLOCK급) — 방 코드 없이 join 하면 **남의 파티에 들어간다**

`GameRelayRegistry.kt:354-361`

```kotlin
private fun autoMatchRoom(gameSlug: String, seats: Int, nowMs: Long): Room? {
    val open = waiting[gameSlug]?.let { rooms[it] }
    if (open != null && !open.started && synchronized(open) { open.seats.any { it == null } }) return open
    ...
}
```

`waiting` 은 **슬러그당 한 칸**(`:106`)이다. 지금은 슬러그가 게임마다 달라서 이게 「빠른 매칭」이지만,
파티는 슬러그가 `party` 하나이므로 **모든 파티가 같은 대기열을 공유한다.**
A 파티 방장이 방을 만들고, B 파티 방장이 방을 만들면 B 는 A 의 방에 앉는다.
테스트가 정확히 이 동작을 고정하고 있다 — `GameRelayRegistryTest.kt:226-228` 에서
방 코드 없이 `seats=20` 으로 join 한 두 피어가 같은 방에 들어간다.

SR-1.2 는 「방 코드는 릴레이가 발급한다」고 못박았는데, 릴레이가 코드를 발급하는 경로는
`newRoom`(`:363`) 하나이고 그건 `autoMatchRoom` 안에서만 불린다. 즉 **릴레이 발급 코드를 받으려면
대기열을 타야 하고, 대기열을 타면 남의 파티와 섞인다.** 클라이언트가 코드를 만들어 `room` 으로
넘기면 섞이지는 않지만 그 순간 SR-1.2 가 거짓이 되고, 코드 알파벳도 갈린다
(`CODE_PATTERN = ^[A-Z0-9]{4,8}$` — `:69` 는 혼동 문자 `0/O/1/I` 를 허용한다).

### F3 (필수) — 「서버 변경 0」을 「서버 변경 소(小)」로 고치고, 무엇을 바꾸는지 적어라

F1·F2 는 둘 다 join 옵션 두 개로 풀린다. 릴레이가 게임 규칙을 알게 되지 않으므로
ADR-0059 의 무권위 원칙을 건드리지 않는다.

| 옵션 | 효과 | 건드리는 곳 |
|---|---|---|
| `private: true` | 대기열(`waiting`)에 올리지 않고 새 방을 연다. 코드는 그대로 릴레이가 발급해 `joined.room` 으로 돌려준다 (`:251` 이 이미 코드를 실어 보낸다) | `autoMatchRoom` 분기 1줄 + `newRoom` |
| `manualStart: true` | `startDueLobbies` 대상에서 빼고, 시작 후 입장 잠금(`:233`)도 걸지 않는다. 판의 시작은 방장이 `move` 로 뿌린다 | `Room` 필드 1개 + 필터 조건 1개 + `:233` 조건 1개 |

스펙의 「Existing Code to Leverage」 표에서 `:400 형식만 검사 — 서버 변경 0으로 열린다` 줄이
이 기능 전체 스코핑의 근거로 쓰이고 있다(D10 「다섯 개 전부 한 번에」 포함). 근거가 틀렸으므로
그 줄과 SR-1.1 을 함께 고쳐야 한다.

덧붙여: **N석(3~20) 경로는 운영에서 한 번도 돈 적이 없다.** 배포된 릴레이 게임 3종이
전부 `seats` 를 안 보낸다 — `frost-outpost/index.html:517`, `sketch-sleuth/index.html:606`,
`echo-duel/index.html:407` 모두 `{t:'join', room, nick}` 뿐이라 2석(legacy)이다.
ADR-0088 의 다인 방은 단위 테스트로만 검증돼 있다(`GameRelayRegistryTest.kt:219-310`).
파티가 그 경로의 첫 실사용자다 — 스펙의 위험 표에 넣을 값어치가 있다.

### F4 (필수) — 릴레이 좌석과 명부 자리를 같은 말로 쓰고 있다

- SR-1.5 「방장은 좌석 0」 → **릴레이 좌석**(`joined.seat`)
- SR-4.4/4.5 「명부에서 자기 것을 골라 앉는다 / 먼저 도착한 쪽이 앉는다」 → **명부 자리**

릴레이는 좌석을 **골라 주지 않는다.** `:238` `indexOfFirst { it == null }` — 빈 자리 중 가장 앞을
서버가 배정하고 클라이언트는 지정할 수 없다. 따라서 명부 자리 픽은 애플리케이션 레이어(`move` 위)에서
일어나고, **누가 중재하느냐가 스펙에 없다.** 릴레이는 무권위라 「먼저 도착한 쪽」을 판정해 주지 않는다.
방장 클라이언트가 판정하는 것으로 정하든 서버 권위를 하나 더 얹든, SR-4.5 는 지금 문장만으로는 구현 불가다.

같은 혼동이 상한에도 있다. **관전자도 릴레이 좌석을 하나 먹는다** — `join` 에 관전 개념이 없고,
빈 좌석이 없으면 `ROOM_FULL`(`:246-249`)로 접속 자체가 거절된다. 즉 실제 상한은
「참가자 12」가 아니라 **「참가자 + 관전자 합계 20」**이다. SR-1.2·SR-1.7·SR-4.6 에 이 값을 명시해야 한다.

또 SR-1.5 의 승계 규칙에 구멍이 있다: 좌석 0 이 비면 `leaveRoom` 이 `seats[0] = null` 로 두고(`:320-322`),
**다음에 들어온 사람이 그 자리를 받는다.** 「좌석 0 = 방장」과 「가장 낮은 번호가 잇는다」가
동시에 유지될 수 없다 — 승계 후 방장이 좌석 1인데 신규 입장자가 좌석 0을 받는다.
방장을 좌석 번호가 아니라 **명시적 값**으로 들고 다녀야 한다.

### F5 (필수) — SR-6.7 「결과가 갈리면 안 된다」는 지금 코드로는 보장할 수 없다

좋은 소식부터. **구슬 레이스의 시뮬은 진짜로 결정적이다**:

- `physics.js:248-259` `advance()` 가 `DT = 1/240` 고정 스텝으로만 전진하고 남은 시간은 누산기에 남긴다
- 시뮬 파일(`physics.js`·`game.js`·`courses.js`·`parts.js`)에 `Math.random`·`Date.now`·`performance.now`가 **하나도 없다**. `Math.random` 은 `fx.js`(파티클)·`audio.js`(노이즈)·`main.js`(코스 무작위 선택)에만 있다
- 구제 장치 `unstick()`(`game.js:120-126`)마저 `S.rng` 를 쓴다
- 프레임 레이트가 달라도 스텝 **순서**는 같다. `MAX_SUB` 초과 시 누산기를 버리지만(`physics.js:257`) 그건 시뮬이 덜 진행될 뿐 상태 열은 동일하다
- **SR-6.5 의 빨리 감기 원시함수가 이미 있다** — `game.js:289-303` `fastForward(seconds)`. 스펙의 「Existing Code to Leverage」에 빠져 있다

나쁜 소식. **엔진 간 동일성은 두 줄에서 깨진다.**

```js
// physics.js:172  (로터)
var ca = Math.cos(a), sa = Math.sin(a);
// physics.js:193  (시소)
var cs = Math.cos(s.a), sn = Math.sin(s.a);
```

`Math.sin/cos` 는 ECMAScript 가 **정밀도를 규정하지 않는** 함수다(V8·JSC·SpiderMonkey 결과가 마지막
비트에서 갈린다). 그 값이 로터 막대와 시소 판의 **충돌 기하**로 바로 들어가고, 초당 240스텝 × 막대 수만큼
평가된다. 구슬 물리는 카오스라 1 ULP 차이가 몇 초 안에 순위를 바꾼다.

그리고 **피할 코스가 없다** — `courses.js:24-72` 의 세 코스(`pinball`·`cascade`·`carousel`)가
전부 `rotorRow`/`seesawRow` 를 갖는다.

이 기능의 타깃은 「각자 자기 폰」(모바일 1순위)이다. 아이폰(JSC)과 안드로이드(V8)가 한 방에 있는 것이
**기본 시나리오**다. OQ-5 를 「post-impl 로 관측한다」로 미루면, 관측 결과가 「갈린다」일 때
남는 선택지가 물리 재작성뿐이라 되돌리는 비용이 가장 큰 지점에서 터진다.

지식베이스에 **같은 판단을 이미 한 기록**이 있다:

> 혹한 전초기지 2P: 상태 동기화. lockstep 이 대역폭상 유리하나 기존 싱글 시뮬이 가변 dt +
> 부동소수 math 라 고정틱 재작성이 필요하고 **그게 곧 싱글 회귀 위험**이었다 → host authority 선택
> — [[msa-game-platform]] (1989v, updated 2026-08-31)

구슬 레이스는 이미 고정틱이라 그때보다 유리하지만, **부동소수 문제는 그대로 남아 있다.**

권고 — OQ-5 를 pre-impl 로 올리고 셋 중 하나를 고른다:

1. **`sin/cos` 를 결정적 구현으로 교체** (호출부 2곳뿐이다). 각도를 정수 양자화한 룩업 테이블이면
   엔진 무관하게 동일하고, 물리 특성 변화는 미미하다. 가장 싸다
2. **호스트 권위** — 방장이 결과를 뿌린다. SR-6.6 「각 기기가 스스로 계산한다」를 포기하는 대신
   갈릴 수가 없다. 선례가 있다
3. **결과 해시 불일치 시 호스트 결과로 수렴** — SR-6.8 을 경고가 아니라 복구 장치로 쓴다

무엇을 고르든 T1(스펙의 검사 배정)은 **같은 엔진 안의 로직**만 잡는다. `test-quality.md` 의
「안 하는 것」에 크로스 브라우저를 넣어 둔 것은 맞지만, 그러면 **SR-6.7 을 지키는 장치가 하나도 없다.**

### F6 (필수) — 각 게임이 릴레이 클라이언트를 새로 가져야 한다. 그 비용이 스펙에 없다

SR-6.8(각 기기가 판 끝에 결과 해시를 릴레이에 흘린다)과 SR-6.5(늦게 들어와 빨리 감기)는
**게임 페이지가 직접 WebSocket 을 들고 있어야** 성립한다. 게임은 `GameDetailPage.tsx:425-428` 의
iframe 으로 뜨는 별도 문서이고, 파티 화면에서 이동하면 부모의 소켓은 죽는다.

그런데 `portal-fe/public/games/lib/` 에 릴레이 클라이언트가 **없다**. 기존 3종은 각자
`index.html` 안에 붙여넣기로 갖고 있다(`frost-outpost:471`, `sketch-sleuth:563`, `echo-duel:370`).
파티 대상 게임이 늘어날수록 그 사본이 늘어난다 — 게임 21곳이 각자 `localStorage` 읽기를 복사해 갖고 있다가
쿠키 전환이 통째로 지나간 사고와 **같은 모양**이다(ADR-0079, 2026-08-28).

권고: `public/games/lib/relay.js` 를 **먼저** 만들고 기존 3종을 거기로 모은 뒤 파티가 그걸 쓴다.
SR-8.5(카탈로그가 규약 구현을 안다)에 「릴레이 클라이언트를 쓴다」가 별도 조건으로 붙는지도
명시해야 한다 — 지금은 `DECIDER` 장르 하나가 두 가지 다른 통합(명부 규약 v2 읽기 / 릴레이 참여)을
동시에 뜻하게 된다.

### F7 (권고) — 채점 원자료의 전송 경로를 못박아라

릴레이는 **메시지 4096자**(`:46`), **초당 40건**(`:49`) 상한이다. 원그리기 궤적 점열(SR-7.3)은
이 안에 안 들어간다. HTTP POST 로 보낼 것이라면 스펙에 그렇게 적어야 한다 —
안 적으면 「릴레이로 보낸다」로 구현됐다가 `TOO_LARGE` 로 세션이 끊긴다(`:129-132`, 경고가 아니라 **연결 종료**다).

### F8 (권고) — 멱등 저장소의 수명이 SR-9.3 과 충돌한다

SR-7.5(같은 (방·판·좌석) 재제출은 첫 값 유지)는 저장소를 요구하고,
SR-9.3(판이 끝나면 남기지 않는다)은 저장을 금지한다. 둘 다 지키려면 멱등 키는
**릴레이와 같은 수명의 인메모리**여야 한다 — 그렇게 정했다고 적으면 된다.
DB 로 구현하면 SR-9.3 이 거짓이 되고, 「별칭이 원장이 된다」는 그 항의 이유가 그대로 발생한다.

그리고 `game_db` 마이그레이션은 **되고칠 수 없다**(main 이 곧 배포 브랜치라 체크섬 불일치가 서비스를 죽인다).
친구 그룹 테이블의 컬럼·인덱스를 한 번에 확정하고 들어가야 한다. 롤백 전략이 스펙에 없다 —
SR-2 서버 저장을 나중에 끄는 경로(옵트인 전면 해제 = 전 행 삭제)를 마이그레이션이 아니라
**운영 절차**로 적어 두는 편이 안전하다.

## 답이 이미 코드에 있는 열린 질문

### OQ-1 (판 사이 유휴 종료) — **닫아도 된다. 서버 변경 불필요**

`GameRelayRegistry.kt:126-138` 은 `onMessage` 진입 시 **메시지 종류를 가리지 않고**
`peer.lastSeenMs = nowMs` 를 찍는다. `ping` 도 정식 명령이다(`:152`).
그리고 배포된 세 게임이 **이미 25초 주기 keepalive 를 보내고 있다**:

```js
net.pingTimer = setInterval(() => netSend({ t:'ping' }), 25000);   // frost-outpost:519
```

`sketch-sleuth:608`, `echo-duel` 도 동일하고, 서버가 60초에 보내는 `ping` 에 되받는 처리도 있다
(`frost-outpost:541`). 25초 간격이면 90초 종료는 영영 안 걸린다.
방은 좌석에 한 명이라도 남아 있으면 유지된다(`:336-339`).

→ OQ-1 을 pre-impl 미결에서 빼고 SR-1.6 을 **「클라이언트가 25초 ping 을 유지한다(기존 3종과 동일)」**로
확정할 수 있다. 실측 e2e(T20)는 회귀 감시로는 여전히 값어치가 있다.

### OQ-4 (명부 규약 v2 버저닝) — 선택지가 하나뿐이다

`party.js:33` 과 `party.ts:49` 가 둘 다 `p.v !== 1` 이면 **null 을 돌려준다.**
`v` 를 2로 올리면 배포된 게임에서 인계가 통째로 죽고 준비 화면이 다시 뜬다.
`v: 1` 을 유지하고 **필드만 추가**하면 옛 리더는 모르는 필드를 무시하고 그대로 돈다.

→ OQ-4 의 답은 「가법적 확장, `v` 는 1로 고정, 새 필드는 전부 선택적」이다. 결정이 아니라 제약이다.
스펙 SR-8.1 이 「확장한다」고 이미 말했으니 문장 하나만 더 붙이면 된다.

한편 SR-8.2 는 늘어나는 것이 「인원 수·비율·방 코드」 셋이라고 하는데,
SR-6.2 는 시드·코스도 필요하다고 한다. 그 둘이 릴레이로 온다면 게임은
**규약(localStorage)과 릴레이 두 곳에서** 판을 조립한다 — 어느 값이 어느 경로로 오는지 표로 못박아야
구현이 갈리지 않는다.

## 그 밖에 짚어 둘 것

- **`game.security.hmac-secret` 이 어디에도 주입돼 있지 않다.** `InfraComponents.kt:58` 의
  기본값 `dev-secret-change-me-in-prod` 가 운영에서 그대로 쓰이고 있다(yml·k8s 전수 grep 0건).
  SR-7.4 의 좌석 토큰을 이 선례 위에 얹으면 **서명이 위조 가능**하고, 그러면 D5(서버 채점)의
  존재 이유가 사라진다. `AUTH_SUBJECT_HASH_KEY` 와 같은 등급의 주입 대상으로 스펙에 적어야 한다.
- **사다리타기는 결정성 위험이 없다.** 결과가 `ladder.js:26-60` 의 빌드 시점에 시드로 확정되고
  애니메이션(`game.js:190-198`, 가변 dt)은 결과에 관여하지 않는다. F5 는 구슬 레이스 한정이다.
  스펙이 두 게임을 한 덩어리로 다루는데 위험 등급이 다르다.
- **코스는 시드에서 안 나온다** — `main.js:590` 이 `Math.random` 으로 고른다.
  SR-6.2 가 코스를 명시적으로 뿌린다고 한 것은 맞다. 유지할 것.
- 폴드 배선은 **추가 작업이 없다.** `GameDataSourceConfig.kt:31,85` 가
  `com.kgd.game` 전체를 잡고 있어 새 하위 패키지가 자동으로 들어온다. 스펙 표현 그대로 정확하다.
- **스코프.** SR-1~SR-9 는 파티 방 + 친구 그룹(서버 저장·옵트인·방침·보존기간) + 익명 투표 +
  결정적 재생 + **클린룸 신작 2종** + ADR 2건이다. 클린룸 게임은 각각 별도 세션 규모다.
  D10(전부 한 번에)은 사용자 결정이므로 뒤집지 않되, **태스크 분해에서 참여형 2종을 독립 그룹으로
  떼어 내야** 나머지가 그것에 인질로 잡히지 않는다.

## 판정: **REVISE**

방향은 옳고 재사용 판단도 대체로 정확하다. 다만 **스코핑의 근거로 쓰인 문장 두 개가 코드와 다르다** —
릴레이 30초 강제 마감(F1)과 대기열 공유(F2). 이 둘을 고치지 않으면 「초대 링크로 모인다」는
기능의 첫 문장이 30초 뒤에 무너진다.

착수 전 반영할 것:

1. SR-1.1 「서버 변경 0」 → 「join 옵션 2개 추가」로 수정, 무엇을 바꾸는지 명시 (F1·F2·F3)
2. SR-1.4 를 릴레이 변경 항목으로 이동. SR-4·SR-6.5 가 여기 걸려 있음을 표시
3. 릴레이 좌석 / 명부 자리 용어 분리, SR-4.5 의 중재자 지정, 상한을 「참가자+관전자 20」으로 (F4)
4. OQ-5 를 pre-impl 로 올리고 F5 의 세 선택지 중 하나 확정
5. `lib/relay.js` 공용화를 태스크로 (F6), 채점 원자료 전송 경로 명시 (F7)
6. OQ-1·OQ-4 는 코드에 답이 있으므로 스펙에 확정으로 반영

권고(막지는 않음): `game.security.hmac-secret` 주입을 SR-7.4 의 전제로 적을 것.
참여형 2종을 독립 태스크 그룹으로 분리할 것.
