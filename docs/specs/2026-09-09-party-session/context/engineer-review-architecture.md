# 아키텍처 리뷰 (3차) — 파티 세션

**판정: REVISE** — 아키텍처 관점의 **블로커는 없다.** B-4 와 R-9~R-13 이 전부 닫혔다.
남은 둘은 새로 보인 것이고 각각 **한 항목 고쳐 쓰면 되는 크기**라, 3차 리뷰 라운드를 또 도는 대신
태스크 생성에 끼워 넣어도 된다.

남은 둘은 같은 뿌리에서 나온다 — **SR-6.4 가 방장의 재추첨 문을 닫으면서, 같은 문이 다른 사람
앞에도 있다는 것을 안 봤다.**

| 요구했던 것 | 반영 | 판정 |
|---|---|---|

| ③ 시작 명령 | SR-1.1 에 항목 추가 + 「명령이 없으면 판이 영영 시작되지 않는다」 근거 | **닫힘** |

무권위 유지도 맞다 — 「릴레이는 설정을 불투명 값으로 나르기만 한다」가 `move` 의 `d` 를 안 열어보는
기존 성질과 같은 형태다. 릴레이가 새로 아는 것은 「시작 명령이 왔다」와 「시드를 뽑는다」뿐이고,
둘 다 이미 하던 일이다(`GameRelayRegistry.kt:272` `SecureRandom`).

### R-11 의 물음 — 「판마다 시드 재발급」이 SR-6.2 로 충분한가

**충분하다.** 이유는 시드 뽑기의 **결속 대상이 바뀌었기** 때문이다.
- 지금 코드에서 `room.seed` 는 `startRoom` 안에서만 대입되고(`:272`), `startRoom` 은 방 수명에
  한 번 도는 경로(만석 · 로비 마감)에 매달려 있다. 그래서 초판 문장으로는 2회차가 1회차 시드를
  물려받을 여지가 있었다.
- SR-6.2 는 시드 뽑기를 **시작 명령 수신**에 걸었고, 시작 명령은 SR-1.1 의 판 단위 `started`
  때문에 판마다 정확히 한 번 온다. 판이 늘면 발급도 는다 — 별도 문장이 필요 없다.

구현 시 한 줄만 주의하면 된다: **시드 대입을 「방이 찼다」 경로에서 떼어 시작 명령 처리로 옮긴다.**
파티 방은 만석이 시작 조건이 아니기 때문이다. 이건 태스크의 일이지 스펙의 일은 아니다.

## REVISE

### N-1. 해시 불일치 무효가 **참가자 한 명이 부를 수 있는 재추첨**이다 (SR-6.4·6.12)

SR-6.4 의 논증은 정확하다 — 「방장이 판을 취소하고 다시 열 수 있으면 재추첨이 되어 3항이 다시
뚫린다.」 그런데 그 논증을 **방장에게만 적용하고 무효 사유 1번에는 적용하지 않았다.**

SR-6.12 는 「각 기기는 판 끝에 결과 해시를 흘리고 **서로 다르면** 판을 무효로 하고 같은 설정으로
다시 한다」고 정한다. 그리고 SR-6.2 대로 다시 하면 **시드가 새로 뽑힌다**(시드는 「설정」이 아니다 —
SR-6.2 가 둘을 갈라 놨다). 따라서:

> 결과가 마음에 안 드는 참가자는 **거짓 해시 하나를 흘려** 재추첨을 만들 수 있다.

방장의 문은 닫았는데 참가자 여섯의 문은 열려 있다. 「무효가 두 번 연속이면 게임을 잠근다」가
상한을 주지만, 잠긴 뒤에는 다른 게임으로 새 판을 열게 되므로 **결국 원하는 것(그 결과를 무르는 것)이
이루어진다.** 벌칙을 정하는 자리에서 이건 작은 구멍이 아니다.

또 하나 — 이 규칙은 **가장 느리거나 가장 오래된 기기 한 대가 방 전체의 판을 계속 무효로 만드는**
모양이기도 하다. SR-6.6 의 룩업 테이블 교체가 엔진 차이를 없애도, 한 대만 옛 번들을 캐시하고 있으면
그 방은 두 판마다 게임이 잠긴다.

**고칠 방향(택일, 한 항목이면 된다):**
- **다수 해시를 채택하고 소수를 이탈로 처리한다.** 소수 쪽 기기에는 「내 화면이 방과 달라졌다」를
  띄우고 방의 결과는 그대로 확정한다. 결과가 갈리는 것을 막는다는 SR-6.11 의 목적은 그대로 지켜지고,
  한 명의 거부권이 사라진다. 동수(2인)일 때만 무효로 떨어뜨린다.
- 또는 **무효를 판정 주체가 있는 사건으로** 만든다 — 해시는 좌석 토큰과 함께 채점 서버로 보내고
  서버가 세어 판정한다. 관측(SR-9.8)이 이미 채점 서버 몫이라 배치가 자연스럽고, 릴레이는
  여전히 아무것도 안 읽는다.

어느 쪽이든 SR-6.4 의 무효 사유 목록에 **「무효를 부를 수 있는 주체」**를 한 줄 덧붙이는 것이 핵심이다.
지금 목록은 「무엇이 무효인가」만 정하고 「누가 그것을 선언하나」를 안 정했다.

### N-2. 시작 명령의 **발신자 검증**이 없다 (SR-1.1 · SR-3.9)

SR-1.1 이 「방장 시작 명령을 받는다」로 끝난다. **좌석 0 에서 온 것만 받는다는 조건이 없다.**

시드 쇼핑은 원자적 발급이 막았으므로 이건 쇼핑 통로는 아니다. 문제는 **권한**이다 —
SR-3.9 가 「비율을 정하는 사람이 방장이다. 그것이 진행 권한의 범위」라고 선언했는데, 아무 좌석이나
설정을 실은 시작 명령을 보낼 수 있으면 그 문장이 클라이언트 UI 의 약속일 뿐 서버 규칙이 아니게 된다.
관전자가 좌석 없이 붙는 구조(SR-4.6)라 발신자 확인은 더 필요하다.

좌석 번호는 릴레이가 이미 아는 사실이므로(`peer.seat`), 이 검사는 **릴레이가 게임 규칙을 알게
만들지 않는다** — SR-1.1 이 세운 「옵션은 형식이지 규칙이 아니다」 기준 안에 있다.
요구: SR-1.1 의 시작 명령 항목에 「좌석 0 에서 온 것만 받는다. 승계(SR-1.6) 후에는 새 방장 좌석이
그 자리를 잇는다」를 붙인다.

## 통과 — 3차에서 확인한 것

- **B-4 의 처리가 지적보다 낫다.** ①만 요구했는데 SR-6.3 의 논증 자체를 「시드」에서 「결과」로
  넓혀 다시 썼다. 다음 사람이 「시드만 서버가 뽑으면 되는 거 아닌가」로 되돌리지 못한다.
- **R-13 을 지우지 않고 남긴 것.** 「초판의 주장 → 실제 → 뒤집은 근거」 표는 하네스 규칙
  (「되돌릴 때 옛 규칙의 이유를 지우지 않는다」)의 정확한 적용이다. 특히 `X-Visitor-Id` 행이
  볼트 페이지와 `VisitorIdFilter.kt:24-25` 를 함께 인용한 것.
- **「컨텍스트 배치」가 이제 구현 지시로 읽힌다.** 네 겹 + 좌석 조회 포트 + 게이트가 무는/안 무는
  자리의 구분까지 있어서, 태스크가 이 절만 보고도 패키지를 만들 수 있다.
- 레이어 방향 위반 없음 · 순환 의존 없음 · 폴드 규약(ADR-0058/0059) 충돌 없음 · 새 JVM/DB 없음 ·
  모듈 이름이 온톨로지에서 나옴 · 얕은 통과 모듈 없음 · 트랜잭션 경계 소유 유지.

## 다음 단계

N-1 · N-2 는 각각 한 항목이다. **아키텍처 관점에서 태스크 생성을 막을 것은 없다** —
둘을 지금 스펙에 반영하고 바로 넘어가도 되고, 태스크 단계에서 해당 SR 을 고치는 작업으로 잡아도 된다.

태스크로 미룰 경우 그 결정을 태스크 설명에 명시적으로 담아야 한다.
