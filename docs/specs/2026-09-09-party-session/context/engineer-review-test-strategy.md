## SHIP 조건 셋 — 전부 확인

**① T3 크리티컬 복귀.** 크리티컬 패스 표가 `T1·T3 → 아이폰과 안드로이드가 다른 결과를 본다`
로 돌아왔고 제외 문구가 사라졌다. requirements.md §5 위험표의 첫 줄을 다시 덮는다.

**② SR-6 신설 4항.** T62 ★(판마다 시드) · T63(원자적 발급) · T64(종료 신호) · T65(무효 사유)
넷이 섰다. 크리티컬 패스 행을 `T9·T62·T63·T64·T65 (방장이 결과에 못 닿는다)` 로 묶고

읽힐 여지가 없어졌다.

**③ 인용 방식 교체.** 서수 → 요구 문구로 바꾼 것이 정답이다. 전수 대조했고 일곱 곳 모두
현재 `spec.md` 문면과 일치한다:

## T60 · T61 (함께 봐 달라고 한 둘)

**T61 — 맞다.** 「좌석 0 이 아닌 좌석의 시작 명령은 거부된다 + 방장 승계 후에는 새 방장 좌석이
통과한다」로 두 방향을 다 본다. 승계(T54)와 물려 있어서 한쪽만 고친 구현이 통과하지 못한다.
회귀(발신 좌석 검사 제거)도 명확하다.

**T60 — 맞고, T25 와 정확히 상보한다.** T60 이 다수 있는 경우(거짓 해시 하나로 무효가 안 된다),
T25 가 다수 없는 경우(무효 + 2회 연속 잠금)를 맡아 SR-6.5 의 두 갈래가 다 덮인다.
회귀(「하나라도 다르면 무효」로 되돌리기)가 원래 구멍을 정확히 되살린다.

### 다만 T60 이 서 있는 바닥에 검사가 하나 없다

SR-6.5 는 「해시는 채점 서버가 **좌석 토큰과 함께** 받아 다수결로 판정한다」로 적었다. 그런데
**그 토큰 요구를 재는 행이 없다.** T10 은 채점 제출, T20 은 투표를 각각 게이트하는데 해시
제출은 세 번째 토큰 관문이고 표에 짝이 없다.

이게 비면 T60 이 세운 성질이 뒤집힌다 — 해시 엔드포인트가 무방비면 외부인이나 관전자가
해시를 채워 **다수를 만들 수 있다.** 원래 구멍(거짓 해시 하나로 재추첨)보다 나쁘다. 그때는
결과를 무르게만 했지만, 다수를 쥐면 **어느 결과를 방의 결과로 만들지 고를 수 있다.**

**추가할 행 하나** — T20 과 같은 모양이면 된다:
「해시 제출은 좌석 토큰을 요구하고 좌석당 한 건만 센다」(integration, W2).
회귀는 「토큰 검사 제거」 또는 「같은 좌석의 두 번째 해시를 함께 세기」.

이것을 SHIP 을 미루는 사유로 잡지 않는다 — 가법이고, 스펙이 이미 요구를 적어 뒀고, 태스크
단계에서 붙는 종류다. 다만 **태스크 생성 때 반드시 들어가야 하고**, 빠지면 T60 이 재는 것이
공격자가 정하는 값이 된다.

### 작은 것 하나

T60 만 서수 인용(`SR-6.5`)을 남겼다. 같은 절의 나머지가 전부 문구로 바뀐 뒤라 여기만
번호로 남으면 다음 개정에서 이 행이 먼저 어긋난다. 「어느 것도 사람이 부르지 않는다」나
「다수 해시가 방의 결과이고」로 맞추면 된다.

## 최종

**SHIP.** 세 바퀴 동안 제기한 것이 전부 닫혔다 — B1(게임 JS 러너 부재) · B2(★ 회귀가 안 물림) ·
B3(기능의 정의 미검증) · R1~R9 · 잔여 1~4 · SHIP 조건 셋.

이 문서에서 남길 만한 것 셋:

- **§0 을 표 앞에 세운 구조.** 「원칙을 문장으로 적는 것과 지켜지게 배선하는 것은 다른 일이다」를
  판정 원칙으로 올리고 W1~W4 로 배선을 먼저 정한 형태. 초판이 실패한 자리가 정확히 거기였다.
- **W4 의 「mock 하지 않는 것」 열거.** mock 해도 되는 것만 적으면 대상 자체를 mock 하는 것을
  못 막는다 — B2 가 그 실패였다.
- **★ 마다 주입할 회귀를 적은 것.** 「안 물리는 검사는 없는 것보다 나쁘다」를 문서가 스스로
  검사 가능하게 만든 형태다. 구현 때 그 회귀를 실제로 넣어 빨간불을 본 뒤에 「켰다」고 적으면
  된다.

태스크로 넘길 때 챙길 것 하나: **해시 제출의 좌석 토큰 게이트 행**(위 참조).
