## 2. 남은 지적

### R-1 · D-1 의 남은 세 지점 — 시드 권위는 옮겼는데 판 경계가 비어 있다 (유일한 1급 불변식 항목)

SR-6.2·6.3 이 「누가 시드를 뽑나」를 옮겼다. 그런데 **「언제 뽑나 · 언제 판이 끝나나」가 비어 있고,
셋 다 같은 불변식에 닿는다.**

**① 판마다 새 시드라는 말이 없다.**
`seed` 는 방 필드다 — `GameRelayRegistry.kt:78` `var seed: Int = 0` 이 `Room` 안에 있고,
`:273` `room.seed = random.nextInt(...)` 이 `startRoom` 에서 한 번 설정한다. SR-1.1 은
`started` **만** 판 단위로 바꾸라고 적었다. 판 2 가 판 1 의 시드를 물려받으면 **방장뿐 아니라
전원이 결과를 미리 안다** — 시드 쇼핑보다 더 나쁘다.
검사도 못 잡는다: T7 은 「두 번째 판이 돈다」만 보고, T9 는 「방장 시드 무시」만 보며,
T2(시드가 다르면 순위가 다르다)는 unit 이라 릴레이 재발급을 재지 않는다.
→ SR-1.1 의 목록에 **「`seed` 도 판 단위」** 를 넣고, T7 에 「두 판의 시드가 다르다」를 붙인다.

**② 판을 여는 방아쇠가 없다.**
`manualStart` 는 로비 자동 마감을 **면제**만 한다. 그러면 `startRoom` 의 남은 호출부는
만석 하나뿐인데(`:263` `if (occupants.size == room.capacity) startRoom(...)`), 파티 방은
관전자·빈 좌석을 허용하므로 만석이 안 될 수 있다. **면제하면 아무도 판을 열지 못한다.**
→ SR-1.1 에 **「좌석 0 이 보내는 명시적 시작 명령」** 을 옵션 목록의 한 항으로 넣는다.
릴레이는 좌석 번호만 보면 되므로 게임 규칙을 알게 되지 않는다.

**③ 판을 끝내는 신호의 주체가 없다 — 여기가 불변식의 남은 구멍이다.**
`started` 를 판 단위로 되돌리려면 릴레이가 「판이 끝났다」를 알아야 한다. 스펙 어디에도
그 신호의 발신자가 없다. **방장이 보내는 것으로 구현하면 방장은 자기가 걸리는 판을 도중에
끊을 수 있다** — SR-1.6 이 뗀 판정 권한이 종료 권한이라는 이름으로 되돌아온다.
SR-6.11(해시 불일치 → 무효)과 SR-7.9(시간 마감)는 *비정상* 종료만 다룬다.
→ 정상 종료의 주체를 정한다. 좌석 하나가 아니라 **전원 또는 정족수의 종료 보고**로 두거나,
릴레이가 판 시작 때 상한 타이머를 걸고 그것으로 되돌리는 편이 방장을 배제한다.

세 항목 모두 「릴레이가 규칙을 모른다」를 깨지 않는다 — 좌석 번호·메시지 종류·타이머만 본다.

### R-2 · 컨텍스트 배치 표가 SR-4 를 빠뜨리고 SR-8 을 통째로 roster 에 넣는다

표의 `party` 행은 SR-1·3·5·6 만 담는다. **SR-4(초대·자리 픽·관전)가 어느 컨텍스트에도 없다** —
방 수명이므로 `party` 다.

더 문제는 `roster` 행이 SR-8 **전체**를 가져가는 것이다. SR-8 은 제목부터 둘이다
(「명부 규약 확장 · 릴레이 클라이언트」).

| SR-8 항 | 실제 귀속 |
|---|---|
| 8.1 ~ 8.7 (규약·필드·어휘) | `roster` ✅ |
| 8.8 (`public/games/lib/relay.js` 공용화) | FE 인프라 — 컨텍스트가 아니다 |
| 8.9 ~ 8.12 (구현 신호 · 태그 축 · `[게임 픽]` 목록) | **`catalog`** — `Genre`·`GameTag` 가 거기 산다 (`game/domain/.../catalog/model/Genre.kt`, `GameTag.kt`) |

이대로 두면 `roster` 가 카탈로그를 알아야 하고, D-3 에서 나눈 것이 SR-8 에서 다시 뭉친다.
→ 표에 SR-4 를 넣고, SR-8 을 세 줄로 쪼개 귀속을 적는다(`catalog` 는 신규가 아니라 기존 확장).

### R-3 · 친구 그룹 SSOT 의 남은 두 구멍

SR-2.3 이 「켜져 있으면 서버가 SSOT, 기기는 캐시」로 승자를 정했다. 그런데 그 규칙이 다음 둘을 못 덮는다.

1. **이름 충돌.** R1.4 가 「그룹은 여러 개, **이름으로 구분한다**」라 이름이 사실상 키다.
   SR-2.5 는 「올릴지 물어본다」까지만 적는다 — 서버에 같은 이름 그룹이 있으면 병합인가 덮어쓰기인가
   나란히 두 개인가. 서버가 SSOT 라면 업로드가 SSOT 를 덮는 유일한 경로라 특히 정해야 한다.
2. **옵트아웃 전 내려받기.** SR-2.3 이 서버를 SSOT 로 만든 결과, 기기 캐시는 낡을 수 있다
   (다른 기기에서 편집). 그 상태에서 SR-2.4 대로 끄면 **최신본(서버)을 지우고 낡은 캐시만 남는다.**
   SR-2.4 의 「삭제 전 확인을 한 번 받는다」는 의사만 묻고 데이터를 안 지킨다.

이 플랫폼에 두 답이 이미 있다 — `[[guest-to-account-migration]]` (1989v 볼트, updated 2026-08-29):
**「계정이 비었을 때만 승계」**(=충돌 시 서버 것이 이기고 기기 것을 지우지 않는다)와
**「계정이 이겨도 게스트 행을 지우지 않는다」**(=어느 쪽도 사라지지 않는 유일한 배치).
→ SR-2 에 두 줄. 특히 「끄기 = 서버 행 삭제 **+ 기기로 내려받기 선행**」이면 손실이 0 이 된다.

### R-4 · 온톨로지는 게임을 셋으로 나누는데 카탈로그 신호는 둘이다 (신규)

온톨로지가 게임 종류를 셋으로 늘렸다 — **비참여형 · 입력형 비참여형 · 참여형**.
그런데 SR-8.9 는 신호를 둘로 정한다 — 「명부 규약을 읽는가 / 릴레이에 붙는가」.

이 둘로는 셋을 못 가른다. **「릴레이에 붙는가」가 입력형 비참여형과 참여형에서 둘 다 참**이기
때문이다(참여형도 좌석·판에 붙는다). 그 결과 아래 둘이 목록을 만들 수 없다.

- SR-5.3 `[랜덤]` — **비참여형** 중 무작위. 입력형 비참여형(카드 뽑기)이 여기 드나?
  온톨로지는 「참여형이 아니다」라 했으니 들어야 하는데, 신호로는 참여형과 구분이 안 된다
- SR-6.6 — 입력 중계가 필요한 게임을 골라내야 하는데 그 신호가 없다

→ SR-8.9 의 신호를 셋으로 하거나(명부 읽음 / 입력 중계 필요 / 서버 채점), 「릴레이에 붙는가」를
「무엇 때문에 붙는가」로 쪼갠다. 온톨로지가 셋으로 갈랐으면 축도 셋을 표현해야 한다.

### R-5 · SR-8.11 의 근거 수치가 오독이다 (신규, 경미하지만 스펙에 남으면 인용된다)

> SR-8.11 — "이미 **110개 게임**에 붙어 있는 카탈로그 태그라…"

110 은 게임 수가 아니라 **`display_order`** 다. `V25__consolidate_tags.sql:18-30` 이
`(slug, name, display_order)` 세 값을 20·30·…·100·**110**·120·130·140 으로 올리는 사다리이고,
`('party', 'Party', 110)` 은 그 열한 번째 칸이다.

실제로 `party` 태그가 붙은 게임은 소수다 — `V13__seed_echo_duel.sql:20`(echo-duel) ·
`V20__seed_expansion_pack1.sql:164`(bracket-battle) · `V24__seed_sketch_sleuth.sql:26`(sketch-sleuth)
와 `V25:52` 의 `drawing` 흡수분.

**결론은 그대로 옳다** — 태그 이름 `party` 를 재사용하면 파티에서 못 쓰는 게임이 목록에 나타난다.
근거만 「이미 다른 뜻으로 쓰이는 카탈로그 태그이고 여러 게임에 붙어 있다」로 고친다.

### R-6 · D-14 미해결 — `PARTY_MAX` 를 별칭 길이로 부른다

`planning/requirements.md:67` (R1.1) — "별칭은 12자 이하(현행 `PARTY_MAX`·`slice(0,12)` 와 일치)".
`PARTY_MAX = 12` 는 **인원 상한**이다(`portal-fe/src/pages/games/party.ts:27`, `party.js:22`).
별칭 길이는 `party.ts:62` 의 `slice(0, 12)` 리터럴이고 이름이 없다. 두 12 가 우연히 같을 뿐이다.

SR-1.3 이 닫은 것은 D-15(좌석 상한)이지 이것이 아니다. SR-2.1 도 "별칭 12자 이하, 2~12명"으로
두 12 를 이름 없이 나란히 둔다. → 한쪽에 이름을 붙여 갈라 적는다(예: 별칭 길이 상한 `ALIAS_MAX_LEN`).

### R-5 — 「110개 게임」은 오독이다 (팀리드가 두 번째로 확인했다고 적었으므로 근거를 다시 든다)

`spec.md:190` 이 여전히 "이미 **110개 게임**에 붙어 있는 카탈로그 태그라" 로 적혀 있다.

`V25__consolidate_tags.sql` 의 해당 구문은 게임 매핑이 아니라 **태그 사전 자체를 채우는
INSERT** 다.

```sql
-- 1) 목표 태그 보장 (display_order = 목록 노출 순서)          ← :15 주석
INSERT INTO game_tag (slug, name, display_order)               ← :16 컬럼 셋
VALUES ('multiplayer', 'Multiplayer', 10),
       ('roguelike',   'Roguelike',   20),
       …
       ('leaderboard', 'Leaderboard', 100),
       ('party',       'Party',       110),                     ← :27
       ('sports',      'Sports',      120),
       …
```

세 번째 값은 `display_order` 이고 10 단위 사다리의 열한 번째 칸이다. 주석이 그것을 명시한다.
같은 태그가 `V13__seed_echo_duel.sql:4` 에서는 `('party', 'Party', **21**)` 로 들어왔다가
V25 의 `ON DUPLICATE KEY UPDATE display_order = VALUES(display_order)` 로 110 이 됐다 —
게임 수라면 21 → 110 으로 갱신될 수 없다.

실제로 `party` 태그가 붙는 곳은 마이그레이션 전체에서 넷이다.

| 붙이는 구문 | 대상 |
|---|---|
| `V13__seed_echo_duel.sql:20` | echo-duel |
| `V20__seed_expansion_pack1.sql:164` | bracket-battle |
| `V24__seed_sketch_sleuth.sql:26` | sketch-sleuth |
| `V25__consolidate_tags.sql:52` | `drawing` 태그를 갖던 게임들(흡수 매핑) |

**SR-8.11 의 결론은 옳다** — 이미 다른 뜻으로 쓰이는 태그라 재사용하면 파티에서 못 쓰는 게임이
목록에 나타난다. 고칠 것은 근거 한 구절뿐이다: 「110개 게임에 붙어 있는」 → 「여러 게임에 이미
붙어 있는(`V13`·`V20`·`V24`·`V25` 흡수분)」.

숫자를 굳이 짚는 이유는, 스펙에 남은 수치는 다음 사람이 세지 않고 인용하기 때문이다.

- `seed` 도 **판 단위**여야 한다(SR-6.4). SR-1.1 은 `started` 만 적는다
