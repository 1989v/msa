# 파티 세션 — 요구사항

한자리에 모인 사람들이 **무엇을 할지 정하고, 누가 걸렸는지 정하는** 자리.
게임은 그 자리에서 갈아끼워지는 소모품이고, 자리 자체가 이 스펙의 대상이다.

## 0. 온톨로지 (이 스펙이 쓰는 말)

| 말 | 뜻 | 아닌 것 |
|---|---|---|
| **파티 방** | 6자리 코드로 열리는 자리. **판보다 오래 산다** — 판이 끝나도 방은 남고 다음 게임을 고른다 | 대전 방(`/ws/games/{게임슬러그}`)이 아니다 |
| **판(Round)** | 방 안에서 한 번 도는 게임. 식별자는 **방 코드 + 순번**, 상태는 구성 → 진행 → 마감 → 확정/무효 | 방이 아니다. 방은 판을 여러 번 담는다 |
| **친구 그룹** | 영속 명부. 별칭 목록. 방 밖에서도 산다 | 이번 판 참가자가 아니다 |
| **판 참가자** | 이번 한 판에만 유효한 부분집합. 그룹에서 토글로 추린다 | 그룹을 바꾸지 않는다 |
| **좌석** | 릴레이가 배정하는 번호. 신원의 근거이고 좌석 토큰의 대상 | 명부의 자리(별칭)와 다른 것이다 — 좌석은 릴레이가, 자리는 사람이 고른다 |
| **관전자** | 좌석 없이 방에 붙은 사람. 화면은 보되 표·채점·참가자 수에 안 들어간다 | 참가자가 아니다 |
| **비참여형 게임** | 결과를 시드가 정하는 것. 사람 입력이 그림만 바꾼다 (구슬·사다리) | 조작이 결과를 바꾸지 않는다 |
| **입력형 비참여형** | 지켜보는 자리이되 **사람 입력이 결과를 바꾸는 것** (카드 뽑기). 입력을 중계해야 같은 판이 된다 | 참여형이 아니다 — 겨루는 게 아니라 뽑는 것이다 |
| **참여형 게임** | 각자 자기 기기로 직접 하고 **서버가 채점**하는 것 (7초·원그리기) | 관전이 아니다 |
| **명부 규약** | 게임이 참가자·방식·인원·비율을 인계받는 계약. 현행 `kgd.party.v1` 의 확장 | URL 쿼리가 아니다 |

**「파티」라는 말은 파티 방과 이 기능 이름에만 쓴다.** 명부 규약·릴레이 슬러그를 부를 때는 쓰지 않는다 —
한 낱말이 네 뜻으로 갈리면 문서가 스스로를 못 가리킨다.

`/hns:glossary` 후보: 파티 방 · 판 · 친구 그룹 · 판 참가자 · 좌석 · 관전자 · 참여형/비참여형/입력형 비참여형 · 명부 규약.

## 3. 요구사항

> 세부 판정의 최신본은 `spec.md` 의 SR 이다. 아래는 shaping 단계의 원문이고, 리뷰로 뒤집힌 곳은
> 그 자리에 표시했다 — 지우면 왜 그렇게 정했는지가 사라진다.

### R1 — 친구 그룹
- R1.1 그룹은 **이름 + 별칭 목록**. 별칭은 12자 이하(현행 `party.ts:62` 의 `slice(0,12)` 리터럴과 일치 — 이름이 붙어 있지 않다). 인원 상한 12는 별개 상수 `PARTY_MAX`(`party.ts:27`)다
- R1.2 **저장 위치가 둘**: 기본은 기기(`localStorage`), 로그인 사용자가 옵트인하면 계정. 옵트인은 그룹 단위가 아니라 **사용자 단위 설정**이고 끄면 서버 행이 지워진다
- R1.3 계정 저장이 켜진 상태에서 기기 그룹이 있으면 **한 번 올릴지 물어본다**. 자동 업로드하지 않는다(동의 없는 전송이 된다)
- R1.4 그룹은 여러 개. 이름으로 구분한다
- R1.5 **명부 규약을 구현한 게임이면 파티 밖에서도 그룹을 불러 쓴다**(게임 상세·게임 안 준비 화면)
- R1.6 별칭은 **실명일 수 있다고 전제**한다 — 로그·에러 리포트·분석 이벤트에 값을 싣지 않는다

### R2 — 파티 방 · 초대
- R2.1 방장이 방을 연다 → 6자리 코드 + **초대 링크** + **QR**
- R2.2 방은 **게임에 묶이지 않는다** — `/ws/games/party` 한 자리에서 게임을 갈아탄다
- R2.3 초대 링크로 들어온 사람은 **그 판의 참가자 목록 중 자기 것을 픽**해서 앉는다. 이미 앉은 자리는 못 고른다
- R2.4 픽하지 않고 들어온 사람은 **관전자**다 — 화면은 보되 참가자 수에 안 들어간다
- R2.5 방장이 나가면 남은 좌석 중 가장 낮은 번호가 방장을 잇는다 (ADR-0088 승계 규칙 재사용)
- R2.6 QR 은 **클라이언트에서 그린다** — 링크가 서버로 갈 이유가 없다

### R3 — 판 구성 (시작 전)
- R3.1 그룹을 고르면 전원이 체크된 상태로 뜬다. **토글로 이번 판만 뺀다** — 그룹 원본은 안 바뀐다
- R3.2 **걸리는 인원 수**를 정한다(1명 ~ 참가자−1)
- R3.3 **사람별 비율**을 정한다. 기본 전원 동일, 올린 사람은 그만큼 확률이 오른다
- R3.4 R3.1~R3.3 은 **판 설정**이고 저장되지 않는다. 다음 판은 기본값에서 시작한다
- R3.5 비율은 게임마다 실현 방식이 다르다(구슬 = 구슬 개수, 카드 = 카드 장수, 사다리 = 줄 개수). **UI 는 하나**이고 게임이 규약을 받아 자기 방식으로 실현한다

### R4 — 게임 선정
- R4.1 세 갈래: `[게임 픽]` · `[랜덤]` · `[참여형]`
- R4.2 `[게임 픽]` 의 대상은 **명부 규약을 구현한 게임 전체**. 나머지 카탈로그는 여기 안 나온다
- R4.3 `[랜덤]` → **비참여형** 중 무작위
- R4.4 `[참여형]` → 참여형 목록 → `[랜덤]`(무작위) 또는 `[하나 픽]`
- R4.5 `[하나 픽]` 은 **익명 투표**다 — 전원이 자기 기기로 하나씩 고르고, 최다득표가 이긴다. **누가 뭘 골랐는지는 아무에게도 보이지 않는다**(방장에게도). 동표는 무작위
- R4.6 투표는 참가자만. 관전자는 표가 없다

### R5 — 비참여형 동시 관전
- R5.1 방장이 시작하면 **전원의 화면에서 같은 판이 돌아간다**
- R5.2 방식은 화면 전송이 아니라 **결정적 재생** — 참가자·코스·판 설정을 각자 기기가 받아 같은 판을 그린다. 대역폭이 판당 수백 바이트다. **시드는 방장이 아니라 릴레이가 뽑고, 설정과 한 메시지로 묶여 나간다**(SR-6.2·6.3 — 초판은 방장이 뿌리는 것으로 적었고 그것이 시드 쇼핑이었다)
- R5.3 늦게 들어온 사람은 **경과 시간만큼 빨리 감아** 따라붙는다. 판이 끝났으면 결과 화면
- R5.4 결과는 전원이 같은 것을 본다. 방장 기기가 결과를 「선언」하지 않는다 — 각자가 계산한 결과가 같은 것이 이 방식의 성질이다
- R5.5 기기가 느려 몇 프레임 어긋나는 것은 허용한다. **결과가 갈리는 것은 허용하지 않는다** — 이것이 R5 의 판정 기준이다

### R6 — 참여형 게임 (신작 2종)
- R6.1 **7초를 맞춰라** — 각자 0초에서 시작하는 타이머를 7초에 멈춘다. 7초에 가까운 순서가 순위
- R6.2 **원그리기 정확도** — 화면의 원을 손으로 따라 그린다. 가장 정확한 사람이 승리
- R6.3 **서버가 채점한다**(D5). 클라이언트가 보낸 「내 점수」를 믿지 않는다
- R6.4 각자 자기 기기에서 하고, 전원이 끝나면 순위가 공개된다
- R6.5 두 게임 모두 **혼자서도 된다**(카탈로그 등재 조건). 파티 밖에서는 기록 도전
- R6.6 게임 제작은 클린룸 파이프라인 가드레일을 탄다 — 모바일 세로·가로 2방향 CDP 실측 포함

### R7 — 실패 의미 (재시도·멱등성)
- R7.1 **방 유실은 판 유실이다** — 릴레이는 in-memory 단일 노드라 재배포·재기동에 방이 사라진다. 진행 중이던 판은 버리고 새 방을 연다. 명부·판 설정은 방장 기기에 남아 있으므로 재입력을 요구하지 않는다 (SR-1.7 — 초판 표현이 스펙과 반대였다)
- R7.2 **채점 제출은 멱등**이다 — 같은 (방, 판, 좌석)의 재제출은 첫 값을 유지한다. 네트워크 재시도가 점수를 바꾸면 안 된다
- R7.3 **제출하지 않은 사람은 최하위**다. 무한정 기다리지 않는다(제한 시간 후 마감)
- R7.4 **투표 미제출은 기권**이다. 전원 기권이면 무작위로 떨어진다
- R7.5 서버 채점이 실패하면 **판을 무효로 하고 다시 한다**. 클라이언트 값으로 폴백하지 않는다 — 폴백하는 순간 D5 가 무의미해진다
- R7.6 그룹 계정 저장이 실패해도 **판은 진행된다**. 저장은 판의 전제가 아니다

### R8 — 관측
- R8.1 방 수·좌석 점유·유휴 종료를 메트릭으로 낸다(릴레이는 지금 로그만 남긴다)
- R8.2 **결정적 재생이 갈렸는지**를 잡을 수 있어야 한다 — 각 기기가 판 끝에 결과 해시를 릴레이에 흘리고, 다르면 경고. 이것이 R5.5 의 계측기다
- R8.3 채점 거부(서명 불일치·중복·시간 초과)를 사유별로 센다
- R8.4 **별칭은 어떤 관측 값에도 안 들어간다**(R1.6)

## 4. 범위 밖

- 돈·포인트·정산 (D8). 「앱 안에 돈이나 포인트는 없다」는 현행 게임 설명의 약속을 유지한다
- 그룹 전적·랭킹 누적 — D8 을 고르며 함께 빠졌다
- 명부 규약을 구현하지 않은 게임을 파티에서 고르는 것 (D3)
- 릴레이 다중 노드 — 단일 노드 전제 그대로(ADR-0059). 방 상한 200 이 상한이다
- 화면 픽셀 전송·WebRTC — R5.2 가 필요 없게 만든다
- 소셜 그래프(친구 요청·수락) — 그룹은 방장이 손으로 적는 명부다

## 5. 위험

| 위험 | 실체 | 다루는 곳 |
|---|---|---|
| 결정적 재생이 갈린다 | 부동소수·타이밍 차이로 기기마다 결과가 다르면 내기가 성립하지 않는다 | R5.5 판정 + R8.2 계측 |
| 서버 채점이 릴레이 원칙을 깬다 | **첫 권위 레이어가 아니다** — 아케이드 채점 스택(Tier A/B · 정수 결정적 코어)이 이미 있고 이 스펙은 그 확장이다. ADR 은 여전히 필요하다 | ADR-0092 |
| 별칭이 실명으로 들어온다 | 자유 텍스트 (D2) | R1.6 + 방침·보존기간 |
| 방이 판보다 오래 사는 것을 릴레이가 모른다 | **유휴 90초가 아니라 로비 30초 강제 시작**이 끊는다. 유휴는 클라이언트 25초 ping 으로 유지된다(OQ-1 닫힘) | SR-1.1 `manualStart` |
| 참여형 신작 2종이 일정을 지배한다 | 클린룸 게임 제작은 각각 별도 세션 규모 (D10 이 감수) | 태스크 분리 |
| N석 릴레이가 운영에서 안 돌아 봤다 | 배포된 릴레이 게임 3종이 전부 `seats` 를 안 보내 2석으로 돈다 — 파티가 그 경로의 첫 사용자다 | SR-1.11 |
| 방 고갈로 전 릴레이 게임이 멈춘다 | 알 수 없는 코드로 붙으면 방이 만들어지고, 상한 200은 전역이며 라우트에 속도 제한이 없다 | SR-1.10 |
| 방장이 종료 시점으로 결과를 고른다 | 판정 권한을 뗐어도 종료 권한으로 돌아온다 | SR-6.6 |
| 판 2가 판 1의 시드를 물려받는다 | 시드가 방 필드라 판 시작에서 한 번만 대입된다 — 전원이 결과를 미리 알게 된다 | SR-6.4 |
| 운영 HMAC 키가 개발 기본값이다 | `GAME_HMAC_SECRET` 이 k8s 에 주입돼 있지 않다 — **이 스펙 밖의 현존 결함**이고 좌석 토큰이 그 위에 얹힌다 | SR-7.7 + 별건 보고 |
