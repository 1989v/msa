## 3. 단계

### 7-0 전국 덮기 — 모든 시장에 가게가 보이게 (판정 규칙 변경, **승인 필요**)
IN 이 없는 시장에서 지도가 비는 것은 조작·도식을 아무리 다듬어도 해결되지 않는다. 먼저 한다.
- **표시 규칙**: IN 이 하나도 없는 시장은 「시장 주변 가게」를 기본으로 보인다 — 시장 중심(또는 경계)에서 R 안의 OUT 가게. R 은 100 m 부터 시작해 가게가 30곳 이상 될 때까지 50 m 씩 넓히되 300 m 상한. 배지 「소속 미확인·주변」. **소속 값은 바꾸지 않는다**(OUT 그대로, 표시만).
- **판정 규칙 후보**(둘 중 하나, 사용자 결정): (a) 온누리 가맹점이 없는 시장은 밀도 규칙 대신 「중심 100 m 안 = IN」; (b) 판정은 두고 표시 규칙만. 권장은 (b) — 되돌릴 수 있고, 다음 OSM 수집이 경계를 주면 자연히 IN 으로 바뀐다.
- **파생 경계가 순환 참조다** (원인 확인, 2026-10-16): `market_osm.py` 의 `prepare(…, in_store_points(state))` 는 **이미 IN 인 가게**의 좌표로만 둘레를 만든다. IN 이 없는 시장은 파생 경계가 안 나오고, 경계가 없으니 IN 도 안 나온다. 지금 DERIVED 는 9곳(OSM 75곳). 고치려면 둘레 입력을 「온누리 가맹점과 짝이 돼 좌표를 얻은 가게」(소속 무관, 3곳 이상인 시장 198곳)로 바꿔야 한다 — 이건 **판정 변경**이라 별도 승인 뒤 다음 정기 OSM 실행에 얹는다. 승인되면 표시 규칙(위)이 덮던 시장 중 198곳이 실제 IN 으로 바뀐다.
- 검증: 828곳 중 「기본 화면에 가게 0」인 시장 수가 488 → 0. 좌표 없는 UNKNOWN 만 있는 286곳은 목록으로 보인다는 것을 확인.

### 7-1 지도 조작·검색 — FE 만 (7-0 과 병행, 먼저 배포 가능)
- **확대·이동**: viewBox 상태로 구현(라이브러리 없음). 휠·핀치·+/− 버튼·더블탭. **핀 버튼을 HTML 백분율 오버레이에서 SVG 안 `<a>`/`<g role="button">` 으로 옮겨** 그림과 클릭 영역이 같이 움직이게 한다(리뷰 반영 — 지금 구조로는 viewBox 만 바꾸면 어긋난다).
- **화면상 충돌 묶기**: `groupMarketPins` 는 같은 필지·같은 좌표만 묶는다. 여기에 **현재 배율에서 화면 거리 24 px 안의 묶음을 하나로** 합치는 단계를 더한다(배율을 올리면 풀린다). 묶음 탭 → 바닥 시트에 가게 목록(건물·층·호 순, 없으면 이름순). 묶음 안 가게 수가 200 이 넘으면 시트는 50행씩 더 보기.
- **검색 결과 → 지도**: 결과 행을 버튼으로 만들어 누르면 그 핀으로 이동·확대, 묶음·시트를 열고 해당 행을 강조한다(리뷰 (d) 반영).
- **섹션 검색 범위를 P5 와 같게**: 이름·품목·업종 **대/중/소**·착한가격 메뉴, 같은 정규화(공백 제거·소문자)와 같은 순위(이름 > 품목 > 메뉴 > 업종). UNKNOWN 결과는 「위치 미확인」 구분. **동의어·상위 분류 확장은 뺀다**(리뷰 반영 — 떡볶이→분식은 근거 없는 가게를 섞는다. 필요하면 공통 검색 정책에서 「관련 업종」으로 따로).
- **구역 칩**: 기본 8개 + 「다른 길 N개」 접기. 정렬은 가게 수 내림차순, 시장 이름 포함 길 우선. 골목 종류(OSM highway 등급)는 공개 응답에 없으므로 쓰지 않는다(리뷰 반영). 지도 위 골목 이름은 그대로 둔다 — 숨기지 않는다.
- **내 위치**: 버튼으로만 요청. 화면(viewBox) 안이면 점 + 정확도 원, 밖이면 가장자리 화살표 + 「시장 중심까지 820 m · 북동」. 기준점은 시장 중심(경계가 있으면 경계 중심). 정확도·측정 시각 표시, 다시 재기, 10초 시간 초과·거부 문구. 이미 시장 안이면 게이트 안내를 하지 않는다(리뷰 반영).
- 검증: `npx tsc -b`(저장소 규칙), 시장 테스트, CDP 4조합 + 모바일 핀치 캡처. 확대 뒤 모든 핀의 그림 좌표와 클릭 좌표 일치(DOM 측정), 충돌 묶음 전체가 시트에서 선택 가능. 검색은 고정 fixture 로 예상 가게 id·순위·오탐 제외를 검사. 남대문에서 「떡볶이」「갈치」「안경」 결과 id 를 `/markets` 와 대조.

### 7-2a 주소 표본 검증 — 작은 단계 (스키마 전)
리뷰 반영. 7-2b 의 스키마·목표치를 정하기 전에 측정한다.
- 남대문·광장·경동 온누리 원문 주소 300건을 손으로 라벨(건물·동·층·호). 파서를 돌려 **필드별 정확도**와 모호 사례 비율을 잰다. 합격선: 건물 95%·층 90%·호 90%, 모호는 미배정.
- 파서 규칙: 접미사가 있는 값만 확정(「1층」「117호」「C동」). `지하1층136` 의 136 은 호 **후보**, `지하양품` 의 지하는 층 후보 — 후보는 별도 열(`…_candidate`)에 두고 화면에는 「추정」 표시.
- 파싱 대상은 **온누리 원문 주소**(`onnuri_raw` 의 주소). `jibun_address` 는 상가정보와 짝이 되면 상가정보 값으로 덮여 있다(리뷰 반영).
- 건물 식별 키: (시장 id, 정규화 건물명, 지번 본번) — 건물명만으로 합치지 않는다. 별칭(대도아케이트=대도아케이드)은 시장 범위 `market_building_alias`, 운영자 편집.
- OSM 건물 폴리곤 연결 조건: 폴리곤 `name` 정규화 일치 → 없으면 같은 건물 IN 가게 좌표 중앙값이 폴리곤 안 → 없으면 미연결(블록은 중심점 + 가게 수 원으로).
- OSM 수집 비용 측정: 남대문 1곳 `way["building"]` 추가 시 응답 크기·시간, 50곳 묶음 메모리. relation 건물(구멍·다중 외곽)은 1차에서 제외하고 `way` 만.

### 7-2b 블록 층 — 적재·API·화면
- 파생 열: `derived_building`·`derived_dong`·`derived_floor`·`derived_ho`(+ 후보 열, 파서 버전). 원천 열은 안 덮는다(외부 데이터 3규칙 ②). 전체 동기화 경로 필드 목록 갱신(③).
- `market_block`(시장 id·키·이름·폴리곤 또는 중심·OSM id·가게 수 IN/UNKNOWN). 블록 id 는 키 해시로 재적재에 안정(리뷰 (d)). 별칭·수동 배정은 `market_change_log` 에 전후 값, 되돌리기, 재적재 보호(기존 P2 규칙 그대로).
- 공개 계약: `blocks[]` + 가게 `blockId`. **UNKNOWN 은 블록 목록에 「추정 연관」으로 들어가되 지도에 개별 점으로 찍지 않는다**(리뷰 반영 — `MarketPublicProjection`·`hasMarketCoordinate` 가 UNKNOWN 좌표를 빼는 규칙은 유지). 블록 누르면 층 → 호 자연 정렬 목록. 기존 BUILDING/FLOOR 구역과의 관계: 구역은 사람이 만든 분류, 블록은 데이터에서 파생 — 구역이 블록을 가리키는 선택 연결만 둔다.
- OSM 수집: 쿼리에 `way["building"]`·`node["railway"="subway_entrance"]` 추가. **수집 기능 버전**(`fetch_version`)을 raw 에 적어 28일 건너뛰기가 「건물 없는 옛 수집」을 다시 돌게 한다. deadline 전 묶음 마감(남은 시간 < 묶음 평균이면 중단하고 끝낸 묶음만 저장). 건물 수집 실패가 골목 수집을 막지 않게 슬롯 분리. 출처 표시는 건물·출구만 OSM 일 때도 붙인다.
- 검증: 7-2a 표본의 정확도 재확인(회귀 주입: 접미사 규칙 제거 → 빨간불). 남대문 블록 ≥ 15, 미확인 1,047 중 블록 연관 ≥ 600 **이되 오배정 0 이 우선**. OSM 응답 크기·묶음 메모리·중단 뒤 재개.

### 7-3 도식화 — 남대문 한 곳에서 먼저
리뷰 반영: 전국 자동 8방향 배치는 지금 범위에서 과하다. 두 단계로 나눈다.
- **3a 전국 공통 — 회전**: 시장 골목의 주축(가장 긴 골목 선 또는 경계의 장축)이 화면 가로가 되게 지도를 통째로 회전한다. 모든 객체(핀·블록·게이트·출구·내 위치)가 같은 변환을 타므로 어긋남이 없다. 북쪽 화살표가 같이 돈다. 대각선 부담의 대부분을 여기서 던다.
- **3b 남대문 — 도식 배치**: 8방향 스냅 + 블록 사각화 + 위상 보존(교차점 유지·골목 좌우 유지·블록 겹침 금지)을 남대문에서 만들고 안내판과 나란히 비교한다. GPS 는 가장 가까운 골목 선의 chainage 로 도식 공간에 보낸다. 통과하면 조건(골목 ≥ 3·경계 있음)을 만족하는 시장으로 넓힌다. 축척 막대 대신 「도식 — 실제 거리와 다릅니다」.
- **특화 골목 이름·게이트 번호**: 편집 대상은 `market_path.name`(골목 선) 과 `market_entrance.label`. 구역 이름 바꾸기는 선 이름으로 이어지지 않으므로 **골목 선 이름 편집**을 운영자·상인회 화면에 추가한다. ENTRANCE 요청 승인 시 `decide()` 가 실제 출입구 행을 만들게 고친다(지금은 상태만 저장).
- **지하철 출구**: OSM `subway_entrance ref` 를 `entrances` 와 같은 모양으로 공개. 버스·은행·화장실은 후속.

### 7-4 위치 설명 — 검증된 것만
- 기본: 「블록 · 층 · 호」 또는 「골목 이름 · 가까운 게이트/출구」.
- 「왼쪽 N번째」: 상인회가 골목 구간의 **점포 순서**를 입력한 구간에서만. 좌표로 만들지 않는다(필지 중심 좌표는 순서·누락을 보장하지 않는다 — 리뷰 반영).
- 길 안내 문장(게이트 → 골목)은 보행 연결 그래프가 없으므로 「가장 가까운 게이트」가 아니라 「가게가 붙은 골목의 양 끝 게이트/출구」를 적는다.

## 7. 음식 품목 검색·메뉴/가격·영문 (분석, 2026-10-16)

### 7.1 왜 「떡볶이」가 안 나오나
검색 가능한 가게(파생 표 12,606행)의 음식 업종은 상가정보 **소분류 이름**까지만 있다. 떡볶이 가게는 「김밥/만두/분식」(362곳)으로 들어 있어 「떡볶이」라는 글자가 어디에도 없다. 품목(온누리 `items`)도 「기타음료식품」 같은 분류어다.

### 7.2 쓸 수 있는 원천

### 7.3 제안
1. **음식 이름 → 업종 사전**(떡볶이·순대·튀김·어묵 → 김밥/만두/분식, 칼국수 → 국수/칼국수, 빈대떡 → 전/부침개 …, 100개 안팎). 결과는 「관련 업종 · 분식」으로 **이름·품목 일치와 구분해** 아래 순위로 보인다(리뷰가 지적한 「근거 없는 가게 섞임」을 표시로 막는다). 사전은 백엔드 한 곳에 두어 `/markets` 와 시장 섹션이 같이 쓴다.
2. **TourAPI 음식점 메뉴를 가게에 붙인다**: 시장 가게와 이름 정규화 일치 + 50 m 안이면 그 가게의 「대표·취급 메뉴」로 보이고 검색에 넣는다(파생 열 — 원천은 `attractions` 그대로). 못 붙은 TourAPI 음식점은 시장 섹션에 「관광공사 소개 음식점」으로 따로.
3. **가격**은 착한가격업소만 있다. 지금은 IN 가게에만 붙어 46곳뿐 — WU-15 의 주변 가게에도 이미 응답에 실려 오므로 화면에 메뉴·가격을 보이게 한다. 다른 가격 원천은 없다.
4. 모범음식점 주된음식은 지자체별 파일이라 시장이 많은 서울 자치구부터 받는다(선택).

### 7.4 영문
- 업종 207종: 고정 번역표(통계청 표준산업분류 영문명 참고 + 검토). 정확·저비용.
- 가게 이름: 영문 원천이 없다. 국어의 로마자 표기법으로 자동 표기하고 한글을 함께 둔다(「Sunhuine Bindaetteok · 순희네빈대떡」).

## 9. 가게 검색을 검색엔진으로 (제안, 2026-10-17 — 결정 대기)

### 9.1 지금
- 시장 섹션의 「가게·품목·업종 찾기」는 **브라우저 안 부분 문자열 매칭**이다(`matchesMarketStore`: 이름 > 품목 > 메뉴 > 업종 > 음식 사전의 관련 업종). `/markets` 와 `/api/v1/place/markets/search` 는 MySQL 파생 표 `market_store_search`(12,606행 — 지도에 보이는 가게만) 에 공백 정규화 `LIKE` 다.
- 그래서 안 되는 것: 오타(「떡복이」), 띄어쓰기 변형(「순대 국밥」↔「순대국밥」), 조사·어미, 동의어(「튀김」↔「덴뿌라」), 로마자 변형(`tteokbokki`↔`ddeokbokki`), 관련도 순 정렬(이름 일치가 품목 일치보다 앞서는 정도만 있고 점수는 없다).

### 9.2 선택지
| | A. OpenSearch 전용 색인 `market-stores` | B. MySQL FULLTEXT(ngram) on `market_store_search` |
|---|---|---|
| 되는 것 | nori 형태소 + 동의어(음식 사전을 색인 시 전개) + `fuzziness`(로마자) + 필드 가중치 점수 + 시장별 집계 | 토큰 단위 일치 + 관련도 점수(BM25 유사). 오타·동의어는 안 됨 |
| 바뀌는 곳 | search:batch 태스클릿 1개(place API `/markets/{id}` 풀스캔 → alias swap, `attraction-reindex` 와 같은 틀) · search:app 조회 API 1개 · FE 두 곳(섹션·`/markets`)이 그 API 를 부르고 실패 시 지금 매칭으로 폴백 | place 마이그레이션 1개(FULLTEXT 인덱스) + 저장소 질의 교체. FE 변경 없음 |

| 신선도 | 하루 1회 배치(+ 상인회 편집은 다음 배치). 섹션 지도 자체는 place 가 그리므로 지도는 즉시, 검색만 하루 뒤 | 즉시 |
| 비용 | 구조 변경 → **ADR(0111) 필요**, 구현 2~3일(Codex 3묶음) | 반나절 |

### 9.3 제안
A 로 간다. 사용자가 짚은 것이 「검색엔진 기반이 아님」이고, 그 핵심(오타·동의어·점수)은 B 가 못 준다. 다만 **섹션 검색은 결과를 지도 강조로 쓰므로 응답은 store id 목록 + 일치 필드**만 받고 렌더는 지금 그대로 — 검색 서비스가 죽어도(게이트웨이 200 빈 바디 함정) 브라우저 매칭으로 폴백한다. 통합 색인(ADR-0090)에 섞지 않는 이유: 가게 12.6k 가 관광지·글·게임 몇 천을 수로 눌러 apex 검색을 가게로 덮는다.

### 9.4 WU-28 계약 초안 (승인 뒤 tasks.md 로)
- 색인 문서: `contentId, marketName, storeId, name, nameRoman, nameEn, items, itemsEn, categorySub/Mid/Major(+en), menus(관광공사 대표·취급 + 착한가격 메뉴), dishes(음식 사전으로 items·업종에서 전개한 음식명 + 영문), membership, nearby, location(geo_point), zone, path`. 범위 = `market_store_search` 와 같다.
- 분석기: 한글 `nori`(사용자 사전에 음식명), 영문 `english`, 로마자는 `fuzziness: AUTO`. 동의어는 `dishes.csv` 한 벌에서 색인 시 전개(별도 동의어 파일을 만들지 않는다 — 사전이 둘이 되면 갈린다).
- API: `GET /api/v1/search/market-stores?q&contentId&lang&page` → `{ items:[{storeId, matchedBy, score}], total, markets:[{contentId, count}] }`. `contentId` 가 있으면 섹션용(해당 시장만), 없으면 `/markets` 용(시장 집계 포함).
- 배치: `market-store-reindex` CronJob, `attraction-reindex` 10분 뒤. place API `/markets/content-ids` → `/markets/{id}?lang=ko`+`en`. 실패율 5% 상한, alias swap.
- FE: 섹션은 입력 300ms 디바운스 → API → 돌아온 storeId 로 핀 강조·시트 배지(`matchedBy`), 실패·빈 응답이면 지금 `matchesMarketStore`. `/markets` 는 API 결과를 그대로.
- 검증: 판정 세트 30문항(떡볶이/떡복이/tteokbokki/순대 국밥/덴뿌라/칼국수 …) 전후 Recall@10, 운영 CDP 남대문·광장.

사용자 지적: 「지도가 특정 위치만큼 잘려서 그림 위에 마커를 올린 느낌 — 지도를 그대로 쓰고 시장 폴리곤을 옅게, 점포를 마커로. 우측 목록 UI 도 깨진다」. 운영 남대문(34550, 번들 `index-Y5LaXt-F.js`)을 1280·1024·390px 에서 재서 진단했다(수치는 `verifications/p7-production.md` 10-17 저녁).

### 10.1 진단 — 세 겹의 구조 선택이 겹친 결과
1. **바탕이 지도가 아니라 그림이다.** 시장당 PNG 한 장(1536×1152, 남대문 줌 17 = 727×545 m)을 SVG `<image>` 로 깔고 viewBox 로 확대한다. 원본 px / 화면 px 가 1배 1.83 → 4배 0.46 → 8배 0.23(데스크톱 1280)으로, 4배부터 두 배 넘게 늘려 그린다. 도로명이 그림에 구워져 있어 확대하면 글자도 같이 커진다. 프레임 밖(1배에서 가장자리 57단위 여유)은 빈 면이라 이동하면 회색이 나오고 회현역·숭례문 같은 주변 기준점을 볼 수 없다. 폴리곤 채움 8% 는 어두운 바탕에서 거의 안 보인다. 사용자가 본 「잘린 그림 위의 마커」가 정확한 묘사다 — 오늘의 줌 선택(18→17→16)은 프레임을 키웠을 뿐 그림이라는 성질은 그대로다.
2. **지도가 상세 글의 한 절이다.** 섹션이 본문 그리드(3fr/2fr) 안에 있어 지도가 706×518(1280)·552×405(1024)·358×263(390)px 다. 가게 2,314곳 시장을 모바일에서 263px 로 본다. 오늘 넣은 「시장 지도」 버튼은 도착을 돕지만 도착한 화면 자체가 작다.
3. **목록이 상태마다 다른 컴포넌트다.** 평소 = `place-market-panel`(제목 + 28rem 중첩 스크롤, 테두리 없음), 핀 선택 = `MarketClusterSheet`(테두리 상자, 데스크톱은 옆 칸·모바일은 55dvh 고정 시트), 검색 = 같은 패널이지만 가게 이름이 버튼 상자. 데스크톱에서 핀을 고르면 패널이 사라지고 시트가 나타나 칸이 통째로 바뀐다. 1024px 에선 시트 상단이 지도 위 툴바(+ −)에 맞아 지도 그림과 52px 어긋난다. 모바일 핀 탭 → 시트(top 380)가 지도(641~904)를 **다 덮어** 고른 핀이 안 보인다. 패널은 2,317행을 전부 DOM 에 두고(16,847 노드, 페이지 18,534 의 91%) 448px 상자 안에서 368,479px 를 스크롤한다 — 보이는 건 3행이고 오버레이 스크롤바라 「잘린」 것처럼 보인다. 정렬이 이름순이라 첫 행이 「(주)삐에아떼르코리아 · 위치 미확인 · 지도 위치 없음」, 지도에 없는 법인부터 나온다. 입력 지연은 25~41ms(지우기 102ms)로 성능이 아니라 구조 문제다.
4. 잔가지: 「내 위치」가 가로 전체 테두리 상자 안 버튼 하나, 출처 3줄·안내 2줄·「관광공사 소개 음식점」 h3 가 간격 없이 붙는다.

운영에서 정상인 것: 터치 드래그는 지도를 끌고 문서를 스크롤하지 않는다(pointermove 12 · pointercancel 0 · viewBox 0,0 → 201,121 · scrollY 불변, `touch-action: none`). 대조군(안내문 위 같은 드래그)은 문서가 140px 스크롤.

### 10.2 개편안
원칙: **지도 엔진은 갈아 끼우고, 오버레이와 목록은 하나.** 「엔진(네이버 | MapLibre) × 오버레이(폴리곤·마커·내 위치) × 목록(한 컴포넌트)」.

**A. 바탕 — 라이브 타일 지도 두 엔진, 같은 오버레이 모델**
- 네이버 Dynamic Map(§8.1 결정, 키 대기): 시장 경계를 `naver.maps.Polygon`(fill 12% · stroke 1.5px)으로 — 지금 `MarketNaverMap` 은 `Polyline` 이라 채움이 없다. 마커는 C.
- MapLibre GL JS 4.7 + OpenFreeMap 벡터 타일(지금 당장, 키·한도 없음 — 공식 페이지 "no limits on the number of map views or requests", 출처 표기 필수): 렌더러가 쓰는 같은 스타일(positron/fiord)이라 모양이 이어지고 어떤 줌에서도 글자·선이 다시 그려진다. 비용 JS 210KB gz + CSS 65KB, 시장 지도 청크로 lazy. CSP 는 `frame-ancestors` 뿐이라 막히는 것 없음. `/privacy` 제3자 요청에 `tiles.openfreemap.org` 한 줄, `data-sources.md` 에 런타임 타일 사용 추가. 영문 페이지는 스타일에서 `name:en` 라벨을 고른다.
- 기본 순서: 키가 없는 지금은 MapLibre 기본, 키가 오면 네이버 기본·MapLibre 폴백(§8.1 그대로). 둘 다 실패하면 폴리곤·마커만 빈 바탕에(지금 SVG 의 골목 선 폴백).
- 정적 PNG 파이프라인(렌더 워크플로·버킷·PAR·프록시·meta)은 라이브 지도가 들어오면 화면에서 쓸 곳이 없다. 프리렌더 HTML(JS 전) 포스터로만 남기거나 폐기 — 결정 ③. 남기면 WU-23~25 의 운영 비용(렌더 워크플로·버킷)이 그대로 든다.

**B. 화면 — 시장 지도를 전용 화면으로**
- 라우트 `/attractions/:id/market`(영문 `/en/attractions/:id/market`), 프리렌더·sitemap 에 추가(ADR-0062 URL 승격 규칙). 전체 뷰포트 지도 + 상단 바(뒤로·시장 이름·검색 입력·구역 칩 가로 스크롤) + 모바일 하단 시트(peek 30% · half 55% · full, **지도를 끝까지 덮지 않는다**) / 데스크톱 좌측 패널 400px(지도 웹 관행).
- 상세 페이지의 「시장 구역·가게」 절은 요약 카드로 줄인다: 작은 지도(정적 그림 또는 상호작용 없는 라이브 지도 16:9) + 「지도 전체 보기」 + 가게 수·구역 칩 3개 + 착한가격 요약. 상세 페이지 DOM 에서 17k 노드가 빠진다. 액션 줄 「시장 지도」 버튼은 이 라우트로.

**C. 마커·폴리곤 — 줌 단계별**
- z ≤ 16: 폴리곤 + 시장 이름·총수 마커 1개. z 17~18: 필지 묶음 숫자 원(지금 규칙, 24px). z ≥ 19: 개별 마커 + 가게 이름 라벨(겹침 회피, 검색 일치는 강조색). 시장 밖·주변 가게는 회색, 좌표 없는 가게는 지도에 없고 목록 끝.
- 폴리곤: 경계 있는 84곳은 OSM 경계, 없는 곳은 IN 가게 convex hull(파생 경계 — 순환 참조 수정 선행, 이전 결정 대기 ④).

**D. 목록 — 하나의 컴포넌트, 하나의 데이터**
- 목록 = 「지도 영역 안 가게 ∩ 검색어 ∩ 구역」. 지도를 움직이면 따라온다(「현 지도에서」). 50행 페이지 + 가상화. 핀 선택은 목록의 정렬·강조(선택 가게가 맨 위, 같은 필지가 이어서)이지 다른 컴포넌트가 아니다. 좌표 없는 가게는 끝. 행 모양은 한 가지(이름·업종·배지·주소·메뉴 접기).
- 검색은 §9 의 검색엔진 결정과 같은 입력 상자를 쓴다(결정 ①).
