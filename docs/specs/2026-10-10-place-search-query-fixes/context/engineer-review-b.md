**T2. 탐침 12 기대값 중 넷은 시스템이 만든 근거다.**

**T3. 채택 조건이 잡음 폭과 맞지 않고 p99 는 판정하지 않는다.**

CONFINE 은 벡터 후보 집합을 바꾸고, 조건 필터는 새 문서를 위로 올린다. 단계 2·3 전에는 그 구성의 top-20 을 늘 풀에 합친다로 맞춘다.

## 2. domain — REVISE

| 체크 | 결과 |

| glossary 존재 | 있음 `search/glossary.md` |
| 용어가 glossary 와 일치 | 불일치 (D2) |
| Avoid 동의어 사용 | 없음 — 「정제 검색어」(`glossary.md:119`) 같은 금지어는 쓰지 않았다 |
| 코드와 용어 일관 | 대체로 일치 — `residual`·`facets`·`AttributeSelection` |
| 불변식 명시·강제 가능 | 부분 — 조건어 규칙의 경계가 비어 있다 (D3·D4·D5) |

**D1. `Condition` 이 presentation 의 문자열을 domain 으로 끌어온다.** SR-3.1 은 `param`·`value` 를 「검색 API 속성 파라미터와 같은 이름·값」으로 정하고(`spec.md:51`), TG2.2 는 「컨트롤러 파라미터 문자열과 같은 상수에서 가져온다」고 한다(`tasks.md:24`). 하지만 컨트롤러에는 그런 상수가 없다. 파라미터 이름은 Kotlin 인자 이름일 뿐이다(`AttractionSearchController.kt:61-68`). 그리고 `QueryIntent` 는 `:search:domain` 에 있으니, 컨트롤러 상수를 import 하면 의존 방향(Domain ← Application ← Presentation, `CLAUDE.md` Architecture)을 거스른다. 수정안: `Condition` 은 도메인 타입으로 둔다 — 예: `AttributeSelection` 의 축 enum(`PARKING`·`PET`…)과 도메인 값(`Availability.YES`·`PetPolicy` 집합). `interpretedConditions` 의 `param`/`value` 문자열은 presentation 이 매핑한다. 「문자열 사본 금지」는 매핑 표 한 곳과, 컨트롤러 `@RequestParam(name = …)` 이 그 표의 상수를 쓰는 것으로 지킨다.

**D2. 용어가 glossary 와 다르다.**
- 스펙은 「질의 이해」(`spec.md:20,29,75,82-83`)라고 쓰는데, glossary 의 정식 용어는 「쿼리 언더스탠딩」(`glossary.md:115`)이다. 사용자 메모(현업 기술 용어는 발음대로)와도 어긋난다. 「쿼리 언더스탠딩」으로 바꾸거나 glossary 피할 말에 「질의 이해」를 올린다.
- 새 용어 가운데 SR-8 이 glossary 에 올리는 것은 「어휘 근거 게이트」「조건어 해석」 둘뿐이다(`spec.md:97`). 「머리말·꼬리말」「한정(CONFINE)」「`noContent`(내용 없는 입력)」「근거 계수 요청」도 행이 필요하다. 「근거」라는 말이 판정 스펙의 `evidence`(질의 출처, `judgment-cases/spec.md:52`)와 겹치므로, 비고에 「판정 세트 `evidence` 와 다르다」를 적는다.

**D3. 조건어 의미 경계가 비어 있다 — 「주차 무료 ≠ 입장 무료」 하나만 막았다.**
- a. **「무료 주차장」「무료 주차 가능한 해수욕장」** — 예외는 「바로 **앞** 어절이 parking 머리말」일 때만 걸린다(`spec.md:56`). 무료가 앞에 오는 어순은 그대로 `admission=FREE` 가 된다. 무료 주차를 찾은 사람에게 입장 무료 필터가 걸린다. 수정: 예외를 「앞 **또는 뒤** 어절이 parking 머리말」로 바꾼다.
- b. **「주차 무료」의 `무료` 가 parking 꼬리로 소비된다**(`spec.md:55`). 요금 뜻은 사라지고 결과는 「주차 가능」(유료 포함)이 된다. 안내 줄이 「‘주차 무료’를 주차 가능 조건으로 읽었습니다」라고 보여 주니 정직하기는 하다. 다만 T4 ⑥대로 예외 규칙과 하는 일이 겹친다. 꼬리말 `무료` 와 admission 예외 중 하나만 남긴다.
- c. **「무료」 단독 머리말이 너무 넓다.** 「무료 셔틀」「무료 체험」「무료 와이파이」「무료 공연」도 입장 무료가 된다. 다른 행은 머리말+꼬리말을 요구하는데(`spec.md:62` ①) admission 만 꼬리 없이 성립한다. 수정: `무료` 단독은 다음 어절이 없거나 쿼리 언더스탠딩이 가져가는 말(유형·분류·불용구, 「무료로 볼 수 있는 곳」「무료 박물관」)일 때만 옮긴다.
- d. **부정어를 반대로 읽는다.** 「반려동물 동반 불가」는 머리말 `반려동물` + 꼬리 `동반` 으로 `pet=ALLOWED,PARTIAL` 이 되고 `불가` 만 잔여에 남는다. 「카드 결제 안 되는」도 `creditCard=YES` 가 된다. Out of Scope 의 「부정 조건」(`spec.md:111`)은 부정 **필터**를 만들지 않는다는 뜻이지 이런 오해석을 허용한다는 뜻이 아니다. 수정: 꼬리말 다음 어절이 부정어(`안`·`못`·`불가`·`불가능`·`금지`·`no`·`not`)이거나 머리말 앞 어절이 `no` 이면 그 행은 옮기지 않는다. 케이스는 T6 에.
- e. **조사 목록에 주격·보조사가 없다**(`spec.md:62` ①: `과·와·랑·이랑·하고·로·으로·도`). 「주차가 되는」「반려견이 갈 수 있는」 같은 흔한 꼴이 해석되지 않는다. `가·이·은·는` 을 더한다. 「가능」 같은 꼬리는 이 목록이 머리말에만 걸리므로 영향이 없다.
- f. ko 전용 행(pet·wheelchair)에 영문 머리말이 있다(`spec.md:57,59`). 그래서 이 말들은 ko 요청에 섞일 때만 동작한다. 의도라면 한 줄로 밝히고, 아니면 지운다.

**D4. 합집합이 사용자가 좁힌 선택을 덮어쓴다.** 사용자가 `반려동물 동반` 칩만 켜 둔 상태(PARTIAL 꺼짐)에서 「반려견 동반 해수욕장」을 치면, 합집합(`spec.md:63`)이 PARTIAL 을 다시 넣는다. Q4 의 근거 「사용자가 PARTIAL 만 끌 수 있다」(`open-questions.yml:22`)를 이 스펙이 스스로 무너뜨린다. 수정: 같은 param 에 명시 선택이 있으면 그 param 의 해석은 버리고 명시 선택을 쓴다(어절은 지금처럼 잔여에서 뺀다).

**D5. 행사 분류에서 속성은 뜻이 없다.** glossary(`glossary.md:75`)와 화면(`PlacePage.tsx:487-489`)은 행사 분류에서 속성 조건을 뺀다. 서버 해석은 `category` 를 보지 않으므로 「주차 되는 축제」 + 행사 분류가 `parking=YES` 로 0건이 된다. 수정: 요청 `category` 가 행사 하나뿐이면 조건어를 옮기지 않는다. 결과는 keepConditionWords 와 같아진다.

**D6. 해석된 필터는 「정보가 있는 곳만」 남긴다.** 속성 필터는 `UNKNOWN` 을 뺀다(`glossary.md:75`, `placeAttributes.ts:76-79` 「정보가 있는 곳만 거릅니다」). 칩은 사용자가 직접 누르니 문제가 없지만, 해석은 사용자가 고르지 않은 좁힘이다. SR-4.2 안내 문구(`spec.md:69`)에 이 범위를 붙인다. 예: 「‘주차 되는’을 주차 가능 조건으로 읽었습니다 · 정보가 있는 곳만」(`ATTRIBUTE_CAPTION` 재사용).

## 3. usecase — REVISE

| 체크 | 결과 |
|---|---|
| 행위자-목표 | 부분 — 허브 사용자만 이야기에 있다. 통합 검색 호출자, env 를 바꾸는 운영자, 평가 Job 은 흐름이 없다 |
| 기본·대체·예외 흐름 | 예외 흐름이 빠졌다 (U3) · 대체 흐름이 GATE 와 충돌한다 (U1) |
| 전후 조건 | 부분 — 재색인 선행은 있다(`tasks.md:8`). v3 선행·단계별 탐침 기대는 없다 (T2·T7) |
| AC 추적 | 대체로 가능 — SR 번호가 TG 와 대응한다 |
| 경계 확장 | 부족 (U2·U4·U5·U7) |
| 테스트 매핑 | 있다 — TG 마다 Verify 줄 |

**U1. 해석을 풀면 GATE 에서 0건이 된다 — 「해제」가 결과를 넓히지 않고 없앤다.** 칩 하나를 끄면 질의 전체가 `keepConditionWords=true` 가 된다(`spec.md:70`). 그러면 그 질의의 조건어가 **모두** 잔여로 돌아가 msm `2<75%` 근거 검사를 받는다(`spec.md:75`). 「주차 되는 반려견 동반 해수욕장」에서 반려동물 칩을 끄면 잔여가 「주차 되는 반려견 동반」이 되고, 분류 필터 안에서 개요에 이 토큰 75% 가 함께 나오는 문서는 드물다. 같은 문제가 세 곳에 더 있다.
- 통합 검색은 늘 `keepConditionWords=true` 다(`spec.md:64`). GATE 에서는 조건 질의의 관광지 묶음이 0 이 된다.
- 꼬리말이 없어 해석되지 않는 조건 질의. v3 CONDITION 질의 문구는 「칩 이름 + 분류 이름」이다(`judgment-cases/spec.md:58`). 「신용카드 박물관」「휠체어 미술관」은 칩 이름에 꼬리가 없어 해석되지 않고, `신용카드` 단독 잔여가 근거 검사에서 0 이 될 수 있다.
- en 「pet friendly」(`spec.md:65`, 해석하지 않는다).

수정안(하나를 고른다):
- (가) 근거 검사의 잔여에서는 조건어 표 머리말·꼬리말 어절을 **늘** 뺀다. `keepConditionWords` 는 필터를 걸지 말라는 뜻이지, 그 말에 어휘 근거를 요구하라는 뜻이 아니다.
- (나) 칩 끄기는 `keepConditionWords` 대신 `skipCondition=pet` 처럼 그 param 의 해석만 버린다. 어절은 계속 잔여에서 빠진다. 전부 문자 그대로 검색하는 것은 「검색어 그대로 검색」 하나만 남긴다.

(나)는 SR-4.3 의 「나머지 조건을 명시 칩으로 옮기기」도 필요 없게 만들어 더 단순하다. 어느 쪽이든 Q2(`open-questions.yml:12`)에 결정을 남긴다.

**U2. 「정답 없음」 0건에 맞지 않는 문구가 나온다.** `relaxConditions` 는 검색어가 있으면 늘 `keyword` 를 후보에 넣는다(`placeView.ts:61`). 그래서 「에펠탑」 0건에도 `relaxable.length > 0` 이 되어 「고른 조건을 모두 만족하는 관광지가 없습니다. 아래에서 조건을 풀면 결과가 넓어집니다.」(`PlacePage.tsx:108,1777`)와 「에펠탑」 해제 버튼이 뜬다. 사용자는 조건을 고른 적이 없고, 이 0건은 조건이 아니라 「색인에 없다」에서 나왔다. SR-4.5(`spec.md:72`)는 해제 목록에 해석 조건을 더할 뿐 이 경우를 다루지 않는다. 화면은 0건이 게이트에서 왔는지 필터에서 왔는지 알 길도 없다. 수정안:
- 응답에 `zeroReason: NO_EVIDENCE | NO_CONTENT | null` 을 둔다. `NO_CONTENT` 는 SR-1.4 의 「ㅁㄴㅇㄹ」이다.
- 문구를 정한다(ko·en). 예: 「‘에펠탑’이 나오는 관광지가 없습니다」, 「검색어에 글자가 없습니다」. 이때는 `emptyReason` 을 쓰지 않는다.
- 지역 같은 사용자 조건이 함께 있으면 해제 버튼은 그대로 둔다(「서울 + 에펠탑」 → 지역을 풀면 CONFINE 에서 8건). 검색어 해제 버튼은 「전체 관광지 보기」로 이름을 바꾼다 — 글자를 지우는 것이 아니라 목록으로 돌아가는 것이다.
- TG3 테스트에 ⑦ `zeroReason=NO_EVIDENCE` → 정답 없음 문구·`emptyReason` 없음을 더한다.

**U3. 근거 요청이 실패하면 어떻게 할지 정해져 있지 않다.** SR-5.4(`spec.md:78`)는 직렬 요청 하나를 더하는데, 그 요청이 실패하거나 타임아웃이면 0건(fail-closed)인지 본 질의 실행(fail-open)인지 오류인지가 없다. 0건으로 삼키면 장애가 「없다」로 보인다. 게이트웨이 빈 200 사고와 같은 꼴이고, 화면에는 U2 의 「정답 없음」 문구까지 뜬다. 수정: 실패는 예외로 올린다. 화면은 이미 「실패는 조건 탓이 아니다」 분기(`PlacePage.tsx:1771-1773`)를 갖고 있다. 이것을 SR-5 에 한 줄로 적고, T4 ⑱로 주입한다.

**U4. 칩 건수가 목록과 어긋난다.** 패싯 건수는 본 질의와 **병렬로** 먼저 출발하고(`AttractionSearchAdapter.kt:177-181`), 하이브리드일 때는 검색어 없이 센다(`AttractionSearchAdapter.kt:229`). 그래서 GATE 에서 근거가 0 이어도 칩에는 「주차 가능 1,2xx」가 뜨고, CONFINE 에서는 칩 건수가 한정된 집합(msm 일치)이 아니라 필터 전체를 센다. SR-3.3(`spec.md:63`)은 선택만 합치고 이 정합은 다루지 않는다. 수정: 근거가 0 이면 건수 요청을 내지 않고 0 으로 둔다. CONFINE 이면 건수 질의에도 msm 일치를 건다. TG4.1 캡처에 넣는다.

**U5. 비슷한 두 링크가 다른 일을 한다.** 「원래 검색어로 검색」(`exact`, 오타 교정 취소, `glossary.md:118`)과 「검색어 그대로 검색」(`keepConditionWords`, `spec.md:69`)은 말이 거의 같다. 「주차 되는 해수욕쟝」처럼 오타와 조건이 함께 있으면 두 링크가 같은 화면에 뜬다. 수정: 조건 쪽 문구를 「조건으로 읽지 않고 검색」 같은 말로 바꾸고, 두 링크가 함께 뜰 때의 배치를 SR-4.2 에 정한다.

**U6. 화면 흐름의 빈칸.**
- 안내 줄 형식: 조건이 둘 이상일 때 줄 하나에 잇는지, 반려동물(칩 둘, `placeAttributes.ts:57-58`)은 어느 칩 이름을 쓰는지, en 문장 틀이 무엇인지 없다(`spec.md:69` 은 ko 예시뿐).
- `keepWordsFor` 를 허브 상태 복원에 더해야 한다. `exactFor` 는 `placeHubState.ts:17,69,89` 에서 직렬화·검증되는데, TG3.2(`tasks.md:32`)에 이 파일이 없다. 빠지면 뒤로가기 복원에서 해제가 풀린다.
- 칩 해제 뒤 같은 칩을 다시 켜는 흐름: 명시 칩 + `keepConditionWords` 가 되어 조건어가 잔여와 필터에 이중으로 걸린다. U1 (나)를 택하면 이 흐름은 없어진다.

**U7. `exact` + GATE.** 「원래 검색어로 검색」을 누르면 교정되지 않은 오타 원문(「경복굼」)이 근거 검사를 받아 0건이 될 가능성이 크다. 정답이 있다고 확인된 질의에서 사용자 조작 하나로 「정답 없음」 문구가 뜨는 것이다. 이렇게 두는 것이 의도라면 SR-5 에 한 줄로 밝히고, U2 의 문구에 「‘경복궁’으로 검색」 되돌리기 링크를 남긴다.
