### HTTP 확인 기록

- **[확인]** [지정 결과 URL](https://rank.1989v.com/cafe?q=바닐라라떼&group=바닐라라떼&sort=sugar&page=0&size=50)은 HTTP 200이다. 초기 HTML의 title은 `1989v`였다. JS 실행 후 메타와 실제 렌더링은 확인하지 않았다. 스크린샷·브라우저 조작·기기별 실측은 수행하지 않았다.
- **[확인]** [공개 유형 API](https://rank.1989v.com/api/v1/ranking/cafe/groups)는 HTTP 200이다. 유형별 합계는 1,922행이다. 기타 461행, 바닐라라떼 46행이다. 로컬 집계와 일치한다. 출처: E4·E8 및 해당 응답.
- **[확인]** 저장소가 인용한 상가정보 `15083033/openapi.do`는 확인 당시 HTTP 404였다. 현재 [공식 상가정보 API 안내](https://www.data.go.kr/data/15012005/openapi.do)의 내장 Swagger에서 `storeListInRadius` 응답 필드 `bizesNm`=상호명, `brchNm`=지점명, `bizesId`, `lat`, `lon`을 확인했다. 실제 인증 API 레코드는 수집하지 않았다. 출처: E9의 원천 식별자와 공식 안내.

## 3. 사용자와 핵심 과업

**[제안]** 서비스 약속은 ‘공식 기본 레시피를 비교하고, 해당 브랜드의 주변 매장을 찾는다’로 둔다. 맛·건강 점수·재고·판매 여부를 보증하지 않는다.

| 타깃 | 핵심 과업 | 성공 결과 |
|---|---|---|
| 출근·외출 중 음료를 고르는 사용자 | 지금 근처에서 덜 단 바닐라라떼 | 같은 유형의 당류를 비교한 뒤 해당 브랜드 매장과 직선거리 확인 |
| 카페인 섭취를 줄이려는 사용자 | 공식 0mg 음료 또는 디카페인 탐색 | 두 범주와 미공개를 구분하고 원문 확인 |
| 브랜드를 바꿔 주문하는 사용자 | 브랜드 간 같은 유형 비교 | 온도·사이즈·제공량 차이를 보며 총량과 농도를 구분 |

‘같은 유형’은 동일 레시피가 아니다. 바닐라라떼 유형 안에도 토핑·대용량·디카페인 변형이 있다. 각 행은 온도·사이즈·카페인 상태를 포함한 한 변형이다. 브랜드 대표 한 행을 자동 선정하지 않는다. 출처: E4의 규칙, E7의 유일키.

## 4. 단계별 범위와 수용 기준

아래 수치와 시간은 **[제안] 목표**다. 달성 실적이 아니다.

### P1 — 위치 없는 탐색·비교·상세

범위: 검색 첫 화면, 유형 비교, 3수치 공통 정렬, 1회/100ml 토글, 카페인 필터 분리, 상세, 데이터 상태, SEO. 브랜드 전체의 변형을 결과 목록으로 비교한다. 가까운 매장 UI는 P2 활성 전 숨긴다.

| ID | 측정 가능한 수용 기준 |
|---|---|
| P1-1 | 360×800과 1280×800에서 페이지 가로 넘침 0px. 비교 수치 확인에 가로 스와이프 0회 |
| P1-2 | 360×800에서 비교 화면 첫 결과의 3수치가 초기 뷰포트에 보인다. 필터는 시트로 접는다. 200% 확대에서는 잘림 없이 세로 탐색한다 |
| P1-3 | 모든 결과에 당류 g·카페인 mg·열량 kcal와 온도·사이즈 또는 ‘미표시’를 표시한다. null→0 오표시 0건 |
| P1-4 | 100ml 모드의 3수치는 양의 공개 ml로만 계산한다. 용량 없는 행은 유지하고 ‘산출 불가’로 표시한다. 정렬은 반올림 전 값, null 마지막 |
| P1-5 | 공식 0mg 선택 결과는 ZERO만, 디카페인은 DECAF만 포함한다. UNDISCLOSED 및 수치 null은 수치 상한 결과에서 제외한다 |
| P1-6 | 같은 유형 전체를 서버에서 정렬 후 페이지 처리한다. 상위 페이지에 없는 브랜드를 누락·판매 없음으로 표현하는 문구 0건. ‘현재 20행 / 전체 N행’ 표시 |

| P1-8 | 로딩·빈 결과·오류·부분 메타 실패·100ml 산출 불가 fixture를 각각 검수한다. 키보드만으로 검색→비교→상세→복귀 가능 |
| P1-9 | 대표 과업 3개를 각 5명에게 수행시킨다. 각 과업 4명 이상이 60초 안에 정확한 수치·상태를 확인한다. 디카페인=0 오답은 0명 |

범위: 일회 위치 획득, 지역 대체, 기본 반경 1km, 0.5/1/3km 선택, 목록, 선택 음료 변형 연결. 지도·길찾기·영업중·매장 재고는 제외한다. 목록 기본을 채택하면 타일·지도 SDK·경로 API가 필요 없다.

| ID | 측정 가능한 수용 기준 |

### 이후 후보

**[제안]** 매핑이 검증된 지역 확대, 유형 교정 사전, 2~4개 음료 고정 비교, 공식 메뉴 갱신 자동화 순으로 검토한다. 가격 비교는 공식 가격 원천 확보 후 별도 기획한다. 지도·영업시간·개인화·커스텀 레시피 계산은 별도 비용·데이터 근거가 있어야 한다.

### 6.2 제안 파이프라인

1. 초기 대상 지역의 상가정보를 배치에서만 확보한다. 수집 전에 현재 명세·활용신청·배포 주기를 재확인한다. 일회 사용자 좌표로 정부 API를 호출하지 않는다.
2. place가 원천 SSOT를 맡는다. `sourceKey/bizesId`, 원문 상호, 원문 지점명, 원본 업종 코드·이름, 도로명·지번, 위경도, 원천 기준일, 수집일을 보존한다. 원천이 기준일을 주지 않으면 수집일과 구분해 null로 둔다.
3. 공백·유니코드·대소문자를 정규화한 뒤, 9브랜드별 승인 별칭과 경계를 대조한다. 스타벅스·STARBUCKS, 메가MGC커피 등은 **별칭 후보**이며 실제 샘플 승인 후 반영한다. ‘메가’·‘컴포즈’ 같은 짧은 부분일치만으로 확정하지 않는다.
4. `CONFIRMED / REVIEW / UNMAPPED` 상태와 `ruleVersion`을 둔다. 복수 브랜드 일치·법인 상호·의심 업종은 REVIEW로 보낸다. 운영자 재정의는 sourceKey에 연결하고 다음 수집에도 유지한다. 공개 주변 목록에는 CONFIRMED만 낸다.
5. source+sourceKey로 중복을 제거한다. 같은 건물의 별개 매장은 주소·좌표만으로 합치지 않는다. sourceKey 체계 변경은 전후 대조 후 전환한다. 지점명 null은 주소로 보조하며 추정 지점명을 만들지 않는다.
6. 전국 원천 전체 적재 대신 승인 지역의 9브랜드 후보만 점진적으로 제공한다. 지역별 coverage를 저장한다. ‘매장 없음’과 ‘아직 지원하지 않는 지역’을 구분한다.

### 6.3 갱신·운영 제안

- 월 1회 매장 원천 전체 대조를 기본으로 둔다. 주 1회 원천 새 배포 여부를 확인한다. 화면에는 원천 기준일과 수집일을 구분한다. 원천 배포가 더 느리면 수집일로 신선도를 과장하지 않는다.
- 공식 안내의 메타에는 실시간 갱신이라고 적혀 있다. 실제 지점 현황 반영 지연까지 검증한 뜻은 아니다. 서비스 월간 대조 주기와 다르다. 출처: [공식 상가정보 API 안내](https://www.data.go.kr/data/15012005/openapi.do).
- 완전 수집·행 수 급변 검사·매핑 검수 후 원자적으로 새 버전을 공개한다. 원천에서 사라진 매장은 두 번의 완전 대조 후 비활성화한다. 완전성 확인 없는 누락은 폐점으로 처리하지 않는다.
- 기존 수집 Job 배선을 재사용하고 동시 실행 1개로 제한한다. 한 번에 한 지역을 처리한다. 샘플 fallback·부분 덮어쓰기 금지. 쿼터 초과 시 중단하고 다음 주기에 재개한다.
- 배치 예산 초안은 일 최대 1,000콜, 실행 메모리 256MiB다. 원천 계약 한도보다 낮게 조정한다. 적재 표본으로 시간·행 크기를 측정한 뒤 승인한다. 기존 인프라 여유가 확인되지 않으면 P2를 연기한다.

## 7. 요청 경로와 개인정보 설계

### 7.1 외부 호출 없는 조회

**[제안]** 사용자 조회는 ranking 소유의 로컬 ‘매장 비교용 투영본’만 읽는다. place 원천 DB를 직접 JOIN하지 않는다. place에서 내부 API로 완전한 브랜드 매장 스냅샷을 제공하고, 배치가 받아 ranking 전용 DB에 복제한다. 사용자 요청 중에는 내부 place API도 호출하지 않는다. 지리 SSOT는 place에 남긴다.

기존 MySQL에 지역·브랜드·위경도 인덱스를 둔다. 경계 상자로 먼저 제한한 뒤 구면거리로 반경을 판정한다. 신규 상시 파드·지도 SDK·타일 서버·새 OpenSearch 인덱스를 추가하지 않는다. 후보가 제한값을 넘으면 잘라서 전량처럼 보여주지 않고 `coverage.status=LIMITED`를 낸다. 성능 목표를 넘으면 지역 범위를 줄인다.

스키마·내부 API·서비스 간 투영본 계약은 새 결정이다. **구현 전에 ADR 초안과 데이터 보존 정책 검토가 필요하다.** 이 문서로 현 ADR을 변경하지 않는다. 근거: E7과 루트 `AGENTS.md`의 서비스 간 DB 공유 금지.

### 7.2 위치 흐름과 좌표 비보존

1. 주변 화면은 기능 설명부터 표시한다. 자동 위치 요청은 없다.
2. ‘현재 위치 사용’에서 일회 `getCurrentPosition`을 요청한다. 제안값은 고정밀 비활성, timeout 10초, maximumAge 60초다. 지속 추적하지 않는다.
3. 거부·미지원·timeout이면 이유별 문구와 ‘지역 선택’을 표시한다. 재시도는 사용자 동작으로만 한다.
4. 정확도 반경이 1km보다 큰 위치는 ‘위치가 넓게 추정됨’을 표시하고 지역 선택을 우선 권한다. 화면의 거리는 직선거리이며 도보시간이 아니다.
5. 좌표는 클라이언트 메모리와 POST 요청 본문에만 둔다. URL·hash·history.state·localStorage·sessionStorage·분석 이벤트에 넣지 않는다. 화면 이탈·탭 종료 시 폐기한다. 새로고침 후 다시 선택한다.
6. 서버는 좌표를 영속화하지 않는다. 예외 메시지·요청 DTO toString·트레이스 태그·APM 본문·프록시 디버그 덤프에서 수집을 막는다. 좌표를 포함한 캐시 키·서버 세션도 만들지 않는다. 응답은 `Cache-Control: no-store`다.
7. 경로별 로그는 method·path template·status·duration·requestId만 허용한다. 본문을 지우는 것만으로 충분하다고 판단하지 않는다. 상관 가능한 IP·식별자와 좌표 결합도 검사한다.

현재 `GET /api/places/nearby?lat&lng`는 좌표를 URL에 싣는다. 이 기능에서 사용하지 않는다. `POST` 자체가 로그 비보존을 보장하지 않으므로 P2-5 검증을 출시 게이트로 둔다. 출처: E11.

지역 선택은 시도→시군구 선택이다. 법정동 코드와 사전 적재한 지역 중심점을 사용한다. GeoNames 지역 ID와 한국 법정동 코드를 섞지 않는다. 지역 중심점을 아직 보유하지 않으면 해당 지역은 지원하지 않는다. 사용자 위치로 간주하지 않고 ‘선택 지역 중심 기준’이라고 표시한다. 출처: `place/CLAUDE.md`의 행정구역 구분.

## 8. API 초안

전부 **[제안]**이다. 기존 공개 API 3개 외에는 구현되지 않았다. 응답은 기존 `ApiResponse<T>` envelope를 따른다. 아래는 data 내부 필드다.

### 8.1 P1 검색·비교·상세

| API | 요청 | 응답·정책 |
|---|---|---|
| GET `/api/v1/ranking/cafe/drinks` 확장 | 기존 q·반복 brand·group·temperature·maxSugar·maxCaffeine·sort·page·size 유지. `basis=serving|100ml`, `caffeineStatus=ZERO|DECAF|DISCLOSED|UNDISCLOSED` 반복 추가 | 기존 행 필드 + `drinkKey`, `kcalPer100ml`. page 기본 0, size 기본 20·상한 200. count는 전체 변형 행 수 |
| 동일 API의 sort 확장 | `sugar|caffeine|kcal`는 basis가 지정한 값으로 정렬. 기존 `sugarPer100ml`은 `basis=100ml&sort=sugar`의 호환 별칭 | 정렬 후 페이지 처리. 동률은 brandSlug·drinkKey. 수치 null 마지막. 기준 전환 시 page=0 |
| GET `/api/v1/ranking/cafe/groups`·`/brands` | 기존 계약 유지 | 원천별 확인일을 포함한 기존 정보 사용. 그룹 이름이 동일 레시피라는 뜻은 아님 |
| GET `/api/v1/ranking/cafe/drinks/{drinkKey}` 추가 | 공개 opaque 키 | 한 변형의 전체 영양정보·파생값·원문·확인일·notes. 없음 404. 동일 자연키 재적재 시 키 유지 |

`drinkKey`는 브랜드·메뉴명·온도·사이즈·카페인 상태의 자연키에서 서버가 안정적으로 발급한다. 삭제 후 재적재마다 바뀌는 DB id는 쓰지 않는다. 메뉴명 변경 시 옛 키는 404와 재검색 대안을 낸다. 기존 응답에 식별키가 없으므로 상세는 API 보완이 선행 조건이다. 출처: E5·E7.

기존 `caffeine=none`은 호환 유지하되 UI에서 생성하지 않는다. 과거 링크는 ‘공식 0·디카페인 포함’ 칩으로 정확히 설명한다. 새 상태 필터와 함께 오면 400으로 모순을 막는다. maxSugar·maxCaffeine은 항상 1회량 조건이다. 수치 미확정은 제외한다.

P1은 UI만 바꾸면 완성되지 않는다. 상태별 필터·농도별 전체 정렬·안정 상세키는 API 변경 범위다. 기존 페이지 안에서만 재정렬하거나 DECAF를 지운 뒤 0개로 보정하는 임시 처리는 금지한다.

### 8.2 P2 주변 검색

`POST /api/v1/ranking/cafe/nearby-search`

| 본문 필드 | 타입·기본값·제약 |
|---|---|
| location | `kind=CURRENT`이면 lat·lng 숫자 필수. WGS84 범위 검증. `kind=AREA`이면 areaCode 필수, 좌표 동시 전달 금지 |
| radiusKm | 0.5·1·3 중 선택, 기본 1. AREA도 선택 지역 중심의 같은 반경 |
| group, q, brands | 비교 조건. group이 없으면 범위 선택 안내. brands는 승인 9브랜드만 |
| temperature, caffeineStatus, maxSugar, maxCaffeine | P1과 동일. 빈 검색과 전송 오류를 구분 |
| basis, sort | 기본 serving·distance. distance 또는 sugar·caffeine·kcal. 수치 정렬은 선택된 해당 변형 기준 |
| selectedDrinkKeys | 브랜드별 선택 변형 키. 미선택 브랜드는 ‘음료 선택 필요’로 표시. 최대 9개, 브랜드당 1개 |
| page, size | 기본 0·20, size 상한 50. 모든 페이지가 같은 요청 조건을 사용 |

| 응답 필드 | 의미 |
|---|---|
| basis, sort, radiusKm, locationKind, areaLabel | 적용 조건. 사용자 중심 좌표는 반사하지 않는다 |
| coverage | status=`SUPPORTED|UNSUPPORTED|LIMITED|STALE`, 대상 지역·매핑 브랜드·사유. 전국 전량 보장 아님 |
| storeSource, storeSourceAsOf, storeFetchedAt, projectionAsOf, mappingRuleVersion | 원천·수집·투영본 신선도 분리 |
| totalStores, matchedBrands, page, size, hasNext | 조건에 맞는 매장 수·브랜드 수. 제한이면 totalStores=null, 상한 도달 안내 |
| items[] | storeKey·brandSlug·brandName·storeName·branchName nullable·address·distanceM·mappingStatus·selectedDrink·selectionRequired |
| items[].selectedDrink | drinkKey·menuName·temperature·sizeLabel·volumeMl·servingBasis·sugarG·caffeineMg·caffeineStatus·kcal·100ml 3수치·checkedAt·sourceUrl |
| items[].menuAvailability | 항상 `UNVERIFIED`. 브랜드 영양 연결일 뿐 매장 판매 확인이 아님 |

매장 선택·지도 표시는 P2 범위 밖이므로 응답에 매장 좌표는 요구하지 않는다. 동일 브랜드 여러 지점은 동일한 선택 변형의 수치를 반복한다. 지점 간 영양 차이처럼 해석하지 않도록 ‘브랜드 공식 기본 레시피’ 라벨을 붙인다.

미선택 브랜드를 가장 작은 사이즈·가장 낮은 당류로 자동 선정하지 않는다. 한 변형만 있으면 그 변형을 사용하고 자동 선택 사실을 알린다. 복수면 브랜드별 선택기를 연다. 미선택 행은 거리순에서는 유지, 수치순에서는 ‘선택 필요’ 묶음으로 뒤에 둔다. 페이지네이션 전 동일 규칙을 적용한다.

잘못된 좌표·조건은 400, 미등록 키는 404, 과도한 요청은 429, 투영본 미준비·조회 장애는 503이다. 지원 지역 밖·결과 없음은 200과 coverage·빈 items로 구분한다. 소급하여 전국 비교 결과를 주변 결과로 내지 않는다.

### 8.3 지역·배치 계약

- GET `/api/v1/ranking/cafe/areas?parent=` 추가. 투영본에 포함된 법정동 지역만 제공한다. code·name·level·parentCode·coverage·sourceAsOf를 반환한다. 사용자 요청 중 외부 지오코딩이 없다.
- GET `/internal/places/cafe-stores/snapshot?version=&cursor=&size=` 추가 초안. 배치 전용이다. version·complete·nextCursor·sourceAsOf·fetchedAt·매장 원본/매핑 필드를 반환한다. 완료 검증 전 활성 버전을 바꾸지 않는다. ingress 공개 금지.
- 원천·매핑·지역 중심점·투영본 계약과 삭제 정책은 구현 전 ADR 검토 항목이다. ranking이 place의 DB 테이블을 직접 읽는 방법은 채택하지 않는다.

## 9. SEO 설계

**[확인]** `portal-fe/src/seo/copy.mjs`에는 rank 허브·보드 메타가 있으며 주유소 소개가 중심이다. 현재 초기 HTML의 카페 전용 메타도 확인되지 않았다. 출처: E13·HTTP 확인 기록.

**[제안]** 같은 파일에 `/cafe` 전용 메타를 추가하고 host 라우팅·프리렌더 경로와 연결한다. JS 후 변경만으로 완료 처리하지 않는다.

- title: `카페 음료 당류·카페인·열량 비교 | 1989v 랭킹`
- description: `브랜드 공식 영양정보로 카페 음료의 당류·카페인·열량을 비교합니다. 1회 제공량과 100ml 기준, 디카페인과 미공개 정보를 구분해 확인하세요.`
- canonical: `https://rank.1989v.com/cafe`

| URL | 색인 제안 | 처리 |
|---|---|---|
| `/cafe` | index, follow | self canonical, sitemap 등록 |
| `/cafe?q=...&group=...`, brand·sort·basis·page·size 조합 | noindex, follow | canonical `/cafe`. 과거 공유 링크는 동작 유지. sitemap 제외 |
| `/cafe/drinks/:drinkKey` | P1 noindex, follow | self canonical. 안정키·고유 설명·수명 정책 확정 후 승격 검토 |
| `/cafe/nearby`, `/cafe/location`, 지역·반경 조합 | noindex, follow | canonical `/cafe`. 좌표를 어떤 URL에도 만들지 않는다 |
| 이후 `/cafe/groups/:slug` | 승인 후 index 후보 | 고유 비교 설명·유효 데이터가 있는 유형만. 기타·빈 유형 제외 |

robots.txt로 noindex 대상의 크롤링을 막아 지시를 못 읽게 하지 않는다. q는 검색 입력값일 뿐 위치·좌표·개인정보를 공유 링크에 자동 포함하지 않는다. 공유 기능은 허용된 비교 필터만 조립한다.

| 항목 | 대응·출시 조건 |

| 원천 자료 이용·자동수집 조항 미확인 | 기존 영양 데이터의 미확인을 허가로 해석하지 않는다. 갱신 자동화 확대 전 브랜드별 검토. E8 |
| 매장 누락·상호 충돌 | 실제 원천 확보·브랜드별 매핑 정밀도·포함률 대조를 P2 게이트로 둔다 |
| 유형 오분류 | 원문 메뉴명·변형을 유지한다. 기타를 숨기지 않는다. 오분류 교정 후보를 별도 관리 |
| 용량 부족 | 100ml 토글에서 제외 수와 산출 불가를 표시한다. 계산 가능한 브랜드만으로 전체 최저라고 하지 않는다 |
| 재적재 상세 링크 변화 | 안정키를 자연키와 연결한다. 사라진 메뉴는 404 대안 제공 |
| 위치 로그 유출 | POST 전환에 더해 전 계층 본문·태그·오류·분석 수집 검증 필요 |
| 단일 노드 과부하 | 신규 상시 파드 없이 제한 지역·배치 예산·후보 상한 적용. 측정 실패 시 P2 보류 |
| 영양 갱신 지연 | 행별 checkedAt 표시. 갱신 SLA 확정 전 ‘항상 최신’ 문구 금지 |

### 사용자 결정 필요

1. **P2 최초 출시 지역**: 단일 시군구 실증 또는 수도권 일부. 제안은 실제 원천 검증이 가능한 단일 시군구다.
2. **비교 단위 정책**: 모든 변형을 유지할지, 브랜드별 사용자가 고른 한 변형을 기본으로 둘지 결정한다. 제안은 P1 전체 변형, P2 브랜드별 선택이다.
3. **반경 정책**: 기본 1km와 0.5/1/3km 선택을 승인할지 결정한다. 지역 중심 비교도 같은 반경을 쓴다.
4. **영양 갱신 운영**: 수동 확인 주기와 담당자를 정한다. 제안은 월 1회 확인이며 자동수집 확대는 원천 검토 후 진행한다.
5. **지도 우선순위**: P2 목록 출시를 유지할지 결정한다. 지도 추가는 별도 비용·외부 호출 정책 검토가 필요하다.

미결정은 문서 완성을 막지 않는다. 관련 구현 착수·P2 공개 전에는 결정 기록과 ADR을 확정한다.
