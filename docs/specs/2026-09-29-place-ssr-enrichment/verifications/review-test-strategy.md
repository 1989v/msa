# 리뷰 — 테스트 전략 (test-strategy)

대상: `spec.md` · `planning/test-quality.md` · `planning/requirements.md` · `context/open-questions.yml`
기준: `docs/standards/test-rules.md`(Kotest BehaviorSpec + MockK), 기존 테스트 관행, 「검사는 대상의 산출물을 본다 · 회귀 주입으로 증명한다」

## 요약

층 배정과 critical 표시는 대체로 맞다. `test-quality.md:18` 이 ★ 검사마다 회귀 주입을 요구한 점도 좋다.
하지만 계획에 빠진 것이 셋 있다. 이 셋은 **검사를 통과해도 대상이 맞다는 증거가 되지 않는** 경우다.

1. 서버 JSON-LD 와 클라이언트 JSON-LD 가 같은지 보는 검사가 없다.
2. 계약 게이트는 필드가 채워졌는지 보지 않는다.
3. nDCG 전후 비교의 설계가 비어 있다.

그 밖에 수용 기준 여러 개에 대응하는 테스트가 없다. 전부 계획 문서를 고치면 풀리므로 판정은 REVISE 다.

## 이슈

### R1 ★ 서버 JSON-LD 와 `useSeo` JSON-LD 가 같은지 보는 검사가 없다 (체크 1·3)
- 스펙은 두 JSON-LD 가 **같은 내용**이어야 한다고 정한다(`spec.md:20`, ADR-0062 §13). 계획은 `data-seo-multi` 표시만 본다(`test-quality.md:5`).
- 기존 방식을 그대로 따르면 기대값을 사람이 손으로 복사해 넣게 된다. 예: `BlogMetaRendererTest.kt:68-69` 는 「portal-fe personRef 와 같은 값」을 문자열 리터럴로 적는다.
  이런 검사는 `copy.mjs` `touristAttractionJsonLd`(`portal-fe/src/seo/copy.mjs:593`)가 바뀌어도 초록불이다. 재는 것이 복사해 둔 사본이다.
- 다른 내용의 JSON-LD 가 두 벌 나가는 사고는 이미 한 번 났다(`prerenderPlace.test.ts:149-154`, 2026-09-10 실측).
- **수정안**: 비교 기준을 대상 코드가 직접 내게 한다.
  1. 고정 입력 문서 하나로 vitest 가 `touristAttractionJsonLd` 와 `attractionMeta` 를 실제로 불러 결과를 공유 픽스처(JSON)로 쓴다.
  2. Kotlin 렌더러 테스트가 같은 입력으로 렌더한 뒤 JSON-LD 를 파싱해 픽스처와 **구조 동등**으로 비교한다.
  3. 픽스처가 오래됐는지는 CI 가 vitest 로 다시 만들어 diff 로 잡는다.
  - 회귀 주입: `copy.mjs` 쪽 필드를 하나 바꾸고 Kotlin 테스트가 빨간불인지 확인한다.

### R2 ★ 계약 게이트 통과는 「필드가 채워졌다」는 증거가 아니다 (체크 1·3)
- 계획은 SR-7 을 `verifySearchIndexContract` 통과로 판정한다(`test-quality.md:15`).
- 이 게이트는 매핑 최상위 키와 data class 의 `val` **이름**만 비교한다(`build.gradle.kts:550`, `:563-564`). 중첩 타입은 별도 파일이라 검사하지 않는다고 스스로 적어 두었다(`:562`).
- 그래서 게이트는 다음 둘을 못 잡는다.
  - 항상 `null` 로 쓰이는 필드
  - 가까운 곳·비슷한 곳의 `id·title·distance` 같은 중첩 필드
- 요구사항 문서도 이 위험을 적어 두었다: 「빠지면 조용히 빈 값」(`requirements.md:71`).
- **수정안**: `AttractionApiReindexTaskletTest` 에 합류 시나리오를 더한다. 이 파일에는 벡터 합류 사례(`AttractionApiReindexTaskletTest.kt:103,120`)가 이미 있다.
  - 속성·지역 집계·가까운 곳·비슷한 곳·인기도가 **실제 bulk 요청 문서**에 값으로 실리는지 캡처해서 본다.
  - 읽기 쪽은 매핑 JSON 샘플을 `AttractionSearchDocument` 로 역직렬화해 중첩 필드까지 채워지는지 본다.

### R3 ★ nDCG 전후 비교의 설계가 비어 있다 (체크 1·2·5)
`test-quality.md:14` 는 「하락 없음」 한 줄뿐이다. 기존 도구를 그대로 쓰면 스펙의 게이트(`spec.md:57`)가 성립하지 않는다. 이유는 셋이다.
- **허용폭이 신호보다 크다**
  - `live-eval.py` 는 고정 기준선에서 0.03 까지 떨어져도 통과시킨다(`live-eval.py:128-133`, `cronjob-eval.yaml:45-51`).
  - 같은 파일 주석이 색인 드리프트만으로 ±0.02 움직인다고 적었다(`cronjob-eval.yaml:45`).
  - 계수 상한 ×1.3(`open-questions.yml:11`)의 효과는 이 잡음 안에 묻힌다.
- **전후를 같은 시점에 잴 방법이 없다**
  - `live-eval.py` 의 C 는 지금 라이브 API 만 잰다(`:66-71`). 계수를 켜기 **전에** 켠 상태를 잴 경로가 없다.
- **판정 풀 편향**
  - 판정 세트는 BM25·벡터 후보로 만들었다(`tools/embed/src/embed/evaluate.py:25-30`).
  - 인기도로 새로 올라온 미판정 문서는 0점으로 계산되어 새 순위에 불리하다.
- **수정안**
  - 같은 색인·같은 시점에 계수 on/off 를 질의별로 짝지어 잰다. 요청 파라미터나 설정 두 벌로 가를 수 있다.
  - 판정 기준을 「평균 하락 없음 **그리고** 질의별 악화 건수 ≤ N」으로 적는다.
  - 상위 10 안 미판정 비율을 같이 출력하고, 비율이 임계를 넘으면 판정을 보류한다.
  - 회귀 주입: 계수를 과하게 올린 설정(예: 상한 ×10)에서 게이트가 빨간불인지 확인한다.

### R4 SR-2 파서 적용률 검사가 자기 기준을 잰다 (체크 3·5)
- `test-quality.md:9` 는 「UNKNOWN 비율이 원문 보유율과 어긋나지 않음」으로 판정한다. 원문이 있으면 전부 「가능」으로 찍는 파서도 이 검사를 통과한다. 커버리지는 재지만 정확도는 재지 않는다.
- 스펙이 가장 강하게 금지한 것은 「UNKNOWN 을 불가로 바꾸지 않는다」(`spec.md:29`)인데, 그 방향의 음수 사례가 계획에 없다.
- **수정안**
  - 표본 2,000건 중 속성마다 30건 이상을 사람이 라벨링해 정확도를 기록한다.
  - 표 기반 단위 테스트에 두 사례를 명시한다.
    - 「원문 없음 → UNKNOWN(불가 아님)」
    - 「반려동물 일부」
  - 패싯 테스트에 「UNKNOWN 문서는 불가 필터 결과에 없다」를 넣는다.

### R6 SR-4·SR-6 경계 사례 (체크 5)
- 지역 집계기(`test-quality.md:11`)는 전량 순회라서 **페이지 경계**에서 누락·중복이 나기 쉽다. 여러 페이지 입력에서 합이 입력 건수와 같은지 본다.
- 같은 시군구·같은 분류가 5곳 미만인 경우와 자기 자신을 빼는지를 본다.
- 인기도 계수는 경계값을 본다: 표본이 최소치 −1, 최소치, 상한을 넘는 값.

### R7 셸 「마지막 정상본」은 렌더러가 아니라 셸 공급자 층이다 (체크 2)
- `test-quality.md:5` 는 이 시나리오를 렌더러 단위에 두었다. 하지만 이 상태를 갖는 쪽은 셸 공급자(`ShellHtmlProvider`)다.
- 기존 `BlogShellHealthIndicatorTest.kt:12-14` 는 상태 플래그를 손으로 세우지 않고 실제 HTTP 로 상태를 만든다. 다만 MISSING·OK 두 상태만 본다(`:18-51`).
- **수정안**: 같은 방식으로 세 시나리오를 더한다.
  - 한 번 성공 → 서버 중단 → 마지막 정상본 + 헬스 표시
  - 5분 TTL 경과 후 다시 받는지
  - 한 번도 못 받은 경우 → 최소 HTML

### R8 Testcontainers OpenSearch 가 없다 (체크 2)
- `test-quality.md:10` 은 패싯을 Testcontainers OpenSearch 로 통합 검증한다고 적었다. 레포 카탈로그에는 OpenSearch 모듈이 없고 junit·mysql·clickhouse·kafka 뿐이다(`gradle/libs.versions.toml:111-114`).
- **수정안**: 다음 중 하나를 계획에 적는다.
  1. 의존성과 버전을 추가한다. 운영과 같은 3.8 이어야 한다(nori 태그 차이 전례).
  2. 대체 경로를 쓴다. 예: 배포 후 라이브 API 로 post_filter 동작 확인.

  요청 빌더 단위 테스트는 **요청 모양**만 본다. 「자기 패싯 건수가 줄지 않는다」는 OpenSearch 가 계산한 결과여서 단위 테스트로는 증명되지 않는다.

### R9 테스트 데이터 전략 (체크 4)

- **수정안**

  - 문서 픽스처 빌더 하나를 렌더러·재색인·서비스 테스트가 같이 쓴다.
  - R1 의 공유 JSON 픽스처도 여기에 포함한다.

### R10 e2e 운영 확인이 서버 렌더를 가리키는지 (체크 1·3)
- `test-quality.md:7` 은 Googlebot UA 로 curl 해 「본문을 가진 HTML」을 확인한다. 프리렌더 제거 전에는 같은 경로를 nginx 프리렌더나 캐시된 옛 응답이 줄 수 있다. 그러면 옛 산출물을 재고 확인했다고 판정하게 된다.
- **수정안**
  - 서버 렌더만 내는 표지로 판정한다. 예: SR-4 문구 「N곳 중 M곳」, 또는 search 가 붙이는 응답 헤더.
  - 표본은 프리렌더 6,000건 **밖**의 id 로 고정한다.
  - 프리렌더 제거 후에는 `/regions/*` 가 계속 프리렌더인지 같이 확인한다.

## 판정 근거
- BLOCK 은 아니다. 문서나 게이트를 위반하는 스펙 결정은 없고, 빠진 것은 전부 계획 문서를 보강하면 해결된다.
- R1·R2·R3 은 구현 전에 고쳐야 한다. 그대로 두면 ★ 검사가 초록불이어도 스펙 결정(`spec.md:20` · `:57` · `:62`)을 지켰다는 증거가 되지 않는다.

VERDICT: REVISE
