# Usecase Review — place 관광지 서버 렌더 + 인리치먼트·패싯

- 대상: `spec.md` · `planning/requirements.md` · `planning/initialization.md` · `planning/test-quality.md` · `context/open-questions.yml`
- 코드 근거: `portal-fe/src/pages/place/{PlacePage,AttractionPage}.tsx` · `placeView.ts` · `api/placeApi.ts` · `scripts/prerender-seo.mjs`
- 차원: usecase만 본다. 아키텍처와 성능은 다른 리뷰어가 본다.

## 요약

사용자 요청 세 가지는 모두 스펙에 들어가 있다. 본문 전량 노출은 SR-1, 속성 추출과 필터 보강은 SR-2·SR-3, A~D 전부는 SR-2·4·5·6이 맡는다.
막을 만한 결함은 없다. 다만 아래 일곱 가지는 구현자가 추측으로 채워야 하므로 AC(수용 기준)로 굳혀야 한다.
- 유지 목록이 스펙 본문에 빠져 있다.
- 「오늘 여는 곳」이 어느 요구사항에도 연결돼 있지 않다.
- 음식·쇼핑 문서가 섞일 때의 의미가 정해지지 않았다.
- 영문 파서가 정해지지 않았다.
- 서버 렌더와 SPA 사이의 메타 규칙이 두 가지 어긋난다.
- UNKNOWN 비율이 높은 칩을 어떻게 다룰지 없다.
- 모바일 필터 흐름이 없다.

## 이슈

### U1. 「이미 있는 건 두고」가 spec.md 에 없다 (체크 1·4)
- 사용자 원문은 `planning/initialization.md:8` 의 「이미있는건 두고」이다. 유지 목록은 `requirements.md:62-63` 에만 있다(주변 관광지 · 편의시설 · 링크 섹션 · 인기 집계 원장/배치 · 임베딩·하이브리드 · popularityScore).
- `spec.md` 는 이 중 두 가지만 적었다. 「주변 관광지」(`spec.md:45`)와 popularityScore(`spec.md:56`)이다. 나머지는 빠졌다.
  - 편의시설 캐로셀: `AttractionPage.tsx:435-477`
  - 링크 섹션: `AttractionPage.tsx:397`
  - 기존 「이용 안내」 표: `AttractionPage.tsx:334-368`
  - 노출 기록 섹션 식별자 `NEARBY_ATTRACTIONS`·`AMENITY_CAROUSEL`: `AttractionPage.tsx:415,454`
  - 임베딩 적재 경로 불변
- SR-2 는 「배지와 방문 정보 목록으로 보여 준다」(`spec.md:31`)고만 적었다. 기존 「이용 안내」(원문 표시)를 대체하는지, 그 위에 더하는지 정하지 않았다.
- SR-5 의 「임베딩과 같은 경로로 적재」(`spec.md:49`)도 기존 임베딩 행과 bulk 계약을 그대로 두는지 밝히지 않았다.
- **수정안**:
  - spec.md 에 `## 유지` 절을 추가하고 `requirements.md:63` 목록과 위 세 가지(이용 안내 원문 표 · 노출 기록 섹션 식별자 · 임베딩 bulk 계약)를 옮긴다.
  - SR-2 에 「기존 이용 안내 표는 원문 그대로 두고, 배지는 그 위에 더한다」를 넣는다.
  - 새 섹션(같은 분류 가까운 곳 · 비슷한 곳)에 새 `sectionId` 로 노출을 기록하는 한 줄을 넣는다. 빠지면 D 의 클릭 신호가 새 섹션을 세지 못한다.
  - test-quality.md 에 「기존 섹션 네 개가 그대로 렌더」 component 행을 추가한다.

### U2. 「오늘 여는 곳」 스토리를 받는 요구사항이 없다 (체크 1·4)
- 스토리는 `spec.md:9` 에 있다. SR-2(`spec.md:28`)는 휴무 요일 집합과 연중무휴만 만들고, SR-3(`spec.md:35-36`)은 정적인 속성 값 필터와 패싯만 정의한다.
- 「오늘」은 요청 시점의 요일(KST)에서 나오는 동적 조건이다. 패싯 값으로 표현되지 않는다. 다음이 모두 정해져 있지 않다.
  - 무엇을 「연다」로 칠지 (연중무휴 ∪ 휴무 요일에 오늘이 없음)
  - UNKNOWN 을 빼는지
  - 공휴일과 계절 휴무를 어떻게 다룰지
  - 이 필터의 건수를 보여 줄지
- **수정안** (둘 중 하나):
  - SR-3 에 「오늘 엶」 필터를 명시한다. 정의는 KST 요일 기준이고, 휴무 요일에 오늘이 없거나 연중무휴인 곳이다. UNKNOWN 은 제외하고, 공휴일과 계절 휴무는 해석하지 않는다(범위 밖). 건수는 요청마다 계산한다. 파서 표 기반 테스트(`test-quality.md:8`)에 요일 경계 행을 더한다.
  - 또는 스토리를 「휴무 요일로 거르기」로 고친다.

### U3. 음식·쇼핑·숙박 문서가 섞일 때의 의미가 정해지지 않았다 (체크 5)
- 사실관계:
  - 색인의 절반 이상이 음식·쇼핑이다(`placeApi.ts:120-121`).
  - 사이트맵 열거는 분류 필터 없이 모든 문서를 훑는다(`prerender-seo.mjs:983`). 따라서 서버 렌더 대상 55,524건(`initialization.md:22`)에는 음식점(38)·쇼핑(39)·숙박 상세가 들어 있다.
  - 목록 화면은 기본값으로 관광 분류만 보낸다(`PlacePage.tsx:262`).
- 빈틈:
  - **SR-4** 의 「{시군구} 관광지 N곳 중 {분류} M곳」(`spec.md:44`)에서 N 이 「시군구별 전체 수」(`spec.md:42`)면 음식점까지 센다. 그러면 관광지 수로 표시되는 값이 약 두 배로 부풀어 거짓이 된다. 음식점 상세에서는 「관광지 N곳 중 음식점 M곳」이라는 어색한 문장이 나온다.
  - **SR-5** 의 비슷한 곳(`spec.md:48`)은 유형을 제한하지 않는다. 관광지 상세에 다른 시도의 식당이 뜰 수 있다.
  - **SR-2** 의 「입장 무료」는 음식·쇼핑에는 의미가 없다. 원천 키도 유형별로 다르다(`restdatefood`, `chkcreditcardfood` — `placeView.test.ts:150,171`).
  - **SR-3** 의 패싯이 기본 관광 분류 필터 아래에서 세는지 명시돼 있지 않다.
- **수정안**:
  - SR-4 에서 N 을 「관광 분류(SIGHT: nature·history·culture·leisure) 수」로 정의한다. 비관광 문서의 문구(예: 「{시군구} 음식점 M곳」)나 섹션 생략을 정한다.
  - SR-5 는 「같은 분류군(SIGHT ↔ SIGHT, AMENITY ↔ AMENITY)」으로 제한한다.
  - SR-2 에 속성×유형 적용 표를 둔다. 입장 무료는 12·14·28 유형에만 적용하고, 나머지는 필드를 싣지 않거나 UNKNOWN 으로 둔다.
  - SR-3 에 「패싯은 요청의 분류 필터가 적용된 집합에서 센다」를 넣는다.
  - test-quality.md 에 음식점 문서 표본 행을 추가한다.

### U4. 영문 페이지와 영문 원문이 빠져 있다 (체크 5)
- 서버 렌더는 `/en/attractions/{id}` 도 대상이다(`spec.md:16`). 필드 채움 실측은 「국문 무작위 2,000건」뿐이다(`initialization.md:25`). 파서 표본(`test-quality.md:8`)도 국문 표기(「연중무휴」 등)만 있다.
- 영문 원천은 restDate·useTime·chk* 값을 영어로 준다. 국문 파서를 그대로 쓰면 영문 문서가 전부 UNKNOWN 이 되고, 영문 화면의 필터 칩이 사실상 비활성이 된다.
- SR-4 문구와 SR-5 목록의 영문 표기도 정하지 않았다. 기존 라벨 표는 ko·en 쌍이다(`placeView.ts:131-149`).
- **수정안**:
  - SR-2 에 「영문 원문 표기도 해석 대상」을 넣거나, 「영문은 이번 범위에서 UNKNOWN, 칩 숨김」을 명시한다.
  - SR-2 의 적용률 측정(`spec.md:32`)을 ko/en 각 표본으로 나눈다.
  - SR-4 와 SR-5 에 영문 문구를 넣는다.

### U5. 서버 렌더와 기존 SPA 메타 규칙이 두 군데 어긋난다 (체크 2)
- **언어 불일치**: `/en/attractions/{ko-id}` 같은 어긋난 주소에서 SPA 는 문서 자신의 언어로 canonical 을 잡는다(`AttractionPage.tsx:131-133,149`). SR-1 은 이 경우 서버 렌더가 어떻게 할지(문서 언어로 canonical · 404 · 리다이렉트) 정하지 않았다.
- **개요 없는 문서**: SPA 는 개요가 없으면 `noindex` 를 건다(`AttractionPage.tsx:152-155`). SR-1(`spec.md:17-20`)은 JSON-LD 가 같아야 한다고만 하고 robots 메타는 언급하지 않는다. 서버가 색인을 허용하고 하이드레이션 뒤에 noindex 가 붙으면, 첫 응답과 렌더 뒤의 판정이 달라진다.
- **수정안**:
  - SR-1 에 「robots·canonical·lang 은 SPA(`useSeo`)와 같은 규칙: 문서 언어 기준 canonical, 개요 없음 → noindex」를 넣는다.
  - test-quality.md:5 행에 두 경우를 추가한다.

### U6. 패싯 건수 0과 UNKNOWN 비율이 높은 속성의 화면 흐름 (체크 2·5)
- SR-3 은 「건수가 0인 값은 비활성」(`spec.md:38`)이라고 한다. 그러나 이미 **선택한** 값이 다른 패싯 선택 때문에 0이 되면, 비활성이 된 칩은 선택을 풀 수 없다.
- UNKNOWN 이 패싯 값으로 나오는지 정하지 않았다. requirements 는 「필터에서 빠진다」(`requirements.md:33`)고 한다.
- 입장 무료(4.7%)·유모차(12%)처럼 원문 보유율이 낮은 속성에서 칩을 고르면 결과가 급격히 줄어든다. 사용자는 이것이 「정보가 없어서 빠졌다」는 뜻임을 알 수 없다. SR-2 는 적용률을 측정하지만(`spec.md:32`), 그 값이 칩 노출 여부에 연결되지 않는다.
- 유모차의 의미도 불분명하다. 기존 라벨은 「유모차 대여 / Stroller rental」(`placeView.ts:137`)이다. 스펙의 「유모차 가능·불가」(`spec.md:28`)와 뜻이 다르다. 대여 여부를 동반 가능 필터로 보이면 오해를 낳는다.
- **수정안**:
  - SR-3 에 다음을 넣는다.
    - 「선택된 값은 건수 0이어도 활성(해제 가능)」
    - 「UNKNOWN 은 패싯 값으로 내지 않는다」
    - 「칩 옆 또는 필터 영역에 '정보가 있는 곳만 거릅니다' 안내」
    - 「원문 적용률이 X% 미만인 속성은 칩을 내지 않고 상세 배지로만 쓴다」(기준값은 SR-2 측정 뒤 확정 — open-questions 에 Q4 로 등록)
  - 유모차는 「유모차 대여」로 이름과 의미를 맞춘다.

### U7. 모바일 흐름과 인기도 사후 조건 (체크 2·3·4)
- **모바일**: 검색 화면의 한 줄에 이미 여러 컨트롤이 있다. 분류 칩 5개, 지도 토글 칩 2개, 지역 select 가 있고(`PlacePage.tsx:970-1024`), 모바일은 지역을 바텀시트로 접는다(`PlacePage.tsx:948-968`).
  - 여기에 속성 6종 × 값 칩과 건수를 더하면 모바일에서 칩 벽이 된다. SR-3(`spec.md:38`)에는 배치 규칙이 없다.
  - 모바일 무한 스크롤은 `query` 에서 page 를 뺀 키로 누적을 초기화한다(`PlacePage.tsx:285-288`). 속성 필터가 `query` 에 들어가 누적이 초기화된다는 조건도 명시돼 있지 않다.
  - 상세는 세로로 쌓는 레이아웃이다(`AttractionPage.tsx:260-263`). 새 섹션 세 개(지역 안 위치 · 같은 분류 가까운 곳 · 비슷한 곳)의 순서가 정해지지 않았다. 「주변 명소」와 「같은 분류 가까운 곳」에 같은 곳이 겹칠 때의 처리도 없다.
- **인기도**: 사람 이벤트는 7일 92건이다(`initialization.md:28`). 기본값인 14일 20회 최소 표본(`open-questions.yml:11`)으로는 「많이 본 곳」 표시와 계수가 거의 모든 문서에서 꺼진다. 이것이 의도된 사후 조건인지 적혀 있지 않다. 이대로면 D 의 효과를 nDCG 로 재도 차이가 0으로 나올 가능성이 크다.
- **수정안**:
  - SR-3 에 모바일 규칙을 넣는다. 「모바일은 속성 필터를 트리거 하나 + 바텀시트로 접는다(지역 시트와 같은 패턴)」, 「속성 필터는 query 키에 포함되어 누적·page 가 초기화된다」.
  - 상세에 섹션 순서를 정한다(예: 이용 안내 → 지역 안 위치 → 주변 명소 → 같은 분류 가까운 곳 → 비슷한 곳 → 편의시설). 「주변 명소에 이미 나온 id 는 같은 분류 목록에서 뺀다」를 넣는다.
  - 모바일 두 방향 측정을 `docs/standards/fe-visual-verification.md` 에 따라 test-quality.md 의 component 행 옆에 추가한다.
  - SR-6 에 「현재 트래픽에서는 대부분 문서가 중립(1.0)이며, 이것이 정상 상태」를 기대 결과로 적는다. nDCG 비교는 「계수가 1.0이 아닌 문서가 N건 이상일 때」로 조건을 건다.

### 개정에서 새로 생긴 문제

- **N1. 반려동물 「일부」가 긍정 필터에 드는지 정하지 않았다.** `spec.md:33` 은 반려동물 값에 「일부 포함」을 두고, `spec.md:43` 은 필터가 긍정 값만 받는다고 한다. 「반려동물 동반」 칩이 「일부 가능」을 포함하는지 스펙에 없다. 결과 수와 사용자 기대가 둘 다 달라진다.
  - 수정안: SR-3 에 「반려동물 칩은 전체 가능만 / 일부 포함」 중 하나를 적는다. 일부를 포함하면 결과 카드에 「일부 구역」 배지를 붙인다. T8 에 행을 추가한다.
- **N2. 「미선택 0 숨김」과 「건수는 현재 선택을 모두 반영」이 겹치면 칩이 사라졌다 나타났다 한다.** `spec.md:45,48` 을 함께 적용하면 칩 하나를 누를 때마다 다른 속성 칩이 숨거나 다시 나온다. 모바일 가로 스크롤 줄에서는 칩 위치가 밀려 다음 탭이 엉뚱한 칩에 떨어진다.
  - 수정안: 둘 중 하나를 고른다. ① 속성별 집계는 **자기 속성 선택을 뺀** 나머지 선택만 반영한다(일반적인 패싯 방식). ② 숨김 대신 흐리게 표시해 자리를 유지한다. T17 에 「칩 하나 선택 뒤 다른 칩 순서·개수 유지」 행을 더한다.
- **N3. 지역 허브의 「대표 관광지」가 정의되지 않았다.** `spec.md:54` 의 「허브는 대표 관광지로 되돌아 링크」에서 몇 곳을, 어떤 기준(정보 충실도 `popularityScore` · 클릭 · 분류별 1곳)으로 고르는지 없다. 허브 프리렌더는 유지 대상이다(`spec.md:29`). 따라서 이 선택은 크롤러가 5.5만 상세에 닿는 내부 링크 경로를 정한다.
  - 수정안: SR-4 에 「허브는 분류별 `popularityScore` 상위 N곳을 링크」처럼 개수와 기준을 적는다.
