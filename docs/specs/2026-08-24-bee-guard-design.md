# 벌 막기 (bee-guard) — 설계 기록

## 1. 무엇을 만드는가

**그린 선이 그대로 물리 물체가 되는** 퍼즐. 벌이 아이에게 오기 전에 선을 그어 막는다.
한 판 20~60초, 10판.

두 단계로 잘려 있다 — **그리기(시간 정지) → 실행(고정 스텝)**. 그리면서 동시에 피하게
만들면 손이 하나뿐인 사람에게 불가능해지고, 무엇보다 "내 그림이 맞았는지" 를 판단할 수 없다.

---

## 2. 판이 풀린다는 것을 증명한다 — 이 게임의 핵심 장치

판마다 **모범 답안 획**을 코드에 넣고 화면 없이 돌려 두 가지를 확인한다 (`dev.verify()`):

| 검사 | 뜻 | 결과 |
|---|---|---|
| 모범 답안 → 성공 | 풀 수 없는 판을 배포하지 않는다 | **10 / 10** |
| 빈 손 → 실패 | 거저 통과되는 판은 퍼즐이 아니다 | **10 / 10** |

**이 검사가 만들다 만 판 다섯 개를 잡았다.** 손으로 확인했다면 열 판을 넘기는 순간
그만뒀을 것이고, 그때 안 풀리는 판이 섞인다.

### 검사가 가르쳐 준 것 — 설계를 두 번 뒤집었다

**① 한 방향에서만 오면 퍼즐이 성립하지 않는다.**
아이 반지름이 46이라 **120px 짜리 선 하나**를 머리 위에 얹으면 끝난다. 더 싸게는
떨어지는 길목 높은 곳에 **선반 하나**만 놓아도 튕겨 나간다. 한 획으로 이기는 경우를
격자·각도·길이 전수로 세어 보니 어떤 판은 **3,722개**였다. 그건 퍼즐이 아니라 낙서장이다.

**② 아이를 걷게 하는 것은 더 나쁜 해법이었다.**
짧은 가림막을 무력화하려고 아이를 왔다 갔다 하게 만들었더니, 벌이 맞느냐가 **그 순간
아이가 어디 있었느냐**로 갈렸다. **막아서 이긴 건지 운이 좋아 빗나간 건지 구분되지 않는다.**
퍼즐은 결정적이어야 한다.

**지금 규칙: 여러 방향.** 위·왼쪽·오른쪽에서 들어오면 짧은 선 하나로는 못 덮고 모양을
만들어야 한다. 예산은 검사기가 찾은 최단 해답보다 조금만 크게 잡는다.

한 획 해답 수를 **판의 헐거움을 재는 자**로 쓴다 (최종):

| 판 | 예산 | 답안 길이 | 최단 한 획 해답 수 |
|---|---|---|---|
| 1 첫 손님 | 880 | 811 | 0 (한 획으로 안 됨) |
| 2 낮게 온다 | 640 | 588 | 0 |
| 3 좁은 틈 | 880 | 813 | 0 |
| 4 소나기 | 1000 | 922 | 1 |
| 6 네 방향 | 910 | 839 | 9 |
| 8 따라온다 | 700 | 651 | 2 |
| 10 난장판 | 880 | 813 | 1 |

5·7 은 각각 181 · 409개로 다른 판보다 헐겁다(전체 후보의 1~2%). 벽으로 틀어막는 답이
꿀 유인·통로 봉인과 함께 성립하기 때문이고, **여러 답을 허용하는 것 자체는 이 장르에서
정상**이라 그대로 뒀다.

## 3. 결정적 실행

- 물리는 **고정 1/240초**. 주사율이 결과를 바꾸면 실패에서 배울 수 없다
- 판에는 무작위가 **아예 없다** — 시드는 화면 흔들림 같은 연출에만 쓴다
- 성공 = **제한 시간 동안 아이가 안 닿는 것**. "벌을 다 쫓아내면 성공" 으로 두면
  두 벽 사이에 갇혀 영원히 튀는 벌 하나 때문에 판이 안 끝난다 —
  구슬 레이스에서 겪은 함정이고, 시간 조건이 그 함정을 원천적으로 없앤다
- 실패해도 **그림은 남는다.** 처음부터 다시 그리게 하면 시행착오 비용이 커진다

---

## 4. 잉크 — 이 장르의 유일한 난이도 손잡이

| 항목 | 값 | 이유 |
|---|---|---|
| 예산 | 150 ~ 1,000 px | 무제한이면 화면을 통째로 칠해 끝난다 |
| 재표본 간격 | 14px | 원본 점을 그대로 쓰면 손 떨림 하나가 물체 수십 개 |
| 최소 획 길이 | 26px | 톡 찍힌 점이 벽이 되면 "안 그렸는데 막혔다" |
| 선 두께 | 반지름 11px | 보이는 선 = 부딪히는 선 |
| 지우개 | 획 단위 | 부분 지우기는 판정이 지저분하고 이득이 없다 |

예산이 모자라면 **가는 데까지 긋고 멈춘다** — 갑자기 안 그려지는 것보다 낫다.

---

## 5. 물리

세상에 있는 것은 둘뿐이다: **원(벌·아이)** 과 **캡슐(그린 선·벽)**.
그린 선을 다각형이 아니라 캡슐로 두는 이유는 손 경로가 곡선이라서다 — 두께 있는 선분들의
합집합이 곧 붓 자국이고, 원-캡슐 충돌은 원-선분 최단거리 하나로 끝난다.

> **선 위에 정확히 겹치면 법선을 뽑을 수 없다.** 그대로 두면 NaN 이 되고, 화면에서는
> "벌이 갑자기 사라졌다" 로 보인다. 선분의 수직 방향으로 밀어내 처리한다.

## 6. 화면·조작 실측치

| 항목 | 값 |
|---|---|
| 캔버스 | 1080 × 1440 (세로) |
| 터치 타깃 | 414 × 896 에서 화면 버튼 **91.2 × 44.5 CSS px** |
| 프레임 | 120fps |
| 콘솔 | 0 (직접 URL 진입 시 AudioContext 경고만) |

> 버튼을 캔버스 좌표 78px 로 두었더니 휴대폰에서 0.383배로 줄어 **29.9 CSS px** 이 됐다.
> 116px 로 올려 44.5 를 맞췄다. **캔버스 게임의 터치 타깃은 캔버스 좌표가 아니라
> 화면에 그려지는 CSS px 로 재야 한다.**

**가상패드(lib/touch.js)를 붙이지 않는다** — 손으로 직접 그리는 게임이라 패드가 판을 가린다.

## 7. 검증

| 항목 | 결과 |
|---|---|
| 판 검사 | 10/10 (답안 성공 · 빈 손 실패) |
| 죽은 입력 감사 | **105칸(5화면 × 21키) 전수 통과** |
| 손으로 그려 완주 | 2판을 실제 포인터 드래그 2획으로 통과 (잉크 640 → 80) |
| fps | 120 |

> 감사가 잡은 것: **첫 판에서 ← 를 누르면 아무 일도 일어나지 않았다.** 이전 판이 없어
> 조용히 무시하고 있었다. 지금은 "첫 판이다" 로 답한다. 감사 신호를 느슨하게 해서
> 통과시키는 대신 입력을 고쳤다 — 카드 뒤집기에서와 같은 판단이다.
