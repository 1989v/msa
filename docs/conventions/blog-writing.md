# 블로그 글 작성 규칙

`blog.1989v.com` 에 올리는 글의 문체·구조 기준. 검증은 `scripts/lint-blog-post.py` 가 한다.

## 1. 목적

블로그 글은 **정보 전달물**이지 에세이도 작업 일지도 아니다. 읽는 사람은 답을 찾으러 왔고, 대개
검색 결과에서 바로 들어와 필요한 줄만 보고 나간다. 스크롤 없이 답이 잡히는 밀도가 먼저다.

읽는 사람이 이미 아는 것을 설명하는 문장, 독자의 생각을 대신 서술하는 문장, 던졌다가 스스로 답하는
질문은 전부 답에 도달하는 시간을 늘린다.

## 1.1 무엇을 담고 무엇을 빼나 (필수)

**담는 것 — 그것이 무엇이고 어떻게 쓰는가.**

| 담는다 | 예 |
|---|---|
| 결과물의 동작 | 강조색은 페이지에서 가장 많이 쓰인 유채색이다 |
| 쓰는 법 | 코드 블록, 명령, 설정 |
| 규칙과 한계 | id 에 하이픈은 못 쓴다 |
| 주장을 받치는 실측값 | 대비 15/255, gzip 16.6 KB |

**빼는 것 — 어떻게 그렇게 됐는가.**

| 뺀다 | 왜 |
|---|---|
| 판올림 이력 (`0.3.2 에서는…`) | 릴리스 노트의 몫이다 |
| 시도와 실패 (`처음에는 …했는데 무너졌다`) | 커밋 메시지의 몫이다 |
| 의사결정 서술 (`…하기로 했다`, `고민 끝에`) | ADR 의 몫이다 |
| 작업 경위 (`재 봤다`, `검토했다`) | 옵시디언 작업 노트의 몫이다 |

옵시디언 노트를 그대로 옮기면 이 네 가지가 딸려 온다. **소개 글에 배경과 판단이 들어가면
독자는 기능을 알러 왔다가 남의 일지를 읽는다.**

설계 이유가 정보로서 필요할 때는 **결과 문장 뒤 한 줄**로 붙인다. 서사로 풀지 않는다.

- 나쁨: `첫 판은 링크 색을 봤다. 그게 무너져서 채도로 바꿨더니 장식 점이 이겼다. 그래서 사용량으로 골랐다.`
- 좋음: `강조색은 가장 많이 쓰인 유채색이다. 채도로 고르면 3px 장식 점이 페이지를 지배하는 색을 이긴다.`

## 2. 문체

**필수**

| 규칙 | 이유 |
|---|---|
| 한 문장 100자 이하 | 긴 문장은 조건이 여러 개 붙어 있다는 뜻이다. 쪼개면 표가 된다 |
| 한 문단 3문장 이하 (리드는 2문장) | 문단이 길면 스캔이 안 된다 |
| 산문에 물음표 금지 | 자문자답은 답을 한 박자 늦춘다. 질문은 h2 제목으로 |
| 1인칭·권유형 금지 | `필자` · `저는` · `살펴보자` · `정리해 보자` |
| 수사 도입어 금지 | `사실은` · `흥미롭게도` · `말하자면` · `한마디로` · `결론부터 말하면` |
| 독자의 생각 대신 서술 금지 | `먼저 떠오른다` · `헛짚기 쉽다` — 독자가 뭘 생각했는지는 알 수 없다 |
| 감상 표현 금지 | `놀랍게도` · `아쉽게도` · `다행히` |

**권장**

- 평균 문장 60자 이하.
- 값·조건·비교는 산문 대신 **표**로. 절차는 **번호 목록**으로.
- 산문 줄이 전체 내용 줄의 55% 를 넘으면 옮길 것이 남아 있다는 신호다.
- 단정형(`~다`)으로 끝낸다. 추측이면 `(추정)` 을 붙이고, 안 붙일 거면 쓰지 않는다.

## 3. 구조

1. **리드 2문장 이하** — 무엇을 다루는 글인지 + 기준 버전/시점.
2. **요약 표** — 결론을 먼저. 목차가 아니라 답을 담는다. **첫 h2 앞에 와야 한다(F8).**
3. **본문** — h2 하나가 하나의 답. 코드·표·목록이 골격이고 산문은 접착제다.
   **코드 이야기면 코드 블록을 낸다** — 설명 문단 세 개보다 여덟 줄짜리 블록이 빠르다.
   블록에는 언어를 표시한다(` ```ts `). `<pre><code>` 로 렌더되고 가로 스크롤이 걸린다.
4. **검증** — 재현 명령과 실측값. 안 재본 것은 쓰지 않는다.

버전·날짜에 의존하는 값은 **기준을 본문에 밝힌다** (`v2.1.241 기준`). frontmatter 의 날짜는 발행일이지
데이터 시점이 아니다.

## 4. 검증 (`scripts/lint-blog-post.py`)

발행 전 초안을 통과시킨다. **본문의 원본은 DB 라서 빌드가 잡을 수 없다** — DB 에 넣기 전 이 단계가
유일한 게이트다.

```bash
scripts/lint-blog-post.py draft.md            # FAIL 있으면 exit 1
scripts/lint-blog-post.py draft.md --strict   # WARN 도 실패로
```

| 코드 | 검사 |
|---|---|
| F1 | front-matter 4필드 + DB 컬럼 상한 (title 200 / slug 80 / summary 300) + slug 형식 |
| F2 | 한 문장 100자 이하 |
| F3 | 한 문단 3문장 이하 |
| F4 | 리드 문단 2문장 이하 |
| F5 | 산문에 물음표 없음 |
| F6 | 금칙 표현 없음 (§2 표) |
| F7 | 이력·의사결정 서술 없음 (§1.1 표) |
| F8 | 첫 h2 앞에 요약 표(또는 항목 2개 이상 목록) |
| W1 | 평균 문장 60자 이하 |
| W2 | 산문 줄 비율 55% 이하 |
| W3 | h2 구간당 산문 8문장 이하 |
| W4 | h2 구간마다 표·코드·목록 중 하나 (산문만 6줄 넘으면 경고) |

코드 블록 · 표 · 인용 · 목록은 산문에서 제외한다. 규칙은 산문에만 건다.
줄 첫머리가 태그인 **raw HTML 블록(다이어그램 SVG)도 제외**한다 — 빈 줄에서 끝난다.
그림 아래 캡션 줄은 산문이라 규칙이 그대로 걸린다 → `blog-diagram.md`.

## 5. 초안 형식

lint 가 읽는 front-matter 는 DB 컬럼과 1:1 이다. 그대로 `blog_post` 에 넣는다.

```markdown
---
title: Claude Code 세션에 시각과 남은 사용량 표시하기
slug: claude-code-session-timestamp-and-usage
category: /harness
summary: 한 화면에 결론이 담기는 두세 문장. 검색 결과의 설명문으로도 쓰인다.
---

본문 …
```

`category` 는 `blog_category.path` 다. 없는 path 를 쓰면 INSERT 가 FK 로 막힌다.

## 6. DB 에 넣을 때

한글은 **hex 로 넣는다.**

```sql
INSERT INTO blog_post (..., title, body) VALUES (..., CONVERT(0x<hex> USING utf8mb4), ...)
```

`oci-mysql` 경유 접속의 클라이언트 charset 이 latin1 이라, 한글을 리터럴로 넣으면 조용히
이중 인코딩된다 (2026-08-24 실제 발생). 값은 들어가고 에러도 없으며, 목록 API 응답에서야 깨져 보인다.
