# ADR-0068 — 첫 사용자 요청을 콜드스타트에 태우지 않는다

- 상태: 채택 (2026-08-12)
- 관련: ADR-0019(배포 모드), ADR-0025(Latency Budget), ADR-0061(엣지 하드닝)

## 맥락

어드민 화면이 "불러오는 중…" 에서 오래 머물거나, 갱신이 안 돼 페이지를 새로고침해야 하는
증상이 반복된다. 데이터량은 수십 건 수준이고 단순 read 라 느릴 이유가 없다.

원인을 두 층에서 확인했다.

### 서버 — Ready 인데 준비되지 않았다

`readinessProbe` 가 `/actuator/health/readiness` 만 본다. 이 엔드포인트는 **애플리케이션
상태만** 보고하고 DB 를 건드리지 않는다. 즉 **쿼리를 한 번도 실행해 보지 않은 채 Ready 가
되고**, 그 순간부터 트래픽이 들어온다.

그래서 첫 요청이 다음을 전부 뒤집어쓴다.

- Hibernate 의 쿼리 플랜 컴파일 (엔티티·쿼리마다 최초 1회)
- JIT 이 아직 인터프리터 구간인 코드 경로
- Hikari 가 `minimum-idle`(2) 을 넘어 커넥션을 새로 만드는 비용
- OpenSearch·Redis 클라이언트의 최초 연결

애플리케이션 시작 시 **워밍업이 전혀 없다.** `lazy-initialization` 은 꺼져 있으므로 빈 생성은
미리 끝나지만, 빈이 만들어졌다는 것과 쿼리 경로가 데워졌다는 것은 다른 이야기다.

무료 티어 단일 노드라 파드 재기동이 드물지 않고, 그때마다 이 비용을 사용자가 낸다.

### 클라이언트 — 느린 요청이 실패로도 바뀌지 않는다

`admin/frontend` 의 `apiClient` 에 **타임아웃이 없다**(axios 기본값은 무한). 그래서 요청이
늘어지면 스피너가 영원히 돌고, 사용자에게는 "멈춘 화면" 으로 보인다.

여기에 두 가지가 겹친다.

- 여러 페이지가 react-query 를 쓰지 않고 `useEffect` 로 직접 패칭한다 → 재시도·리페치 없음
- QueryClient 가 `refetchOnWindowFocus: false` → 탭을 다시 봐도 갱신되지 않음

**"새로고침해야 보인다" 는 증상이 정확히 이 조합이다.** 서버가 느린 것과 화면이 복구하지
못하는 것은 별개의 결함이고, 둘 다 고쳐야 한다.

## 결정

**Ready 는 "트래픽을 받을 준비" 를 뜻해야 한다.** 워밍업이 끝나기 전에는 Ready 가 되지 않게 한다.

1. **기동 워밍업** — `ApplicationReadyEvent` 를 **동기 리스너**로 받아 데이터소스마다 가벼운
   쿼리를 한 번 실행한다. 이 리스너가 끝나야 Boot 이 가용성 상태를 `ACCEPTING_TRAFFIC` 으로
   올리므로, 워밍업이 곧 readiness 게이트가 된다. 별도 상태 플래그를 만들 필요가 없다.
2. **범위는 좁게** — 커넥션 획득과 최소 1회 쿼리까지. "주요 엔드포인트 예열" 같은 것은 하지
   않는다. 무엇이 주요한지는 계속 바뀌고, 기동 시간만 늘어난다.
3. **실패해도 기동은 막지 않는다** — 워밍업 실패를 치명으로 다루면 DB 일시 장애가 배포 실패로
   번진다. 경고를 남기고 계속한다. 워밍업은 최적화이지 정합성 요건이 아니다.
4. **클라이언트도 고친다** — 어드민 `apiClient` 에 타임아웃을 두어 느린 요청이 **실패로
   드러나게** 한다. 화면은 실패 상태와 재시도 수단을 제공해 전체 새로고침 없이 복구되게 한다.

### 왜 probe 에 DB 체크를 붙이지 않는가

`readinessProbe` 가 DB 를 직접 확인하게 만드는 방법도 있다. 그러나 그러면 **DB 가 잠깐
흔들릴 때 멀쩡한 파드가 전부 트래픽에서 빠진다.** 단일 노드에서 이는 전면 장애로 직결된다.
워밍업은 기동 시 1회로 끝내고, 이후의 DB 상태는 애플리케이션이 처리하게 둔다.

## 결과

- 파드가 Ready 가 되는 시점이 조금 늦어진다 — 그만큼 첫 요청이 빨라진다. 배포 중 롤링 업데이트가
  느려지지만, 단일 노드에서는 오히려 동시 전환을 완만하게 만든다
- 어드민에서 느린 요청이 무한 스피너 대신 실패로 나타난다. 사용자가 원인을 알 수 있다
- 워밍업은 최적화라 실패해도 서비스가 뜬다 — 조용히 느려질 뿐이므로 로그를 남긴다

## 대안

- **lazy-initialization 을 켜서 기동을 빠르게** — 정반대 방향이다. 첫 요청 비용이 더 커진다
- **주기적 셀프 핑으로 항상 데워두기** — 무료 티어에서 CPU 를 상시 소모하고, 재기동 직후
  구간은 여전히 비어 있다
- **AOT/네이티브 이미지** — 콜드스타트를 근본적으로 줄이지만 빌드·운영 복잡도가 크게 는다.
  지금 문제는 첫 요청 한 번이라 비용 대비 효과가 맞지 않는다
