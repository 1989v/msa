# ADR-0089 — 비밀 게임은 카탈로그가 아니라 파일 앞에서 막는다

- 상태: 채택 (2026-09-05)
- 관련: ADR-0059(게임 플랫폼), ADR-0078(회원 식별 최소화), ADR-0079(단일 로그인 진입점),
  ADR-0064(이력서 게이트 — 같은 문제의 다른 답)

## 맥락

일부 게임은 **아무에게나 보이면 안 된다.** 첫 사례는 「깊은 밤」(복셀 샌드박스)으로,
벤치마크작과 너무 닮아 공개 카탈로그에 올릴 상태가 아니다. 원하는 것은 「없앤다」가 아니라
**「정해 준 계정만 들어간다」** 다.

가장 먼저 떠오르는 답 — 카탈로그에서 빼기(`status=DRAFT`) — 은 **막지 못한다.**
게임 파일은 카탈로그와 아무 상관 없이 portal-fe 의 nginx 가 정적으로 내준다:

```
GET /games/deep-night/Build/xxx.wasm.gz   →  nginx  →  200 (누구에게나)
```

카탈로그는 **목록에 뭘 싣느냐**만 정한다. 주소를 아는 사람은 그대로 받아 간다.
공개 레포에 슬러그가 남고, 산출물이 이미지에 들어가 있으므로 주소는 결국 알려진다.

### 이력서(ADR-0064)와 왜 답이 다른가

이력서는 **본문을 DB 로 옮겨** API 한 곳에서 게이트를 걸었다. 게임에는 그 수가 안 통한다 —
7MB 짜리 wasm·data 를 DB 에 넣을 수도, API 로 흘려보낼 수도 없다(게이트웨이가 정적 파일
서버가 된다). 막아야 하는 것이 **콘텐츠가 아니라 파일**이라 게이트를 파일 앞에 세워야 한다.

## 결정

**경로 앞에 관문을 세운다 — ingress `auth-url`.**

```
브라우저 ──/games/deep-night/*──▶ ingress-nginx
                                      │ (요청마다)
                                      ├─▶ gateway → game: /api/v1/games/private/{slug}/allow
                                      │            쿠키 검증 + 허용 명단 조회
                                      │            204 통과 / 401 로그인 / 403 거절
                                      ▼
                                   portal-fe (정적 파일)
```

- **허용 명단은 DB 표 한 장** — `game_private_access(game_slug, member_id, note)`.
  어드민 `/admin/games/private` 에서 넣고 뺀다. 사람을 늘리는 데 배포가 필요 없다.
- **관문만 쿠키를 직접 읽는다.** 다른 API 는 게이트웨이가 `Authorization` 헤더를 보고
  `X-User-Id` 를 붙여 주지만, 브라우저가 `.wasm` 을 받을 때는 헤더를 붙일 방법이 없다 —
  그 요청이 들고 오는 신원은 도메인 쿠키뿐이다(ADR-0079). 그래서 이 엔드포인트는
  게이트웨이 인증 필터를 안 거치고 `portal_access_token` 을 스스로 검증한다.
- **카탈로그에는 넣지 않는다.** 넣으면 목록·검색·사이트맵·프리렌더에 다 나타난다.
  카탈로그 행이 없어도 파일은 서빙되므로, 관문이 있으면 그것으로 충분하다.

## 지켜야 할 것

- **게임마다 Ingress 를 따로 만든다.** 인증 애너테이션은 Ingress 단위라 경로마다 다르게
  걸 수 없다. 한 Ingress 에 두 게임을 담으면 관문이 **한 슬러그만** 물어보게 되어
  다른 게임이 무료 통과한다.
- **robots.txt 에 적지 않는다.** robots.txt 는 공개 파일이라 거기 경로를 쓰면
  **비밀 주소를 광고하는 것**이 된다. 관문이 이미 막고 있어 색인될 것도 없고,
  헤더(`X-Robots-Tag: noindex`)는 ingress 가 붙인다.
- **명단이 비면 아무도 못 들어간다** — 그것이 안전한 기본값이다. 화면도 그렇게 알린다.
- **회원 번호로 식별한다.** 이 플랫폼은 소셜에서 이메일·실명을 받지 않으므로(ADR-0078)
  사람을 가리킬 수 있는 것이 번호뿐이다. 누구인지는 `note` 에 사람 말로 적는다.
- **관문이 죽으면 게임이 막힌다** — 열리는 게 아니라. `auth-url` 이 응답하지 않으면
  ingress 는 500 을 낸다. 공개 게임에는 이 애너테이션을 붙이지 않는 이유가 그것이다.

## 대안과 기각 이유

| 대안 | 왜 안 했나 |
|---|---|
| 카탈로그에서만 빼기 | 주소를 알면 그대로 열린다. 「비밀」이 되지 않는다 |
| 서명된 URL (`secure_link`) | 링크가 곧 열쇠라 한 번 새면 회수할 수 없다. 계정 단위로 끊을 수 없다 |
| 게임 파일을 서빙 이미지에서 제외 | 가장 확실하지만 아무에게도 못 보여 준다 — 목적이 「일부에게 보여 주기」다 |
| 게임 안에서 비밀번호 확인 | 파일은 이미 내려간 뒤다. 클라이언트가 확인하는 것은 확인이 아니다 |
| portal-fe nginx 에 `auth_request` | FE 파드가 게이트웨이를 직접 알게 된다. 라우팅은 ingress 의 일이다 |

## 검증

- `PrivateGameGateControllerTest` — 쿠키 없음 401 · 위조 토큰 401 · 명단 밖 403 ·
  명단 안 204 · 게스트(숫자 아닌 주체) 401. 토큰은 같은 `JwtUtil` 로 실제 발급해 쓴다
  (문자열을 지어내면 서명 검증을 지워도 초록불이 난다).
- 배포 뒤 확인할 것: 로그아웃 상태에서 `/games/deep-night/index.html` 이 로그인으로 튕기는가,
  로그인했지만 명단 밖인 계정이 **wasm 까지** 403 인가 (index.html 만 막고 하위 파일이
  새면 게이트가 없는 것과 같다).

## 남은 구멍 — 릴레이 방

이 관문은 **정적 파일 경로**에만 걸린다. `deep-night` 에 같이 하기(ADR-0088 릴레이)가
붙으면서 `/ws/games/deep-night` 도 쓰는데, 그 라우트(`game-relay-ws`)는 게스트 통과라
**허용 명단이 걸리지 않는다.**

지금 실질 위험이 낮은 이유는 두 가지다 — ① 방은 코드로만 만난다(빠른 매칭을 안 쓴다)
② 코드가 32글자 6자리라 약 10억 가지다. 그래도 **코드를 아는 사람은 명단에 없어도
방에 들어올 수 있다**는 사실은 그대로다. 막으려면 릴레이 핸들러가 join 때 슬러그를 보고
같은 명단을 물어야 하는데, 그러면 권위 없는 릴레이가 게임별 정책을 알게 된다 —
넣는다면 「슬러그가 비밀 게임인가」만 묻는 얇은 훅이어야 한다. 지금은 안 넣었다.
