# ADR-0085: 유니티 웹게임을 챕터로 쪼갠다 — 단, 쪼개지는 건 절반뿐이다

<!-- source: docs/standards/unity-game-pipeline.md, portal-fe/nginx.conf, portal-fe/public/games/_src/archer-outbreak/Assets/Scripts/Sim/Progress.cs -->

- 상태: 제안
- 날짜: 2026-08-31
- 관련: ADR-0059(게임 플랫폼), `docs/standards/unity-game-pipeline.md` §6.1(실측 기준선)

## 맥락

「궁수 키우기보다 큰 유니티 웹게임」을 만들 때 무엇이 먼저 막히는지를 **재고 나서** 정한다.
배포본을 헤드리스 크롬 + CDP 로 직접 측정했다 (2026-08-31, 390×844 모바일, 캐시 없음).

| 항목 | 예산 | 실측 |
|---|---|---|
| 전송량(압축 후) | ≤ 15MB | 7.84MB |
| 첫 화면 | ≤ 5초 | **5.66초 — 초과** |
| wasm 선형 메모리 | 크래시 없음 | 38.4MB / 상한 2048MB |

**메모리는 병목이 아니다.** 38.4MB 는 설정 상한의 1.9% 이고 40초 동안 한 번도 안 늘었다.
막는 것은 **전송량과 첫 프레임** 둘뿐이다.

## 결정

**챕터 단위로 콘텐츠를 쪼개고, 챕터 진입 시 그 챕터 것만 받는다.** 다만 **이것이 줄이는 것은
전송량의 절반 이하**라는 사실을 함께 못박는다.

### 왜 절반뿐인가 — 이 ADR 의 핵심

실측 내역이 그대로 답이다.

| 파일 | 와이어 | 성격 | 챕터로 쪼개지나 |
|---|---|---|---|
| `.wasm.gz` | **5.38MB (69%)** | IL2CPP 가 만든 **코드 단일 모듈** | **안 된다** |
| `.data.gz` | 2.37MB (30%) | 씬·에셋 | 된다 |
| `.framework.js.gz` + `.loader.js` | 0.10MB | 런타임 글루 | 안 된다 |

전송량의 **69% 가 코드**다. IL2CPP WebGL 산출물은 모듈 하나라 챕터별로 나눌 수 없고,
챕터를 몇 개로 쪼개든 **5.48MB 는 매번 먼저 내려간다.**

그래서 기대치는 이렇게 잡는다 — 첫 진입 **7.84MB → 5.8~6.1MB**
(고정 5.48MB + 에셋 2.37MB 를 4~8 챕터로 나눈 한 몫). 전송량으로 20~25% 다.

**첫 프레임은 그만큼도 안 준다.** 5.66초 중 `unityInstance` 준비까지가 3.65초인데
이건 wasm 내려받기·컴파일·초기화이고 챕터 분할이 손대지 못하는 구간이다.
줄어드는 것은 에셋 다운로드분뿐이라 **5초 예산을 이걸로 넘길 수 있다고 보면 안 된다.**

이 구조의 값은 다른 데 있다 — **콘텐츠를 10배로 늘려도 첫 진입이 그대로**인 것.
지금 것을 빠르게 만드는 수단이 아니다.

> [!warning] 챕터 분할로 풀리지 않는 것
> 코드가 커지면(적 종류·시스템 추가) `.wasm` 이 커지고, 그건 **모든 챕터가 부담한다.**
> 첫 프레임을 진짜로 줄이려면 코드를 줄이거나(스트리핑·기능 축소) Brotli 를 붙여야 한다.
> Brotli 는 지금 nginx 에 없고, wasm 에서 gzip 대비 통상 15~20% 를 더 깎는다.

### 무엇을 챕터로 보나

**챕터 = 에셋 경계이자 저장 경계**다. 지도 한 판·적 세트·BGM 이 한 묶음으로 움직이는 단위.
챕터를 넘을 때만 새로 받고, 챕터 안에서는 네트워크를 타지 않는다.

### 전달 경로 — AssetBundle 직접, 같은 오리진

**Addressables 를 쓰지 않는다.** 번들이 셋이고 주소를 우리가 이미 정하고 있어서
(해시 파일명 + `immutable` 은 nginx 가 이미 한다) 카탈로그 계층이 하는 일이 없다.
`com.unity.modules.assetbundle` 과 `...unitywebrequestassetbundle` 은 매니페스트에 이미 있다.

호스팅은 **지금의 nginx 그대로**다.

- `.gz` MIME·`Content-Encoding`·`immutable` 규칙이 `portal-fe/nginx.conf` 에 이미 있고,
  챕터 번들도 같은 규칙에 태우면 된다
- 앞에 Cloudflare 가 있어 오리진 대역폭은 이미 방어된다. **OCI 무료 범위를 벗어나지 않는다**
- R2 같은 별도 스토리지는 **CF 캐시 적중률이 나쁘다고 측정된 뒤에** 꺼낸다.
  지금 옮기면 근거 없는 이동이고, 오리진이 둘로 갈려 캐시 규칙도 두 벌이 된다

### 세이브 정책 — 여기가 진짜 위험

「챕터를 계속 업데이트해 지속적으로 플레이」가 목적인데, 지금 로직은 정반대다.

```csharp
return v != null && v.version == RunSave.Version ? v : null;   // Progress.cs:638
```

**버전이 다르면 버린다.** 챕터를 낼 때마다 `Version` 을 올리면 **진행 중인 런이 전부 죽는다.**
업데이트가 잦을수록 더 죽으므로, 목적과 정면으로 충돌한다.

답은 이미 같은 파일에 있다.

```csharp
public float wallHp = -1f;     // -1 은 "저장에 없음" — 0(무너짐)과 갈라야 한다
public float roadDoorK = -1f;  // -1 은 문짝이 없던 시절의 저장
```

**필드 추가는 필드 기본값이 흡수한다.** 그러니 규칙을 이렇게 가른다.

| 변화 | `Version` | 이유 |
|---|---|---|
| 챕터 추가, 필드 추가 | **올리지 않는다** | 기본값으로 흡수된다. 진행 중 런이 살아야 한다 |
| 기존 필드의 **의미**가 바뀜 (좌표계·구역 번호) | **올린다** | 이어 붙이면 엉뚱한 자리에서 시작한다 — v1→v2 가 실제로 그랬다 |

즉 **`Version` 은 「지도가 달라졌다」는 신호로만 쓴다.** 챕터 추가에 올리면 안 된다.

## 결과

- 첫 진입 전송량이 콘텐츠 총량과 분리된다 — **콘텐츠를 늘려도 첫 진입이 안 늘어난다**
- 대신 **챕터 경계에서 로딩이 생긴다.** 젤다식 무경계 오픈월드와 갈리는 지점이고,
  이걸 감추려 하지 말고 챕터 전환을 연출로 쓴다
- 코드(`.wasm`)가 여전히 전송량의 대부분이라 **기능을 늘리면 전 챕터가 무거워진다.**
  기능 추가는 챕터 추가보다 비싸다는 뜻이고, 이 비대칭을 설계 입력으로 삼는다
- 파일럿은 **새 유니티 프로젝트에서** 한다 (`nine-bells`). 궁수 키우기에 챕터 로딩을
  끼워 넣으면 이미 도는 게임의 로딩 경로를 갈아엎게 된다

## 대안

| 안 | 왜 안 골랐나 |
|---|---|
| 무경계 오픈월드 (젤다식) | 코드 5.4MB 가 고정이고 에셋은 무한히 는다. 첫 프레임 예산이 곧 깨진다 |
| 전부 한 번에 받기 (지금) | 콘텐츠 총량이 첫 진입 비용이다. 확장할수록 이탈이 는다 |
| 챕터별 **빌드** 분리 | wasm·framework 를 챕터 수만큼 중복 전송한다. 5.48MB × N — 더 나쁘다 |
| R2 등 별도 스토리지로 즉시 이전 | CF 캐시 적중률을 재 보지도 않고 오리진을 둘로 가른다 |
| Addressables | 번들 셋에 카탈로그·프로파일·빌드 파이프라인이 붙는다. 주소는 우리가 이미 정하고 있다 |
