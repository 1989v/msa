# ADR-0101 — 토큰을 HttpOnly 쿠키로: 서버가 내리고 게이트웨이가 읽는다

- 상태: 채택 (2026-09-26)
- 관련: ADR-0079(로그인은 apex 한 곳 · 도메인 쿠키 — 이 결정이 그 §1 의 「httpOnly 는 별도 결정」이다),
  ADR-0078(식별 최소화), ADR-0061(엣지 노출면)

## 맥락

ADR-0079 는 토큰을 `.1989v.com` 도메인 쿠키로 옮기면서 **JS 가 쓰고 읽게** 두었다.
전송을 `Authorization` 헤더로 해 CSRF 표면을 만들지 않으려는 선택이었고, XSS 노출은 `localStorage` 와 같다고 적었다.

같다는 것이 문제다. 페이지에 스크립트 하나만 끼어들면 **액세스 토큰과 30일짜리 리프레시 토큰을 그대로 가져간다.**
리프레시 토큰은 회전하지만 가져간 쪽이 먼저 쓰면 정상 사용자가 밀려난다. 이 사이트는 사용자 글(블로그 · 댓글)과
여러 게임의 인라인 스크립트, 서드파티 로더(AdSense · GA)를 같은 오리진에 싣는다 — XSS 한 번의 값이 크다.

함께 발견된 것: OAuth `state` 가 제공자 이름(`kakao` · `google`) 고정값이라 **로그인 CSRF** 를 막지 못한다.
공격자가 자기 인가 코드로 만든 콜백 링크를 밟게 하면 피해자가 공격자 계정으로 로그인된다.

## 결정

### 1) 토큰은 서버가 HttpOnly 쿠키로 내린다

auth 의 로그인 · 갱신 응답이 본문 대신 `Set-Cookie` 로 토큰을 싣는다. **응답 본문에 토큰을 두지 않는다** — 두면 JS 가 읽을 수 있다.

| 쿠키 | 속성 | 뜻 |
|---|---|---|
| `portal_access_token` | HttpOnly · Secure · SameSite=Lax · Path=/ · Domain=.1989v.com | 게이트웨이가 읽는다 |
| `portal_refresh_token` | HttpOnly · Secure · SameSite=Lax · **Path=/api/auth** · Domain=.1989v.com | 갱신 · 로그아웃에만 실린다 |
| `portal_user_id` | Secure · SameSite=Lax · Path=/ · Domain=.1989v.com (**HttpOnly 아님**) | 「로그인했다」는 표시. 비밀이 아니다 |

수명은 셋 다 리프레시 토큰과 같다(30일). 로그아웃은 서버가 세 쿠키를 `Max-Age=0` 으로 지운다 — HttpOnly 는 JS 가 못 지운다.
`Domain` 과 `Secure` 는 설정값이다(로컬 http · host-only 에서 로그인이 조용히 막히지 않게).

### 2) 게이트웨이는 헤더가 없으면 쿠키에서 읽는다

`Authorization` 헤더가 있으면 지금처럼 그것을 쓴다(서버 간 호출 · 도구). 없으면 `portal_access_token` 쿠키를 쓴다.

**쿠키로 인증된 쓰기 요청(POST · PUT · PATCH · DELETE)은 `Origin`(없으면 `Referer`)이 우리 도메인일 때만 받는다.**
쿠키는 자동으로 실리므로 CSRF 방어가 새로 필요하다. SameSite=Lax 가 다른 사이트의 POST 에 쿠키를 싣지 않지만,
이것만 믿지 않고 게이트웨이에서 출처를 한 번 더 본다. 인증 필수 경로는 403, 게스트 허용 경로는 익명으로 통과시킨다.

### 3) FE 는 토큰을 모른다

- API 호출은 같은 오리진 상대 경로라 쿠키가 저절로 실린다. `Authorization` 을 만들지 않는다.
- 로그인 여부는 `portal_user_id` 표시 쿠키로 본다. 401 이면 `/api/auth/refresh` 를 부르고(쿠키가 실린다) 재시도한다.
- 게임 공용 `lib/auth.js` 는 `GameAuth.signedIn()` 을 내고, `token()` 은 늘 `null` 이다(고치지 못한 게임은 게스트로 떨어질 뿐 깨지지 않는다).

### 4) OAuth `state` 는 매번 새 난수

로그인 시작 때 `<provider>.<난수>` 를 만들어 `sessionStorage` 에 두고, 콜백에서 같은지 본 뒤 지운다.
다르거나 없으면 코드 교환을 하지 않는다. 로그인은 apex 한 곳이라(ADR-0079) 시작과 콜백이 같은 오리진이다.

### 5) 이미 로그인한 사람은 끊지 않는다

옛 세션의 쿠키는 JS 가 쓴 것이라 HttpOnly 가 아니다. 게이트웨이는 이름만 보므로 그대로 인증된다.
새 FE 는 읽을 수 있는 옛 리프레시 토큰이 보이면 한 번 갱신을 불러 서버가 HttpOnly 쿠키로 바꿔 끼우게 하고,
옛 쿠키를 지운다. 사용자에게는 아무 일도 일어나지 않는다.

## 대안

- **토큰을 그대로 두고 CSP 만 조인다** — 게임 인라인 스크립트 · 서드파티 로더 때문에 `unsafe-inline` 을 못 뺀다. 방어가 되지 않는다.
- **BFF 세션(서버 세션 id 만 쿠키)** — 게이트웨이 앞에 세션 저장소가 하나 더 생긴다. 이미 있는 JWT · Redis 블랙리스트로 충분하다.
- **CSRF 토큰(더블 서브밋)** — FE 와 게임 25개가 모두 헤더를 붙여야 한다. 출처 확인이 같은 목적을 FE 변경 없이 이룬다.

## 결과

- XSS 가 토큰을 가져가지 못한다. 할 수 있는 것은 그 페이지가 떠 있는 동안 그 사용자로 요청하는 것뿐이다.
- 게이트웨이가 인증 경계에서 출처를 본다 — 우리 도메인이 아닌 곳에서 쿠키로 쓰기 요청을 보내면 막힌다.
- 서버 간 호출과 도구는 지금처럼 헤더를 쓴다.
- 로컬 개발은 `auth.cookie.domain` 을 비우고 `auth.cookie.secure=false` 로 host-only · http 쿠키를 쓴다.
