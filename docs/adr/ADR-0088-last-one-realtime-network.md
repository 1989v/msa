# ADR-0088: 마지막 한 사람(last-one) 실시간 20인 네트워크 — 호스트 권위 + 릴레이 N석

- 상태: Accepted (2026-09-02)
- 관련: PRD `docs/specs/2026-09-02-last-one-prd.md` §6 · 릴레이 ADR-0059 · frost-outpost 협동(host authority 선례)

## 결정

**A. 호스트 권위(host authority)로 간다.** 좌석 중 가장 낮은 번호의 사람이 시뮬레이션
전체(20인 + 봇)를 돌리고, 10Hz 스냅샷을 릴레이로 뿌린다. 나머지 사람은 **의도(intent)만**
20Hz 로 호스트에게 보낸다. 릴레이는 규칙을 계속 모른다 — 기존 무권위 원칙(ADR-0059) 그대로.

릴레이는 2석 고정에서 **N석(상한 20)** 으로 넓힌다. 서버가 새로 아는 것은 좌석 수와
로비 마감(30초)뿐이고, 게임 규칙·봇 충원·승계는 전부 클라이언트가 한다.

## 후보 판정 (PRD §6 의 표를 재결)

| 후보 | 판정 | 근거 |
|---|---|---|
| A. 호스트 권위 | **채택** | 서버 비용 0 증가(릴레이 확장뿐). frost-outpost 가 같은 구조(좌석 0 시뮬 + 10Hz 스냅샷 + 의도 전송 + 승계)를 이미 검증했다 — 이 게임은 그것의 20석 판이다 |
| B. 결정론 락스텝 | 탈락 | 20명 중 한 명의 지연이 전원의 입력 지연이 된다. 모바일 웹 20인에서 성립하지 않는다 |
| C. 서버 권위 | 탈락 | 무료 티어(4 OCPU 단일 노드)에서 동시 2~3판이 상한이고, C# 규칙의 JVM 이중 구현이 생긴다. 치팅 방어의 실익은 게스트 랭킹이 없어 작다(PRD §9) |

## 판정 기준 세 가지 (PRD §6 이 ADR 에 요구한 것)

### ① 대역 — 노드 하나에서 몇 판인가

PRD 의 추산(20 × 19 × 10Hz × 600B ≈ 2.3MB/s/판)은 **전원이 전원에게 뿌리는 모델**의
값이다. 호스트 권위에서는 흐름이 비대칭이라 훨씬 싸다:

| 흐름 | 빈도 · 크기 | 판당(최악: 사람 20) |
|---|---|---|
| 호스트 → 릴레이 스냅샷 | 10Hz × ≤2KB (양자화 JSON, 상한 4KB 는 `SnapGate` 가 잰다) | 20KB/s 인바운드 |
| 릴레이 → 게스트 19 팬아웃 | 10Hz × ≤2KB × 19 | 380KB/s 아웃바운드 |
| 게스트 19 → 릴레이 의도 | 20Hz × ~120B × 19 | 46KB/s 인바운드 |
| 릴레이 → 호스트 의도 (**`to` 지정 전달**) | 위와 동일 | 46KB/s 아웃바운드 |

최악 판 하나 = 아웃바운드 **~430KB/s (≈3.4Mbit/s)**. 현실 판(사람 1~3, 나머지 봇)은
스냅샷 팬아웃이 사람 수-1 에 비례해 **판당 수십 KB/s** 다. 사람 1 이면 릴레이를 아예
안 탄다(오프라인 판). 릴레이는 문자열 전달만 하므로 CPU 는 방 수보다 팬아웃 횟수에
비례하고, 기존 방 상한(200)과 좌석 상한(20)이 곧 상한이다 — **대역이 아니라 사람 수가
동시 판 수를 정한다.** 의도를 방 전체에 뿌리면 판당 아웃바운드가 +870KB/s 로 3배가
되므로, `move` 에 **`to`(좌석 지정 전달)** 를 추가해 의도는 호스트에게만 보낸다.

### ② 호스트 승계가 2초 안에 되는가

- **명시 이탈**(탭 닫기·leave): 릴레이가 즉시 `left`(좌석 번호)를 방에 뿌린다. 남은
  사람 중 가장 낮은 좌석이 마지막 스냅샷에서 시뮬을 이어받는다 — 전파 지연(~100ms)뿐.
- **무언 이탈**(전파 끊김): 릴레이의 유휴 정리는 60~90초라 승계 신호로 못 쓴다. 대신
  **스냅샷 자체가 심장박동**이다 — 스냅샷이 2.5초 끊기면 생존 좌석 순위 k 가
  `2.5s + 0.5s×k` 에 승계를 선언(스냅샷 송신 시작)한다. 순위가 시간을 가르므로 둘이
  동시에 선언하지 않고, 늦게 온 옛 호스트의 스냅샷은 좌석 번호가 높으면 무시한다.
- 판정: 명시 이탈 ≤ 0.5초 · 무언 이탈 ≤ 3.0초(최초 생존자 기준). **2초 기준은 명시
  이탈에만 걸고, 무언 이탈은 3초를 허용한다** — 끊김 감지 자체에 2.5초를 쓰기 때문이며,
  그보다 좁히면 모바일 백그라운드 전환(탭 스위치)마다 승계가 오발한다.

### ③ 모바일 WebGL 이 20체를 버티는가

아홉 종 실측(같은 지도·같은 킷, 15체 상한): 소프트웨어 렌더러에서 세로 51.8fps.
20체는 +5체·+33% 개체이고 스냅샷 수신·예측 비용이 더해진다. **이 판정은 계산으로
못 내린다** — last-one 의 완성 게이트(실기 ≥45fps, PRD §7)가 그대로 잰다. 안 되면
인원을 16 으로 줄인다(PRD §9 — 인원은 조정 가능한 숫자, 원칙이 아니다).

## 릴레이 프로토콜 변경 (`/ws/games/{slug}`)

방의 좌석 수는 **방을 만드는 join 이 정한다** (`seats`, 2~20, 생략 시 2). 기존 2인
게임(echo-duel·sketch-sleuth·frost-outpost)은 보내지 않으므로 그대로 2석이다.

| 방향 | 추가/변경 | 내용 |
|---|---|---|
| C→S | `join` 에 `seats` | 방 생성 시에만 반영. 이후 join 의 값은 무시 |
| C→S | `move` 에 `to` (선택) | 지정 좌석에게만 전달. 없으면 기존대로 방 전체(발신자 제외) |
| S→C | `joined` 에 `seats` | 방의 좌석 수를 알려 준다 |
| S→C | `seat` (신규, 3석 이상 방) | 로비에서 누가 들어왔나 — `{"t":"seat","seat":k,"nick":"…"}` |
| S→C | `start` 의 `players` | 좌석 수만큼의 배열. 빈 좌석은 빈 문자열 — **호스트가 봇으로 채운다** |
| S→C | `left` (신규, 3석 이상 방) | `{"t":"left","seat":k}`. 2석 방은 기존 `opponentLeft` 유지 |
| S | 로비 마감 | 3석 이상 방은 **생성 30초 뒤 인원 무관 강제 시작**(1초 틱). 가득 차면 즉시 |
| S | 시작 후 잠금 | `start` 이후의 join 은 `ROOM_STARTED` — 판 중간 충원은 없다(PRD §3 죽음) |
| S | 메시지 상한 | 20 → **40 msg/s** (의도 20Hz + 이모트·핑 여유. 스냅샷 10Hz 는 그 안) |

## 안 하는 것

- **Redis/브로커**: 호스트 1 레플리카 전제 그대로 (ADR-0059 의 in-memory 근거 불변)
- **서버 측 봇**: 봇은 호스트 클라이언트의 시뮬 안에 산다. 서버가 봇을 알면 규칙을 알게 된다
- **재입장·중간 충원**: 죽은 사람의 값을 지키는 규칙(PRD §3)이자 프로토콜 단순화
- **치팅 방어**: 게스트 랭킹이 없어 이득이 작다. 랭킹 등록이 로그인 전용이 되는 시점에
  판 기록 재생 검증을 후보로 다시 본다 (PRD §9)

## 결과

- `GameRelayRegistry` — 좌석 배열 N, 로비 마감 틱, `to` 전달, 시작 잠금 (이 커밋)
- 게임 클라이언트 — `KgdRelay`(패키지, WebSocket .jslib) + last-one 호스트/게스트 시뮬
- 수치 검증 — `NetGate`: 스냅샷 ≤4KB · 의도 ≤200B · 승계 시간(위 ②) · 실기 fps(위 ③)
