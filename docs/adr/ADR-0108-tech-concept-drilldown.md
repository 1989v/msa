# ADR-0108 — tech 드릴다운: 온톨로지가 그리는 다이어그램

- 상태: 채택 (2026-10-12), 개정 (2026-10-12 — 추천 도메인 추가 · 단계 중첩)
- 관련: ADR-0100(개념 온톨로지 원본), ADR-0062(SEO · 프리렌더)
- 스펙: `docs/specs/2026-10-12-tech-concept-drilldown/spec.md`
- 샘플: 아티팩트 「검색 아키텍처 드릴다운」 v4 (화면 구조 승인본)

## 맥락

`/tech/search` 는 레포 마크다운 한 편(구조 · 흐름 · 기법 표)을 빌드 때 렌더한 문서다. 서비스 설명이 먼저 나오고
검색의 일반 개념은 표의 한 열이라, 검색을 모르는 사람이 읽을 이유가 없다. 같은 방식으로 다른 도메인을 늘리면
도메인마다 문서와 그림을 손으로 다시 쓴다.

개념 온톨로지(ADR-0100)에는 이미 검색 개념 490개가 유형(`kind`) · 포함(`contains`) · 흐름(`flows_to`) · 코드 위치
(`code: path + symbol`)와 함께 들어 있다. 없는 것은 「이 서비스가 그 개념을 지금 쓰는가, 어떤 값으로」뿐이다.

## 결정

1. **그림은 온톨로지 데이터에서 규칙으로 만든다.** 화면 쪽에 노드 · 좌표 · 간선 · 설명을 적지 않는다.

   | 규칙 | 내용 |
   |---|---|
   | R1 노드 | 개념 X 의 그림 = X 의 `contains` 자식 중 `STAGE` 이거나 `flows_to` 로 이어진 것. 나머지 자식은 그림 아래 「관련 개념」 목록 |
   | R2 간선 | 같은 그림 안 자식끼리의 `flows_to`. 간선 글자는 관계의 `label` |
   | R3 병렬 묶음 | 흐름 노드의 자식 중 `STAGE` 가 둘 이상이고 자식 사이에 흐름이 하나도 없으면, 그 노드를 묶음 틀로 그리고 `STAGE` 자식을 나란히 펼친다 |
   | R4 [상세보기] | 자식이 있는 노드. 누르면 그 노드의 그림(R1)이 아래에 열린다. 깊이 3단계까지 |
   | R5 배치 | 좌표를 저장하지 않는다. 흐름 순서로 열을 정하는 자동 배치, 좁은 화면은 세로 |

2. **온톨로지에 「적용 상태」를 더한다.** 개념에 선택 필드 `applied` 를 둔다 —
   `status`(LIVE · PARTIAL · DISABLED · NONE), `summary`(이 서비스가 하는 일), `facts`(이름 · 값 쌍, 코드 대조용 `key` 선택).
   일반 개념 설명(`description`)과 서비스 상태를 한 개념에 두되 필드로 가른다. `flows_to` 관계에는 선택 키 `label` 을 더한다.
   드릴다운에 그려지는 개념은 `applied.status` 가 있어야 한다 — 없는 단계를 빼고 그리면 읽는 사람은 있다고 가정한다.

3. **검색 도메인의 흐름을 업계 기준 파이프라인으로 재구성한다.** `search-query` 의 흐름:
   사용자 검색 → 쿼리 리포뮬레이션 → 쿼리 언더스탠딩 · 쿼리 임베딩 → 후보 생성(스파스 · 덴스, R3) → 융합 → 리랭킹 · 후처리 →
   0건 대응 → 결과 구성. 리포뮬레이션 · 0건 대응은 쿼리 언더스탠딩 아래 장치에서 단계로 올린다. `/tech` 아틀라스도 같은
   원본을 쓰므로 함께 바뀐다.

4. **화면 데이터는 내보낸 파일이다.** portal-fe 이미지 빌드는 온톨로지 디렉토리를 못 본다(아틀라스와 같은 사정). Kotlin
   스펙이 YAML 을 부팅 로더와 같은 리더로 읽어 `portal-fe/src/content/drill/<domain>.json` 을 만들고,
   커밋된 파일과 다르면 실패한다. 코드 스니펫은 내보낼 때 `symbol` 이 처음 나오는 줄부터 잘라 싣는다.
   GitHub 링크는 FE 빌드가 그 빌드의 커밋(`GIT_SHA`)으로 고정한다 — 스니펫과 링크가 같은 코드를 가리킨다.

5. **값 대조는 온톨로지로 옮긴다.** 기존 마크다운 표가 하던 드리프트 대조(RRF 상수 · 가중치 · 모델 ref · HNSW 등)는
   `applied.facts[].key` 를 코드 · 매니페스트 값과 대조하는 테스트가 맡는다. 마크다운 원본과 그 렌더 단계는 걷어낸다.

6. **내부 결정 문서 번호는 화면에 내지 않는다.** 온톨로지의 `evidence`(ADR 등)는 개념 사전용으로 남기고 드릴다운은 싣지 않는다.

7. **게시 위치.** 메인은 `/tech` 아틀라스 첫 화면 본문에 진입 카드(IT 타일의 하위). 이력서는 운영 DB 의 검색 프로젝트
   항목에 절대주소 링크 한 줄 — 레포가 아니라 운영 데이터라 문안을 승인받고 어드민 API 로 넣는다.

## 기각

- **페이지별 뷰 파일(노드 · 좌표 · 설명을 화면 쪽에)** — 샘플이 이 방식이었다. 온톨로지와 두 원본이 되어 한쪽만 고치면 어긋난다.
- **실행 중 API 로 그리기** — 정적 페이지에 백엔드 왕복이 생기고 프리렌더가 본문을 못 담는다.
- **온톨로지에서 mermaid 텍스트 생성** — 노드 클릭 · 상태 표시 · 병렬 묶음을 표현할 수 없다.
- **스니펫을 브라우저가 `main` 에서 가져오기(아틀라스 방식)** — 링크가 움직이는 브랜치를 가리켜 시간이 지나면 다른 코드를 보인다.
- **상태를 별도 파일에** — 개념이 옮겨지거나 이름이 바뀔 때 키가 끊긴다. 원본을 하나로 둔다.

## 개정 (2026-10-12) — 추천 도메인 · 단계 중첩

8. **펼친 단계는 앞 단계 안에 품는다.** 단계를 형제로 늘어놓으면 1단계 탭 바로 뒤에 2단계 머리가 붙어, 모바일에서
   어디까지가 어느 단계인지 안 보였다. 다음 단계는 앞 단계 카드 안(탭 뒤)에 들여 넣고 왼쪽 띠로 잇는다. 머리는
   면(띠)과 단계 번호 배지로 가른다.
9. **그림이 없는 이유를 화면이 말한다.** 하위 개념이 없는 개념은 「더 나뉘는 하위 단계가 없다」, 하위 개념끼리 흐름이
   없으면(노드 0개) 그림 대신 「하위 개념」 목록, 펼침 한계(3단계)에 닿으면 그 사실을 적는다. 한계 값은 내보내기가
   `maxDepth` 로 함께 낸다 — 화면에 숫자를 다시 적지 않는다.
10. **좁은 화면의 한 행이 폭을 넘으면 여러 줄로 접는다.** 세로 배치에서 같은 단계 노드가 많으면(추천 후보 원천 다섯)
    그림 상자 안 가로 스크롤이 생겼다. 접힌 줄을 지나는 간선은 사이 상자를 비켜 돌고, 그 글자는 출발 상자 밑에 둔다.
11. **도메인 목록은 한 곳이다.** `portal-fe/src/pages/tech/drillPages.mjs` 의 `DRILL_PAGES` 를 라우트 · GNB · 아틀라스 카드 ·
    렌더 · 프리렌더 · sitemap · llms.txt 가 돈다. 화면은 `TechDrillPage` 하나이고 도메인 페이지는 데이터만 묶는 얇은 파일이다
    (도메인마다 청크를 나눈다). 도메인 추가 = `DrillExportSpec.DRILLS` 한 줄 + `DRILL_PAGES` 한 줄 + `PORTAL_PAGES` 한 줄 +
    얇은 페이지 파일 + 라우트 한 줄, 그리고 그 도메인 YAML 의 `flows_to` · `applied`. 대조 키를 달면 그 도메인의 드리프트 테스트도.
12. **추천의 적용 상태는 운영에서 확인한 대로 적는다.** 2026-10-12 운영 확인: ClickHouse 에 추천 행동 테이블이 없고, Redis 에
    `reco:*` 키가 0개, ANN 사이드카 모델 볼륨이 비어 `degraded`, 동기화 · 재학습 스케줄은 배포 목록에 없다. 그래서 대부분 단계가
    「비활성」(구현돼 있으나 운영에서 결과를 내지 않음)이다. 상태를 실제보다 좋게 적으면 이 페이지의 「현재 적용 상태」가 거짓이 된다.

## 결과

새 도메인 드릴다운은 화면 코드 없이(얇은 페이지 파일 하나) 그 도메인 YAML 에 `flows_to` 와 `applied` 를 채우고 다시 내보내면 생긴다.
대가는 온톨로지가 「일반 개념」과 「이 서비스의 상태」를 함께 갖게 된 것 — 서비스 코드가 바뀌면 `applied` 도 낡을 수 있고,
대조 키가 있는 값만 테스트가 잡는다. 서술(`summary`)은 사람이 고친다.
