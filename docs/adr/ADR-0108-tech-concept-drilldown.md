# ADR-0108 — tech 드릴다운: 온톨로지가 그리는 다이어그램

- 상태: 채택 (2026-10-12), 개정 (2026-10-12 — 추천 도메인 추가 · 단계 중첩)
- 관련: ADR-0100(개념 온톨로지 원본), ADR-0062(SEO · 프리렌더)
- 스펙: `docs/specs/2026-10-12-tech-concept-drilldown/spec.md`
- 샘플: 아티팩트 「검색 아키텍처 드릴다운」 v4 (화면 구조 승인본)

## 맥락

`/tech/search` 는 레포 마크다운 한 편(구조 · 흐름 · 기법 표)을 빌드 때 렌더한 문서다. 서비스 설명이 먼저 나오고
검색의 일반 개념은 표의 한 열이라, 검색을 모르는 사람이 읽을 이유가 없다. 같은 방식으로 다른 도메인을 늘리면
도메인마다 문서와 그림을 손으로 다시 쓴다.

개념 온톨로지(ADR-0100)에는 이미 검색 개념 490개가 유형(`kind`) · 포함(`contains`) · 흐름(`flows_to`) · 코드 위치
(`code: path + symbol`)와 함께 들어 있다. 없는 것은 「이 서비스가 그 개념을 지금 쓰는가, 어떤 값으로」뿐이다.

## 결정

1. **그림은 온톨로지 데이터에서 규칙으로 만든다.** 화면 쪽에 노드 · 좌표 · 간선 · 설명을 적지 않는다.

   | 규칙 | 내용 |
   |---|---|
   | R1 노드 | 개념 X 의 그림 = X 의 `contains` 자식 중 `STAGE` 이거나 `flows_to` 로 이어진 것. 나머지 자식은 그림 아래 「관련 개념」 목록 |
   | R2 간선 | 같은 그림 안 자식끼리의 `flows_to`. 간선 글자는 관계의 `label` |
   | R3 병렬 묶음 | 흐름 노드의 자식 중 `STAGE` 가 둘 이상이고 자식 사이에 흐름이 하나도 없으면, 그 노드를 묶음 틀로 그리고 `STAGE` 자식을 나란히 펼친다 |
   | R4 [상세보기] | 자식이 있는 노드. 누르면 그 노드의 그림(R1)이 아래에 열린다. 깊이 상한 없음(18) |
   | R5 배치 | 좌표를 저장하지 않는다. 흐름 순서로 열을 정하는 자동 배치, 좁은 화면은 세로 |

2. **온톨로지에 「적용 상태」를 더한다.** 개념에 선택 필드 `applied` 를 둔다 —
   `status`(LIVE · PARTIAL · DISABLED · NONE), `summary`(이 서비스가 하는 일), `facts`(이름 · 값 쌍, 코드 대조용 `key` 선택).
   일반 개념 설명(`description`)과 서비스 상태를 한 개념에 두되 필드로 가른다. `flows_to` 관계에는 선택 키 `label` 을 더한다.
   드릴다운에 그려지는 개념은 `applied.status` 가 있어야 한다 — 없는 단계를 빼고 그리면 읽는 사람은 있다고 가정한다.

3. **검색 도메인의 흐름을 업계 기준 파이프라인으로 재구성한다.** `search-query` 의 흐름:
   사용자 검색 → 쿼리 리포뮬레이션 → 쿼리 언더스탠딩 · 쿼리 임베딩 → 후보 생성(스파스 · 덴스, R3) → 융합 → 리랭킹 · 후처리 →
   0건 대응 → 결과 구성. 리포뮬레이션 · 0건 대응은 쿼리 언더스탠딩 아래 장치에서 단계로 올린다. `/tech` 아틀라스도 같은
   원본을 쓰므로 함께 바뀐다.

4. **화면 데이터는 내보낸 파일이다.** portal-fe 이미지 빌드는 온톨로지 디렉토리를 못 본다(아틀라스와 같은 사정). Kotlin
   스펙이 YAML 을 부팅 로더와 같은 리더로 읽어 `portal-fe/src/content/drill/<domain>.json` 을 만들고,
   커밋된 파일과 다르면 실패한다. 코드 스니펫은 내보낼 때 `symbol` 이 처음 나오는 줄부터 잘라 싣는다.
   GitHub 링크는 FE 빌드가 그 빌드의 커밋(`GIT_SHA`)으로 고정한다 — 스니펫과 링크가 같은 코드를 가리킨다.

5. **값 대조는 온톨로지로 옮긴다.** 기존 마크다운 표가 하던 드리프트 대조(RRF 상수 · 가중치 · 모델 ref · HNSW 등)는
   `applied.facts[].key` 를 코드 · 매니페스트 값과 대조하는 테스트가 맡는다. 마크다운 원본과 그 렌더 단계는 걷어낸다.

6. **내부 결정 문서 번호는 화면에 내지 않는다.** 온톨로지의 `evidence`(ADR 등)는 개념 사전용으로 남기고 드릴다운은 싣지 않는다.

7. **게시 위치.** 메인은 `/tech` 아틀라스 첫 화면 본문에 진입 카드(IT 타일의 하위). 이력서는 운영 DB 의 검색 프로젝트
   항목에 절대주소 링크 한 줄 — 레포가 아니라 운영 데이터라 문안을 승인받고 어드민 API 로 넣는다.

## 기각

- **페이지별 뷰 파일(노드 · 좌표 · 설명을 화면 쪽에)** — 샘플이 이 방식이었다. 온톨로지와 두 원본이 되어 한쪽만 고치면 어긋난다.
- **실행 중 API 로 그리기** — 정적 페이지에 백엔드 왕복이 생기고 프리렌더가 본문을 못 담는다.
- **온톨로지에서 mermaid 텍스트 생성** — 노드 클릭 · 상태 표시 · 병렬 묶음을 표현할 수 없다.
- **스니펫을 브라우저가 `main` 에서 가져오기(아틀라스 방식)** — 링크가 움직이는 브랜치를 가리켜 시간이 지나면 다른 코드를 보인다.
- **상태를 별도 파일에** — 개념이 옮겨지거나 이름이 바뀔 때 키가 끊긴다. 원본을 하나로 둔다.

## 개정 (2026-10-12) — 추천 도메인 · 단계 중첩

8. **펼친 단계는 앞 단계 안에 품는다.** 단계를 형제로 늘어놓으면 1단계 탭 바로 뒤에 2단계 머리가 붙어, 모바일에서
   어디까지가 어느 단계인지 안 보였다. 다음 단계는 앞 단계 카드 안(탭 뒤)에 들여 넣고 왼쪽 띠로 잇는다. 머리는
   면(띠)과 단계 번호 배지로 가른다.
9. **그림이 없는 이유를 화면이 말한다.** 하위 개념이 없는 개념은 「더 나뉘는 하위 단계가 없다」, 하위 개념끼리 흐름이
   없으면(노드 0개) 그림 대신 「하위 개념」 목록, 펼침 한계(3단계)에 닿으면 그 사실을 적는다. 한계 값은 내보내기가
   `maxDepth` 로 함께 낸다 — 화면에 숫자를 다시 적지 않는다.
10. **좁은 화면의 한 행이 폭을 넘으면 여러 줄로 접는다.** 세로 배치에서 같은 단계 노드가 많으면(추천 후보 원천 다섯)
    그림 상자 안 가로 스크롤이 생겼다. 접힌 줄을 지나는 간선은 사이 상자를 비켜 돌고, 그 글자는 출발 상자 밑에 둔다.
11. **도메인 목록은 한 곳이다.** `portal-fe/src/pages/tech/drillPages.mjs` 의 `DRILL_PAGES` 를 라우트 · GNB · 아틀라스 카드 ·
    렌더 · 프리렌더 · sitemap · llms.txt 가 돈다. 화면은 `TechDrillPage` 하나이고 도메인 페이지는 데이터만 묶는 얇은 파일이다
    (도메인마다 청크를 나눈다). 도메인 추가 = `DrillExportSpec.DRILLS` 한 줄 + `DRILL_PAGES` 한 줄 + `PORTAL_PAGES` 한 줄 +
    얇은 페이지 파일 + 라우트 한 줄, 그리고 그 도메인 YAML 의 `flows_to` · `applied`. 대조 키를 달면 그 도메인의 드리프트 테스트도.
12. **추천의 적용 상태는 운영에서 확인한 대로 적는다.** 2026-10-12 운영 확인: ClickHouse 에 추천 행동 테이블이 없고, Redis 에
    `reco:*` 키가 0개, ANN 사이드카 모델 볼륨이 비어 `degraded`, 동기화 · 재학습 스케줄은 배포 목록에 없다. 그래서 대부분 단계가
    「비활성」(구현돼 있으나 운영에서 결과를 내지 않음)이다. 상태를 실제보다 좋게 적으면 이 페이지의 「현재 적용 상태」가 거짓이 된다.

13. **드릴다운 HTML 은 엣지에 5분 두고, 지연 청크는 프리렌더가 미리 받게 한다.** 2026-10-12 실측: 국내 회선(KT 대역)에서
    1989v.com 이 `colo=LAX` 로 붙어 HTML 한 장이 0.8~2.8초(오리진 안쪽은 ingress 9ms), 캐시 끈 첫 화면은 다이어그램까지 4.4초였다.
    다이어그램 데이터 청크 자체는 0.3초 — 데이터 조회가 아니라 왕복 횟수 × 태평양이 원인이다.
    - nginx 가 드릴다운 경로에만 `Cache-Control: public, max-age=0, s-maxage=300, must-revalidate` 를 단다. 브라우저는 매번 다시 묻는다
    - **Cloudflare 대시보드 캐시 규칙이 짝이다**(API 토큰이 레포에 없다): 이름 `tech drill html`,
      식 `(http.host eq "1989v.com" and starts_with(http.request.uri.path, "/tech/"))`(도메인이 늘어도 규칙을 안 고친다 — 용어집은 오리진이
      `no-cache` 라 담기지 않는다),
      동작 「캐시 대상」, 엣지 TTL 「오리진 Cache-Control 을 따름」, 브라우저 TTL 「오리진을 따름」. 규칙이 없으면 헤더는 무동작이다(`cf-cache-status: DYNAMIC`)
    - 배포 뒤 최대 5분은 옛 셸이 나갈 수 있다 — 옛 청크는 이미지가 직전 릴리스 자산을 함께 담아(retain-assets) 404 가 나지 않는다
    - 프리렌더가 vite 매니페스트에서 페이지 · 화면 · 목록 청크와 CSS 를 찾아 `modulepreload` 로 head 에 넣는다. 메인 번들을 기다린 뒤에야
      청크를 요청하던 한 줄의 왕복이 겹쳐진다. 매니페스트는 프리렌더가 읽고 이미지 빌드가 지운다(서빙물에 남기지 않는다)
    - 사이트 전체 HTML(DYNAMIC)이 같은 경로를 탄다 — 이 규칙을 다른 경로로 넓힐지는 따로 정한다

14. **주문 · 결제(`/tech/order`)도 운영 확인으로 상태를 적는다.** 2026-10-12 확인: 주문 사가가 운영에서 끝까지 돈다(데모 주문 9건,
    사가 완료 6 · 실패 3, 원장 35줄 차대 합 0, 정산서 1장 지급). 결제 상대는 항상 승인하는 모의 PG(결제 6건 모두 `mock-` 키,
    `PAYMENT_PG` 미설정, 토스 웹훅 404)이고 지급도 모의 송금이라 결제 · 대사 · 지급은 「일부 구현」, 송장 연동 · 세금계산서는 없다.
    드릴다운 경로를 nginx 엣지 캐시 location 에 빠뜨리면 용어집 location 이 받아 헤더가 안 붙는다 — 프리렌더 테스트가
    `DRILL_PAGES` 경로 전부를 그 location 정규식에 대 본다.

15. **광고(`/tech/ads`)도 운영 확인으로 적는다.** 2026-10-12 확인: 결정 API 가 허용 호스트에서 200 · 밖에서 404, 지면 4곳 등록,
    소재 3건 승인, ads.txt 응답. 광고주 캠페인 1건은 초안이라 유료 채움 0 — 지금은 자체 홍보만 나간다. 원장은 충전 1건 · 정산 0건(합 0).
    그래서 서빙 · 자격 · 경매는 「운영 중」이되 서술이 「유료 후보 없음」을 말하고, 과금 · 정산은 「돌지만 정산 0건」이다.
16. **세로 그림의 돌아가는 선은 통로가 겹치면 반대쪽으로 돈다.** 같은 쪽에 높이가 겹치는 선이 이미 있으면 다른 쪽을 쓴다 — 두 선이
    한 통로를 쓰면 엇갈려 어느 선이 어디로 가는지 안 보였다(광고 이벤트 계측). 오른쪽 통로는 바깥에 자리가 있으면 글자를 그 옆에 단다.

17. **상품 · 재고(`/tech/catalog`)도 운영 확인으로 적는다.** 2026-10-12 확인: 상품 27개(판매 중 25) · 판매자 2 · 카테고리 18종(자유 문자열),
    창고 1곳 · 재고 27행 · 예약 8건 모두 확정, 장바구니 2건, 혜택 보류 6건 확정. 정의된 쿠폰 · 지급된 포인트는 0건이라 혜택 설계 · 포인트는
    「일부 구현」이고, 주간 상품 전체 재색인 CronJob 은 멈춰 있다(suspend). 재고 Redis 선차감은 코드가 있어도 판정에 쓰지 않아 「일부 구현」이다.

## 개정 (2026-10-13) — 깊이 상한 제거 · 단계 카드 평탄화

18. **펼침 깊이에 상한을 두지 않는다 — 8 · 9 의 일부를 대체한다.** 3단계 상한은 3단계에서 연 개념의 하위 구조를 내보내지 않아,
    하위 개념이 넷인 「검색 사전」의 자식처럼 진짜 끝 항목에도, 하위가 있는 개념에도 같은 「3단계까지 그린다」 문장이 나왔다.
    상한을 빼면 3단계 이하에서 하위가 있는 개념이 검색 28 · 광고 15 · 주문 7 · 추천 4 개 열리고(대부분 흐름 없는 목록),
    가장 깊은 단계는 검색 6 · 광고 5 다. `maxDepth` 필드는 없앴다. 내보내기 게이트에 「하위 개념이 있는데 그림이 없다」를 더해
    상한이 되살아나면 실패한다.
    단계는 앞 단계 안에 들여 넣지 않고 같은 폭의 카드로 차례로 쌓는다. 들여 넣으면 깊어질수록 왼쪽 띠가 겹치고 그림 폭이
    줄어든다(6단계면 모바일 그림 폭이 사라진다). 경계는 카드 간격 · 머리 띠 · 단계 번호 · 경로 줄이 가른다.

## 개정 (2026-10-13) — 검색 첫 그림을 시스템 전체로 · 검색 JD 적용 지도와 이름 · 상태 맞춤

19. **검색 드릴다운의 첫 그림은 `search-system` 이다 — 3 의 「첫 그림 = 검색어 파이프라인」을 대체한다.** 검색 JD 적용 지도
    아티팩트(2026-10-13, 기술 28가지)를 빠짐없이 노드로 두려면 요청 경로 밖의 콘텐츠 이해 · 색인 · 평가 · 서빙이 첫 그림에 있어야
    한다. 첫 그림: 콘텐츠 이해 → 색인 · 파이프라인 → 검색어 파이프라인 → 평가 · 로그, 서빙 · 운영 → 검색어 파이프라인.
    색인 내부 구조 · 용어 사전은 관련 개념이다. 검색어 파이프라인은 한 단계 안으로 들어갔다.
    - **겹치는 개념은 아티팩트의 이름을 쓴다** — 쿼리 리포뮬레이션 → 쿼리 재작성, 후보 생성 → 리트리벌, 스파스 · 덴스 검색 →
      키워드 · 정확 일치 · 덴스 + 1-bit, 융합 → 하이브리드 RRF, 후처리 → 랭킹, 리랭킹 → 리랭킹 모델, 벌크 인덱싱 → 데이터 파이프라인,
      색인 동기화 → Kafka · RDB 색인, 오프라인 평가 → 평가 체계, 추론 서버 → Triton · vLLM 등. 없던 것은 새 개념으로 넣었다
      (콘텐츠 이해와 그 아래 다섯, OpenSearch 운영, 다국어 · 자연어, Milvus · FAISS, 랭킹 피처 결합, 검색 로그 분석, 지표 기반 개선,
      장애 · 성능 개선, 연구 → 서비스, 모델 서빙, 최신 논문 적용, Python · Go).
    - **상태 이름도 아티팩트를 따른다** — 운영 중 · 일부 구현 · 미구현 → 적용 · 부분 · 미적용(비활성은 그대로). 모든 드릴다운에 적용된다.
    - **28가지의 상태가 아티팩트와 같다.** 리랭킹 모델은 상품 검색 밴딧 재정렬 때문에 「부분」이었으나, 밴딧은 모델이 아니라 탐색이라
      「밴딧 · 탐색」(적용)에 두고 리랭킹 모델은 「미적용」으로 맞췄다. 아티팩트와 코드가 다른 곳은 코드를 따랐다 — 증분 색인은 상품만
      Kafka 이고 관광지는 전체 재색인뿐, 개념 온톨로지의 관계 종류는 9, 평가 게이트는 Kotlin 배치가 아니라 `search-eval` CronJob.
      학습 리랭커 · 학습형 스파스 실험 코드는 레포에 없어 「오프라인 측정」 값으로만 적었다.
    - 새로 대조하는 값 넷 — 재색인 교체 하한 90% · 조회 실패 상한 5% · 평가 허용 하락폭 0.03 · 판정 없는 문서 상한 15%.

## 결과

새 도메인 드릴다운은 화면 코드 없이(얇은 페이지 파일 하나) 그 도메인 YAML 에 `flows_to` 와 `applied` 를 채우고 다시 내보내면 생긴다.
대가는 온톨로지가 「일반 개념」과 「이 서비스의 상태」를 함께 갖게 된 것 — 서비스 코드가 바뀌면 `applied` 도 낡을 수 있고,
대조 키가 있는 값만 테스트가 잡는다. 서술(`summary`)은 사람이 고친다.
