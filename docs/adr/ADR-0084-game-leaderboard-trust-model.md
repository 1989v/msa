# ADR-0084: 게임 랭킹은 신뢰 기반이다 — 막지 않기로 **결정**한다

<!-- source: game/feature/src/main/kotlin/com/kgd/game/application/play/service/GameScoreService.kt, portal-fe/public/games/lib/rank.js -->

- 상태: 수용
- 날짜: 2026-08-31 (개정 2026-09-20 — 운영자·자동화 제출 미기록)
- 관련: ADR-0059(게임 플랫폼), ADR-0074(찜하기 opaque key), `docs/benchmarks/2026-08-31-game-technique-catalog.md` I5

## 맥락

게임 75종의 점수 제출은 `GameScoreService` 한 곳으로 들어온다. 지금 검증은 둘뿐이다.

```kotlin
private const val MAX_SCORE = 1_000_000_000_000L   // 명백한 조작값 상한
if (!NICK_REGEX.matches(nick)) …
if (score !in 0..MAX_SCORE) …
```

**게임은 전부 클라이언트에서 돈다.** 캔버스 게임은 `portal-fe/public/games/**` 의 평문
JavaScript 이고, 유니티 게임도 WebGL 산출물이라 브라우저에 통째로 내려간다. 점수를 만드는
로직이 사용자 기기에 있고, 제출은 그 기기가 한다.

기법 대장(포켓로그 편)이 같은 구조의 결말을 보여 준다 — 그 게임은 중간 상태를 브라우저에
**암호화해서** 저장하지만 오픈소스라 키와 방식이 함께 공개돼 있고, 결국 누구나 파티에 뮤를
넣거나 스테이지를 건너뛴다. **소스가 공개된 클라이언트에서 암호화는 시간을 벌 뿐이다.**

## 결정

**막지 않는다. 대신 막지 않는다고 적는다.**

랭킹은 **신뢰 기반**이다. 서버는 「말이 되는 범위인가」만 보고, 「정말 그렇게 플레이했는가」는
묻지 않는다.

### 왜 「타당성 상한」을 넣지 않는가

검토한 대안은 게임마다 이론 최대 점수를 계산해 상한으로 쓰는 것이다. 궁수 키우기는
`처치×10 + 러시×120 + 둥지×400 + 클리어 5000` 이라 경과 시간에서 상한이 나온다.

넣지 않기로 한 이유는 셋이다.

1. **75종에 각각 필요하다.** 게임 하나의 공식은 그 게임만의 것이라 공용 규칙이 없다.
   한두 개만 넣으면 나머지가 뚫린 채로 「막고 있다」는 인상만 남는다 — 그게 더 나쁘다.
2. **공식이 게임과 함께 움직인다.** 밸런스를 고칠 때마다 서버의 상한도 같이 고쳐야 하고,
   안 고치면 정상 플레이가 거부된다. 조작을 막으려다 **진짜 기록을 버리는** 쪽이 더 비싸다.
3. **막을 값이 크지 않다.** 이 랭킹에는 상금도 순위 보상도 없다. 닉네임당 최고 기록을
   보여 주는 게시판이고, 부정 기록의 피해는 「목록 위쪽이 이상하다」까지다.

### 그래서 무엇을 하는가

- **서버가 날짜를 정한다** (`GameDay.today()`). 기기 시계를 믿으면 보드가 타임존만큼 갈린다.
  이건 조작 방어가 아니라 **일관성**이고, 그래서 계속 한다.
- **명백한 값만 거른다** — 음수, 상한 초과, 규격 밖 닉네임.
- **어뷰징 방어를 노출로 대체한다.** 표 수·기록 수를 함께 보여 주면 이상한 기록이 눈에 띈다
  (익명 투표에서 쓴 것과 같은 수 — ADR-0074).

## 결과

- 랭킹은 **경쟁 장치가 아니라 기록 게시판**이다. 그렇게 읽히도록 화면 문구를 맞춘다.
- 나중에 상금·보상이 붙으면 **이 ADR을 먼저 뒤집어야 한다.** 그때는 서버 권위 경로
  (서버가 판정을 갖는 구조)가 필요하고, 클라이언트 상한 몇 줄로는 안 된다.
- **암호화·난독화는 하지 않는다.** 위 이유로 값을 못 하고, 하면 「막고 있다」는 착각만 만든다.

## 대안

| 안 | 왜 안 골랐나 |
|---|---|
| 게임별 타당성 상한 | 75종 각각 필요 · 밸런스와 함께 움직여 정상 기록을 거부할 위험 |
| 세이브/점수 암호화 | 클라이언트가 공개돼 있어 키도 공개된다. 시간만 번다 |
| 서버 권위(리플레이 검증) | 이 랭킹의 값에 비해 비용이 과하다. 보상이 붙으면 그때 |
| 지금처럼 두되 적지 않기 | **막지도 못하고 못 막는다고 적혀 있지도 않은 상태** — 가장 나쁘다 |

## 개정 2026-09-20 — 운영자·자동화 제출은 기록하지 않는다

신뢰 모델은 그대로다. 이 규칙은 **조작 방어가 아니라 데이터 위생**이다 — 운영자의 시험 플레이와
헤드리스 e2e 스크립트의 제출은 실제 플레이가 아니므로 기록이 아니다. 2026-09-20 운영 `game_score`
36행 중 17행이 그것이었다(`실측NNNNNN` 13행은 `amp-arena/tools/e2e-prod-score.mjs` 가 매번 만든 닉).

`POST /api/v1/games/{slug}/scores` 는 다음을 **받되 쓰지 않고** `applied=false, rank=0, excluded=true` 로
답한다(성공 응답 — 운영자 플레이마다 warn 로그가 남지 않게 예외를 던지지 않는다. 분석 원장 ADR-0095 가
크롤러를 202/`accepted=0` 로 버리는 것과 같은 모양).

| 제출자 | 판별 |
|---|---|
| 자동화 | `User-Agent` 가 `com.kgd.common.web.CrawlerUserAgents.isCrawler()` — HeadlessChrome·크롤러·`(compatible; …)`·UA 없음 |
| 운영자 | 게이트웨이가 넣은 `X-User-Roles` 에 `ROLE_ADMIN` (손으로 붙인 헤더는 게이트웨이가 지운다) |

- 판별은 제출 경로에서만 본다. 조회는 손대지 않는다 — 쓰지 않은 행은 걸러 낼 것도 없다. 숨김 컬럼
  방식은 조회 지점 다섯 중 하나만 빠져도 새고 스키마 변경이 들어 고르지 않았다.
- 닉네임 접두로 거르지 않는다 — 검사가 자기 이름을 재는 것이고 다음 스크립트가 다른 이름을 쓰면 끝난다.
- 운영자 판별의 한계: 게스트 상태의 운영자는 구별할 수 없다(테스트는 로그인 상태로). 액세스 토큰은
  1시간이고 게임 안에 재발급이 없어, 상세 페이지를 연 지 1시간 뒤의 제출은 게스트로 기록된다.
- 공용 위젯 `lib/rank.js` 가 Bearer 를 싣기 시작했다 — 그 전에는 캔버스 게임의 로그인 제출이 전부
  `member_id NULL` 이었다(V64 가 의도한 연결이 아레나 밖에서는 죽어 있었다). 부수로 회원 기록 연결이
  복원된다.
- 아케이드 보드(`/api/v1/games/arcade/scores`, 세션 토큰 + 리플레이 검증)는 신뢰 모델이 달라 이 개정
  밖이다.
- e2e 는 UA 를 사람 것으로 씌우지 않는다 — 씌우면 행이 남는다. 양성 경로(`applied=true`)를 운영에서
  재야 하면 사람 UA + 사후 삭제, 또는 로컬 k3d.
