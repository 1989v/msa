# ADR-0063 — 어드민 콘솔은 단일 호스트(admin.1989v.com)로 고정한다

- 상태: 채택 (2026-08-09)
- 관련: ADR-0058(서비스 토폴로지 통합 — R3 FE 흡수), ADR-0061(엣지 하드닝)

## 맥락

ADR-0058 R3 는 sub-FE 들(admin/quant/gifticon/agent-viewer)을 portal-fe 한 벌로 흡수하려는
계획이고, 그에 따라 `portal-fe/src/apps/admin` 에 어드민 앱이 복제돼 `1989v.com/admin/*` 로
서빙되고 있었다. 동시에 기존 `admin-fe` 도 `admin.1989v.com` 으로 계속 서빙됐다 —
**어드민 입구가 두 개**였다.

2026-08-09 어드민 로그인 장애를 조사하다 이 이중화가 실제 위험임이 드러났다:

- ADR-0061 에서 어드민 콘솔 앞에 Cloudflare Access 를 세웠는데, **Access 는 `admin` 서브도메인
  대상이라 apex 의 `/admin/*` 경로는 보호하지 않는다.** 즉 하드닝이 절반만 걸려 있었다
- 인증 우회 플래그(`BYPASS_AUTH`)가 두 곳에 복제돼 있었고, 그 결과 인증 없는 방문자에게
  어드민 UI 구조와 번들에 포함된 내부 API 경로가 **Access 가 없는 경로로** 노출됐다
- 공개 포털 번들에 어드민 화면·API 클라이언트가 함께 실려 나갔다

## 결정

**어드민은 `admin.1989v.com` 한 곳만 정식 경로로 둔다.** `portal-fe` 에서 어드민 앱을
완전히 제거하고, `1989v.com/admin/*` 는 정식 호스트로 리다이렉트만 한다(기존 링크 보존).

ADR-0058 R3 의 흡수 대상에서 **admin 을 제외**한다. quant/gifticon/agent-viewer 는 그대로 둔다 —
이들은 일반 사용자 기능이라 공개 포털에 흡수되는 것이 자연스럽지만, 어드민은 성격이 다르다.

## 근거

- **보호 경계는 하나여야 한다.** 입구가 둘이면 하드닝도 둘 다 걸어야 하고, 한쪽을 잊는 순간
  약한 쪽이 실질 보안 수준이 된다. 이번이 정확히 그 사례다
- **공개 번들에 어드민 코드를 넣을 이유가 없다.** 어드민 화면·라우트·내부 API 경로가
  누구나 받을 수 있는 JS 에 포함되는 것은 그 자체로 정보 노출이다. 번들 크기도 준다
- OAuth 리디렉션 URI 도 하나만 등록하면 되어 설정 표면이 줄어든다

## 결과

- `portal-fe/src/apps/admin/**` 삭제(66 파일, 약 5,300줄), `@admin` alias 제거
- `1989v.com/admin/*` → `https://admin.1989v.com` 리다이렉트 (번들에 어드민 코드 없음)
- Google OAuth 승인 리디렉션 URI 는 `https://admin.1989v.com/oauth/callback` 하나만 등록
- 어드민 보호는 Cloudflare Access(엣지) → 앱 로그인 → 게이트웨이 ROLE_ADMIN 3중으로 유지

## 대안과 기각 사유

- **양쪽 유지 + apex 에도 Access 적용**: Access 는 경로 단위로도 걸 수 있지만, 같은 호스트에서
  공개 포털과 어드민이 섞이면 정책 실수 여지가 계속 남는다. 입구를 줄이는 쪽이 단순하다
- **portal-fe 로 통합하고 admin-fe 폐기**: 반대 방향의 단일화. 그러려면 apex 에 어드민 전용
  보호를 새로 설계해야 하고, 이미 동작 중인 Access + AOP 구성을 흔든다. 얻는 것이 없다
