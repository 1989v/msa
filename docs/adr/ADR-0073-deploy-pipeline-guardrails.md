# ADR-0073 — 배포 파이프라인 안전장치: 멈춘 동기화 차단 + 변경분만 적용

- 상태: 채택 (2026-08-22)
- 관련: ADR-0019(K8s 전환·GitOps), ADR-0061(엣지 하드닝), ADR-0072(블로그 — 이 사고의 계기)

## 맥락

2026-08-21, `code-dictionary` 파드가 Flyway 체크섬 불일치로 CrashLoopBackOff 에 빠졌다.
그 자체는 애플리케이션 버그였고 고치면 끝날 일이었다. 문제는 **고친 것이 배포되지 않았다**는
것이다.

Argo CD 의 동기화 작업이 `Running` 상태로 **6시간 30분** 머물렀다. 그동안 이미지 태그 롤백도,
마이그레이션 수정본도 클러스터에 닿지 못했다. 작업을 수동으로 끊자 다음 동기화는 6분 42초에
끝났다. 즉 장애 시간의 대부분은 버그가 아니라 **배포 경로가 막혀 있던 시간**이었다.

기존 장치는 이 상황을 다루지 못한다.

| 장치 | 값 | 왜 안 걸렸나 |
|---|---|---|
| `progressDeadlineSeconds` | 600 | Deployment 수준 신호일 뿐, Argo 작업을 끝내지 않는다 |
| `syncPolicy.retry` | limit 5 | **실패**를 재시도한다. "안 끝남"은 실패가 아니다 |
| `maxSurge: 0` | 전 서비스 | 자원 경합은 막지만 이 사고와 무관 (당시 노드 메모리 50%) |
| CI `concurrency` | images-\<ref\> | 빌드는 이미 직렬. 문제는 빌드 이후 구간 |

Argo 는 Application 당 작업을 하나만 돌린다 — **이미 큐다.** 큐가 밀린 게 아니라 큐 머리가
영원히 안 끝난 것이 원인이다. 그러니 필요한 것은 큐를 더 만드는 게 아니라 **머리에 시간 상한**을
두는 것이다.

## 결정

### 1) 멈춘 동기화 워치독 — 20분 넘게 `Running` 이면 작업을 끊는다

`k8s/argocd/stuck-sync-watchdog.yaml`. 5분 주기 CronJob 이 Application 의
`status.operationState` 를 읽어 `phase=Running` 이고 `startedAt` 이 임계(1200초)를 넘으면
`/operation` 을 제거한다 (= `argocd app terminate-op`). 다음 자동 동기화가 **최신 리비전으로**
다시 건다.

- **Argo 가 이 워치독을 배포하지 않는다.** 막힌 것을 푸는 물건을 막힌 것이 배포하면 같이 막힌다.
  `k8s/argocd/install.sh` 가 Application 과 나란히 직접 apply 한다. GitOps 예외지만, 이 예외가
  이 장치의 존재 이유다.
- 이미지는 노드에 이미 있는 `curlimages/curl` 을 쓴다. `argocd --core` 도 검토했으나 그 모드는
  argocd-server 급 권한(argocd ns 의 configmap·secret **전체** list)을 요구한다 — 워치독에
  리포 자격증명과 admin 비밀번호를 읽을 권한을 주는 셈이라 접었다. SA 토큰으로 K8s API 를
  직접 부르면 필요한 권한이 `applications` 의 get/patch 둘로 끝난다.
- 임계 20분의 근거: 정상 동기화는 관측상 7분 안에 끝난다. 느린 날에도 걸리지 않으면서
  6시간짜리 정지는 확실히 자른다.
- 대상 Application 은 **환경변수에 명시**한다(`APPS="commerce"`). 목록을 JSON 에서 긁으면
  status 안의 수백 개 `"name"` 과 뒤섞여 조용히 틀린다.

### 2) `ApplyOutOfSyncOnly=true` — 바뀐 리소스만 적용한다

없으면 태그 한 줄 bump 에도 매니페스트 전체(~25종)를 훑는다. 한 서비스의 문제가 동기화 전체를
붙잡는 확대 경로였다. 이 옵션으로 동기화의 작업량과 실패 반경이 실제 변경분에 비례하게 된다.

### 3) 하지 않기로 한 것 — Application 분할

`commerce` 하나를 infra/backend/frontend 로 쪼개면 한 앱이 막혀도 나머지가 진행한다. 효과는
크지만 `install.sh` 와 부트스트랩 절차를 함께 고쳐야 하고, 위 두 장치로 이번 실패 모드는
닫힌다. **다음에 또 막히면 그때 쪼갠다** — 그때는 근거가 두 건이 된다.

## 결과

- (+) 배포 경로가 최대 20분 이상 막히지 않는다. 이번 장애의 지배적 시간(6시간 30분)이 사라진다.
- (+) 동기화 실패 반경이 변경분에 비례한다.
- (+) 새 상시 파드 0. 워치독은 5분마다 몇 초 도는 CronJob 이고 이미지도 노드에 이미 있다.
- (−) 워치독이 GitOps 밖에 산다 — `install.sh` 를 다시 돌리지 않으면 클러스터에만 있고
  레포 변경이 자동 반영되지 않는다. 이건 의도된 예외이고 파일 상단에 이유를 적어 두었다.
- (−) 정말로 20분 넘게 정당하게 도는 동기화가 생기면 끊긴다. 그런 동기화가 생겼다는 것
  자체가 신호이므로, 임계를 올리기 전에 왜 길어졌는지를 먼저 본다.
- (−) 워치독은 **막힌 것을 풀 뿐 원인을 고치지 않는다.** 끊긴 뒤에도 앱이 계속 Degraded 면
  근본 원인은 그대로다. 로그(`kubectl -n argocd logs job/...`)가 유일한 알림 수단이다.
