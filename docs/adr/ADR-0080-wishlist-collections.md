# ADR-0080 — 찜 묶음(컬렉션): 관광지를 여행 단위로 모으고, 찜 목록으로 가는 길을 연다

- 상태: 채택 (2026-08-23)
- 관련: ADR-0074(찜 다형화 — 이 문서가 확장하는 대상), ADR-0065(place), ADR-0071(지역),
  ADR-0079(로그인 단일화 — 찜은 로그인 전용이라 선행 조건)

## 맥락

찜 기능에 두 가지 문제가 겹쳐 있었다.

### ① 찜은 되는데 목록을 볼 수가 없었다

`place` 호스트는 앱 셸(하단 탭바)이 없고 GNB 도 렌더하지 않는다. 그런데 `/favorites`
라우트도, `FavoritesPage` 의 `place: 'ATTRACTION'` 분기도 **이미 준비돼 있었다.**
길만 없었다 — 주소를 직접 쳐야 열렸다.

`game` 도 마찬가지로 탭바에 찜이 없어 GNB 서랍을 열어야만 닿았다. 모바일에서 서랍을
열어야 하는 것은 상시 진입점이 아니다.

화면을 만든 쪽과 셸을 만든 쪽이 달라 아무도 눈치채지 못했다. **찜 버튼이 뜨는 호스트와
찜 목록으로 가는 길이 있는 호스트가 같아야 한다**는 규칙이 어디에도 적혀 있지 않았다.

### ② 관광지 찜은 "다시 찾아가기"가 본 목적인데 묶을 수가 없었다

place 의 찜은 게임·블로그 글의 찜과 성격이 다르다. 게임 찜은 "나중에 또 하고 싶다"지만
관광지 찜은 **"이번 여행에서 여길 간다"** 다. 여행이 여럿이면 목록 하나에 뒤섞이고,
제주 갈 때 강원도 찜이 함께 보인다.

## 결정

### 1) 셸이 없던 호스트에 찜 진입점을 만든다

```
place   지도 · 내 찜 · 서비스      ← 신설
game    로비 · 장르 · 내 찜 · 서비스  ← 찜 추가
```

place 에 장르 같은 분류 탭을 두지 않는다 — 지역 드릴다운은 지도·지역 페이지 **안에서**
일어나고, 탭으로 올리면 지도 위 컨텍스트를 버리는 이동이 된다.

`resume`·`deal` 은 셸 없음을 유지한다. 찜 대상이 아니고 문서·단일 목록 성격이다.

**규칙을 테스트로 고정한다** (`appShell.test.ts`): 찜 버튼이 뜨는 호스트에는 반드시 찜
탭이 있어야 한다. 이 조합이 어긋난 것이 ①의 원인이었다.

### 2) 컬렉션은 nullable 이다 — 기본 그룹을 만들지 않는다

```sql
wishlist_collection (id, member_id, name, created_at)
wishlist_items.collection_id BIGINT NULL
```

회원마다 "기본" 컬렉션을 자동 생성하지 않는다. `collection_id IS NULL` 이 곧 미분류다.

자동 생성을 택하지 않은 이유: 가입 시점에 행을 만들면 **찜을 한 번도 안 한 회원에게도
빈 컬렉션이 생기고**, 그 행을 지울지 말지가 다시 문제가 된다. NULL 은 부트스트랩도,
정리도 필요 없다. 기존 1건도 그대로 NULL 로 남는다.

### 3) 한 항목은 한 컬렉션에만 속한다 — 유니크를 넓히지 않는다

```sql
UNIQUE (member_id, target_type, target_key)   -- 그대로
```

다중 소속을 허용하려면 유니크를 `(collection_id, ...)` 로 넓혀야 하는데, 그러면 하트의
의미가 무너진다 — "찜됨/아님" 이진이었던 것이 "어느 컬렉션에서 찜됨?" 이 된다.
`fetchFavoriteKeys` 로 목록 화면을 하이드레이션하는 구조도 컬렉션마다 갈라야 한다.

여행 계획에서 한 장소는 보통 한 여행에 속한다. 필요해지면 **유니크를 넓히는 방향은
파괴적이지 않으므로** 지금 단순하게 두고 나중에 확장한다.

그룹 이동은 `UPDATE collection_id` 한 번이다.

### 4) 스키마는 범용, UI 는 관광지 전용

`wishlist_collection` 은 대상 타입을 가리지 않는다(컬럼에 타입이 없다). 반면 **그룹
선택 UI 는 ATTRACTION 에만 노출한다.**

게임·블로그 글을 여행 묶음에 넣을 이유가 없고, 전 타입에 열면 하트를 누를 때마다
그룹을 묻게 되어 찜의 가벼움이 사라진다. 스키마를 범용으로 두는 것은 나중에 다른 타입이
묶음을 원할 때 두 번째 마이그레이션을 하지 않기 위해서다 — 비용이 0 인 여지다.

### 5) 하트 한 번은 그대로 즉시 찜이다

그룹 선택을 **필수 단계로 만들지 않는다.** 한 번 누르면 미분류로 바로 들어가고, 그룹은
찜 목록에서 나중에 지정하거나 하트 옆 보조 동작으로 고른다.

매번 그룹을 묻는 순간 찜은 "한 번 누르는 것"에서 "결정하는 것"이 되고, 지도에서 훑어보다
가볍게 찍어두는 사용이 사라진다. 그 가벼움이 place 찜의 쓰임 자체다.

## 결과

**켜짐**

- place·game 에서 찜 목록에 상시로 닿는다.
- 관광지를 여행 단위로 묶어 "제주 갈 때 볼 것"만 따로 열 수 있다.
- 진입점 규칙이 테스트로 고정돼 같은 누락이 재발하지 않는다.

**대가**

- 컬렉션 CRUD 만큼 API·화면이 늘었다.
- 한 장소를 두 여행에 넣을 수 없다(3항의 의도된 제약).
- `wishlist_items` 에 FK 가 생겨 컬렉션 삭제 시 소속 항목 처리를 정해야 한다 —
  **컬렉션을 지워도 찜은 남긴다**(`ON DELETE SET NULL`). 묶음을 없애는 것과 장소를
  버리는 것은 다른 일이다.

**되돌리기**

`collection_id` 를 무시하면 기능만 사라지고 찜 자체는 그대로 동작한다. 컬럼을 드롭하지
않아도 되므로 되돌림이 싸다.
