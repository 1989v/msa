# ADR-0087: 게임별 개선 제안 — 상태 있는 공개 피드백

<!-- source: game/domain/src/main/kotlin/com/kgd/game/domain/suggestion/model/GameSuggestion.kt, game/feature/src/main/resources/gamedb/migration/V71__game_suggestion.sql, portal-fe/src/pages/games/GameSuggestions.tsx -->

- 상태: 수용
- 날짜: 2026-09-01
- 관련: ADR-0059(게임 플랫폼), ADR-0072(블로그 댓글 — 소유권 판정의 선례), ADR-0078(회원 식별 최소화), ADR-0079(로그인 진입점), ADR-0084(랭킹 신뢰 모델)

## 맥락

게임 70여 종이 올라가 있는데 **플레이어가 말을 걸 자리가 없다.** 지금 사이트가 받는 신호는
평점(1~10 한 표)과 랭킹 기록뿐이다. 둘 다 「얼마나 좋은가」는 말해 주지만 **「무엇을 바꿔야
하는가」는 말해 주지 못한다.** 실제로 모바일 조작 문제 50여 건은 사용자 제보가 아니라
뒤늦은 자체 실측(ADR 없이 `game/CLAUDE.md` G5 로 정리)에서 나왔다.

받는 통로를 만들 때 갈리는 지점이 셋이다.

1. **익명으로 받을 것인가.** 평점·랭킹은 익명이다(게스트도 표를 던진다). 하지만 자유 서술은
   익명일 때 관리 비용이 급격히 오르고, 되물을 상대가 없어 「어느 구간인가」를 확인할 수 없다.
2. **처리 결과를 어떻게 돌려줄 것인가.** 글만 쌓이고 아무 반응이 없으면 두 번째 제안은 오지
   않는다. 「읽었다」와 「반영했다」는 다른 신호다.
3. **누가 고칠 수 있는가.** 남이 내 글을 고칠 수 있으면 그것은 더 이상 내가 쓴 말이 아니다.

## 결정

게임 상세에 **개선 제안** 판을 둔다. 표 둘(`game_suggestion`, `game_suggestion_reply`)로
전 게임이 공유한다 — 게임마다 표를 나누면 화면이 게임마다 달라지고, 어드민이 「오늘 들어온
제안」을 한 번에 볼 수 없다 (`game_release_note` 와 같은 판단).

### 1. 쓰기는 로그인, 읽기는 공개

게이트웨이가 라우트를 둘로 나눈다. 읽기(`GET`)는 게스트를 통과시키고, 쓰기는 로그인을
요구한다 + Rate Limiter.

```
game-suggestion-read   GET  /api/v1/games/*/suggestions/**   optionalUser
game-suggestion-write        /api/v1/games/*/suggestions/**   userConfig + RateLimiter
```

**읽기에도 인증 필터를 건다.** 필터가 없으면 클라이언트가 손으로 붙인 `X-User-Id` 가 그대로
백엔드에 도달해, 서버가 계산하는 `mine`(= 「내 글인가」)이 남의 글에서도 참이 된다. 게스트는
필터를 통과하면서 신원 헤더가 **벗겨진** 상태로 간다.

### 2. 소유권은 서비스가, 로그인 여부만 엣지가

블로그 댓글과 같은 경계다 — 게이트웨이는 「로그인했는가」까지만 안다. 「내 글인가」는 엣지가
알 수 없는 정보다.

**운영자에게도 본문 수정 권한을 주지 않는다.** 반영·반려의 근거로 남은 문장이 사후에 달라질
수 있으면 그 상태 표시가 무의미해진다. 운영자가 하는 일은 상태를 옮기고 답글을 다는 것이다.

판정은 도메인이 갖는다. `editBy(memberId, body)` 는 **확인과 변경을 한 함수로 묶어**,
부르는 쪽이 확인을 건너뛴 채 본문만 바꾸는 조립을 불가능하게 한다. 같은 이유로
`GameSuggestion` 은 데이터 클래스가 아니다 — `copy(body = …)` 가 열려 있으면 그 묶음이
풀린다.

### 3. 상태 넷 — 「읽었다」와 「반영했다」를 가른다

`OPEN`(접수) → `REVIEWING`(검토중) → `APPLIED`(반영) / `DECLINED`(반려).

**전이를 한 방향으로 잠그지 않는다.** 상태를 바꾸는 손이 하나뿐이라 오조작을 되돌릴 다른
경로가 없고, 반영했다가 되돌리는 일도 실제로 일어난다.

### 4. 답글은 제안자와 운영자만, 자격은 서버가 정한다

제3자의 참견까지 받으면 개선 제안이 아니라 게임별 게시판이 되고, 그때 필요한 것(신고·정렬·
차단)은 여기 없다. 답글에 다시 답글을 달지 않는다 — 두 사람뿐이라 갈래가 생기지 않는다.

**`author_type`(OPERATOR/AUTHOR)은 요청이 아니라 서버가 정한다.** 닉네임은 사용자가
「운영자」로 지을 수 있어서 이름만으로는 진짜 답변과 사칭을 가를 수 없다. 화면의 배지는 이
값이 그리고, 운영자 답글의 표시 이름도 서버가 붙인다(`GameSuggestion.OPERATOR_NAME`).

어드민도 **공개 쓰기 경로**로 답글을 단다. 답글을 다는 길이 둘이면 자격 판정도 둘이 된다.

### 5. 표시 이름은 랭킹에 쓰는 것과 같은 값

`game_nickname`(브라우저 localStorage) — 랭킹 위젯 `public/games/lib/rank.js` 가 쓰는 그
키다. 그래서 한 사람이 게임 안에서 늘 같은 이름으로 보이고, **목록을 그릴 때 회원 서비스를
부르지 않는다.** 신원은 `member_id` 가 갖고 있어 이름을 바꿔도 소유권은 그대로다.

아직 이름이 없으면 **회원 닉네임(`members.name`)을 받아 채운다.** member 가 가입 시점에
이미 만들어 둔 표시 이름이 있으므로(ADR-0078 `Nickname.generate()`) 게임 쪽에 생성기를 다시
두지 않는다. 이 호출은 **쓰려는 사람에게 한 번**이고 목록 조회 경로에는 없다. 실패하면 그
자리에서 입력받는다 — 제안을 쓰려던 사람을 다른 화면으로 보내지 않는다.

## 결과

- 캔버스·유니티 어느 쪽이든 게임 코드는 **한 줄도 바뀌지 않는다** — 판은 게임 밖(상세 화면)에 있다
- 상태가 붙은 제안이 쌓이므로 「무엇을 먼저 고칠까」를 사이트가 아니라 기록이 말한다
- 익명 제보는 받지 못한다. 로그인 없이 남기고 싶은 사람의 말은 여기 오지 않는다 —
  그 대가로 되물을 수 있고(답글), 스팸 관리 비용이 낮다

## 대안

| 대안 | 기각 이유 |
|---|---|
| 익명 허용 (평점과 같은 기준) | 되물을 상대가 없어 「어느 구간인가」를 확인할 수 없다. 자유 서술은 익명일 때 관리 비용이 급격히 오른다 |
| 게임마다 표를 분리 | 화면이 게임마다 달라지고 어드민이 전 게임을 한 번에 못 본다 (`game_release_note` 에서 이미 내린 판단) |
| 상태 없이 글만 | 반응이 없으면 두 번째 제안이 오지 않는다. 「읽었다」가 곧 이 기능의 값이다 |
| 어드민이 본문도 수정 | 반영·반려의 근거 문장이 사후에 달라질 수 있다 |
| 게임 안(`platform.js`)에도 제안 버튼 | 게임 21종의 화면 검증이 추가로 필요하다. 상세 화면에서 먼저 쓰이는지 보고 정한다 |
| 다른 플레이어의 공감(추천) | 제안이 몇 건 올지 모르는 상태에서 우선순위 장치를 먼저 만드는 일이다. 쌓인 뒤에 넣는다 |

## 아직 없는 것

- **삭제** — 수정만 있다. 답글이 달린 제안을 지우면 답변이 부모를 잃는다(소프트 삭제가 필요하고,
  그 화면을 지금 정할 근거가 없다)
- **공감·정렬** — 최신순 하나뿐이다
- **알림** — 상태가 바뀌어도 제안자에게 알리지 않는다. 플랫폼에 알림 경로가 없다
- **보존기간 정리** — 제안은 원장이 아니라 콘텐츠라 ADR-0077 의 90일 대상이 아니다
