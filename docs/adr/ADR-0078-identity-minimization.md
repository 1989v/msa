# ADR-0078 — 회원 식별 최소화: 이메일을 받지 않고, 제공자 식별값은 해시로 둔다

- 상태: 채택 (2026-08-22)
- 관련: ADR-0076(AdSense·개인정보처리방침 — 이 결정의 계기), ADR-0077(원장 보존기간),
  ADR-0058(member 폴드), ADR-0064(이력서 게이트), ADR-0072(블로그 프로필)

## 맥락

ADR-0076 에서 개인정보처리방침을 쓰다가 소셜 로그인 항목을 적으려니, 실제로 무엇을 왜
받는지 설명할 수 없었다. 코드를 뒤져 보니 이유가 분명했다 — **효용이 없었다.**

| 항목 | 저장 | 실제 사용 |
|---|---|---|
| `ssoProvider` + `ssoProviderId` | ✅ | **유일한 조회 키** (`findBySsoProviderAndSsoProviderId`) |
| `email` | ✅ | `findByEmail` 이 없다. FE 미사용, JWT 미포함, 메일 발송 기능 자체가 없음 |
| `name` | ✅ | FE 어디에서도 표시하지 않음. 블로그는 `blog_profile.display_name` 을 따로 가짐 |

이메일의 유일한 실사용처는 로그인 때마다 도는 어드민 부트스트랩 비교(`admin-emails`)였다.
그런데 그 장치가 부여하는 `ROLE_ADMIN` 은 **이미 `member_roles` 행으로 남아 있었다**
(2026-08-09 부여). 즉 소임을 다한 코드가 이메일을 받는 유일한 이유였다.

받아서 저장만 하고 아무도 읽지 않는 상태는 개인정보 최소화 관점에서 최악의 형태다 —
위험은 지고 효용은 0이다.

시점도 좋았다. 실사용자가 **0명**이었다(회원 2행 중 1행은 합성 probe). 사용자가 생긴 뒤엔
같은 작업이 훨씬 비싸진다.

## 결정

### 1) 스코프에서 뺀다 — 저장하지 않는 것보다 받지 않는 것이 확실하다

Google 스코프를 `openid email profile` → `openid` 로 줄인다. 응답에 `sub` 말고는 오지 않는다.
Kakao 도 동의항목에서 이메일·프로필을 뺀다.

부수 효과가 하나 더 있다: **동의 화면이 정확해진다.** 쓰지도 않을 이름·이메일을 요구하는
화면은 그 자체로 사용자에게 거짓말이다.

### 2) 제공자 식별값은 HMAC 으로 가린다

`sub` 은 우리 쪽에서 개인을 알아볼 수 없는 값이지만 **제공자에게는 계정을 지목하는 값**이다.
평문으로 두면 DB 유출 시 Google/Kakao 계정과 그대로 대조된다.

`HMAC-SHA256(서버키, "$provider:$sub")` 로 저장한다. 서버키 없이는 원본을 복원할 수 없어
가명처리(개인정보보호법 2조 1의2호)에 해당한다. 조회는 들어온 값을 같은 방식으로 해시해
맞추므로 **기능 손실이 0** 이다.

단순 SHA-256 이 아닌 이유: `sub` 은 값의 공간이 좁고 형식이 알려져 있어(Google 은 21자리
숫자) 무키 해시는 사전 공격으로 되돌릴 수 있다. 서버키가 그 길을 막는다.

제공자 이름을 함께 넣는 이유: 제공자가 다르면 같은 문자열이라도 다른 사람이다.

**해싱은 auth 안에서 한다.** member 로 넘기기 전에 바꾸므로 원본이 서비스 경계를 넘지 않고
`member_db` 에도 남지 않는다.

### 3) 키가 없으면 뜨지 않는다

`AUTH_SUBJECT_HASH_KEY` 가 없거나 32바이트 미만이면 기동에 실패한다. 평문으로 되돌아가는
경로를 두면 그날부터 조용히 원본이 쌓이고, **그 사실은 유출된 뒤에야 드러난다.**

대가는 명확하다 — 키를 잃으면 기존 회원 전원이 로그인 불가다. 저장된 해시를 다시 만들 수
없기 때문이다. 그래서 이 키는 백업 대상이고, 교체 절차는 `auth/CLAUDE.md` 에 적었다.

### 4) 표시 이름은 우리가 만든다

소셜 계정의 실명·닉네임을 받지 않으므로 가입 시점에 이름이 없다. 빈 값으로 두면 화면마다
"이름 없음" 분기가 생기고, 회원 번호를 보여주면 사람이 부를 수 없는 이름이 된다.

`Nickname.generate()` 가 `푸른소나무-4821` 류를 만든다. **실명과 섞이지 않는 어휘**를 쓴다 —
사람 이름처럼 보이는 조합은 그 자체로 실명으로 오해받고, 오해받는 순간 다른 사람이 그것을
개인정보로 다루기 시작한다. 사용자는 `updateName` 으로 언제든 바꿀 수 있다.

### 5) 어드민 부트스트랩을 제거한다 — sub 으로 바꾸지 않는다

`admin-emails` → `admin-subjects` 로 바꾸는 안을 검토했으나 실익이 없었다.

- **레포가 PUBLIC 이라 sub 도 평문 설정에 못 넣는다.** Secret 관리가 그대로 남으므로
  "sub 으로 대체"의 이득이 이메일 스코프 제거 하나인데, 그건 제거해도 똑같이 달성된다.
- 오히려 이 변경의 취지에 역행한다 — 보호하려는 식별자를 설정값으로 한 군데 더 복사한다.
- 매 로그인마다 "이 값과 같으면 ADMIN 부여"가 도는 **상시 권한 상승 경로**를 남기게 된다.

역할은 DB 행에만 둔다. 복구가 필요하면 `INSERT` 한 줄이고, 절차는 `auth/CLAUDE.md` 에 있다.
관리자 1명 규모에서 자동 복구 장치를 위해 상시 경로를 두는 것은 과하다.

**자체 ID/PW 어드민 로그인도 검토했으나 채택하지 않았다.** 지금 이 시스템은 크리덴셜을 하나도
갖고 있지 않다는 것이 큰 장점이다 — 인증을 전부 제공자에 위임했으니 비밀번호 유출 사고가
구조적으로 불가능하다. 관리자 1명을 위해 그 성질을 버리는 것은 YAGNI 이고, 역설적으로
비밀번호 분실 복구에 이메일이 다시 필요해진다.

### 6) `member_db` 에 Flyway 를 붙인다

`email` 이 `NOT NULL` 이라 컬럼을 그대로 두면 신규 가입이 DB 레벨에서 깨진다. 그런데
member_db 에는 Flyway 가 없었고 `ddl-auto: validate` 만 걸려 있었다.

`ScopedFlywayMigrator` 에 이미 "Hibernate 로 만든 스키마에 뒤늦게 Flyway 를 붙이는 경우"를
위한 `baselineVersion` 이 있다. 기존 `members` 를 V1 로 간주하고 `V2__minimize_identity.sql`
부터 적용한다 (game 과 같은 구조, location 은 `classpath:memberdb/migration`).

## 결과

**켜짐**

- 이메일을 **받지 않는다.** 저장 여부를 고민할 필요가 없어졌다.
- 저장된 식별자만으로는 어느 소셜 계정인지 알 수 없다.
- 개인정보처리방침에 "무엇을 왜 받는지"를 정직하게 적을 수 있다.
- 크리덴셜을 하나도 갖지 않는 성질이 유지된다.

**대가**

- **해시 키가 단일 실패점이다.** 잃으면 전원 로그인 불가.
- 제공자 간 계정 통합이 영원히 불가능하다(지금도 그랬지만, 이제는 이메일이라는 복구 수단
  자체가 없다). Google 과 Kakao 로 각각 로그인하면 별개 회원이다.
- 소셜 계정을 잃으면 복구 경로가 DB 직접 수정뿐이다.
- 보존기간처럼 이 결정도 코드·방침·이 문서 세 곳에 걸쳐 있다.

**되돌리기**

되돌릴 수 없다 — 이미 지운 이메일은 다시 받아야 하고, 해시는 원본으로 복원되지 않는다.
그래서 실사용자가 0명인 지금 한 것이다.
