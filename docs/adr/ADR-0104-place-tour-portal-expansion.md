# ADR-0104 — place 에 행사·숙박·여행코스를 같은 관광지 행으로 넣고, 행사 상태는 날짜로 판정한다

- 상태: 제안 (2026-10-02)
- 관련: ADR-0062(SEO·sitemap, §8 · §13), ADR-0065(K-관광 검색), ADR-0069(혜택 링크 허브), ADR-0070(place-ingest CronJob),
  ADR-0071(지역 드릴다운, §5 목록·지도 역할), ADR-0103(관광지 서버 렌더)
- 스펙: `docs/specs/2026-10-02-place-tour-portal-expansion/`

## 맥락

place 는 TourAPI 의 5개 유형(관광지·문화시설·레포츠·쇼핑·음식점)만 받는다. 운영 키로 확인한 결과(2026-10-02)
행사 국문 294·영문 94(10-01 이후 시작), 숙박 국문 2,990·영문 211, 여행코스 국문 1,068 이 더 있고, 지금 DB 의 행사는 0건이다.

행사는 다른 유형과 성질이 다르다 — **시간이 지나면 틀린 정보가 된다.** 「진행 중」을 저장하면 수집이 하루 밀린 날
끝난 행사가 진행 중으로 남는다. 페이지도 끝난 뒤 언제까지 색인에 둘지 정해야 한다. 그런데 place sitemap 은
portal-fe 빌드 시점에 만들어져 배포 사이에 낡는다.

TourAPI 밖의 공공데이터(무장애 · 집중률 · 연관 관광지 · 날씨 등 12종)도 붙일 계획이지만 활용신청 승인 전이라
응답 필드를 아직 실호출로 보지 못했다.

## 결정

1. **새 유형은 `attractions` 행으로 넣는다.** 행사·숙박·여행코스는 TourAPI 의 같은 contentId 체계·같은 보강 오퍼레이션
   (개요·이용정보·사진·반복정보)·같은 서버 렌더 경로를 쓴다. 표·색인을 따로 두면 보강 잡·재색인·렌더가 둘씩 된다.
   다만 파생 분류 `category` 는 유형 코드가 먼저 정한다(`festival`·`stay`·`course`) — 행사의 신분류 `EV` 가 `culture` 로
   접혀 문화시설 목록·지역 건수에 섞이지 않게. 관광 분류(`SIGHT_CATEGORIES`)와 지역 건수 정의는 바꾸지 않는다.
   신분류 `AC` 로 `stay` 가 되는 레포츠 캠핑장은 그대로 두고, 화면의 「숙소」는 `category=stay` 전체로 본다.
2. **행사 상태는 저장하지 않는다.** 원천의 시작일·종료일은 컬럼(V23)에 그대로 두고, 색인에는 재색인이 정규화한 유효 시작일·
   유효 종료일(종료일이 없으면 시작일)을 `date` 필드로 싣는다 — 원값을 그대로 실으면 종료일 없는 행사가 범위 질의에서 빠진다.
   상태(진행 중·예정·종료·날짜 없음)와 필터 범위(진행 중·이번 주말·예정·이번 달·종료 아님)는 search:domain 의 객체 하나
   (`EventSchedule`)가 함께 갖고, 범위로 고른 문서에 상태를 다시 매기면 같은 답이 나오는 것을 날짜 격자 픽스처로 묶는다.
   오늘(KST)은 application 서비스가 `Clock` 으로 계산해 넘기고 렌더러·어댑터는 시계를 읽지 않는다. 스케줄이 밀려도 상태가 낡지 않는다.
3. **수집은 별도 place-ingest CronJob(매일 KST 03:10)이다.** 재색인은 외부 API 를 부르지 않는 구조라 합치지 않는다(ADR-0070 과 같은 이유 —
   외부 :443 은 place-ingest 파드에만 열린다). 새 egress 정책은 없다. 시각은 구글 place_id 보강(03:20)과 겹치지 않는 자리다 —
   두 경로 사이에 낙관적 잠금이 없어 겹치면 한쪽이 쓴 값을 다른 쪽이 덮는다.
4. **만료: 종료 페이지는 200 + 「종료된 행사」, 종료 + 31일부터 `noindex`.** 이미 색인된 URL 을 404 로 지우면 사용자가 지난 행사를
   찾아오는 길도 끊긴다. 30일 유예 뒤에는 검색 결과에서 내린다. `noindex` 는 「개요 없음 OR 종료 + 31일」이다.
   **정본은 서버 렌더의 robots 다** — 요청마다 계산하므로 빌드 시점에 묶이지 않는다. 화면 `useSeo` 는 같은 판정을 따른다.
5. **행사 URL 은 정적 sitemap 에서 빼고 동적 sitemap 하나로 낸다.** `sitemap-places-events.xml` 을 portal-fe nginx 가 search 의 내부 렌더
   경로로 프록시하고(ADR-0103 의 프록시·네트워크 정책 재사용), search 가 요청 시 「종료 + 30일 ≥ 오늘」인 행사만 싣는다.
   조회 실패는 503 이다 — 빈 200 은 크롤러에게 URL 이 모두 사라졌다는 뜻이 된다. 그래서 이 location 은 상세 렌더 location 의
   SPA 셸 폴백을 갖지 않고, place 호스트가 아니면 404 다(한 server 블록이 여러 호스트를 서빙한다).
6. **숙박은 정보만 낸다.** 예약 URL·예약 안내 원문 키는 저장하되(원천 전부 적재) 그리지 않고, 제휴·예약 링크를 두지 않는다.
   모든 관광지에 붙는 「여행 상품」 검색 딥링크(OTA)도 숙박에는 내지 않는다 — 제휴 승인 때 스펙 변경 없이 숙박 제휴 링크가 되는 길을 막는다.
   제휴 링크는 deal(ADR-0069)의 고지·리다이렉터 규칙 아래에서만 다룬다.
7. **2단계 공공데이터는 승인 순서대로 API 마다 독립 배포한다.** 각 API 는 승인 뒤 첫 호출 표본을 스펙 `implementation/` 에 남기고
   표본의 필드를 전부 적재한 다음 화면을 정한다. 날씨·대기는 CronJob 이 시군구·측정소 단위로 선수집하고 상세는 저장값만 읽는다.
   TourAPI 가 아닌 원천을 관광지 행으로 넣을 때의 자연키(원천 구분)는 첫 해당 API 착수 때 이 ADR 에 덧붙여 정한다.

## 대안

- **행사 전용 표·색인** — 날짜 필드가 자연스럽지만 보강 잡 4종·재색인·서버 렌더·검색 API 가 두 벌이 된다. 차이는 날짜 두 개뿐이다. 기각.
- **상태를 수집 잡이 저장** — 판정이 단순하지만 잡이 실패한 날 상태가 틀린다. 저장 플래그를 지우는 배치도 하나 더 필요하다. 기각.
- **재색인 잡에서 행사 목록도 받기** — CronJob 하나가 줄지만 search-batch 에 외부 egress 를 열어야 하고 한쪽 실패가 다른 쪽을 막는다. 기각.
- **종료 즉시 404/410** — 색인 정리는 빠르지만 지난 행사를 찾는 방문이 끊기고, 수집 지연·원천 날짜 정정 때 살아 있는 행사가 410 이 될 수 있다. 기각.
- **정적 sitemap 에 행사를 두고 빌드 주기를 늘리기** — 배포마다 이미지가 바뀌고, 배포가 없는 주에는 여전히 낡는다. 기각.
- **숙박 예약 링크(제휴)** — 수익원이지만 규제·고지 규칙이 deal 에 있고 place 에 두면 두 곳에서 관리된다. 이번 범위 밖.

## 결과

- place 에 컬럼 셋(V23: 행사 시작일·종료일, 목록 행 원문), CronJob 하나(`place-ingest-tour-sync`). 하루 호출은 숙박·코스 약 44콜 +
  행사 −365 창 쪽수이고, 행사 쪽은 첫 호출 표본으로 확정한다(국·영 합 60쪽을 넘으면 창을 −180일로 줄인다).
  새 행 약 4,600건(국 4,352 · 영 305)은 기존 보강 잡의 대상이 되어 개요·이용정보·사진이 며칠에 걸쳐 채워진다.
- 관광지 색인에 유효 날짜 `date` 필드 둘과 색인하지 않는 코스 구성 객체. 검색 API 에 `eventStatus` 필터(종료 아님 포함)와 `sort=eventStart`.
- 숙박은 개요와 대표 사진이 둘 다 있을 때만 정적 sitemap 에 싣고, 새 유형 상세에는 `attraction-end` 광고 지면을 그리지 않는다 —
  원천 개요를 그대로 쓴 관광지 상세가 AdSense 반려 사유였고(ADR-0076), 숙박 본문은 자체 가공이 가장 적은 유형이다.
- nginx 정확 일치 location 하나, search 에 행사 sitemap 렌더 하나. 새 네트워크 정책 없음.
- 정적 sitemap 의 시도 조각이 10,000건 창을 넘으면 빌드가 실패한다(새 유형이 늘린 문서가 조용히 잘리지 않게).
- 원천 대장(`data-sources.md`)에 오퍼레이션 셋과 CronJob, 2단계 API 는 승인될 때마다 한 줄씩.
