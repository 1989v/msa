AI 에이전트에게 주는 규칙은 한 파일에 모으면 지켜지지 않는다. 이 글은 규칙을 네 층으로 나누는 기준과 층별 작성 항목을 다룬다.

| 층 | 파일 | 담는 것 | 강제되나 |
|---|---|---|---|
| 전역 | `~/.claude/CLAUDE.md` | 내 작업 방식 — 응답 형식·검증 습관·안전장치 | 아니오 |
| 레포 루트 | `{repo}/CLAUDE.md` | 프로젝트 아키텍처·네비게이션 | 아니오 |
| 도메인 | `{service}/CLAUDE.md` | 그 도메인의 규칙·불변식·계약 | 아니오 |
| 게이트 | 빌드 태스크·훅·CI | 위반 시 빌드 실패 | **예** |

로드는 위에서 아래로 누적된다. 아래층이 위층을 덮지 않고 더한다.

## 전역과 레포 루트는 다르다

로드 순서로는 전역이 먼저다. 공유되는 컨벤션의 시작점은 레포 루트다.

전역 파일은 홈 디렉토리에 있다. 레포를 클론한 사람에게는 가지 않는다. 팀이 따라야 할 규칙을 여기 쓰면 내 노트북에만 존재하게 된다.

판정은 한 문장으로 끝난다. **이 레포 밖에서도 똑같이 적용되나.**

## 배치 판정 두 질문

```
규칙이 하나 생겼다
  │
  ├─ 이 레포 밖에서도 적용되나?
  │     예 → 전역
  │     아니오 ↓
  │
  ├─ 어겼을 때 컴파일·테스트가 잡아주나?
  │     아니오(조용히 깨진다) → 게이트
  │     예 ↓
  │
  └─ 한 도메인에만 해당하나?
        예 → 도메인 문서
        아니오 → 레포 루트
```

두 번째 질문이 핵심이다. 컴파일 에러가 나는 규칙은 이미 강제되고 있으니 문서로 충분하다. 게이트로 내릴 것은 **배포된 뒤에야 드러나는 것**이다.

## 전역에 쓰는 것

레포와 무관하게 늘 같은 것만 쓴다. 프로젝트 전용 규칙을 넣으면 다른 레포에서 오작동한다.

| 넣는 것 | 예 |
|---|---|
| 응답 형식 | 답 먼저. 결론 반복 금지 |
| 검증 습관 | 비자명한 수정 뒤 검증 실행. 출력 없이 통과 주장 금지 |
| 안전장치 | 파괴적 작업 사전 고지. 훅 우회 금지 |
| 설계 원칙 | KISS → YAGNI → Rule of Three. 최소 수정 |

넣지 않는 것은 특정 레포의 빌드 명령, 도메인 용어, 배포 절차다.

## 레포 루트에 쓰는 것

루트는 규칙 본문을 담지 않는다. 길어지면 끝까지 읽히지 않는다. 어디를 보라고만 하고 본문은 `docs/` 로 보낸다.

| 절 | 내용 |
|---|---|
| Commands | 빌드·테스트·배포 + 최초 1회 설정(훅 활성화 등) |
| Architecture | 의존성 방향, 레이어 규칙, 구조 변경 시 ADR 필수 |
| Key Conventions | 한 줄 요약 + 문서 링크. 위반 시 결과를 한 문장으로 |
| Navigation | 서비스 표 — 각 서비스가 무엇이고 문서가 어디 있나 |
| Agent Behavior | 리스크 분류, 검증 루프, 컨텍스트 복구 |

## 도메인 문서에 쓰는 것

가장 오해받는 층이다. 과거에 터진 것 모음이 아니라 **그 비즈니스 도메인의 규칙**이다. 사고 이력은 규칙에 근거로 붙는다.

| 항목 | 무엇을 적나 |
|---|---|
| 도메인 언어 | 이 도메인에서 단어가 무엇을 뜻하나. 비슷한 두 개념의 구분 |
| 불변식 | 항상 참이어야 하는 것 |
| 대외 계약 | 이벤트 토픽·API 응답·저장 포맷 중 남이 의존하는 것 |
| 소유권 경계 | 무엇을 쓰고 무엇을 읽기만 하나 |
| 판단 기준 | 이 도메인 특유의 선택 규칙 |
| 함정 | 위 규칙을 어겼을 때 실제로 벌어진 일 |

도메인별로 무엇이 오는지는 아래와 같다.

| 도메인 | 그 층에 올 것 |
|---|---|
| 검색 | 읽기 전용 모델. 색인 계약의 SSOT 위치. 쓰기/읽기 모델을 합치지 않는 이유 |
| 주문 | 상태 전이표. 외부 IO 를 트랜잭션 밖에 두는 규칙. 발행 토픽 계약 |
| 재고 | 수량의 진실이 어디인가. 동시성 제어 방식. 같은 JVM 이라도 메시지로만 통신 |
| 트레이딩 | 도메인 원칙이 곧 타입 제약. 멀티테넌시 키 필수 |
| 외부 데이터 연동 | 원천 필드 전량 적재. 가공은 파생 컬럼. 호출 한도가 자원이라는 것 |
| 제휴·광고 | 법률 제약이 스키마 제약이 되는 지점. 링크 무변조 규칙 |

## 게이트로 내리는 것

문서로 안 되는 것만 내린다. 무거운 도구는 필요 없다. 소스를 텍스트로 읽어 판정하는 빌드 태스크로 대부분 커버된다.

| 종류 | 신호 |
|---|---|
| 레이어 의존 | 그 패키지가 부르면 안 되는 패키지를 import 하나 |
| 기술 누수 | 안쪽 레이어가 DB·HTTP·메시징 클라이언트를 직접 쥐나 |
| 역방향 의존 | 바깥 레이어가 안쪽을 참조하나 |
| 구조 규약 | 디렉토리와 패키지 선언이 같은가 |
| 계약 일치 | 스키마 정의와 코드의 필드가 같은가 |
| 모듈 경계 | 자기 소유가 아닌 모듈을 import 하나 |

## 문체가 곧 규칙이다

세 문서 층 모두 같은 형태를 쓴다.

> 굵은 단정 → 실측 근거(숫자·날짜·사건) → 위반 시 무엇이 깨지나

```markdown
- **전체 동기화 API 는 부분 레코드를 넣으면 나머지 필드를 지운다.**
  2026-08-17 대표 레코드의 좌표·본문이 실제로 날아갔다.
  부분 갱신이 필요하면 전용 경로를 쓴다.
```

"~하는 것이 좋다"는 지켜지지 않는다. "~하면 X 가 깨진다"만 지켜진다. 근거가 없으면 6개월 뒤 그 규칙이 사실인지 미신인지 판별할 수 없다.

보조 규칙은 넷이다.

1. 본문은 한 곳에만 둔다. 다른 층에서는 링크만 건다.
2. 실제 장애에는 표식을 붙인다. 새로 온 사람이 여기부터 읽는다.
3. 날짜를 적는다. 규칙에는 유효기간이 있다.
4. 문서와 코드가 어긋나면 문서를 먼저 의심한다.

## 허용목록이 진짜 실패 모드다

새 게이트를 켜면 기존 위반이 쏟아진다. 통과시키는 방식이 게이트의 수명을 정한다.

```
허용목록에 넣되, 항목마다 "왜 · 언제 비우는지"를 적는다
  → 단계마다 비운다
  → 비운 항목은 다시 넣지 못한다
```

두 종류의 예외를 섞으면 안 된다.

| 종류 | 성격 | 표시 |
|---|---|---|
| 부채 | 정리 중. 결국 비어야 정상 | "정리 완료 — 새 항목 금지" |
| 영구 예외 | 구조적으로 정당. 비울 대상이 아님 | "문서화된 유일한 예외 — 이유" |

섞으면 다음 사람이 영구 예외를 지우려 들거나 부채를 영구 예외로 착각한다.

## 게이트 배선을 잊으면 없는 것과 같다

빌드 도구의 `check` 같은 상위 태스크에 붙였다고 안심하면 안 된다. CI 가 그 태스크를 부르지 않으면 아무 데서도 돌지 않는다.

훅·CI·배포 파이프라인 세 지점에서 부른다. 개별 이름이 아니라 묶음 태스크 하나를 부른다. 개별 이름을 부르면 게이트가 늘 때 호출부 추가를 잊는다.

훅은 켜져 있는지 확인한다. 저장소에 훅 파일이 있는 것과 그것이 동작하는 것은 다르다. 설치 절차는 루트 문서 맨 앞에 둔다.

## 세우는 순서

1. 전역부터. 어느 레포에서나 같은 작업 방식이다. 한 번 쓰고 계속 쓴다.
2. 레포 루트 골격. Commands · Architecture · Navigation. 규칙은 아직 몰라도 된다.
3. 게이트 먼저, 정리는 나중. 정리하는 동안에도 새 코드가 생긴다.
4. 도메인이 생길 때마다 도메인 문서. 도메인 언어와 불변식부터 적는다.
5. 사고가 나면 별도 문서가 아니라 그 코드 옆에 규칙을 추가한다.

## 체크리스트

- [ ] 전역에 프로젝트 전용 규칙이 섞여 있지 않은가
- [ ] 레포만 클론한 사람이 필요한 규칙을 다 볼 수 있는가
- [ ] 루트 문서가 본문을 담지 않고 링크만 거는가
- [ ] 도메인 문서에 도메인 규칙이 있는가. 사고 목록만 있지 않은가
- [ ] 같은 규칙이 두 곳에 복제돼 있지 않은가
- [ ] 조용히 깨지는 규칙이 게이트로 내려가 있는가
- [ ] 게이트를 훅·CI·배포 세 지점에서 묶음 태스크로 부르는가
- [ ] 허용목록의 모든 항목에 이유가 적혀 있는가
- [ ] 훅 설치 절차가 루트 문서 맨 앞에 있는가
