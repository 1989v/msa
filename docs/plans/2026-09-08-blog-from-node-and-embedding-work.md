# 블로그 적재 계획 — 노드 회수 · 임베딩 결정 · 모델 공급망

옵시디언 `1989v` 볼트에 쌓인 것 중 **밖에 내놓을 값이 있는 것 셋**을 글로 옮기는 계획.
초안 작성부터 DB 반영까지의 순서는 `blog-post` 스킬이 갖고 있다. 이 문서는 **무엇을 쓸지와
무엇을 버릴지**만 정한다.

## 옮길 때 반드시 버려야 하는 것

볼트 문서는 전부 **경위**다. 블로그 규약(`docs/conventions/blog-writing.md` §1.1)은 그것을 뺀다.

| 볼트에 있는 것 | 글에 담나 | 이유 |
|---|---|---|
| 「켠 채로 지우려다 사이트를 6분 죽였다」 | **뺀다** | 시도와 실패 — 커밋 메시지의 몫 |
| 「처음 검사가 476,751 을 내고 멈췄다」 | **뺀다** | 작업 경위 — 옵시디언의 몫 |
| 「사전 방식으로 하기로 했다」 | **뺀다** | 의사결정 서술 — ADR 의 몫 |
| 「인덱스가 5개라 10만 행 배치가 3분 40초에도 커밋 안 된다」 | **담는다** | 규칙과 한계 |
| 「`freelist_count = 0` 이면 VACUUM 은 회수할 것이 없다」 | **담는다** | 결과물의 동작 |
| 「e5-small 1스레드 43.8ms, 2스레드 45.1ms」 | **담는다** | 주장을 받치는 실측값 |

`scripts/lint-blog-post.py` 의 **F7 이 이력·경위 문장을 정규식으로 잡는다.** 볼트 문장을 그대로
붙이면 발행 전에 막힌다. 설계 이유가 정보로 필요하면 **결과 문장 뒤 한 줄**로 붙이고 서사로 풀지 않는다.

## 글 1 — k3s 의 state.db 가 커지는 이유와 막는 법

```yaml
title: k3s state.db 가 26GB 가 되는 이유
slug: k3s-kine-state-db-growth
category: /tech/server
summary: k3s 는 etcd 대신 kine 을 쓰고, kine 은 오브젝트가 바뀔 때마다 행을 추가한다. 컴팩션이 진척되지 않으면 리스 갱신만으로 하루 4만 행이 쌓인다. VACUUM 은 회수하지 못하고, 지우는 방식은 apiserver 를 굶긴다.
```

**결론 요약 표(첫 h2 앞, F8 필수)**

| 항목 | 값 |
|---|---|
| 행이 쌓이는 원리 | 오브젝트 변경 1회 = 행 1개 (append) · 삭제도 행 1개(tombstone) |
| 주 원인 | 리더 선출·하트비트 리스 — 하루 약 4만 행 |
| 확인 | `SELECT MAX(prev_revision) FROM kine WHERE name='compact_rev_key'` 가 0 이면 컴팩션이 멈춘 것 |
| VACUUM | `freelist_count = 0` 이면 회수할 공간이 없다 |
| 안전한 정리 | k3s 정지 → 생존 행만 새 파일에 복사 → 인덱스 일괄 생성 |
| 평시 방지 | 10분 주기 · 2,000행 청크 타이머 |

**절 구성**
1. kine 이 무엇이고 무엇을 저장하나 — `state.db` = 이 클러스터의 etcd
2. 행 수는 오브젝트 수가 아니다 — 711만 행 / 고유 키 47.8만 / 살아있는 키 1,345 (실측 표)
3. 무엇이 쌓나 — 리스 522만 · CronJob 계열 139만
4. VACUUM 이 듣지 않는 조건 — `page_count` · `freelist_count` 읽는 법
5. 지우기가 위험한 이유 — 인덱스 5개(`UNIQUE(name, prev_revision)` 포함), 10만 행 배치가 3분 40초
6. 옮기는 방식 — SQL 전문 + 불변식은 **살아있는(deleted=0) 최신 행 수**
7. 가드 타이머 — 청크 크기가 안전장치다 (처리 용량 576만행/일 vs 생성 4만행/일)

**담을 실측**: 26.4GB → 24MB · ReplicaSet 동기화 4.47초 → 83µs · Slow SQL 상시 → 0건
**주의**: tombstone 을 「최신 행」으로 세면 안 되는 이유는 **규칙**으로 쓴다(경위 아님).

## 글 2 — 임베딩 질의 사전과 라이브 인코딩의 손익분기점

```yaml
title: 임베딩 검색에서 질의 사전이 라이브 인코딩을 이기는 조건
slug: embedding-query-dictionary-vs-live-breakeven
category: /tech/server/search
summary: 미리 만든 질의 사전은 적중한 질의에만 이득을 준다. 작은 모델을 상주시키면 이득은 작지만 모든 질의에 적용된다. 두 방식의 우열은 한 줄의 나눗셈으로 갈린다.
```

**결론 요약 표**

| 항목 | 값 |
|---|---|
| 판정식 | `라이브가 이기는 적중률 = Δ작은모델 / Δ큰모델` |
| 실측 예 (ko) | e5-small +0.0317 / Qwen3-4B +0.0541 → **58.6%** |
| 영어 | arctic-ko +0.0530 / Qwen3-4B +0.0619 → **86%** |
| 부수 효과 | 작은 모델은 차원도 작다 — k-NN 색인 478MB → 180MB |

**절 구성**
1. 두 방식이 각각 무엇을 하는가 (그림 1장 — mermaid flowchart)
2. 이득의 모양이 다르다 — 사전은 적중률에 비례, 라이브는 상수
3. 판정식과 대입 (nDCG 표)
4. 라이브 쪽 비용 — ARM CPU 실측 표 (1/2/4 스레드)
5. 작은 모델이 코어를 더 안 쓴다는 사실 — 1코어 43.8ms vs 2코어 45.1ms
6. 크기가 커지면 왜 급격히 나빠지나 — 질의 지수 1.13 · 1,000자 문서 지수 1.54
7. 한계 — 적중률은 서비스마다 다르므로 **재기 전에는 고를 수 없다**

**주의**: 「처음에 arctic-ko 를 골랐다가 바꿨다」는 **뺀다.** 대신 규칙으로:
*「오프라인 임베딩에서 인코딩 속도는 판정 기준이 아니다 — 사용자 요청 경로에 없다.」*

## 글 3 — 자체 호스팅 모델의 위험은 가중치가 아니라 적재 경로

```yaml
title: 모델을 내 서버에 올릴 때 실제로 위험한 것
slug: self-hosted-model-loading-path-risk
category: /tech/server
summary: 임베딩 모델의 순전파는 네트워크를 열지 않는다. 위험은 가중치를 불러오는 경로에 있고, pickle 역직렬화와 커스텀 모델 코드가 그 경로다. 확인은 저장소 파일 목록 세 줄로 끝난다.
```

**결론 요약 표**

| 층 | 코드 실행 | 확인 방법 |
|---|---|---|
| safetensors 가중치 | 없음 | 포맷에 코드 개념이 없다 |
| pickle 가중치 (`.bin`/`.pt`) | **있음** | 확장자로 판별 |
| 커스텀 모델 코드 | **있음** | `modeling_*.py` · `config.json` 의 `auto_map` |
| 토크나이저·설정 | 없음 | 위 항목과 함께 본다 |

**절 구성**
1. 방향이 뒤집힌다 — API 는 데이터가 나가고, 자체 호스팅은 남의 바이너리가 들어온다
2. 실제로 실행되는 층 (표)
3. 확인은 파일 목록 세 줄
4. 후보 6종 감사 결과 표 — **조직 계정이 적재 경로의 안전을 보장하지 않는다**
5. 통제 네 겹 — safetensors 강제 / `trust_remote_code=False` / 리비전 고정 / egress·토큰 없음
6. 검사가 아니라 차단으로 — 적재 함수 한 곳에서 예외를 던지는 코드
7. 리비전 고정은 보안이 아니라 재현성 때문에도 필요하다 (벡터 공간 식별)

**주의**: 특정 모델을 「위험하다」고 단정하지 않는다. `bge-m3` 는 **pickle 만 배포한다**는
사실만 쓰고, 그것이 무엇을 뜻하는지는 표가 말하게 한다.
