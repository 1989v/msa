## 이 프롬프트는 한 번만 온다

사용자는 이 메시지 뒤로 답하지 않는다. 질문은 답을 받지 못한다. 세부 기획·조작 방식·기술 선택·연출은 네가 결정한다. 이번 작업은 최초 프롬프트 하나로 네가 어디까지 게임을 완성할 수 있는지 확인하는 시험이다.

계획·설계·코드 초안·첫 실행 성공에서 멈추지 마라. 구현 → 실행 → 관찰 → 디버깅 → 개선 → 재검증을 스스로 이어간다. 토큰이나 시간을 아끼려고 범위를 줄이지 마라. 긴 작업을 나눠 달라고 하지 마라. 쉬운 MVP 수준에 스스로 상한을 두지 마라. 장식과 기능 개수로 품질을 대신하지 마라.

## 품질의 정의 (우선순위 순)

1. 정확성과 안정적인 프레임 — 입력이 씹히지 않고, 60fps 가 유지된다
2. 장르 특유의 판단과 보상 — {{GENRE}} 를 하는 이유가 되는 손맛·긴장·쾌감. 이것이 없으면 나머지는 의미가 없다
3. 캐릭터·소리·화면의 완성도 — 무음은 미완성, 정적인 화면은 미완성, 예고 없는 적 공격은 금지
4. 콘텐츠 양 — BRIEF.md 의 벤치마크는 하한이다

첫 판부터 어려워야 한다. 가만히 있으면 죽고, 아무 키나 난타해서는 못 깬다. 몸풀기·튜토리얼 구간을 두지 마라.

## 완성의 정의 — 도구가 판정한다

- `node forge/gate.mjs` 가 전 축 PASS 다. 문턱은 forge/thresholds.json 이고 하한이다. 게이트를 통과하지 못하면 세션은 끝나지 않는다(Stop 훅). 게이트를 낮추지 말고 게임을 고쳐라.
- 게이트가 만든 스크린샷을 전부 Read 로 직접 보고 verifications/visual-review.md 에 한 장 한 줄로 적는다. 수치가 초록이어도 그림에서만 보이는 결함이 있다.
- 그 뒤 처음부터 끝까지 직접 플레이(forge/play.mjs 의 keys/touch 시퀀스)해 재미없는 지점을 찾아 고친다. "동작한다" 와 "재미있다" 는 다르다.

판정 근거는 네가 만든 것이 아니어야 한다. "고쳤다" 는 코드가 아니라 게이트의 측정값이 달라진 것으로 말한다. 옛 산출물을 재고 확인했다고 하지 마라(게이트가 sourceHash 로 잡는다). 스크린샷은 파일로 남기고 Read 로 본다 — base64 를 대화로 흘리지 않는다.

## 기술

- 순수 HTML5 Canvas(2D 또는 WebGL) + 바닐라 JS. 빌드 도구 0, 외부 라이브러리 0. index.html 을 열면 바로 실행된다.
- 결정론적 스텝 API window.__forge 를 forge/step-api.md 계약대로 붙인다. 이것이 없으면 검증도 완성도 없다 — 첫 실행 가능 시점에 가장 먼저 만든다.
- 입력은 이벤트에서 상태만 기록하고 판정은 step 안에서 한다. 난수는 시드 RNG 하나. alert/prompt/confirm 은 쓰지 않는다.
- 한국어 UI. 게임 용어는 한국 통용("스테이지 N").
