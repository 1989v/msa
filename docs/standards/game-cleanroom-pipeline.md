# 게임 클린룸 파이프라인 — 신작 생산 표준

> **용도**: 게임 신작 1개 = 새 클린 세션 1개. 아래 **마스터 프롬프트**의 `⟨…⟩` 슬롯만 채워
> 새 세션에 그대로 전달한다. 완료 후 **통합 절차**(이 문서 하단)는 메인/통합 세션이 수행한다.
>
> **근거**: 클린룸 실험 2회(abyssal-crown, raging-fist-saga) 실측 — 기존 게임·lib 맥락을 차단한
> 세션이 메인 세션 대비 일관되게 높은 게임 코어 품질을 냈다(기존 관습이 앵커로 작용).
> 품질 마지노선 = **abyssal-crown** (`docs/conventions/game-art-baseline.md` 기준 상향 참조).

## 사용법

1. 새 세션을 연다. **완전 클린룸을 원하면** 레포 밖 빈 디렉토리에서 세션을 시작해 산출물
   폴더만 절대경로로 지정한다 (레포 안에서 시작하면 CLAUDE.md 의 게임 목록이 자동 로드되어
   약한 오염이 생긴다 — 허용 범위지만 알고 쓸 것).
2. 아래 마스터 프롬프트의 슬롯을 채워 첫 메시지로 보낸다.
3. 완료 보고를 받으면 이 문서의 **통합 절차**를 메인 세션에서 실행한다.

## 진행 모드 (2026-08-15 실측 피드백 반영 — 디폴트 변경)

- **디폴트 = 수직 슬라이스 우선.** 전량 생산 후 첫 노출이 아니라, **극초반 1구간**을 목표
  품질 100% 로 먼저 완성해 사용자에게 체크를 받는다. 슬라이스에 반드시 포함:
  핵심 조작 전부(이동/점프/대시/공격/차지 등) · 대표 적 2~3종 · 이펙트/사운드/아트 문법
  최종본 · 대표 배경 1세트 · 벤치마크 나란히 비교표. **슬라이스의 품질이 전체 품질의
  상한이므로, 벤치마크 하한 판정을 슬라이스 단계에서 끝낸다.**
- 사용자 피드백 반영 후 나머지를 완주한다.
- **예외**: 사용자가 "끝까지 완성" / "완주" 를 명시적으로 지시하면 중간 체크 없이 묻지 않고
  끝까지 완성한다.
- 근거: nova-strike 1차 실측 — 전량 생산 후 첫 노출에서 벤치마크(32비트 세대 대표작) 대비
  그래픽·해상도 활용·조작감이 하한 미달(사용자 평가 30점)로 판정. 슬라이스 체크포인트가
  있었다면 초반에 교정됐을 갭이다.

## 전역 가드레일 (장르 불문 — 2026-08-24 신설)

프리셋보다 위에 있는 규칙이다. **모든 게임에 적용**되고, 반복해서 지적받은 것만 올렸다.

### G1. 플레이어블 해상도 — "캐릭터가 커서 맵이 작아 보인다"

가장 자주 나오는 지적이다. 원인은 맵이 실제로 작은 것보다 **카메라가 너무 붙어 있는 것**인
경우가 많다. 카메라 종류별 상한을 지켜라.

| 카메라 | 주인공 높이 / 화면 높이 | 한 화면이 보는 월드 |
|---|---|---|
| 사이드뷰 액션 (벨트스크롤·플랫포머) | **1/7 ~ 1/9** | — |
| 탑다운·쿼터뷰 전투 | **1/12 ~ 1/16** | 월드의 **10% 이하** |
| 전략·디펜스 (대형 맵) | **1/16 ~ 1/24** | 월드의 **10% 이하** (권장 5%) |
| 시뮬·건설 | **1/12 ~ 1/20** | 월드의 **10% 이하** |

- **판정 신호**: 플레이 영상을 보고 "맵이 좁다 / 캐릭터가 크다" 는 말이 나오면 **실패**다.
  수치를 다시 재라
- **비율은 논리값이 아니라 "실제로 그려지는 높이" 로 재라.** stats 의 크기 값과 화면에 찍히는
  픽셀은 다르다(스프라이트 여백·스케일·리그 확대). 실측 사례: stats 기준으로는 맞는 줄 알았는데
  실제 렌더 높이로 재니 1/11.2 였다 (목표 1/16~1/24)
- **규칙은 결과 수치다. 도달 방법은 자유다** — 표의 비율만 만족하면 된다.
  다만 **캐릭터 축소보다 월드 확대를 우선하라**: 캐릭터를 줄이면 **소품·사거리·판정폭을 함께
  재조정**해야 하고 그게 "닿는데 안 맞는다" 의 발생 경로다. 월드만 키우면 **지도 배치 좌표만**
  바뀌어 그 경로가 아예 생기지 않는다 (실측: 10240² + 캐릭터 원본 유지로 1/19.4·5.88% 달성,
  전투 수치 한 줄도 안 건드림)
  - 월드 크기는 **줌 단계가 전부 표 안에 들어오는지**로도 결정된다. 너무 작으면 유효 줌 구간이
    좁아져 3단 줌의 폭이 안 나온다
- **★ 두 수치가 서로 당길 때 — 월드를 키워라.** 캐릭터 비율과 시야 % 는 같은 카메라를 두고
  반대로 움직인다. 줌아웃하면 캐릭터 비율은 맞지만 시야 % 가 상한을 넘고, 줌인하면 반대다.
  **둘 중 하나를 포기하지 말고 월드 크기를 늘려서 둘 다 맞춰라.**
  (실측: 6144² 에서 1/20 을 맞추면 시야가 15.8% 로 10% 상한 초과 → 8192² 로 확대가 정답.
  "맵이 짧다" 는 사용자 지적과도 같은 방향이다)
- **줌을 넣어라** — 최소 2단, 대형 맵은 3단. 기본 줌은 위 표의 중간값
- 캐릭터를 줄일 때 **상호작용 소품·사거리·판정폭을 함께 재조정**하라 (프리셋 1-b 참조)

### G2. 한국어 명명 — 직역투 금지

**반복 지적**: `봉화` `결속` `환류` `병기회수` 처럼 **영문 개념을 한자어로 직역한 말**이 계속 나온다.
뜻은 맞아도 **처음 본 사람이 기능을 못 짐작하면 실패**다.

**판단 기준 하나**: *이 단어를 처음 본 플레이어가 그 기능을 짐작할 수 있는가?*

| 금지 | 대신 |
|---|---|
| 영문 개념의 한자어 직역 (`환류` ← recycle, `결속` ← bond, `병기회수` ← salvage) | **일상어** (`되팔기` `연결` `재활용`) |
| 문어체·옛말 (`잿불` `황천길` `통금`) | 지금 쓰는 말 |
| 억지 음차 (`어비스 크라운` `기어 배스천`) | **영문 그대로** 쓰거나 한국어 일상어로 |
| `~소` `~장` `~단` `~전` 접미사 남발 | 짧고 입에 붙는 2~5음절 |

- 서구권 세계관이면 **영문 그대로**가 낫다. 음차하지 마라
- 한국어는 **진짜 한국 소재이거나 일상어일 때만**
- **★ 기능 라벨과 세계관 고유명사를 구분하라 — 강도가 다르다**
  - **기능 라벨(강제)**: 자원명 · 버튼 · 상태 표시 · 시스템 용어. **플레이에 필요한 정보**이므로
    처음 본 사람이 바로 읽혀야 한다. `툴팁으로 설명해야 이해되면 이름이 틀린 것이다`
  - **세계관 고유명사(권고)**: 몬스터·지명·인명. 톤을 위해 예스러운 말을 써도 된다.
    다만 **기능을 가리키는 순간**(예: 자원 이름을 겸하는 고유명사) 강제 규칙으로 넘어간다
  - 판별법: *이 단어를 몰라도 게임을 진행할 수 있는가?* 못 하면 기능 라벨이다
- **★ 노출 빈도와 명확도를 뒤바꾸지 마라.** 가장 많이 보이는 자리(배지·HUD·이름표)에는
  **가장 명확한 표현**을 두고, 긴 설명은 패널로 내려라. 반대로 하면 — 짧은 약어를 상시 노출하고
  뜻이 확실한 말을 패널 안에만 두면 — **처음 온 사람은 그 패널을 열어볼 이유가 없어서**
  핵심 개념이 영영 전달되지 않는다.
  실측: `자동 조종`(패널) + `자동`(배지) 조합에서 배지만 본 사람은 "자동 공격 토글" 로 읽었다.
  배지를 **`AI`**, 패널을 **`AI 가 조종 중`**(문장이라 해석이 필요 없다)으로 바꿔 해결
- **개명 후에는 "처음 본 사람이 그 기능으로 읽는가" 를 자가 검증하라.** 1차 개명이 기준에
  미달인 경우가 실제로 있었다
- 위 금지 목록은 **게임 제목·기능 라벨**에 하드하게 적용된다 (제목 정책은 V40/V42 재작명 참조)

### G3. 화면 흔들림 — 눈이 아프면 실패

**반복 지적**: 보스 처치 등에서 흔들림이 과해 눈이 아프다.

| 상황 | 진폭 (화면 높이 대비) | 지속 |
|---|---|---|
| 일반 타격 | **≤ 0.6%** | ≤ 180ms |
| 대형 이벤트 (보스 처치·필살) | **≤ 1.5%** | ≤ 500ms |

- **연속 이벤트에서 가산하지 마라** — 겹치면 합이 아니라 **최댓값으로 대체**하고 감쇠시켜라.
  가산이 "눈이 아픈" 흔들림의 실제 원인이다
- 설정에 **「화면 흔들림 줄이기 / 끄기」** 를 둬라 (접근성)
- 흔들림으로 타격감을 만들려 하지 마라 — 히트스톱·이펙트·사운드가 먼저다

### G4. 2D / 어중간한 3D 금지

**반복 지적**: "3D 같은데 어중간해서 별로다. 차라리 2D 가 낫다."

- 리그·부품 조립 방식은 **부품이 따로 노는 순간 2D 도 3D 도 아닌 룩**이 된다.
  관절 겹침·외곽선 연속성·경계 그림자로 **하나의 실루엣**으로 읽히게 하라
- **원근 과장을 억제**하라. 깊이 표현이 필요해도 룩은 명확한 2D 를 목표로
- 애매하면 **2D 로 확실히 가라.** 어중간한 입체감보다 잘 그린 2D 가 낫다
- 상호작용 순간(탑승·잡기·줍기)이 가장 자주 깨진다 — 전수 점검

### G5. 모바일은 기본값이다
새 게임은 **처음부터 가상패드/터치로 조작 가능한 형태**로 설계한다.
배선·검증은 통합 절차의 필수 항목이다(해당 절 참조). 협동 게임에서 **다른 플레이어의 화면을
크게 보여줄 필요는 없다** — 미니맵 표식과 상태 요약이면 충분하다.

## 장르 프리셋 (2026-08-16 신설 — 실측 피드백을 수치로 고정)

> [!important] §0 전 프리셋 공통 — **첫 판부터 어려워야 한다** (2026-08-22 사용자 지시)
> 초반을 쉽게 깔면 "계속할 맛"이 사라진다. **몸풀기 스테이지·워밍업 구간·튜토리얼 판을
> 두지 마라.** 조작은 두세 번이면 저절로 익으므로 난이도로 가르칠 필요가 없다.
> 허용되는 여유는 **화면을 읽을 2~3초**뿐이고 그건 난이도가 아니다.
>
> 반대 방향의 실패도 명시한다 — **너무 어려워도 안 된다.** 기준은 "첫 판에서
> 생각하거나 손을 바쁘게 움직여야 하지만, 규칙을 몰라서 지지는 않는" 지점이다.
> 이 조항은 아래 모든 프리셋의 "쉬운 시작" 문구보다 우선한다.

**용도**: 사용자가 "이런 느낌의 게임" 이라고 컨셉만 줘도 그 장르의 **필(feel) 규약이 수치로**
프롬프트에 실려 나가게 한다. 슬롯 `⟨장르/컨셉⟩` 옆에 프리셋을 지정하면 아래 블록을 통째로
마스터 프롬프트에 붙인다.

> **왜 필요한가**: `ashen-warband` 1차 슬라이스는 6축 게이트를 전부 통과했는데도 사용자
> 플레이에서 하한 미달 판정을 받았다. 원인은 그래픽이 아니라 **장르 필** — 캐릭터가 너무 크고,
> 이동 평면이 좁고, 시체가 길을 막고, 공격이 느리고 미끄러졌다. 6축(그래픽/애니/해상도/
> 이펙트/조작감/연출)은 이걸 잡아내지 못한다. 장르마다 다른 **체감 규약**을 따로 박아야 한다.

> [!important] 우선순위 — **프리셋 > 일반 품질 게이트**
> 프리셋의 수치는 그 장르에서 실측으로 확인된 규약이므로, 마스터 프롬프트의 일반 게이트와
> 충돌하면 **프리셋이 이긴다.** 예: 일반 게이트 A 는 "주인공이 화면 높이의 1/5 이상" 을
> 요구하지만, 벨트스크롤에서 1/5 초과는 필드를 가려 **실패**다 → 프리셋의 1/7 을 따른다.

### 프리셋 `arcade-beltscroll` — 고속 아케이드 벨트스크롤 (대작 기준)

> **지향 = 90년대 아케이드 벨트스크롤 4대작의 합성.** 이 프리셋은 "벨트스크롤 2D" 라는
> 말만 나와도 아래 수준을 목표로 삼는다는 뜻이다. **속도감·조작감·타격감이 최우선**이며
> 그래픽은 그 다음이다. (서빙 파일에 작품명 금지 — 아래 서술자로만 지칭)
>
> | 참조 축 | 서술자 | 이 프리셋에 기여하는 시그니처 |
> |---|---|---|
> | A | 90년대 중반 **던전 판타지** 대작 | 클래스 4~6종 · 장비/인벤토리/상점 · **분기 루트 + 멀티 엔딩** · 주문 선택 UI |
> | B | 90년대 후반 **서커스/현상금 사냥 테마** | **기술을 돈으로 사서 늘린다**(스테이지 사이 구매) · 커맨드 필살 · 캐릭터별 이동 방식 차별(비행/고속대시) |
> | C | 90년대 후반 **삼국지 소재 고속형** | 빠른 연타 · **높은 콤보 카운터** · 장비가 외형에 반영 · **컷인 대형 필살** |
> | D | 90년대 초 **야구 테마 닌자 액션** | 과장 애니메이션(스쿼시&스트레치) · **공중 저글** · 적을 던져 연쇄 · 경쾌한 튕김 |

**1. 카메라·스케일 (전부 "화면 높이 대비 %" 로 잰다 — "주인공 몇 명분" 은 금지)**
- 주인공 높이 = **화면 높이의 1/7 안팎**. 1/5 보다 크면 필드가 안 보여 실패
- **플레이 가능 z 레인 깊이 = 화면 높이의 55~65%** (1440p 기준 800~930px).
  벤치마크의 실제 값이 60% 안팎이다. "주인공 3명분" 같은 상대 기준으로 재면 44% 짜리
  좁은 레인이 나온다 — 눈이 판단하는 건 화면 대비 비율이다 (ashen-warband 실측)
- 한 화면에 **적 6~8기**가 겹치지 않고 들어올 것
- 좌우 스크롤 구간도 넉넉히. "길이 좁다"는 피드백이 나오면 실패

**1-b. 타격 판정 — 레인 폭과 반드시 함께 움직인다 (실측 함정)**
- **아케이드 벨트스크롤은 z 판정이 관대한 게 정상이다.** 보이는 것보다 넓게 잡아야 손맛이 산다
- **레인을 넓히면 z 허용폭도 같이 올려라.** 넓은 레인 + 좁은 판정 = "닿을 것 같은데 안 맞는다"
- **캐릭터를 줄이면 사거리가 스프라이트 비율로 같이 줄어든다** — 축소 후 사거리를 재조정하라
- **상호작용 소품은 비례 축소하면 안 된다.** 상자·통·줍는 아이템 등 플레이어가 때리거나
  줍는 것은 **주인공 키의 45~60%** 를 유지하라 (배경 장식은 비례 축소해도 무방).
  캐릭터 축소 시 같이 줄이면 "상자가 너무 작다" 가 된다 (ashen-warband 실측)
- 공중(저글)용으로 세로 밴드를 넓혔다면 **지상 z 판정도 같이** 넓혔는지 확인
- 합격 기준: "보기엔 닿는데 안 맞는" 케이스 **실측 0**

**2. 액터 충돌 (아케이드 규약 — 어기면 조작감이 죽는다)**
- 살아있는 적도 **스쳐 지나갈 수 있다**. 하드 블로킹 금지, soft separation 만
- **시체는 즉시 통과 가능** + 페이드 아웃. 길을 막으면 실패

**2-b. 전투 락 구간 — 보이는 바닥은 전부 걸어갈 수 있어야 한다**
- 인카운터 카메라 락 자체는 장르 문법이라 써도 된다. 문제는 **보이지 않는 벽이 화면
  안쪽에 들어와 있는 것** — "좌우 끝이 중간에서 막힌 느낌" 이 그것이다
- 락 구간의 **좌우 이동 한계 = 화면 가시 영역의 양 끝** (여유는 캐릭터 반폭 정도만)
- **화면에 보이는 바닥 중 못 가는 곳이 하나라도 있으면 실패**
- 락이 걸리는 지점도 점검 — 아레나가 화면 폭을 꽉 채우는 위치에서 잠겨야 한다

**3. 응답성 — "손이 빠른 게임" (수치 목표, 전부 실측해 보고)**

> [!warning] 속도감 ≠ 이동 속도
> 사용자가 "속도감"을 요구할 때 그것은 **입력 반응·공격 발동의 빠름**이지 캐릭터의 보행
> 속도가 아니다. 둘을 뭉뚱그려 "횡단 ≤2.5초" 같은 목표를 주면 걸음만 과속해 오히려
> 체감이 나빠진다 (ashen-warband 실측 — 지시자 오류). **걸음은 묵직하게, 손은 즉각적으로.**

| 항목 | 목표 |
|---|---|
| 약공 입력 → 타격 판정 | **≤ 0.08초** |
| 히트스톱 (약공 / 강공·필살) | **40~60ms / 80~100ms** |
| 대시 발동 | 입력 후 **≤ 2프레임** |
| 이동 → 공격 전이 | 미끄러짐·끊김 **0프레임** (속도 즉시 0, 급정지 튐도 없이) |
| 점프·점프공격 | 보간 끊김 0 |
| 적 다운 → 기상 사이클 | **≤ 1.2초** (느리면 리듬이 죽는다) |
| 연타 입력 씹힘 | **0** — 버퍼가 받아 다음 단으로 흘러야 한다 |
| 가감속 | 즉각적 (최고 속도는 낮아도 반응은 빨라야 한다) |

**3-b. 이동 속도 — 응답성과 별개로 잡는다**
| 항목 | 목표 |
|---|---|
| 기본 보행 · 화면 폭 횡단 | **3.5~4.5초** (빠르면 가볍고 붕 뜬 느낌이 난다) |
| 질주/대시 · 화면 폭 횡단 | **1.5~2.0초** — **속도의 대비**가 아케이드의 문법이다 |
| **깊이(z) 이동 / 좌우 이동** | **화면 픽셀 기준 60~75%** — 보행·질주 **양쪽 다** |

- **깊이 속도는 반드시 "화면 픽셀" 로 재라.** 원근 압축 때문에 월드 좌표로는 정상인데
  화면상으로는 안 움직이는 것처럼 보인다. 사용자가 보는 건 **화면상 대각선 각도**다
- **질주/대시 배율이 z 에도 걸리는지 확인하라** — x 에만 걸면 대각선 질주 각도가 거의
  수평이 된다 (ashen-warband 실측)
- 대각선 정규화가 **z 만 과하게 깎지** 않는지 점검

**4. 시점·애니메이션**
- **측면 프로필**이 기본. 얼굴이 카메라를 향해 정면으로 보이면 실패
- 깊이 레인은 장르 문법이므로 유지하되 원근·비율 과장은 억제 (2D 룩 우선, 렌더 비용 증가 지양)
- **과장 애니메이션(스쿼시&스트레치)** — 착지·타격·기상에서 형태가 눌리고 늘어날 것 (참조 D)

**5. 기술 체계 (셋 다 필수)**
- **모션 커맨드** (↓↘→+공격 류) — 캐릭터당 **최소 2종**
- **구매형 기술 획득** — 스테이지 사이 상점에서 **돈으로 새 기술을 산다** (참조 B 시그니처, 최소 3종)
- **레벨업 해금 스킬을 커맨드 입력 형태로** 얹는다 (레벨 시스템은 검증된 호평 요소)

**6. 콤보 문법 (타격감의 실체)**
- 약공 **4단 이상 체인** + 강공/필살로 캔슬
- **공중 저글** — 런처로 띄운 뒤 최소 2회 추가 타격 가능 (참조 D)
- **콤보 카운터** 대형 표시, **10히트 이상**이 실제로 나오는 밸런스 (참조 C)
- 잡기 → 던지기로 **다른 적을 쓰러뜨린다**, 벽 충돌 시 추가 판정
- 처치 시 적이 튕겨 날아가며 화면 밖으로 (팝 연출)

**7. 연출**
- **컷인 대형 필살** — 화면 암전/집중선 + 캐릭터 컷인 + 대형 타격 (참조 B·C)
- 보스 등장 전용 컷, 페이즈 전환 배너, 처치 슬로모
- **장비 교체가 외형에 반영**될 것 (참조 C)

**7-b. 성장 곡선·난이도 — 슬라이스가 아니라 완주 분량 기준으로 잡는다**
- **성장 곡선은 전체 스테이지 수로 배분하라.** 슬라이스에 맞춰 튜닝하면 1스테이지에
  Lv6 이 찍히고 완주 시 조기 만렙이 된다 → 슬라이스 종료 시 **Lv2~3**, 최종 스테이지에서
  최대 레벨. 해금 커맨드도 "1스테이지에 다 열리지 않는다" (ashen-warband 실측)
- 금화도 같은 관점 — 한 구간 수입으로 구매형 기술을 2개씩 사면 곡선이 무너진다
- **난이도 하한**: 자동 플레이가 전 구간을 무피격에 가깝게 클리어하면 **너무 쉽다.**
  동시 공격 토큰 3기 이상 · 후방/측면 접근 AI · 웨이브 밀도 · 회복 희소화로 올린다
- **단, 텔레그래프는 절대 유지.** "보고 피할 수 있는데 어려운" 것이 목표다 —
  예고 없는 피격으로 만든 난이도는 실패다

**7-c. 2인 협동 — 이 장르의 정체성이다 (곁가지가 아니다)**
- 벤치마크 4작품이 전부 아케이드 협동 캐비닛이다. **처음부터 2인을 전제로 설계**하라 —
  나중에 얹으면 카메라·진행 구조를 다시 써야 한다
- 형태는 **한 키보드 로컬 협동**. 온라인은 통합 단계의 몫
- **키 배열을 인원수에 따라 동적으로 바꿔라 (실측 필수 사항)**:
  - **1인 모드** — 한 사람이 키보드 전체를 쓰므로 **양손 배치**(방향키+ZXC / WASD+JKL)가 편하다
  - **2인 모드** — 양손 배치를 그대로 1P/2P 에 나눠주면 **두 사람의 손이 중앙에서 겹친다**
    (방향키는 우측 끝, ZXC 는 좌측 끝). 플레이어별로 키가 **물리적으로 한쪽에 뭉치게** 재배치:
    **1P = 방향키 + 우측 클러스터**(`; ' L K P . , /`), **2P = WASD + 좌측 클러스터**
    (`F G V B T R Q E`). **ZXC 는 WASD 바로 아래라 2P 액션 키로 쓰면 안 된다**
  - **2P 참가 순간 자동 전환**, 이탈 시 복귀. 전환 시 **양쪽 배열표를 화면에 안내**하고
    조작 안내·일시정지 화면도 현재 모드를 반영할 것
  - 동시 눌림이 많이 겹치는 배치는 피하라 — **키보드 롤오버는 실제 하드웨어 제약**이다
- **카메라가 가장 어렵다** — 두 플레이어를 항상 화면에 담는 중점 추적 + 화면 끝 소프트 리시.
  전투 락 구간(2-b)과 조율할 것
- 체력·레벨·금화·인벤토리는 **플레이어별 독립**(아케이드 관례), 다운 시 파트너 소생,
  **적 수·체력을 인원수로 스케일**(2인이라고 난이도가 반토막 나면 안 된다)
- 협동 전용 재미: friendly fire 없음 · **협동 던지기** · **합체 필살기**(근접 동시 입력,
  대형 컷인) · 공유 콤보 카운터
- **1인 경험 회귀 금지** — 2인 코드가 1인 경로의 카메라/성능을 망가뜨리지 않는지 검증
- 플레이어 상태는 배열로 다루고 단일 플레이어 하드코딩 가정을 남기지 마라

**7-d. 탈것·특수 구간 — "탈 의미"가 없으면 넣지 마라**
- **탈것 속도 >> 적 속도.** 타는 순간 화면이 확 빨라지는 질주감이 나야 한다.
  속도가 같으면 그냥 느린 이동 구간이다 (ashen-warband 실측)
- 지속 **60~90초 이상**의 본격 구간으로. 짧으면 탄 줄도 모르고 끝난다
- **전용 기믹 필수**: 낙하물 회피 · 레일 분기 · 점프 갭 · 추격자 · 구간 한정 보상
- **탈 이유**를 만들어라 — 걸어서 못 가는 곳, 시간 제한 돌파, 히든 분기 진입
- **탑승 전용 포즈 클립**을 만들어라. 서 있는 캐릭터를 탈것 위에 얹으면 "어중간한 3D" 로
  보인다 — 손이 손잡이에 붙고 흔들림에 몸이 반응해야 한다

**7-e. 부품 이음새 — 퍼펫 리그의 고질병**
- 리그 방식은 부품이 따로 노는 순간 **"2D 도 3D 도 아닌 어중간한" 룩**이 된다.
  관절 겹침 처리 · 외곽선 연속성 · 부품 경계 그림자로 **하나의 실루엣**으로 읽히게 하라
- 상호작용(탑승·잡기·던지기·줍기·상점) 순간이 가장 자주 깨진다 — 전수 점검 대상

**8. 콘텐츠 규모 (대작 기준)**
- **1스테이지 플레이타임 10분+**, 총 80분+ . 시간을 "적 웨이브 반복" 으로 늘리면 실패
- 스테이지 1개의 구성 최저선: 구간 다양성 3종+(전투 아레나/이동·탐색/기믹/탈것) ·
  **중간보스 1기+** · **층 보스 1기**(패턴 2개+·페이즈) · **신규 적 2~3종**(스탯만 올린
  재탕 금지) · **히든 2~3개** · 스토리 이벤트 1회+ · 테마가 실제로 다를 것
- 합계: 스테이지 8+ · 층 보스 8 · 중간보스 8+ · **적 20종+** · **히든 20개+** ·
  **분기 루트 2곳+ · 멀티 엔딩** (참조 A) · 플레이어블 4종
- **직업별 방어기** — 이동 방식 차별과 **별개**로 1종씩. **성격이 서로 달라야 한다**
  (같은 것의 스킨 4개면 실패): **지속형**(가드 — 저위험 저보상, 가드 게이지·브레이크) /
  **타이밍형**(패링 — 좁은 창, 성공 시 완전 무효+반격, 실패 시 무방비) /
  **특화형**(쳐내기 — 투사체 무효·반사, 근접엔 약함) /
  **자원 흡수형**(실드 — 별도 흡수 게이지, 유지 중 자원 소모).
  성능 차이가 아니라 **쓰는 방식**이 달라야 클래스 정체성이 산다. 전용 키 + 게이지 시각화

**8-b. 보스 — "공략"이 있어야 한다 (예고만으로는 부족)**
- **패턴마다 요구하는 대응이 달라야** 하고 플레이어가 그걸 **학습**하는 구조여야 한다.
  대응 유형: 점프 회피 / 거리 벌리기 / **붙기(안쪽이 안전)** / 측면·등 뒤 / 가드·패링 /
  **스턴 유발**(차지 중 약점 타격 → 경직 + 큰 딜) / 엄폐물 / 무적기로 관통
- **보스마다 패턴 4개+, 그중 최소 3개는 서로 다른 대응**을 요구할 것.
  전부 대시 회피 하나로 풀리면 실패다
- **예고를 패턴별로 구분 가능하게** — 모션·색·사운드가 달라야 정답을 고를 수 있다.
  전부 같은 붉은 링이면 학습이 성립하지 않는다
- **정답 대응 → 보상**의 리듬: 제대로 대응하면 경직/스턴으로 큰 딜 기회가 열린다. 이게 공략의 실체
- **페이즈 전환 시 정답이 바뀌는** 패턴을 1개 이상 (후반 보스)
- **방어기가 쓰일 자리를 실제로 배치**하라 — 가드/패링으로 넘기는 패턴, 쳐내기로 무효화하는
  원거리 패턴. 방어기를 만들어놓고 쓸 데가 없으면 둘 다 죽는다
- **예고는 색만 바꾸면 안 된다** — 다섯 패턴이 전부 같은 그림이 된다. **형태(도형) · 색 ·
  소리 3중으로 분리**하라. 정답이 도형에서 읽혀야 한다 (낮게 깔린 띠=넘어라 / 안쪽이 초록인
  도넛=붙어라 / 전방 쐐기=막아라 / 보스로 수축하는 고리=지금 때려라)
> [!important] 정답이 **실제로 쓰이는** 3조건 (ashen-warband 실측 — 셋 다 어겨봤다)
> ① **정답 성립 창 ≥ 예고 시간** — 넘을 수 있는 시간이 예고보다 짧으면 정답이 없는 것이다
> ② **정답 직후 안전한 시간이 있을 것** — 대응해도 바로 다음 패턴에 맞으면 의미가 없다
> ③ **패턴이 "정답이 필요한 거리" 에서 발동할 것** — 붙기 패턴이 이미 안전 지대 안(≈200px)
>    에서 나오면, 정답을 지키든 말든 안 맞는다. 그 패턴은 존재하지 않는 것과 같다

- **구간 단위 테스트는 그 구간이 "남긴 상태" 가 나중에 터지는 것을 못 잡는다.**
  실측 사례: 탈것 구간 하네스가 도착 직후 종료해서, 도착 보상으로 받은 **정의 없는 아이템**을
  나중에 사용하려 할 때 매 프레임 예외가 나는 것을 놓쳤다 — 4초 만에 예외 차단기가 게임을
  세웠다. **완주 회귀(처음부터 끝까지 한 런)를 배포 전 필수 게이트로 두어라.**
  구간 테스트는 그 구간만 증명한다
- **조회 실패를 매 프레임 던지지 마라** — 정의 없는 키·잘못된 참조를 만나면 **조용히 버리고**
  진행하라. 프레임마다 던지면 예외 차단기가 런 전체를 죽인다. 데이터 한 줄의 오타가
  게임을 정지시키는 구조를 만들지 말 것
- **절차 생성 코스는 독립 확률로 굴리지 마라** — 시드에 따라 "핵심 상호작용이 하나도 없는
  코스" 가 실제로 나온다 (실측: 탈것 구간 15행 연속 회피물만 나와 들이받을 적이 0).
  **N행 묶음 고정 비율**로 배분해 시드 운을 제거하라
- **정답이 물리적으로 가능한지 프레임 데이터로 먼저 검증하라.** ashen-warband 는 "점프로
  넘어라" 패턴에서 **점프 정점 127px < 판정 높이 118px** 라, 0.46초 예고를 보고 **0.13초짜리
  창**에 정확히 들어가야만 넘어졌다 — 정답이 사실상 존재하지 않았다.
  **합격 기준: 정답이 성립하는 시간 창 ≥ 예고 시간.** 점프 정점·무적 프레임·이동 속도를
  판정값과 나란히 놓고 계산하라
- **대응할 시간이 있는지도 재라** — 패턴 간격이 짧으면 정답을 지켜도 다음 패턴에 맞는다.
  **비공격(안전) 프레임 비율**을 지표로 써라 (실측: 공략 잘 되는 보스 68% vs 미달 보스 32%)
- **소환 잡몹·장판 등 "정답과 무관한 상시 피해원"에 동시 상한**을 걸어라 —
  최종보스전 피해의 **50%가 소환 잡몹**이면 정답을 지켜도 죽는다
- **정답 대응의 효과를 수치로 증명하라**: **감소율 60% 이상**이 나와야 그 보스에 공략이 있다.
  단 **대조군은 "무대응봇" 이 아니라 "오답봇"으로 만들어라** — 가만히 있는 봇은 `close`(붙기)
  정답 패턴에서 **우연히 안전 지대에 서 있게 되어** 비율이 압축된다. 오답봇은 정답의 반대를
  한다(붙어야 할 때 물러서고, 넘어야 할 때 서 있는다). 비율이 낮게 나오면 **설계를 고치기
  전에 대조군부터 의심하라** — 지표를 맞추려고 정답을 약화시키는 것은 본말전도다
- 보조 지표를 함께 보라: **피격 횟수 · 초당 피해 절대치 · 피해 출처 분해**.
  비율 하나로 판정하지 마라 (ashen-warband 실측)
- **표준 지표 = 정답별 · 패턴 인스턴스 단위 적중률 + 피해** (보스 단위 비율이 아니다).
  보스 단위 비율은 **대조군의 위치에 ±30%p 흔들린다** — 어떤 대조군을 만들어도 편향이 남는다
  (가만히 있는 봇은 안전 지대 안에, 오답봇은 사거리 밖에 우연히 서 있게 된다).
  대조군은 **"교전은 유지하되 정답 행동만 하지 않는" 봇**이 가장 낫고, 표본은 40초 단발이
  아니라 **인스턴스 100+** 로 모아라 (ashen-warband: 이 지표로 전 항목 정답 유효 입증)
- **가드/패링형 정답은 적중률이 아니라 피해로 읽어라** — 설계상 "맞되 경감" 이라
  맞은 횟수는 대조군과 같고 피해만 줄어든다 (실측 적중률 0% 감소 / 피해 95% 감소)
- **패턴 추첨이 균등이면 특정 패턴이 실전에서 안 나온다** — 특정 방어기 전용 패턴(포격 등)은
  조건부 우선 선택을 걸어라. 안 나오면 그 방어기의 존재 이유가 사라진다 (75초에 0회 실측)
- DESIGN.md 에 **패턴 → 정답 대응 → 예고(형태/소리) → 실패 시 결과** 표를 남기고,
  자동 플레이로 각 정답이 실제로 성립하는지 실측하라
- **8스테이지를 관통하는 스토리라인** — 도입/전개/분기점/엔딩 분기. 과한 텍스트 모달로
  아케이드 페이스를 끊지 말 것
- RPG 층(경험치·레벨·장비·상점·인벤토리) · 무기 줍기 · 파괴 오브젝트
- 캐릭터별 **이동 방식 차별** (참조 B — 비행/고속대시/이단점프 등)

**9. 절대 금지 — 필을 죽이는 안티패턴 (실측으로 확인된 것)**
- 공격 시작 시 미끄러지거나 급정지로 튀는 것
- 시체·적의 하드 블로킹
- 100ms 초과 히트스톱 남발 → "렉 걸린 느낌"
- 주인공이 화면의 1/5 보다 큰 것
- 얼굴이 정면을 보는 것
- 느린 다운/기상, 긴 공격 후경직, 연타 중 입력 유실
- 이동 평면이 좁아 "길이 좁다"고 느껴지는 것
- 보행이 과속이라 가볍게 느껴지는 것 (속도감은 손의 반응이지 발의 속도가 아니다)
- 전투 락 구간에서 보이는 바닥인데 걸어갈 수 없는 것
- 상호작용 소품(상자·아이템)이 캐릭터 축소에 딸려 작아진 것
- 슬라이스 기준으로 튜닝한 성장 곡선 / 무피격 클리어되는 난이도
- 탈것 속도가 적 속도와 비슷해 "탈 의미가 없는" 구간
- 리그 부품이 따로 놀아 2D 도 3D 도 아닌 룩이 되는 것
- 2인 협동을 완주 후에 얹으려는 것 (카메라·진행 구조를 다시 쓰게 된다)

### 프리셋 `survival-basebuilding` — 좀비 아포칼립스 생존·건설·디펜스 (초장기)

> **지향**: 파밍 → 제작 → 건설 → 디펜스 루프를 **기술 시대 진행**으로 묶은 초장기 생존물.
> 핵심은 그래픽이 아니라 **"내가 캔 자원으로 내 기지를 세운다"는 인과의 납득성**과
> **100시간을 버티는 진행 깊이**다.

**1. 시점·스케일**
- **쿼터뷰(아이소메트릭 2:1) 또는 항공뷰(top-down)**. 캐릭터는 작게 —
  **화면 높이의 1/12~1/16**. 건설·디펜스는 시야가 자산이다. 기지 전경이 한 화면에 들어와야 한다
- **2.5D~3D 룩**: 아이소메트릭 투영 + 높이(z) 오프셋 + 접지 그림자/AO/방향광으로 입체감.
  빌드 스텝 없는 순수 캔버스로 충분히 성립한다 (WebGL 은 선택)
- 줌 2~3단계 + 기지 전체 조망 지원

**2. 자원-구조물 인과 (이 장르의 정체성 — 어기면 전부 무의미)**
- **건설물은 실제로 파밍한 자원으로만 만들어진다.** 추상 "건설 포인트" 금지
- 대응이 물리적으로 납득 가능해야 한다: 벌목 → 나무 펜스·문·바닥 / 채석 → 석벽 ·
  화덕 / **쇠파이프·고철 수거 → 철제 방벽·스파이크** / 전선·배터리 → 전기 함정·조명
- 자원마다 **획득 수단·도구·소요 시간**이 다르고, 상위 자원은 상위 도구를 요구한다

**3. 기술 시대 (진행의 척추 — 5~6단계)**
- 예: 맨손·석기 → 목재 → 석재 → **철기** → 기계·전기 → 후반 자동화
- **시대 전환은 자원 문턱으로 게이트**된다 (철기로 넘어가려면 고철·쇠파이프를 모아야 한다)
- 시대마다 **새 위협 + 새 도구 + 새 지역**이 함께 열려야 한다. 숫자만 커지면 실패

**4. 코어 루프**
파밍(채집·벌목·채광·건물 수색) → 제작 → 건설 → **디펜스(야간/웨이브 습격)** → 확장
- 좀비가 **구조물을 실제로 파괴**한다(내구도·경로 탐색). 벽은 장식이 아니다
- 함정·포탑·조명·시야 차단 등 **방어 설계의 선택지**가 있어야 한다
- 낮/밤 사이클, 배고픔·체온·부상 등 생존 압박 (과하면 스트레스, 없으면 심심 — 균형)

**5. 100시간 설계**
- **생존 카운터 = 누적 실플레이 시간.** 100시간 도달 시 클리어(엔딩), **이후 무한 계속**
- 이 분량을 채우는 건 반복이 아니라 **깊이**다. 최저선: 제작 레시피 150종+ ·
  구조물 60종+ · 좀비 20종+ · 지역/바이오옴 6종+ · 대규모 습격 이벤트 · 랜드마크 탐험
- **시간 때우기 반복 금지** — "같은 걸 더 오래" 로 늘리면 실패
- **세션 간 세이브 필수** (대용량 로컬 저장). 100시간짜리 게임에 세이브가 없으면 성립 불가

**6. 2인 협동**
- 한 키보드 로컬 2인. 역할 분담이 자연스러운 장르다 (한 명 파밍 / 한 명 건설·방어)
- 공유 카메라 + 소프트 리시 기본. 자원·인벤토리는 **공유 창고 + 개인 소지품** 이원화
- 좀비 수·체력을 인원수로 스케일

**7. 성능**
- 좀비 100기+ 동시 · 구조물 수백 개가 기본 규모다. **오브젝트 풀 + 공간 해시** 전제로 설계하라
- 경로 탐색은 개체마다 매 프레임 돌리지 말고 플로우 필드/그리드 캐시 등으로 분산

**8. 절대 금지**
- 추상 포인트로 짓는 건설 · 자원과 무관한 구조물 트리
- 시대 전환이 숫자 상향뿐인 것 · 좀비가 벽을 무시하거나 벽이 무적인 것
- 캐릭터가 커서 기지가 화면에 안 들어오는 것 · 세이브 없음

### 프리셋 `iso-scavenge` — 쿼터뷰 생존 파밍 (액션 파트와 이원 구조)

> **용도**: 액션 파트가 따로 있고 그 사이에 **탐색·파밍 페이즈**가 **별도 뷰**로 들어가는
> 이원 구조 전용. `survival-basebuilding` 과 다른 점은 주가 건설이 아니라 **수색과 탈출**이고,
> 100시간 설계가 아니라 **한 판 4~7분의 압축된 긴장**이라는 것이다.
>
> **최우선 불변식**: 두 뷰가 **"게임 두 개"로 보이면 실패**다. 팔레트 · UI 문법 · 캐릭터 리그 ·
> 사운드 문법 · 폰트는 **하나**로 유지하고, 다른 것은 카메라와 페이스뿐이어야 한다.

**1. 시점·스케일**
- 아이소메트릭 2:1(또는 3:2). 캐릭터 = **화면 높이의 1/12~1/16** — 방 구조가 한눈에 읽혀야 한다
- 실내 진입 시 **지붕/앞벽 컷어웨이**(페이드 또는 절단). 방 안이 가려지면 실패
- 줌 2단계 이상

**2. 시야·정보 은폐 (이 페이즈의 정체성)**
- **시야 원뿔 + 기억 안개**: 아직 못 본 방은 어둡고, 봤던 곳은 흐리게 남는다.
  전지적 시야는 이 페이즈를 통째로 무의미하게 만든다
- 안 보이는 정보는 **소리로** 준다 — 벽 너머 신음·발소리를 화면 가장자리 방향 표시로
- 코너 너머가 안 보이는 것이 긴장의 원천이다

### 프리셋 `casual-catch` — 낙하물 받기·피하기 캐주얼 아케이드 (팝콘)

**1. 화면·스케일 — 세로 길이가 곧 반응 시간이다**
- 캔버스 **3:4 또는 9:16 세로**(1080×1440급). 낙하 거리 = 플레이어에게 주는 생각할 시간

**2. 판정 비대칭 — 이 장르의 손맛 (가장 중요)**

  보상 판정은 스프라이트보다 **15~25% 넓게**, 피해 판정은 **10~20% 좁게**
- 판정 기준점은 **받는 부위(입·바구니)** 이지 발밑이 아니다
- **판정 폭을 스프라이트 상수로 박지 마라.** 실제로 그려지는 실루엣에서 유도하고
  거기에 배율만 곱하라. 스킨·변형(웅크림·성장)이 하나라도 있으면 상수는 반드시
  어긋난다 — `coin-corgi` 는 몸이 긴 스킨이 실제 반폭 124px 인데 판정을 95px 로 돌려
  **옆구리에 닿아도 안 먹히는** 상태였다. 그림과 판정의 단일 원본을 만들어라
- 합격 기준: "닿을 것 같은데 안 먹힌" 실측 **0**, "안 닿았는데 맞은" 실측 **0**

### 프리셋 `grid-number-puzzle` — 격자 숫자 퍼즐 (경로 드래그형)

> **지향**: 한 판 2~5분. 격자를 손가락/커서로 훑어 조건을 맞추는 퍼즐.
> 정체성은 **경로를 그리는 손맛**과 **수가 딱 떨어지는 순간**이다.
> 이 장르는 `casual-catch` 와 달리 **포인터가 1급 시민**이라 "마우스 조준 금지" 조항이
> 적용되지 않는다. 대신 **키보드로도 완전히 플레이 가능해야 한다**(아래 2절).

**1. 화면·스케일 — 격자가 화면의 주인공이다**
- 캔버스 3:4 또는 9:16 세로. **격자가 화면 폭의 82~92%**를 차지할 것
- 셀 한 변 **≥ 화면 폭의 1/9** — 터치 타깃 하한이자 숫자 가독성 하한
- 셀 안의 숫자는 **셀 높이의 50% 이상**. 작으면 훑는 중에 못 읽는다
- 상단에 목표, 하단에 진행도. 격자를 UI 가 가리면 실패

**2. 조작 — 포인터 우선, 키보드 완전 지원**
- **포인터**: 드래그로 경로를 그린다. 셀 중심에서 **셀 한 변의 0.6~0.65배** 안이면
  선택된다 — 셀 반폭(0.5배)보다 넓어 카드 사이 여백까지 받아주고, 반대각선(0.71배)보다
  좁아 대각선 오선택은 막는다. 정확히 셀 경계 안일 필요는 없다 — 손가락은 부정확하다
- **되돌리기**: 드래그 중 직전 셀로 되짚으면 마지막 선택이 취소된다 (필수)
- **키보드**: 방향키로 커서 이동 → 경로 끝에 인접한 칸으로 가면 자동으로 이어지고,
  직전 칸으로 되돌아가면 취소된다. 포인터 전용으로 만들면 데스크톱에서 못 논다
- **선택 중 현재 합계를 손가락·커서 옆에 크게 표시**하라. 없으면 암산 게임이 된다

**3. 피드백 (이 장르의 손맛)**
| 항목 | 목표 |
|---|---|
| 셀 하나 추가 → 시각·청각 반응 | ≤ 1프레임. **음정이 경로 길이를 따라 올라갈 것** |
| 목표 달성 | 즉시 확정 (별도 확인 키 금지 — 정확히 맞은 순간이 유일한 정지점이다) |
| 초과(합 > 목표) | 즉시 빨강 + 더 못 잇게 막고 **왜 막혔는지 보여준다** |
| 클리어 → 낙하 시작 | ≤ 0.15초 |
| 낙하 + 리필 완료 | ≤ 0.45초 — 길면 리듬이 끊긴다 |

**4. 격자 규칙 (어기면 판이 죽는다)**
- **되메우기(refill) 없으면 판이 말라 죽는다.** 지운 자리는 위에서 떨어져 채운다
- **막힌 판 감지는 필수다.** 남은 배치로 목표를 만들 수 없으면 목표를 바꾸거나 섞어라.
  "풀 수 없는데 시간만 가는" 상태는 그 자체로 실패다
- 리필은 난수로 뿌리고 끝내지 말고 **해가 존재하는지 검사**하라 (제한 깊이 DFS 로 충분)

**5. 난이도**
- **셀 값 범위를 넓히는 것이 가장 강한 상향**이다 — 탐색 공간이 급증한다.
  목표 수 · 라운드 할당량 · 제한 시간은 그 다음
- **라운드 1부터 제대로 된 판이어야 한다** — 몸풀기 라운드를 두면 첫 1분이 지루하다.
  경로 그리기는 두세 번이면 저절로 익는다 (§0 공통 원칙)
- 실수 한 번에 즉시 게임오버는 금지 — 퍼즐은 되돌릴 수 있어야 한다

**6. 규모**
- 라운드 8+ · 방해 타일 2종+ · **목표 유형 2종+**(단순 합 / 길이 제약 / 금지 숫자 등)
- 한 판 2~5분, 숙련 시 10분+

**7. 절대 금지**
- 현재 합계 표시 없이 암산 강요 · 되메우기 없음 · 막힌 판 방치
- 셀이 손가락보다 작은 것 · 포인터 전용 · 실수 1회 즉사
- **모바일에 가상패드를 붙이는 것** — 이 장르는 네이티브 터치 드래그가 정답이다.
  조이스틱을 얹으면 격자를 가리고 조작도 나빠진다

> 상태: **1차 가설** (2026-08-22 작성). 수치는 `sum-trail` 실측 후 확정한다.

### 프리셋 `sort-puzzle` — 정렬 퍼즐 (턴제 · 되돌리기 필수)

> **지향**: 시간이 아니라 **생각**으로 푸는 퍼즐. 한 판 1~4분.
> 정체성은 **"한 수만 물러 보자"** 와 **마지막 한 개가 제자리에 들어가는 순간**이다.
> `casual-catch`·`grid-number-puzzle` 과 달리 **제한 시간을 두지 않는다** — 이 장르에
> 초시계를 붙이면 생각할 시간을 뺏어 장르 자체가 무너진다.

**1. 화면·스케일**
- 대상(기둥·컨테이너)이 화면의 주인공. **전체가 한 화면에 다 보여야 한다 — 스크롤 금지**
- 개별 조각(링·물방울)은 **화면 폭의 1/12 이상**. 색 구분이 안 되면 퍼즐이 성립하지 않는다
- **색만으로 구분하지 마라.** 무늬·기호를 함께 넣거나 색각 이상에서도 구분되는 팔레트를 쓴다

**2. 조작**
- **2탭이 표준**: 대상 탭 → 조각이 뜬다 → 대상 탭 → 놓는다. 드래그도 받으면 좋다
- 같은 대상을 다시 탭하면 **집기 취소**
- 놓을 수 없는 곳을 탭하면 **왜 안 되는지 보여준다** — 거절음만으로는 부족하다
- 키보드: 방향키로 대상 선택 + 확정으로 집기/놓기

**3. 되돌리기 — 이 장르의 필수 기능**
- **없으면 실수 한 번에 판을 통째로 버려야 한다.** 반드시 넣어라
- 무제한이면 긴장이 사라지고 0이면 스트레스다 — **판당 3~5회**가 적정
- 남은 횟수를 항상 화면에 두고, 다 쓰면 이유를 말해라

**4. 해 존재 보장 — 절대 조건**
> **랜덤 배치 후 솔버로 검사하지 마라. 완성 상태에서 역으로 섞어라.**
> 그 역순이 곧 해답이므로 **항상 풀 수 있다.** 솔버가 아예 필요 없고,
> 덤으로 그 역순 길이가 **par(기준 수순)** 이 된다.
>
> [!warning] 역섞기의 조건은 "정방향 규칙" 이 아니다 (`hoop-order` 실측)
> 조건은 **"이 역이동을 정방향으로 되돌릴 수 있는가"** 다. 둘을 혼동하면 판이
> 아예 섞이지 않는다 — 링 정렬에서 정방향 규칙(같은 색 위에만)으로 섞었더니
> **단색 스택이 영원히 단색으로 남아 시작부터 풀린 판**이 나왔다.
> 올바른 형태: `역이동 = B 의 맨 위 조각 r 을 A 로 옮긴다(A 에는 제약 없음)` +
> `되돌릴 수 있는 조건 = r 을 뺀 뒤 B 가 비거나 B 의 새 맨 위가 r 과 같다`.
> **받는 쪽(A)에 정방향 제약을 걸지 마라** — 그게 안 섞이는 원인이다.
>
> 같은 이유로 **"목표 지정"을 놓기 규칙으로 만들면 안 된다.** 역섞기 해답은 도중에
> 목표 칸을 임시로 다른 것으로 채우므로, 목표를 놓기 제한으로 걸면 그 해답이
> 통과하지 못해 **풀 수 없는 판**이 된다. 목표는 **표시**로만 두어라
- 섞는 횟수가 곧 난이도다 — 부족하면 시작부터 반쯤 풀려 있다
- **막다른 길을 알려라**: 유효한 수가 하나도 없으면 즉시 알리고 되돌리기/재시작을 권해라

> [!important] **이 장르는 단순 봇으로 난이도를 재지 마라**
> greedy 정책 봇은 정렬 퍼즐을 **829수를 두고도 못 푼다**(실측). 그건 게임 버그가
> 아니라 봇의 한계다. 검증 봇은 greedy 가 아니라 **저장해 둔 역섞기 해답을 따라가게**
> 만들어라 — 목적이 "판이 실제로 풀린다"를 조작으로 증명하는 것이기 때문이다.

**5. 피드백**
| 항목 | 목표 |
|---|---|
| 집기 → 조각이 뜨는 것 | 즉시. 무엇을 들었는지 화면에서 명확할 것 |
| 놓기 → 착지 | ≤ 0.25초. 튕김 한 번이면 충분 |
| **대상 하나 완성** | **즉시 축하 연출** — 이 장르의 도파민은 여기 하나뿐이다 |
| 클리어 | 수순 수·남은 되돌리기로 평가 |

**6. 난이도**
- **여유 공간(빈 대상)이 가장 강한 축**이다. 색 수보다 먼저 줄여라
- 그다음 색 수 · 용량 · 섞는 횟수 순
- **스테이지 1부터 제대로 된 퍼즐이어야 한다.** 튜토리얼 판을 두면 처음 몇 분이
  지루해 계속할 이유가 사라진다 — 조작은 두세 수 만에 저절로 익는다 (§0 공통 원칙)

**7. 절대 금지**
- 되돌리기 없음 · 해 존재 미보장 · **제한 시간**
- 색만으로 구분 · 스크롤해야 전체가 보이는 판
- 막다른 길을 만들어놓고 알려주지 않는 것

> 상태: **1차 가설** (2026-08-22 작성). 수치는 `hoop-order` 실측 후 확정한다.

### 프리셋 `picture-logic` — 그림 논리 퍼즐 (네모로직/노노그램형)

> **지향**: 숫자 힌트만 보고 칸을 칠하면 **그림이 드러나는** 퍼즐. 한 판 2~12분.
> 정체성은 **"다 풀고 나서 뭐가 나오는지"** 하나다. 이게 없으면 그냥 계산 노동이다.

**1. 완성 그림 — 이 장르의 존재 이유**
- 난수 격자는 금지. 다 풀어도 아무것도 아니라서 **푸는 보람이 사라진다**
- 각 그림에 **이름과 한 줄 태그**를 붙여라. 이름이 없으면 모을 대상이 되지 않는다

> [!warning] **손으로 '#' 을 찍지 마라 — 벡터 실루엣을 판 크기에 맞춰 굽는다** (`pixel-logic` 실측)
> 격자에 직접 `#` 을 타이핑하면 어떤 크기에서도 계단 덩어리가 된다. 실제로
> **연필이 종, 꽃이 돋보기, 나비가 네모**로 보였다(사용자 반려). 원본은 도형 대수
> (타원·사각·다각형·굵은 선분의 더하기/빼기)로 갖고 있다가, 판 크기가 정해질 때
> 칸마다 ss×ss 로 훑어 **덮인 비율**로 칠할지 정한다 — 사진을 줄여 픽셀아트로 만드는
> 것과 같은 방식이다. 한 번 그려 두면 15×15 에서도 25×25 에서도 형태가 유지된다.
>
> **가는 부분에는 하한이 있다.** 상자 긴 변 기준 **0.09 미만인 획은 최소 판에서 사라진다**
> (줄기 0.035 → 15칸에서 0.4칸 → 튤립의 줄기가 통째로 증발). 자루·손잡이·돛대·팔은
> **0.10~0.15** 로 잡아라.
>
> **덩어리로 뭉치는 것도 같은 크기의 실패다.** 붙어 있는 두 부분(날개와 몸통, 모자와 머리,
> 돛대와 돛)은 최소 판에서 한 칸도 안 벌어져 통짜가 된다 — 나비가 해골로 읽혔다.
> **사이에 빈 줄 한 칸(≥0.09)을 강제로 확보**하고 그 안에 몸통을 다시 그려라.

**2. 유일해 — 절대 조건**
> **줄 단위 논리(가능한 배치의 교집합)만으로 전부 확정돼야 한다.** 찍어야 풀리면
> 퍼즐이 아니라 복권이다. 백트래킹 솔버로 "해가 하나뿐"임을 보이는 것으로는 부족하다 —
> 사람이 풀 수 있어야 한다.
- 검사는 **판을 낼 때마다** 돌린다. 통과 못 한 조합은 그 판으로 쓰지 않는다
- 안 풀리면 그림을 버리지 말고 **굵기(threshold)를 흔들어 다시 구워라** — 실루엣이 반 칸
  두꺼워지면 힌트가 통째로 달라진다. `pixel-logic` 은 굵기 후보 7개로 **24그림 × 5티어
  = 120조합 전부**를 통과시켰다(전수 검사 78ms)
- **대각선 띠는 피하라** — 굵기를 바꿔도 통째로 밀 수 있어 유일해가 안 나온다
  (연필을 대각선으로 눕혔더니 미확정 100칸)

**3. 그림을 미리 보여주지 마라**
- 도감/컬렉션의 **잠긴 칸은 물음표만**. 흐린 실루엣이라도 내보이면 그 판의 답이 새어 나가고,
  "완성해야 볼 수 있다"는 이 장르의 유일한 보상이 사라진다
- **타이틀 데모에도 실제 수집 그림을 쓰지 마라.** 데모 전용 도형을 따로 둬라

**4. 난이도 = 판 크기**
- 정보를 숨기거나 시간을 줄이는 게 아니라 **칸 수**로 조절한다. 15×15 → 20×20 → 25×25
- **난이도를 고르게 하라.** 같은 15×15 라도 사람마다 체감이 다르고, 이 장르는 한 판이 길어서
  "잘못 골랐다" 의 비용이 크다
- 정사각만 쓰지 마라 — 그림 비율에 맞는 **n×m 격자**를 골라야 형태가 안 눌린다
- **1스테이지부터 제대로 된 크기여야 한다.** 5×5 튜토리얼 판을 두면 처음 몇 분이 지루하다
  (§0 공통 원칙). 조작은 두세 칸 칠하면 저절로 익는다

**5. 실수 처리**
- **틀린 칸은 즉시 알려준다.** 안 알려주면 어디서 틀렸는지 못 찾아 판을 통째로 버려야 한다
- 틀린 칸은 **엑스로 확정해 남긴다**(그 칸이 빈칸이라는 정보는 이미 준 셈이다)
- 허용 횟수 2~3회. 1회 즉사는 이 길이의 퍼즐에 붙일 벌이 아니다
- **맞게 칠한 칸도 지울 수 있어야 한다** — 되돌릴 수 없으면 실험을 못 한다

**6. 화면·조작**
| 항목 | 목표 |
|---|---|
| 칸 크기 | 최소 판에서 **20 CSS px 이상**. 25칸 판은 큰 화면 권장이라고 **명시**해라 |
| 칠한 칸 대비 | 빈 칸과 **한눈에** 갈릴 것. 어두운 판에 어두운 채움은 가독성이 곧 난이도가 된다 |
| 힌트 숫자 | 격자를 **절대 가리지 않는다**. 힌트 폭을 먼저 확보하고 남는 공간을 칸이 나눈다 |
| 다 센 줄 | 힌트를 흐리게 — 같은 줄을 두 번 세지 않게 |
| 드래그 칠하기 | 필수. 시작 칸의 상태가 이번 드래그의 모드를 정한다(칠하다 지우는 사고 방지) |
| 엑스 표시 | 별도 도구로. **확실히 빈칸**을 표시해 두는 것이 이 퍼즐의 실제 풀이법이다 |
| 5칸 밴딩 | 격자 배경과 굵은 선 양쪽으로. 없으면 열을 세다 틀린다 |
| 완성 연출 | 격자를 지우고 **그림만** 크게. 판 격자 크기를 그대로 쓰면 세로로 긴 그림이 화면 밖으로 넘쳐 이름이 잘린다 — 전용 상자에 맞춰 다시 잰다 |

**7. 절대 금지**
- 난수 격자 · 추측이 필요한 판 · 잠긴 그림의 실루엣 노출
- 힌트가 칸을 가리는 배치 · 손가락보다 작은 칸
- 틀린 위치를 안 알려주는 것 · 지우기 불가
- **모바일에 가상패드를 붙이는 것** — 칸을 눌러 칠하는 퍼즐이라 조이스틱은 판을 가리기만 한다

### 프리셋 `party-decider` — 여럿이서 정하는 도구 (구슬 레이스 · 사다리 · 카드 뒤집기)

> **지향**: 커피 사는 사람 정하기처럼 **여럿이 모여 뭔가를 정할 때** 켜는 물건.
> 실력 게임이 아니라 도구다. 그래서 1급 목표가 재미가 아니라 **공정성과 그 증명**이고,
> 재미는 "결과가 나오기까지 지켜보게 만드는 연출" 로 만든다.

**1. 사행성 가드레일 — 협상 대상이 아니다**
- 앱 안에 **돈·포인트·베팅 금액을 넣을 곳을 만들지 않는다.** 입력란 자체가 없어야 한다
- **"당첨금 · 배당 · 베팅 · 환전" 을 쓰지 않는다.** 결과는 "걸린 사람 / 뽑힌 사람 / 순서"
- **결과를 미리 뽑아 놓고 애니메이션만 재생하지 마라.** 이게 이 장르에서 가장 흔한 구현이고,
  들키는 순간 도구로서 죽는다
- 참가자 이름은 **기기에만** 남긴다. 서버로 보내는 순간 결정 도구가 개인정보 처리가 된다
  (그래서 `구슬 레이스` 는 플랫폼 저장 동기화·랭킹을 아예 붙이지 않았다)
- 가중치를 준다면 **"구슬 개수"** 처럼 확률로 설명되는 형태여야 한다. 배당률이 아니다

**2. 공정성은 주장하지 말고 증명하라**
| 장치 | 왜 |
|---|---|
| 시드 하나에서 모든 무작위를 뽑는다 | 시뮬레이션 안에서 `Math.random` 을 부르는 순간 재현이 불가능해진다 |
| 물리는 **고정 시간 간격** | 주사율이 달라도 결과가 같아야 같은 시드가 같은 결과를 낸다 |
| 시드를 화면에 띄우고 **"같은 시드로 다시"** 를 준다 | "미리 정해 둔 게 아니다" 를 사용자가 직접 확인하는 유일한 방법이다 |
| 참가자별 조건을 **물리적으로 동일**하게 | 구슬 반지름·질량·반발계수·마찰이 같아야 한다 |
| 판은 고정, **출발 자리만 매 판 섞는다** | 자리마다 유불리가 있어도 배정이 균등하면 사람별 확률은 같아진다 |
| **레이스 중 조작을 주지 않는다** | 손댈 수 있으면 결과에 손댈 수 있다는 뜻이다. 방향키는 거절하고 이유를 말해라 |

검증은 말이 아니라 수치로 남긴다: **같은 시드 재현 시험**(불일치 0)과
**균등성 검정**(χ² 대 자유도별 임계값). `구슬 레이스` 는 360판에서 χ²=5.9/6.43 (df=5, 임계 11.07).

**3. 트랙은 한 화면보다 길게, 대신 미니맵을 같이 띄운다**
- 한 화면에 다 넣으면 장애물을 몇 개 못 놓아 **출발 순서가 그대로 도착 순서**가 된다
- **4~5화면(5K px 내외)** 이 하한이다. `구슬 레이스` 1차본은 3화면·한 판 11~20초였고
  "너무 빨리 끝난다" 로 반려됐다. 2배로 늘려 17~33초가 됐다
- **결승 직전에 결과가 확정되는 관문을 하나 둬라.** 마지막이 밋밋하면 앞이 아무리
  요란해도 싱겁게 끝난다. 범퍼로 한 번 흩고 **구슬 지름 + 8** 짜리 구멍으로만 통과시킨다 —
  통과 시험으로 확인한 가장 좁은 통과 가능 폭이고, 거기서 줄 서고 튕겨 나가는 게 긴장의 전부다
- 카메라는 선두를 따라가되, **전체 판과 모든 참가자를 보여 주는 미니맵을 상시 표시**한다.
  화면 밖에서 벌어진 일을 못 본다면 도구를 신뢰할 이유가 없다
- 결승 가까이서 살짝 줌인 — 이 장르의 도파민은 마지막 한 명이 들어오는 순간 하나뿐이다

**3-a. 출발 — 한 줄로 세우지 말고 한 통에 담아 쏟아라**

> [!warning] **출발 자리가 순위를 정하면 지켜볼 이유가 없다** (`구슬 레이스` 실측)
> 참가자를 화면 폭 전체에 한 줄로 세우면 코스가 섞을 일이 없어 출발 자리가 그대로 순위가 된다.
> 자리 배정을 시드로 섞어도 **사람별 확률만** 균등해질 뿐, 눈에는 그대로 보인다.
> 측정 지표: **출발 x ↔ 도착 등수 스피어만 ρ**. 한 줄 출발일 때 폭포 코스가 **−0.27** 이었고,
> 한 통 출발로 바꾸니 **−0.01** 이 됐다. |ρ| < 0.1 을 하한으로 삼아라.
- 통 폭은 참가자 지름의 5~6배, 아래 목은 그 절반. 뭉쳐서 나와야 코스가 일을 한다
- **통 바로 다음은 흩는 구간**이어야 한다. 비탈이 오면 줄줄이 같은 길로 간다
- 통 위에 **카메라 여유**를 둬라. 상한이 출발선 바로 위면 통이 늘 화면 맨 위에 붙어 HUD 뒤로 들어간다

**3-b. 카메라 — 정적인 추종만으로는 지켜볼 이유가 약하다**
- **자동 줌**: 선두 무리가 화면을 채우도록 가로·세로 퍼짐에서 역산한다.
  단, 뒤처진 하나 때문에 화면이 멀어지지 않게 **선두 60% 만** 센다
- **결정적 순간 슬로 모션**: "다음 도착이 결과를 정하는 도착" 일 때만 느리게(0.3배 안팎).
  도파민이 그 한 번뿐이라 거기만 늘린다. 배속은 지수 보간 — 뚝 끊기면 렉으로 보인다
- **사용자 조작을 허용해라.** 카메라와 배속은 그림만 바꾸므로 결과와 무관하다.
  진행 중 조작을 막는 이유는 결과 보호이지 불편함이 아니다
- 물리는 여전히 고정 스텝이라 느린 배속이 재현성을 깨지 않는다(프레임당 서브스텝이 줄 뿐)

**4. 물리 — 여기서 나는 사고가 전부 "판이 안 끝난다" 로 나타난다**

> [!warning] **통로는 눈으로 못 본다. 통과 시험으로 잡아라** (`구슬 레이스` 실측)
> 구슬 하나를 여러 x 에서 떨어뜨려 결승까지 가는지 세는 자동 시험을 만들어라.
> 이걸로 잡은 것들:
> · **비탈에 파묻힌 장식 못** — 넘을 수 없는 턱이 되어 구슬이 60초를 버텼다.
>   비탈 위 장애물은 비탈면에서 `2R+12` 를 띄워 **매달아라**
> · **완만한 비탈(5°)에서 정지** — 구름 마찰의 접선 부호를 뒤집으면 굴러가지 않는다.
>   접촉점 속도는 `vt - ω·r` 다. 부호가 맞으면 `v ≈ ω·r` 로 수렴한다
> · **수평 칸막이** — 구슬이 그 위에 서 버린다. 구멍 쪽으로 기운 ⋀ 로 만들어라
> · **레일 쪽으로 기울어진 면** — 레일과의 사이가 빠져나올 수 없는 주머니가 된다.
>   양쪽에 통로가 남는 자리에만 놓아라
> · **비탈 간격 < 낙차 + 구슬 지름** — 위 비탈의 끝과 아래 비탈 사이에 V 자 주머니가 생긴다
> · **꼭대기가 평평한 기둥** — 구슬이 얹힌다. ⋀ 로 바꿔라

> [!warning] **반발계수 > 1 로 범퍼를 만들지 마라** (`구슬 레이스` 실측)
> 낀 구슬이 매 스텝 에너지를 벌어 **초속 3만 픽셀로 화면 밖으로 날아간다.**
> 범퍼는 **나가는 속도의 하한(kick)** 으로 만들고, 별개로 **전역 속도 상한**을 둬라.

- 장애물 사이 통로는 **최소 `2R + 12`**. 회전체 날개 길이는 개수에서 역산해라 —
  고정값으로 두면 개수를 늘리는 순간 통로가 구슬보다 좁아진다
- 그래도 끼는 경우가 남으므로 **구제 장치 2종**을 둔다: ① 속도가 오래 낮으면 흔든다
  ② **빠른데 앞으로 못 나가면**(벨트·회전체를 도는 중) 흔든다 — 속도만 보면 이걸 못 잡는다.
  흔드는 값도 **시드에서 뽑아** 재현성을 지킨다. **흔들 때는 아래로 치우쳐 밀어라** —
  위로 밀면 좁은 통로에 들어간 것을 도로 뱉어내 구제 장치가 판을 못 끝내게 만든다

**4-a. 화면 문구 — 외래어 직역을 두지 마라**
- 게이머가 아닌 사람도 쓰는 도구다. **씨앗/시드 → 코드**, **슬로 모션 → 느리게**,
  **줌 인/아웃 → 화면 크게/작게**, **맵 → 코스**, **모드 → 방식**
- 어려운 개념은 **무엇인지가 아니라 무엇에 쓰는지**로 불러라 — 「판 번호」는 반려됐고
  「**다시 보기 코드**」가 통했다. 버튼도 「같은 시드로」가 아니라 「**똑같이 다시**」다
- 기술 주석에서는 정확한 용어를 써도 되지만, **화면 표기가 다르다는 걸 코드에 밝혀 둬라**

**5. 조작·화면**
| 항목 | 목표 |
|---|---|
| 이름 입력 | **DOM 폼으로.** 캔버스에 가짜 입력창을 만들면 모바일 키보드·한글 조합·붙여넣기가 전부 반쪽이 된다 |
| 결정 모드 | 1등 / 꼴찌 / N등 / 전체 순서 — 쓰임새가 다 다르다 |
| 빨리 감기 | 필수. 물리를 건너뛰는 게 아니라 **같은 물리를 빨리 돌린다** |
| 버튼 | 최소 44 CSS px. 경주는 지켜보는 화면이라 가상패드를 붙이지 않는다 |
| 한 판 길이 | **10~25초.** 30초를 넘기면 사람들이 화면에서 눈을 뗀다 |
| 색 구분 | 색만으로 구분하지 마라. 구슬에 **번호**를 새겨라 |

**6. 절대 금지**
- 결과 선정 후 연출 재생 · 돈/포인트/베팅 표현 · 이름 서버 전송
- 레이스 중 조작 · 시드 비공개 · 재현 불가
- 판이 안 끝나는 코스(통과 시험 없이 배포)

**7. 장르 계약 — 이 프리셋의 산출물은 `DECIDER` 장르에 등록한다**

이 장르는 분류 미관이 아니라 **기능**이다. 허브(게임 목록)의 「랜덤으로 돌리기」가
`GET /api/v1/games?genre=DECIDER` 로 뽑기 대상을 만들기 때문에, 이 장르로 등록하는 순간
새 게임은 **코드 수정 없이** 뽑기에 함께 들어간다. 그 대신 두 가지를 지켜야 한다.

| 계약 | 내용 |
|---|---|
| 파티 인계 | 부팅 때 `GameParty.take('<슬러그>')`(`games/lib/party.js`) 한 줄을 부르고, 값이 있으면 **준비 화면을 건너뛰고 바로 시작**한다. 값은 `{ names, mode }` 이고 `mode` 는 `'last'`(한 명이 걸린다) / `'order'`(순서 정하기) 둘뿐 — 장르의 모든 게임이 이름만 다를 뿐 둘 다 할 수 있어야 한다 |
| 출발 편향 | **출발 위치 ↔ 도착 등수 스피어만 \|ρ\| < 0.1.** dev 훅으로 직접 재고 설계 문서에 수치를 남긴다 |

인계를 **주소가 아니라 `localStorage`(`kgd.party.v1`)로** 받는 이유: 게임은 정적 파일이라
`?names=민수,영희` 는 그대로 웹서버 접근 로그에 남고, 그 순간 "이름은 기기 밖으로 나가지
않는다" 는 이 장르의 약속이 깨진다. 읽으면 즉시 지운다 — 남기면 새로고침마다 같은 판이
다시 시작돼 준비 화면에 영영 못 들어간다.

출발 편향은 **구현 방식과 무관하게 같은 자리에서 터진다.** 물리든 사다리든 "가만 두면
출발 자리가 결과"이고, 그걸 지우는 장치가 게임마다 다를 뿐이다 — 구슬은 **한 통에 담아
쏟기**(한 줄 출발 −0.27 → 한 통 −0.014), 사다리는 **아래 항목 섞기**(n=12 에서 0.641 →
0.003). 어느 쪽이든 **재고 나서 통과라고 말한다.**

> 상태: **1차 가설** (2026-08-23 작성). 수치는 `marble-race`·`ladder-draw` 실측에서 나왔다.

### 프리셋 `coop-usemap-defense` — 대형 맵 협동 디펜스/오펜스 (커스텀맵 계열)

> **지향**: 한국 스타크래프트 커스텀맵 상위권 계열(랜덤/운빨 디펜스 · 포커 디펜스 · 타워
> 디펜스 · 넥서스 부수기)의 웹 이식. **이 장르의 정체성은 규모다** — 한 화면에 다 들어오는
> 판은 이 장르가 아니다.
>
> **최우선 불변식**: 사용자가 "원작 스케일 유지" 를 말하면 그것은 **맵 크기**를 뜻한다.
> 길이만 상수로 주고 맵 규모를 안 주면 **단일 화면 타워디펜스로 수렴한다** (2026-08-23 실측 —
> 3개 세션 동시에 같은 방향으로 갔다).

**1. 맵 규모 (수치)**
| 항목 | 최저선 | 권장 |
|---|---|---|
| 월드 크기 | **128×128 타일** (원작 기준) | 192×192 타일 |
| 타일 픽셀 | 40~64px | — |
| 월드 픽셀 | **5,000×5,000 이상** | 8,000~12,000 사각 |
| **한 화면이 보는 면적** | **월드의 10% 이하** | 5% 안팎 |
| 플레이어 구역 | 슬롯마다 자기 구역 + 공유 중앙/보스 구역 | 4~8 |
| 동시 개체 | **100+** | 200~300 |

**2. 규모가 강제하는 것 (없으면 플레이 불가)**
- **미니맵** — 전체 맵·내 위치·아군·적 웨이브·알림. 선택이 아니라 필수다
- **카메라 이동** — 드래그 / 가장자리 스크롤 / **미니맵 클릭 점프**, 줌 2단계+
- **오브젝트 풀 + 공간 해시** 전제. **렌더 컬링과 시뮬을 분리**하라 — 화면 밖 개체도 계속 굴러야 한다
- **모바일**: 미니맵 탭 점프 + 핀치/버튼 줌

**3. 길이와 규모는 별개다**
맵이 크다고 판이 길 필요는 없다. **큰 맵 + 높은 밀도 + 10~15분**이 목표다.
웨이브가 넓은 회로를 돌고 여러 구역이 동시에 굴러가면 짧아도 규모감이 산다.
이동이 지루해지지 않게 이동 속도·탈것·소환 지점을 조절하라.

**4. 이탈 내성 (온라인 협동 전제)**
- **1판 10~15분** — 길면 사람이 못 버티고 나간다. 길이를 결과가 아니라 **설계 입력**으로 잡아라
- 플레이어를 **슬롯 배열**로 두고 각 슬롯이 **`human | ai` 로 런타임 전환**된다.
  이탈 즉시 **AI 승계**, 복귀 시 되돌림. 남은 사람의 판이 깨지지 않아야 한다
- **AI 승계가 "봐줄 만해야" 한다** — 역할에 맞는 행동(힐러는 힐, 궁수는 거리 유지)을 하고,
  **AI가 이어받았다는 표시**가 있어야 한다. 구역제 게임에서는 빈 구역이 뚫리면 전체가 무너진다
- **네트워크 계층은 클린룸이 만들지 않는다** (플랫폼 릴레이 + 통합 몫).
  **host authority** 전제로 설계하고 입력은 **의도(intent)** 로 분리해 둘 것

**5. 절대 금지**
- 한 화면에 다 들어오는 판 · 미니맵 없음 · 입구가 하나뿐인 방어선(뭉쳐 서면 끝난다)
- 오펜스 모드에서 적 기지가 옆 화면에 보이는 것 (거리가 곧 게임이다)
- 카드/UI 가 화면을 차지하고 전장이 곁가지가 되는 것
- **원작 IP** — 이 계열 유명 맵은 타사 IP를 스킨으로 쓴다(애니·게임 캐릭터·실존 인물·RTS 유닛명).
  전부 금지. 세계관·유닛·등급명은 창작한다

### 프리셋 `draw-to-solve` — 그려서 푸는 물리 퍼즐 (한 붓에 답이 정해진다)

> **지향**: 손으로 **그린 선이 그대로 물리 물체가 되는** 퍼즐. 한 판 20~60초.
> 정체성은 **"이렇게 하면 되겠는데?" 를 그림으로 말하는 것**이다. 정답이 하나가 아니어도 되지만
> **아무렇게나 그어서 풀리면 안 된다** — 그 순간 이 장르는 낙서장이 된다.

**1. 두 단계로 자른다 — 그리기 / 실행**
- 그리는 동안 시간은 멈춘다. 그리면서 동시에 피하게 만들면 손이 하나뿐인 사람에게 불가능해진다
- 실행은 **결정적**이어야 한다(고정 스텝 + 시드). 같은 그림 = 같은 결과여야
  "왜 실패했는지" 를 배울 수 있다. 매번 달라지면 실력이 아니라 운이 된다
- 실패하면 **그림은 남기고** 고쳐 그릴 수 있게 한다. 처음부터 다시 그리게 하면 시행착오 비용이 커진다

**2. 잉크는 예산이다 — 이 장르의 유일한 난이도 손잡이**
- 총 길이(px)로 준다. 무제한이면 화면을 통째로 칠해 끝나고, 그러면 퍼즐이 아니다
- **남은 양을 항상 보여 준다.** 다 쓰고 나서 아는 것은 실패가 아니라 사고다
- 지우개를 준다 — 획 단위로만(부분 지우기는 판정이 지저분해지고 이득도 없다)

**3. 그림은 그대로 물리가 된다**
- 손가락 경로를 **점 간격으로 재표본**한 뒤 캡슐(굵은 선분)로 만든다. 원본 점을 그대로 쓰면
  손 떨림 하나가 물체 수십 개가 되어 프레임이 죽는다
- **최소 길이 미만의 획은 버린다** — 톡 하고 찍힌 점이 벽이 되면 "안 그렸는데 막혔다" 가 된다
- 그린 선은 **움직이지 않는다**(정적 물체). 움직이게 하는 순간 난이도가 물리 감각이 아니라
  손재주로 옮겨 간다

**4. 판마다 두 가지를 반드시 증명하라 — 자동 검사**
- **풀린다**: 판마다 **모범 답안 획**을 코드에 넣고, 헤드리스로 그려 실행해 성공하는지 본다.
  사람이 손으로 확인하면 열 판을 넘기는 순간 안 하게 되고, 안 풀리는 판이 배포된다
- **거저 풀리지 않는다**: **아무것도 안 그린 상태로 실행해 반드시 실패**해야 한다.
  이게 통과하면 그 판은 첫 판이든 마지막 판이든 **볼거리일 뿐 퍼즐이 아니다**
- 둘 다 CI 가 아니라 `dev` 훅으로 두고 판을 고칠 때마다 돌린다

**5. 첫 판부터 어렵게 — 몸풀기 판을 두지 마라**
- 1단계도 **모범 답안이 필요**해야 한다. "선 하나 그으면 끝" 은 튜토리얼이지 판이 아니다
- 조작 설명은 판을 쉽게 만들어서 하지 말고 **화면 위 글자로** 한다

**6. 절대 금지**
- 무제한 잉크 · 비결정적 실행 · 그리는 중 시간 진행
- 모범 답안 검사 없이 판 추가 · 빈 손으로 통과되는 판
- 손 떨림을 그대로 물체로 만들기(프레임 사망) · 획 하나가 화면 밖으로 나가 판을 가두기

> 상태: **1차 가설** (2026-08-24 작성). 수치는 `bee-guard` 실측에서 나왔다.

### 프리셋 추가 규칙

새 장르를 하면서 "게이트는 통과했는데 체감이 아니다" 가 나오면, 그 교정 내용을 **수치로**
여기에 프리셋으로 박는다. 프리셋은 다음을 반드시 수치·불변식으로 포함한다:
카메라 스케일 / 액터 충돌 규약 / 응답성 목표(입력→판정, 히트스톱, 이동 속도) / 시점 /
그 장르의 필수 기술 체계 / 규모.

기존 산출물에서 뽑을 수 있는 프리셋 후보: `roguelike-action`(abyssal-crown 계열),
`run-and-gun`(nova-strike — 1차 30점 실패 원인 분석 후 작성할 것).

## 기술 도입 게이트 (WASM · WebGL · Worker 등)

**원칙: 측정 없이 도입하지 않는다.** 새 런타임 기술은 "빠를 것 같아서" 가 아니라
**병목을 수치로 특정한 뒤** 그 병목에 맞는 것만 넣는다.

> **왜 이 게이트가 필요한가** (2026-08-18 실측)
> "좀비 생존물에 WASM 을 넣을까" 를 검토하며 실제 코드·수치를 열어보니:
> `ashen-warband` 는 프레임 코스트가 **0.4~1.2ms / 예산 16.7ms**(3~7%)로 CPU 여유가 93% 였고,
> `rustline-hold` 는 경로 탐색이 **이미 플로우 필드**(개체별 A* 가 아님)라 WASM 이 노릴 루프가
> 없었으며, 자기 문서가 정의한 최악 조건이 **"밤 = 조명 합성 + 날씨 + 비네트"**, 즉 전체 화면
> 채우기 비용이었다. fps 가 좀비 수와 **역상관**으로 나온 이상한 측정도 이걸로 설명된다.
> **도입했다면 병목이 아닌 곳을 최적화하면서 빌드 스텝만 얻었을 것이다.**

### 0. 깨지면 안 되는 전제
**빌드 스텝 없음**이 이 생산 체제의 근간이다 — 게임이 폴더째 드롭인으로 배포되고, 클린룸
세션이 툴체인 없이 만들어낸다. 이걸 깨는 결정은 **게임 하나가 아니라 생산 라인 전체**에
비용을 지운다. 예외를 만들려면 아래 게이트를 통과해야 한다.

### 1. 측정 프로토콜 (게이트 진입 조건)
- **`sim`(그리기 제외) / `draw` / `composite`(전체 화면 패스) 를 분리해서 재라.**
  합산 프레임 코스트 하나로는 어떤 기술이 맞는지 고를 수 없다
- **목표 규모에서 재라.** 도달해본 적 없는 규모(예: "좀비 100기") 를 근거로 판단하지 않는다.
  최대 실측치를 명시하고, 목표에 못 미쳤으면 **먼저 그 규모를 만들어라**
- 지표가 **직관과 어긋나면**(개체 수와 fps 가 역상관 등) 측정이 오염된 것이다.
  결론을 내지 말고 측정을 고쳐라

### 2. 사다리 — 싼 것부터. 아랫단을 건너뛰고 윗단으로 가지 않는다
| 단 | 조치 | 비용 |
|---|---|---|
| 1 | **확인된 낭비 제거** — 프레임당 할당(그라디언트·배열·객체), 매 프레임 재계산 | 0 |
| 2 | **자료구조** — 오브젝트 풀, 공간 해시, 필드 1회 계산 후 샘플링(플로우 필드) | 0 |
| 3 | **렌더 비용** — 조명 버퍼 저해상도 + 업스케일, 전체 화면 패스 병합, 오프스크린 캐시 | 0 |
| 4 | **OffscreenCanvas + Worker** — 시뮬레이션을 메인 스레드에서 분리 | **빌드 스텝 0** |
| 5 | **WebGL** — 드로우콜 배칭 | 중 (빌드 스텝 없이 가능) |
| 6 | **WASM** — 덩어리 연산만 | 큼 (**빌드 스텝 도입**) |

### 3. 수치 게이트
- **WebGL 로 간다**: `draw + composite ≥ 8ms`(예산의 절반) **그리고** 1~3 단을 마쳤고
  **그리고** 드로우콜 수 또는 fill rate 가 병목임을 확인했을 때
- **WASM 으로 간다**: `sim ≥ 8ms` **그리고** 1~4 단을 마쳤고 **그리고** 대상이
  **JS↔WASM 경계를 자주 넘지 않는 덩어리 연산**일 때.
  경계를 자주 넘는 작업(개체마다 Canvas 를 그리는 류)은 **오히려 느려진다**
- **게임 전체를 옮기지 않는다. 그 덩어리 하나만 옮긴다**

### 4. WASM 이 값을 하는 작업 / 하지 않는 작업
| 값을 한다 | 하지 않는다 |
|---|---|
| 구조물 파괴 전파·구조 안정성 계산 | Canvas 2D 그리기 (네이티브가 한다) |
| 유체·화재 확산 시뮬 | 조명 합성·전체 화면 채우기 |
| 대규모 물리·충돌 해석 | 이미 플로우 필드로 amortize 된 경로 탐색 |
| 월드/절차 생성 (큰 배열 한 번에) | 개체마다 JS 를 호출해야 하는 로직 |

### 5. 금지
- **코드 보호를 이유로 한 단독 도입.** `wasm2wat`·디컴파일러가 있어 난독화가 **한 단계**
  올라갈 뿐이다. sitelock · frame-ancestors · minify · private 레포 위에 얹기엔 비용이 크다
- **체감으로 이어지지 않는 최적화.** 예산의 7% 를 쓰는 게임을 3% 로 만드는 일은 하지 않는다

### 6. 도구 선택 (도입이 확정된 경우)
**AssemblyScript 우선** — TS 문법이라 클린룸 세션이 그대로 다룰 수 있고, 툴체인이 npm 패키지
하나에 산출물도 `.wasm` 하나라 드롭인 배포에 가장 가깝다. Rust/Emscripten 은 산출물과 CI 가
무거워지므로, AssemblyScript 로 표현이 안 되는 경우에만 고려한다.

### 7. 기록 의무
도입했다면 **전/후 수치(sim·draw·composite 분리)** 를 그 게임의 `DESIGN.md` 에 남긴다.
개선이 없었으면 **되돌린다** — 남겨두면 다음 사람이 근거 없이 따라 한다.

```
당신은 브라우저 게임을 처음부터 만드는 시니어 게임 개발자다. 외부 참조 없는 독립
프로젝트로, 아래 요구만을 근거로 게임을 완성하라. 디자인 판단은 질문하지 말고 스스로

## 진행 방식

이펙트/사운드/아트 문법 최종본)을 목표 품질 100% 로 완성해 벤치마크 비교표와 함께 보고하고
사용자 체크를 받은 뒤, 피드백 반영 후 완주하라." / 명시적 완주 지시 시: "중간 체크 없이

## 과제
⟨장르/컨셉 — 예: "로그라이크 액션", "벨트스크롤+대전격투 커맨드",

테마·세계관·이름은 자유롭게 창작하되 slug 는 ⟨slug — 영문 kebab-case, 미정이면 "직접 정하고 보고"⟩ 를 쓴다.

## ★ 품질 게이트 — 이 과제의 핵심. 미달이면 "완성" 선언 금지
이 프로젝트에서 품질은 협상 대상이 아니다. 아래 게이트를 **전부** 넘어야 완성이다.
"동작한다" 와 "완성했다" 를 구분하라.

**⟨벤치마크⟩는 참고가 아니라 하한선이다.** 벤치마크작과 나란히 놓고 아래 축을 비교표로
만들어, 전 축 "동급 이상" 판정이 나와야 완성이다:
①그래픽(스프라이트 밀도·디테일) ②애니메이션(주인공 프레임 수·보간 부드러움)
③해상도·화면 활용 ④이펙트 밀도(피격/폭발/궤적) ⑤조작감(입력 반응·프레임 데이터)
⑥연출(보스 등장·화면 전환·스테이지 도입).
미달 축이 있으면 "미완 명시 후 종료"가 아니라 **개선을 반복**한다. 반복해도 물리적으로
불가능하다고 판단되면 그 시점에 멈추고 사용자에게 갭과 대안을 보고하라 — 미달 상태의
자체 완성 선언은 금지다.

### A. 아트 (가장 자주 미달하는 축 — 최우선 투자)
- **오리지널 디자인 의무 (IP 세이프)**: 벤치마크는 품질·연출의 기준일 뿐이다. 캐릭터·로고·
  고유 디자인을 원작과 유사하게 만들지 않는다 — 마스코트의 실루엣+컬러웨이 조합(예: 파란
  원형 헬멧+얼굴 노출 안드로이드 = 메가맨), 고유 명칭, 트레이드마크 요소 재현 금지.
  "누가 봐도 그 게임 캐릭터" 면 실패. 장르 문법(대시/차지샷 등 메커닉)은 자유

## 실측 함정 목록 (앞선 제작에서 실제로 터진 것 — 같은 함정에 빠지지 말 것)
- 120Hz 디스플레이: 고정스텝이 0회 도는 렌더 프레임에서 edge-trigger 입력을 비우면 입력 유실
- **"렉 걸린 느낌"의 진범은 대개 히트스톱이 아니라 프레임 페이싱이다** — 고정 1/60 누적
  방식은 120Hz 에서 **렌더 프레임의 절반이 0스텝**으로 돌아 개체가 두 프레임에 한 번만
  움직인다(미세 스터터). **클램프된 가변 스텝**(프레임당 1~4 서브스텝, 서브스텝 ≤20ms)으로
  바꿔 렌더 프레임마다 반드시 시뮬한다. 무겁다는 피드백이 오면 히트스톱부터 줄이지 말고
  **여기부터 계측**하라 (ashen-warband 실측)
- 공격 시작에서 속도를 통째로 죽이면(`vx *= 0.25` 류) 걷다 치는 순간 끊기고, **공중에도
  같은 감속을 걸면 점프 궤적이 끊긴다** — 감속은 지상에만, 공중 관성은 100% 보존
- 잡기가 약공을 가로채면 연타가 막힌다 — 근접만으로 잡기로 새면 실측 입력의 절반이
  유실된다(24회 중 12회). 잡기는 **콤보 미시작 + 적 방향 입력 유지**일 때만 성립시켜라
- **공중 저글이 "안 되는" 원인은 저글 로직이 아니라 판정·넉백이다** (실측 원인 2개):
  ①투사체/공격의 **세로 판정 밴드가 좁아**(±30px) 뜬 적을 통과한다 → ±90~110px 로 확대
  ②**런처 넉백이 적을 사거리 밖으로 밀어낸다** → 런처만 넉백을 대폭 낮추고(200→50)
  **저글 자석**(뜬 적을 공격자 앞 ~105px·같은 깊이로 흡인)을 넣는다.
  추가로 저글 중 중력 ~0.46배 + 피격마다 재상승(감쇠 0.85) + **상승 상한**(너무 높이 뜨면
  후속타 사거리를 벗어난다). 근접 가로채기 기술이 체인을 먹지 않는지도 확인
- `ctx.filter = 'blur()'` 는 프레임을 죽인다 (33fps 실측) — 그라디언트/스트로크로 대체
- `undefined <= 0` 는 false — 타이머류는 0 으로 명시 초기화하고 부정형(`!(x > 0)`) 비교
- 커맨드 입력은 **입력 당시 facing** 을 히스토리에 함께 기록 (도중 돌아서면 의미 반전)
- **"대각선으로 걸으며 공격하면 공격이 안 되고 위로만 간다"의 진짜 원인은 깊이축 감쇠 누락**
  이다 — 공격 진입/지속에서 **vx 만 감쇠하고 vz(깊이)를 빼먹으면**, 공격 내내 깊이 방향으로
  full 속도 미끄러짐이 남고 그 사이 대상의 깊이 띠를 벗어나 헛친다. 두 증상이 한 원인이다.
  **적 쪽에는 vz 감쇠가 이미 있는데 플레이어만 빠진 비대칭**으로 나타나기 쉬우니 양쪽을
  대조하라. (ashen-warband 실측 — 커맨드 파서/facing 접힘 가설은 전부 틀렸다)
- 2.5D 는 **모든 속도·감쇠·판정 로직에 축이 하나 더 있다**는 뜻이다. x 에만 적용한 처리가
  없는지 전수 점검하고, 8방향 × 공격 종류 전조합으로 검증하라
- 테스트 하네스로 월드 상태를 임의 조작(인카운터 스킵용 인덱스 변경 등)하면 **씬 전이가
  트리거돼 입력이 안 먹는 것을 게임 버그로 오독**한다 — 재현은 실제 플레이 경로에서 하라
- 승룡(623)류는 인식창을 좁혀라 — 넓으면 "걷다 파동"이 승룡으로 오폭
- 보스 + 카메라 클램프 조합에서 보스가 화면 밖으로 나가지 않는지 확인 (동적 줌 고려)
- 마지막 적이 스폰되는 프레임에 웨이브 클리어가 나지 않게 스폰 큐까지 판정에 포함
- 오디오는 첫 사용자 입력 후 AudioContext 활성화 (자동재생 정책)
- **난이도가 낮으면 사망 경로가 통째로 미검증 상태로 남는다.** 난이도를 올리자마자 이번에
  드러난 것: `kill` 이 플레이어에 적용돼 "죽었는데 다운 상태" 좀비가 되어 부활도 게임오버도
  안 오고, 게임오버 후에도 매 프레임 `lives` 가 줄어 −37 까지 갔다. **새 사망/실패 경로를
  만들 때마다 그 경로를 실제로 밟아라** — 낙사·구간 이탈·탈것 사망·전멸, 협동이면 한 명만
  사망 / 동시 사망까지 (ashen-warband 실측)
- **데이터 구조 확인은 검증이 아니다.** "보스 8기가 정의되어 있다" 와 "8기가 실제로 스폰되어
  패턴을 돌리고 처치된다" 는 완전히 다른 명제다. ashen-warband 는 이 착각으로 **보스 8기 중
  7기가 스폰 즉시 크래시**해 2층 이후가 플레이 불가인 상태로 "완주 완료" 보고가 나갔다.
  **모든 콘텐츠는 라이브로 밟아라** — 스테이지·보스·기믹·히든·엔딩 전부, 한 번씩 실제로
  도달해 동작을 확인한 것만 검증으로 친다. 최소한 **전 개체를 실제로 소환하는 스모크 테스트**를
  상시 돌려라 (정의된 적·보스를 하나씩 스폰해 한 프레임이라도 그려보는 것으로 대부분 잡힌다)
- **베이스 병합 순서 함정**: `Object.assign(base, override)` 를 먼저 하고 나중에 base 의
  파생값을 읽으면, override 에 없는 `pal`/`style` 같은 키가 통째로 날아가 `undefined` 참조로
  터진다. 병합은 **파생값 계산 전에**, 또는 override 를 얕은 병합으로 제한하라
- **렌더 루프 예외 = 영구 정지**: tick 끝에서만 rAF 를 재요청하면 한 프레임의 오류로 화면이
  검게 멈춘다. **rAF 재요청을 try/finally 로 보장**하되 오류는 콘솔에 그대로 남겨라 (은폐 금지)
- **오브젝트 풀에서 빈 슬롯을 선형 탐색하지 마라.** 격전에서 풀이 가득 차면 매 생성마다
  전체를 훑어 **fps 가 2~6 으로 붕괴**한다(실측). **링 버퍼(회전 인덱스)로 덮어쓰기** 하면
  같은 상황에서 284개체 1.97ms 다. 풀을 "넣었다" 와 "빠르다" 는 다른 얘기다
- **정의만 있고 구현이 없는 공격 종류**를 조심하라 — 데이터에 `lob`(포물선) 을 적어놓고
  구현을 안 하면 근접 분기로 떨어져 터진다. **정의된 공격마다 실발동 테스트**를 돌려라
- **검증 봇의 체력을 부풀리지 마라** — maxHp 를 올려놓고 재면 함정·기믹 난이도가 통째로
  가려진다. 실제 클래스 체력으로 측정하라
- **함정·기믹 피해는 최대 체력 비율로** 잡아라. 고정값은 체력 낮은 직업에게만 즉사기가 된다
- **시간 기반 스폰 구간(탈것 등)에는 동시 상한**을 걸어라 — 없으면 낙오가 누적돼
  60초 주행 끝에 30기 도살장이 된다
- **멀티플레이는 "1P 만 동작"이 기본 실수다** — 렌더 drawables, 상점, 결과 집계, 인벤토리가
  각각 단일 플레이어를 하드코딩하고 있지 않은지 **개별로** 확인하라
- **원거리 직업이 못 푸는 상호작용 = 진행 불가 데드락**. 밸브·레버·파괴 오브젝트가 근접
  공격만 인정하면 궁수/마법사가 그 자리에 영구히 묶인다. 모든 클래스로 진행 경로를 밟아라
- **★ macOS 에서 `nativeVirtualKeyCode` 에 윈도 VK 코드를 넘기지 마라.** 크롬이 그 값을
  **맥 네이티브 키코드로 해석**한다 — `49`=Space, `51`=Backspace. 그래서 `Digit1` 을 보내면
  게임은 **Space** 를 받고, `Digit2`/`Digit4` 는 **이벤트 자체가 안 온다**.
  **`code` + `windowsVirtualKeyCode` 만 넘기고 `nativeVirtualKeyCode` 는 빼라.**
  - 증상이 고약하다: 어긋난 이벤트가 **입력 파이프라인을 막아 `Runtime.evaluate` 가 12~27초
    지연되고 30초 타임아웃**이 난다 → **"게임이 멈췄다" 로 오판**하게 된다.
    실제로 이 오진으로 몇 시간을 날렸다 (ashen-warband 계열 세션 실측).
    수정 후 같은 입력 폭주에서 evaluate **15~28ms**
  - "배치로 돌리면 실패하는데 따로 돌리면 통과" 하는 **위치 의존 실패**도 대부분 이것이다
  - **살아 있는지 확인하는 법**(오진 방지): 프레임 카운터를 `document.title` 에 실어
    **브라우저 프로세스에서 HTTP(`/json/list`)로 읽어라** — 렌더러 평가가 막혀도 읽힌다.
    카운터가 오르면 게임은 정상이다. `Debugger.pause` 즉시 성립도 보조 신호
  - **검증 시작 전에 키 매핑을 먼저 검증하라** — 게임의 입력 큐를 계측해
    "보낸 키 = 받은 키" 를 한 번 확인하고 본 검증에 들어가라
- **★ 하네스가 설정한 값을 화면에서 되읽어 확인하라.** 설정 UI 가 **순환이 아니라 클램프**면
  `3 → → ` 가 1 이 아니라 **4** 다. 실측 사례: "1슬롯이 계속 진다" 는 결과가 4번 나왔는데
  게임이 아니라 **4슬롯을 1슬롯이라 재고 있었던 것**이다. 조건을 설정했으면 **그 조건이
  실제로 걸렸는지 화면에서 확인한 뒤** 측정에 들어가라
- **CDP `openPage` 류가 열린 페이지를 전부 닫는 구현인지 확인하라.** 두 테스트를 동시에
  돌리면 서로를 죽인다 (실측으로 당한 사례 있음)
- **★ 헤드리스에 `--disable-gpu` 를 붙이지 마라.** 크롬이 **SwiftShader(소프트웨어 래스터)** 로
  떨어져 **fps 10~30 + 렌더러 굳음**이 난다. 빼면 같은 조건에서 **120fps** 다 (실측).
  `--headless=new` 는 GPU 를 쓸 수 있다 — 관성으로 붙이던 플래그다.
  fps 를 측정할 거면 특히 빼라. 헤드리스 fps 가 낮게 나오면 **게임 비용이 아니라 이 플래그**를
  먼저 의심하라
- **세션마다 CDP 포트·프로필을 분리하라.** 두 클린룸 세션이 같은 Chrome 인스턴스(같은 포트·
  같은 user-data-dir)를 쓰면 서로의 페이지를 background 로 밀어 **rAF 가 조용히 멈춘다**.
  예외도 안 남고 측정만 죽는다 (실측: 이 사고로 측정 3회 유실). 포트와 프로필 경로에
  세션 식별자를 넣어라
- **CDP 고아 페이지를 정리하라** — 죽인 스크립트가 남긴 탭이 rAF 를 나눠 먹어 fps·난이도
  측정이 왜곡된다. 측정 전 열린 페이지를 확인하는 습관을 넣어라
- **봇이 못 깬다고 밸런스를 낮추지 마라** — 단순 정책 봇은 유리대포 클래스의 운용(거리 유지·
  회피기 활용)을 못 한다. 클래스 고유 방어/유틸 액션을 다 넣은 뒤 분포를 재측정하고,
  조정하더라도 스탯 하향보다 **도구(자원 회복·지속시간) 조정**을 우선한다
- **조건 분기에 걸려 아무 반응도 없는 입력** — `if (held.light && near)` 처럼 조건이 안 맞으면
  키를 소비조차 하지 않고 흘리는 코드. 애니메이션·소리·상태 전부 0 이라 사용자는 **"고장" 으로
  읽는다.** curfew-siren 은 낮 페이즈에서 밤의 공격 키(Z)가 정확히 이 상태였고, 게임의 첫 5분이
  그랬다. **한 페이즈에서 공격이던 키는 다른 페이즈에서도 반드시 무언가를 해야 한다** —
  손버릇은 페이즈를 넘어 유지된다. 위 "죽은 입력 감사" 로 전수 점검하라
- **바닥 없는 지속 피해 = 탈출 불가 사망 루프.** 굶주림·출혈처럼 시간이 지나면 깎는 자원에
  **하한이 없고, 부활이 그 자원을 회복시키지 않으면**, 임계를 넘은 순간부터 "부활 → N초 뒤 사망 →
  부활" 이 무한 반복된다. curfew-siren 은 밤 342초를 넘기면 163초마다 확정 사망하는 루프에
  들어갔고, **적이 멀쩡히 있는데 진행만 안 되는 소프트 스톨**로 나타나 원인을 AI·웨이브 판정에서
  찾게 만들었다. **치명적인 시계는 하나만 두고**(감염 등), 나머지는 **최대치 대비 하한**(예: 25%)에서
  멈추고 **스탯 페널티로** 벌하라. 그리고 **스탯을 바꾸는 자원은 반드시 그 화면에 게이지가 있어야
  한다** — 약해진 이유를 읽을 방법이 없으면 그것도 "고장" 이다
- **"1/4 확률" 로 보이는 스톨은 대개 확률이 아니라 시간 임계값**이다. 봇이 빨리 깨면 안 걸리고
  한 번 늦어지면 반드시 걸린다. 재현율을 세기 전에 **무엇이 임계를 넘겼는지**부터 찾아라
- **스케일은 "이름값" 이 아니라 "그려지는 픽셀" 로 재라.** `coin-corgi` 는 플레이어
  높이 상수가 150px(화면의 1/9.6)이라 스펙 안이라고 믿었지만, 리그가 다리+몸통+머리를
  쌓아 올리며 **실제로는 227px = 화면의 1/6.3** 을 그리고 있었다. 프리셋이 "전부 화면
  높이 대비 %로 잰다"고 못박은 게 정확히 이 함정인데, 상수만 보고 통과 처리했다.
  **리그가 그리는 바운딩 박스를 함수로 돌려받아 실측하라** — 그 함수는 판정 박스의
  단일 원본이기도 하다
- **6축 게이트(그래픽/애니/해상도/이펙트/조작감/연출)는 캐릭터 매력을 못 잡는다.**
  `coin-corgi` 의 마스코트는 6축을 전부 통과하고도 사용자에게 "무슨 튜브 형태 이상한
  캐릭터" 판정을 받았다. 원인은 품질이 아니라 **비율과 실루엣 문법**이었다 —
  머리가 몸통 폭의 0.47 밖에 안 되고, 몸통이 매끈한 가로 타원 하나였고, 눈이 작았다.
  **마스코트가 있는 게임은 실루엣을 따로 판정받아라**: ①머리:몸통 폭 0.6 이상(치비)
  ②몸통을 단일 타원으로 두지 말 것(어깨/엉덩이 폭이 달라야 동물로 읽힌다)
  ③가슴털·볼털 같은 **윤곽을 깨는 부품** ④눈은 머리 반지름의 0.2 이상 + 어두운
  개체는 밝은 눈두덩. 견종·종족이 여럿이면 색만 바꾸지 말고 **리그 수치를 바꿔라**
- **반투명 HUD 는 낙하물·투사체를 통과시킨다** — 패널 알파가 낮으면 떨어지는 위험물이
  체력 칸에 겹쳐 남은 목숨을 오독하게 만든다. 상단 HUD 는 불투명에 가깝게 두어라
- **검증 하네스를 먼저 의심하라 (2건 실측)**: ①**키를 누른 뒤 한 번만 상태를 찍으면 짧은 동작을
  통째로 놓친다** — 0.24초 약공이 "무반응" 으로 나온다. **누르는 동안 40~50ms 간격으로 폴링**하라.
  ②**긴 세션의 후반 블록에서 CDP 입력이 씹힌다** — 마지막 7칸이 전부 실패로 나왔는데, **블록 순서를
  바꾸자 실패가 순서를 따라 이동**해 씬·키가 아닌 위치 의존(하네스 드리프트)으로 판명됐다.
  **블록마다 프로세스를 분리**해 재측정하라. 두 경우 모두 그대로 믿었으면 **멀쩡한 코드를 뜯을
  뻔했다.** 대량 실패가 한꺼번에 나오면 코드보다 측정을 먼저 의심하고, 격리 재현 → 누적 상태
  배제 → **순서 바꾸기** 3단계로 확인하라
```

>    (필요 시 `data-dirkeys="wasd"` · `data-stick` · `data-fit`).
>    **순서가 곧 자리다** — 1번째=주공격(코너 대형), 2번째=점프/결정, 3번째=대시/특수,
>    4·5번째=보조. 라벨은 한글 1~3자 필수. **Esc 가 일시정지/뒤로로 동작하면
>    `data-pause="1"`(시스템 ⏸ 버튼)도 켠다** → `docs/conventions/game-input-standard.md`
> 2. **터치 에뮬레이션 실측** — `#vt-root` 생성 · 버튼 개수 · **조이스틱 드래그로 실제 이동**까지.
>    **패드가 뜨는 것과 조작이 먹히는 것은 다른 문제다**
> 3. 통과한 뒤에만 `supports_mobile = 1` 로 시드한다 — 이 플래그는 "모바일에서 할 만하다"는
>    약속이고, 켜놓고 안 되면 안 켠 것보다 나쁘다
>
> **실측 함정 2종**
> - `touch.js` 는 **보이는 `.panel` 이 있으면 패드를 숨긴다**(메뉴 위에 버튼이 겹치는 것을
>   막는 규약). 게임이 **플레이 화면에도 `.panel` 클래스를 쓰면 패드가 영원히 안 뜬다** —
>   클래스 이름 충돌을 확인하라
> - **합성 터치는 `click` 을 만들지 않는다.** DOM 버튼 메뉴는 터치로 넘어가지 않으므로,
>   메뉴 통과는 `click()` 으로, 패드 검증은 실제 터치 이벤트로 **나눠서** 테스트하라

1. **스모크 테스트**: 직접 열어 콘솔 에러 0·부팅·기본 조작 확인
   + **IP 스캔**: 서빙 파일에서 타사 게임 명칭 grep, `DESIGN.md` 를 `docs/specs/`
   로 이동(벤치마크 서술은 서빙 경로에 남기지 않는다 — 2026-08-15 전수 점검 정책)
2. **platform.js 배선** (`portal-fe/public/games/lib/platform.js`):
   - index.html 게임 스크립트 앞에:
     ```html
     <script src="../lib/rank.js"></script>
     <script src="../lib/platform.js"></script>
     <script>PlatformAdapter.init({ slug: '<slug>', title: '<한글명>', saveKeys: ['<localStorage 키…>'] });</script>
     ```
   - 게임의 런/스테이지 종료 지점에 한 줄:
     `window.PlatformAdapter && PlatformAdapter.runEnd({ score, detail })`
   - 서버 세이브는 어댑터가 localStorage 가로채기로 자동 동기화
3. **썸네일**: 전투 실플레이 320×180 캡처 → `thumbs/shots/<slug>.png`
   (반드시 업로드 서버 방식 — base64 를 대화로 통과시키지 않는다)
3-b. **SNS 공유 카드 (OG) — 필수**
   > 목록 썸네일 320×180 을 og:image 로 쓰면 안 된다. 큰 카드 최소치(600×315)에 한참
   > 못 미쳐 카카오톡·슬랙·X·페이스북에서 뭉개진 카드가 나온다.
   - **1200×630 전용 카드**를 `thumbs/og/<slug>.png` 로 만든다 — 실플레이 화면을
     16:9 로 잘라 넣고 하단 그라디언트 위에 **게임 한글명 + 한 줄 소개 + 브랜드**를 얹는다
   - 프리렌더가 이 파일의 존재를 보고 자동으로 큰 카드로 승격한다
     (`socialImage()` → `game.ogImageUrl`, 없으면 썸네일 + `summary` 로 폴백)
   - **게임 자체 `index.html` 에도 OG 를 넣는다** — 누군가 iframe URL 을 직접 공유해도
     카드가 나오게. 단 `og:url` 과 `<link rel=canonical>` 은 **포털의 게임 상세**
     (`https://game.1989v.com/games/<slug>`)를 가리켜 공유 지표가 한 URL 로 모이게 한다
   - 확인 항목: og:title / og:description / og:url / og:image(+secure_url·type·width·
     height·alt) / twitter:card=summary_large_image / canonical
4. **V시드**: `game/feature/src/main/resources/gamedb/migration/V{next}__seed_<slug>.sql`
   - V30 을 템플릿으로. 태그는 V25 생존 슬러그만 매핑(roguelike/leaderboard 등),
     장르는 genre 컬럼. title_en/description_en 필수(SEO). supports_mobile 은 키보드 전용이면 0
   - `./gradlew :game:feature:test --tests '*GameSchemaIntegrationSpec*' --rerun-tasks` 로 실 MySQL 검증
5. **game/CLAUDE.md** 정적 자산 표에 행 추가
6. **msa-games 푸시 + 본체 포인터 범프** — 서브모듈에서 커밋·푸시 후 msa 에서
   `git add portal-fe/public/games` (포인터) → 시드·문서와 함께 커밋
7. 커밋 → 푸시 → 배포 확인 → **portal-fe 재빌드**(`gh workflow run images -f services=portal-fe`)
   — 프리렌더/사이트맵은 빌드 시점 API 를 읽으므로 백엔드 반영 후 한 번 더 돌아야 잡힌다
