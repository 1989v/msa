# 게임 클린룸 파이프라인 — 신작 생산 표준

> **용도**: 게임 신작 1개 = 새 클린 세션 1개. 아래 **마스터 프롬프트**의 `⟨…⟩` 슬롯만 채워
> 새 세션에 그대로 전달한다. 완료 후 **통합 절차**(이 문서 하단)는 메인/통합 세션이 수행한다.
>
> **근거**: 클린룸 실험 2회(abyssal-crown, raging-fist-saga) 실측 — 기존 게임·lib 맥락을 차단한
> 세션이 메인 세션 대비 일관되게 높은 게임 코어 품질을 냈다(기존 관습이 앵커로 작용).
> 품질 마지노선 = **abyssal-crown** (`docs/conventions/game-art-baseline.md` 기준 상향 참조).

## 사용법

1. 새 세션을 연다. **완전 클린룸을 원하면** 레포 밖 빈 디렉토리에서 세션을 시작해 산출물
   폴더만 절대경로로 지정한다 (레포 안에서 시작하면 CLAUDE.md 의 게임 목록이 자동 로드되어
   약한 오염이 생긴다 — 허용 범위지만 알고 쓸 것).
2. 아래 마스터 프롬프트의 슬롯을 채워 첫 메시지로 보낸다.
3. 완료 보고를 받으면 이 문서의 **통합 절차**를 메인 세션에서 실행한다.

## 진행 모드 (2026-08-15 실측 피드백 반영 — 디폴트 변경)

- **디폴트 = 수직 슬라이스 우선.** 전량 생산 후 첫 노출이 아니라, **극초반 1구간**을 목표
  품질 100% 로 먼저 완성해 사용자에게 체크를 받는다. 슬라이스에 반드시 포함:
  핵심 조작 전부(이동/점프/대시/공격/차지 등) · 대표 적 2~3종 · 이펙트/사운드/아트 문법
  최종본 · 대표 배경 1세트 · 벤치마크 나란히 비교표. **슬라이스의 품질이 전체 품질의
  상한이므로, 벤치마크 하한 판정을 슬라이스 단계에서 끝낸다.**
- 사용자 피드백 반영 후 나머지를 완주한다.
- **예외**: 사용자가 "끝까지 완성" / "완주" 를 명시적으로 지시하면 중간 체크 없이 묻지 않고
  끝까지 완성한다.
- 근거: nova-strike 1차 실측 — 전량 생산 후 첫 노출에서 벤치마크(32비트 세대 대표작) 대비
  그래픽·해상도 활용·조작감이 하한 미달(사용자 평가 30점)로 판정. 슬라이스 체크포인트가
  있었다면 초반에 교정됐을 갭이다.

## 시드 계약 — 두 라인이 같은 개념을 쓴다 (2026-08-31 신설)

시드 난수는 **이미 두 라인에 각자 있다.** 캔버스는 `portal-fe/public/games/lib/daily.js`,
유니티는 게임 안. 코드를 공유할 수는 없지만(언어도 런타임도 다르다) **개념이 갈리면
안 된다** — 같은 말이 두 뜻을 갖는 순간 다음 사람이 잘못된 쪽을 고른다.

| 개념 | 뜻 | 캔버스 | 유니티 |
|---|---|---|---|
| **시드** | 판 하나를 통째로 재현하는 정수 하나 | `GameDaily.seed(slug)` (날짜+슬러그) | `Progress.NewMapSeed()` (판마다 무작위) |
| **파생 시드** | 시드 하나에서 부분마다 다른 난수원을 만드는 법 | — | `World.ZoneSeed(salt, zone)` |
| **결정적 난수** | 같은 시드면 같은 수열 | `GameDaily.rng(s)` (mulberry32) | `System.Random(seed)` |
| **주머니** | 한 바퀴 안의 등장 횟수를 못박는 뽑기 | `GameDaily.shuffle` (Fisher-Yates) | `Odds.ShuffleBag<T>` |

**지켜야 할 것 셋**

1. **시드는 저장에 실린다.** 안 실으면 이어하기가 다른 판을 깐다 — 좌표·진행이 그 판 기준이라
   벽 속에서 시작한다. 유니티 쪽은 `RunSave.mapSeed`, **0 은 「시드 이전 저장」**으로 읽는다.
2. **난수 소비 순서가 곧 결과다.** 생성 단계를 앞에 끼워 넣으면 뒤따르는 배치가 전부 밀린다 —
   가드 하나를 더하는 것만으로 지도가 재배열된 사고가 있었다. **거르기는 난수를 뽑은 뒤에** 한다.
3. **시드를 사람에게 보여 준다.** 이상한 판을 신고할 때 그 번호 하나면 같은 판을 다시 깐다.
   유니티 쪽은 결과 화면의 「지도 #」이 그것이다.

**검사도 시드를 고정한다.** 매번 새로 뽑으면 빨간불이 떴을 때 그 판을 다시 못 만든다 —
`Editor/GateSeeds.cs` 가 그 목록의 단일 원본이고, 지도에 의존하는 검사 넷이 같은 목록을 쓴다.

## 전역 가드레일 (장르 불문 — 2026-08-24 신설)

프리셋보다 위에 있는 규칙이다. **모든 게임에 적용**되고, 반복해서 지적받은 것만 올렸다.

### G1. 플레이어블 해상도 — "캐릭터가 커서 맵이 작아 보인다"

가장 자주 나오는 지적이다. 원인은 맵이 실제로 작은 것보다 **카메라가 너무 붙어 있는 것**인
경우가 많다. 카메라 종류별 상한을 지켜라.

| 카메라 | 주인공 높이 / 화면 높이 | 한 화면이 보는 월드 |
|---|---|---|
| 사이드뷰 액션 (벨트스크롤·플랫포머) | **1/7 ~ 1/9** | — |
| 탑다운·쿼터뷰 전투 | **1/12 ~ 1/16** | 월드의 **10% 이하** |
| 전략·디펜스 (대형 맵) | **1/16 ~ 1/24** | 월드의 **10% 이하** (권장 5%) |
| 시뮬·건설 | **1/12 ~ 1/20** | 월드의 **10% 이하** |

- **판정 신호**: 플레이 영상을 보고 "맵이 좁다 / 캐릭터가 크다" 는 말이 나오면 **실패**다.
  수치를 다시 재라
- **비율은 논리값이 아니라 "실제로 그려지는 높이" 로 재라.** stats 의 크기 값과 화면에 찍히는
  픽셀은 다르다(스프라이트 여백·스케일·리그 확대). 실측 사례: stats 기준으로는 맞는 줄 알았는데
  실제 렌더 높이로 재니 1/11.2 였다 (목표 1/16~1/24)
- **규칙은 결과 수치다. 도달 방법은 자유다** — 표의 비율만 만족하면 된다.
  다만 **캐릭터 축소보다 월드 확대를 우선하라**: 캐릭터를 줄이면 **소품·사거리·판정폭을 함께
  재조정**해야 하고 그게 "닿는데 안 맞는다" 의 발생 경로다. 월드만 키우면 **지도 배치 좌표만**
  바뀌어 그 경로가 아예 생기지 않는다 (실측: 10240² + 캐릭터 원본 유지로 1/19.4·5.88% 달성,
  전투 수치 한 줄도 안 건드림)
  - 월드 크기는 **줌 단계가 전부 표 안에 들어오는지**로도 결정된다. 너무 작으면 유효 줌 구간이
    좁아져 3단 줌의 폭이 안 나온다
- **★ 두 수치가 서로 당길 때 — 월드를 키워라.** 캐릭터 비율과 시야 % 는 같은 카메라를 두고
  반대로 움직인다. 줌아웃하면 캐릭터 비율은 맞지만 시야 % 가 상한을 넘고, 줌인하면 반대다.
  **둘 중 하나를 포기하지 말고 월드 크기를 늘려서 둘 다 맞춰라.**
  (실측: 6144² 에서 1/20 을 맞추면 시야가 15.8% 로 10% 상한 초과 → 8192² 로 확대가 정답.
  "맵이 짧다" 는 사용자 지적과도 같은 방향이다)
- **줌을 넣어라** — 최소 2단, 대형 맵은 3단. 기본 줌은 위 표의 중간값
- 캐릭터를 줄일 때 **상호작용 소품·사거리·판정폭을 함께 재조정**하라 (프리셋 1-b 참조)

**★ 줌 아웃 하한 — "충분히 축소되는가" 도 게이트다 (2026-08-24 신설)**

위 표는 **너무 붙어 있는 것**만 막는다. 반대쪽 실패가 실제로 나왔다 — 랜덤 카드 디펜스는
**웹에서 보더라도 전체 맵 구조가 파악이 안 될 정도**라는 지적을 받았다. 최대 축소로도
경로가 어디서 어디로 가는지 안 보이면, 전략을 세울 수가 없어 장르 자체가 성립하지 않는다.

- **최대 축소 단계에서 맵 전모(또는 구조를 파악할 수 있는 범위)가 한 화면에 들어와야 한다.**
  전모가 물리적으로 불가능한 크기라면 **미니맵이 그 역할을 대신**해야 한다 — 둘 중 하나는 필수다
- **전략·디펜스·유즈맵류는 「경로/회로 구조를 한눈에」가 기능 요건이다.** 적이 어디로 와서
  어디로 빠지는지, 내 방어선이 그 경로의 어디에 있는지가 **줌 조작 없이** 읽혀야 한다
- 판정 신호: 플레이 영상을 보고 **"맵이 어떻게 생겼는지 모르겠다"** 는 말이 나오면 실패다.
  G1 상단의 "맵이 좁다/캐릭터가 크다"와 **반대 방향의 같은 실패**이고, 둘 다 카메라 문제다
- 이 항목은 **모바일 이전에 웹에서 먼저** 걸린다 — 화면이 작아지면 더 나빠질 뿐이다

### G1-2. **화면 축척** — 벤치마크에서 가져오고, 하한과 **상한**을 모두 잰다 (2026-08-28 신설)

**반복 지적.** "캐릭터가 너무 크다 / 더 넓게 보여야 한다 / 해상도를 더 높여야 한다" 가 매 게임 나온다.
G1 은 "주인공이 화면 높이의 1/5 이상" 이라는 **하한만** 있어서, **벤치마크보다 크게 만든 것**을
잡아내지 못했다. 사용자가 말한 "해상도" 는 픽셀 수가 아니라 **이 축척**이다.

**세 수치로 말한다 — 전부 실측값이다**

| 이름 | 정의 | 어디에 쓰나 |
|---|---|---|
| **시야 폭** | 화면 **짧은 변**이 담는 월드 유닛 수 | 얼마나 넓게 보이는가 |
| **주인공 화면 비율** | 주인공 화면 높이 ÷ **짧은 변** 길이 → `1/N` 로 적는다 | 캐릭터가 얼마나 작은가 |
| **주인공 CSS px** | 실제 화면 픽셀 (390×844 세로 기준) | 모바일 하한 판정 |

**비율의 분모는 화면 높이가 아니라 짧은 변이다.** 높이로 재면 같은 게임이 세로에서 1/28,
가로에서 1/18 로 나와 어느 쪽이 기준인지 알 수 없다. 짧은 변으로 재면 두 방향이 같은 값이 되고,
그 값 하나로 판정할 수 있다.

**벤치마크 장르별 축척 — 여기서 고른다**

| 벤치마크 유형 | 주인공 화면 비율 | 성격 |
|---|---|---|
| **RTS · 유즈맵** (스타크래프트 계열) | **1/16 ~ 1/24** | 유닛이 작고 전장이 넓다. 무리·주둔지·진출이 보이는 축척 |
| 탑다운 액션 (하데스류) | 1/8 ~ 1/12 | 캐릭터가 주인공 |
| 종스크롤 슈팅 | 1/10 ~ 1/16 | 탄막이 보여야 한다 |
| 플랫포머 | 1/6 ~ 1/10 | |
| 벨트스크롤 · 대전 | 1/4 ~ 1/6 | 캐릭터가 화면을 채운다 |

RTS 대역의 근거는 실측이다 — 스타크래프트는 640×480 에서 마린 스프라이트가 약 25 px 이라
짧은 변(480) 대비 **1/19** 이고, 한 화면에 마린이 가로로 약 25명 들어간다.

- **벤치마크가 정해지면 그 줄의 비율을 목표로 박고, 완성 전에 실측한다.** 눈으로 "적당한 것 같다"
  는 판정이 아니다 — 카메라 수식에서 계산하거나 스크린샷에서 픽셀을 재라.
- **모바일 하한과 충돌하면**(G5-2 조작 대상 ≥28 CSS px) 축척을 포기하지 말고 **표식으로 푼다**:
  발밑 고리 + 머리 위 표식 + 자기 광원. 그리고 **잰 값과 완화 수단을 문서에 적는다.**
  RTS 축척은 구조적으로 이 충돌이 일어난다 — 1/18 이면 세로 화면(짧은 변 390px)에서 21 CSS px 다.
- **줌 3단을 준다** (가깝게 / 보통 / 넓게). 기본값은 벤치마크 비율에 맞춘 칸이다.
  이건 도피가 아니라 표준이다 — `infinity-tower` 가 이미 줌 3단을 쓴다.
- 시야 폭은 **짧은 변** 기준이다. 긴 변으로 재면 세로 화면에서 절반만 보인다.

**기준을 파일에 박고, 이후에는 드리프트로 판정한다.**
매번 새로 재기만 하면 "이번 값이 맞나" 를 매번 눈으로 판단하게 되고, 조금씩 밀린 것은 아무도 못 잡는다.
벤치마크에서 뽑은 세 수치를 **게임의 프리셋에 기준값으로 적어 두고**, 이후 갱신은 그 기준 대비
**±8% 를 넘으면 반려**한다. 넘겼다면 고치거나, 왜 벗어나야 하는지를 프리셋에 함께 고쳐 적는다.

| | 기준(벤치마크에서 확정) | 판정 |
|---|---|---|
| 시야 폭 | 예: 25 월드 유닛 | 드리프트 ±8% |
| 주인공 화면 비율 | 예: 1/18.2 | 드리프트 ±8% |
| 주인공 CSS px | 예: 21 px | 하한(G5-2)과 함께 본다 |

출처: `0x0funky/agent-sprite-forge` (MIT) 의 QC 게이트가 프레임마다 재는 대신 **합격한 기준
프로파일 대비 드리프트**로 막는 방식. 그쪽 지표(`body_scale_cv` 등)는 생성형 이미지가 프레임마다
줌이 튀는 실패를 막는 것이라 우리와 무관하고, **가져온 것은 "기준을 고정하고 드리프트로 잰다"는
형태**뿐이다.

### G1-3. **벤치마크 일치도 심사** — 배포 갱신마다 깨끗한 서브에이전트가 본다 (2026-08-28 신설)

**반복 지적.** 벤치마크작을 주고 시작해도 회차를 거듭할수록 원작에 있던 요소가 조용히 빠진다.
만든 사람은 자기가 넣은 것만 기억하므로 **빠진 것을 스스로 찾지 못한다** — 없는 것은 안 보인다.

**규칙**: 사용자 요청을 다 처리하고 **배포(빌드 산출물 갱신)를 할 때마다**, 서브에이전트를 띄워
**현재 게임 구성과 벤치마크작의 일치도**를 심사시킨다. 결과는 사용자 보고에 그대로 싣는다.

- **깨끗한 컨텍스트여야 한다.** `subagent_type: "fork"` 를 쓰지 않는다 — 만든 과정을 아는 에이전트는
  "구현했다고 말한 것"을 "있는 것"으로 읽는다. 새 에이전트에게 **소스와 벤치마크 자료만** 주고 판정시킨다.
- **심사 대상은 코드다.** 계획 문서·ADR·이 대화의 주장이 아니라 `Assets/Scripts/**` 의 실제 값과
  분기를 읽고 판정하게 한다. "문서에 있으니 있다" 는 이 게이트가 막으려는 바로 그 실패다.
- **출력 형식**: ① 벤치마크 요소 표(요소 · 원작 동작 · 우리 구현 · 판정 있음/부분/없음 · 근거 파일:라인)
  ② **없음·부분 항목만 모은 누락 목록**, 영향이 큰 순 ③ 원작에 없는데 우리가 넣은 것(과잉)
- **판정을 숨기지 않는다.** 누락이 나오면 보고에 그대로 적고, 고칠지 말지는 사용자가 정한다.

### G7. **프레임 예산과 발열** — 폰은 화질보다 온도가 먼저 온다 (2026-08-28 신설)

**실제 사고.** `archer-outbreak` 이 폰에서 발열 신고를 받았다. "그래픽이 화려하지도 몹이 많지도
않은데" 심했다 — 원인은 보이는 것의 양이 아니라 **매 프레임 쉬지 않고 도는 일의 양**이었고,
셋이 서로 곱해지고 있었다: 픽셀 수(DPR 2) × 전체화면 포스트 패스(6) × MSAA 샘플(4).

**기기로 가른다.** 데스크톱 값을 폰에 그대로 쓰면 몇 분 만에 손이 뜨거워진다.
분기는 `KgdDevice.IsCoarsePointer` 하나면 된다.

| 항목 | 데스크톱 | 폰 상한 | 왜 |
|---|---|---|---|
| 목표 프레임 | 60 | **45** | 60 은 GPU 가 쉬는 구간을 없앤다. 자동 조준·저속 게임은 45 로 조작이 상하지 않는다 |
| **메뉴·일시정지 프레임** | **20** | **20** | 세상이 멈춘 화면을 같은 속도로 다시 그리는 것이 발열 신고에서 가장 흔한 모양이다 |
| 그림자 거리 | 시야를 덮는 최소값 | 같음 | 화면 밖까지 그림자 맵을 그리지 마라. **카메라~주인공 거리보다 짧으면 발밑 그림자가 잘린다** — 그 사이 값을 쓴다 |
| 그림자 해상도 / cascade | Medium / 1 | Low / 1 | |
| MSAA | 2 | **0** | 폰에서 프레임버퍼 대역폭이 배로 든다. 화질 손해가 눈에 보이는 유일한 항목이라 마지막에 깎는다 |
| 전체화면 포스트 패스 | ≤6 | **≤4**, 버퍼 1/4 해상도 | 화면을 매 프레임 몇 번 다시 칠하는가가 곧 GPU 점유다 |
| 실시간 광원(pixelLightCount) | 4 | **2** | 광원이 겹치면 픽셀당 조명 패스가 곱해진다 |
| DPR 상한 | 2 | **2 이하**(1.5 검토) | 픽셀 수는 위 항목 **전체에 곱해진다** — 단일 항목 중 효과가 가장 크다 |
| 스킨드 메시 `updateWhenOffscreen` | 주역만 true | 주역만 true | 무리에 켜면 스킨을 다시 풀어 AABB 를 뽑는 일이 개체 수만큼 든다. 무리는 **생성 시 실제 자세를 한 번 재서 굳힌다** (눈대중 값을 박으면 개체가 통째로 안 그려진다) |

- **완성 판정에 넣는다** — 폰에서 30분 플레이 후 발열·배터리 소모를 확인하고 보고에 적는다.
- **헤드리스로는 못 잰다.** 소프트웨어 렌더링이라 GPU 비용이 재현되지 않는다 — 실기 확인만 유효하다.
- 깎는 순서는 **온도에 기여한 순서**지 화질이 덜 아까운 순서가 아니다. 프레임 상한 → 메뉴 스로틀
  → 그림자 범위 → 포스트 패스 → MSAA → DPR 순으로 손대고, 각 단계에서 **게임성이 어떻게 바뀌는지**
  한 줄로 적어 사용자가 고를 수 있게 한다.

### G2. 한국어 명명 — 직역투 금지

**반복 지적**: `봉화` `결속` `환류` `병기회수` 처럼 **영문 개념을 한자어로 직역한 말**이 계속 나온다.
뜻은 맞아도 **처음 본 사람이 기능을 못 짐작하면 실패**다.

**판단 기준 하나**: *이 단어를 처음 본 플레이어가 그 기능을 짐작할 수 있는가?*

| 금지 | 대신 |
|---|---|
| 영문 개념의 한자어 직역 (`환류` ← recycle, `결속` ← bond, `병기회수` ← salvage) | **일상어** (`되팔기` `연결` `재활용`) |
| 문어체·옛말 (`잿불` `황천길` `통금`) | 지금 쓰는 말 |
| 억지 음차 (`어비스 크라운` `기어 배스천`) | **영문 그대로** 쓰거나 한국어 일상어로 |
| `~소` `~장` `~단` `~전` 접미사 남발 | 짧고 입에 붙는 2~5음절 |

- 서구권 세계관이면 **영문 그대로**가 낫다. 음차하지 마라
- 한국어는 **진짜 한국 소재이거나 일상어일 때만**
- **★ 기능 라벨과 세계관 고유명사를 구분하라 — 강도가 다르다**
  - **기능 라벨(강제)**: 자원명 · 버튼 · 상태 표시 · 시스템 용어. **플레이에 필요한 정보**이므로
    처음 본 사람이 바로 읽혀야 한다. `툴팁으로 설명해야 이해되면 이름이 틀린 것이다`
  - **세계관 고유명사(권고)**: 몬스터·지명·인명. 톤을 위해 예스러운 말을 써도 된다.
    다만 **기능을 가리키는 순간**(예: 자원 이름을 겸하는 고유명사) 강제 규칙으로 넘어간다
  - 판별법: *이 단어를 몰라도 게임을 진행할 수 있는가?* 못 하면 기능 라벨이다
- **★ 노출 빈도와 명확도를 뒤바꾸지 마라.** 가장 많이 보이는 자리(배지·HUD·이름표)에는
  **가장 명확한 표현**을 두고, 긴 설명은 패널로 내려라. 반대로 하면 — 짧은 약어를 상시 노출하고
  뜻이 확실한 말을 패널 안에만 두면 — **처음 온 사람은 그 패널을 열어볼 이유가 없어서**
  핵심 개념이 영영 전달되지 않는다.
  실측: `자동 조종`(패널) + `자동`(배지) 조합에서 배지만 본 사람은 "자동 공격 토글" 로 읽었다.
  배지를 **`AI`**, 패널을 **`AI 가 조종 중`**(문장이라 해석이 필요 없다)으로 바꿔 해결
- **개명 후에는 "처음 본 사람이 그 기능으로 읽는가" 를 자가 검증하라.** 1차 개명이 기준에
  미달인 경우가 실제로 있었다
- 위 금지 목록은 **게임 제목·기능 라벨**에 하드하게 적용된다 (제목 정책은 V40/V42 재작명 참조)

### G3. 화면 흔들림 — 눈이 아프면 실패

**반복 지적**: 보스 처치 등에서 흔들림이 과해 눈이 아프다.

| 상황 | 진폭 (화면 높이 대비) | 지속 |
|---|---|---|
| 일반 타격 | **≤ 0.6%** | ≤ 180ms |
| 대형 이벤트 (보스 처치·필살) | **≤ 1.5%** | ≤ 500ms |

- **연속 이벤트에서 가산하지 마라** — 겹치면 합이 아니라 **최댓값으로 대체**하고 감쇠시켜라.
  가산이 "눈이 아픈" 흔들림의 실제 원인이다
- 설정에 **「화면 흔들림 줄이기 / 끄기」** 를 둬라 (접근성)
- 흔들림으로 타격감을 만들려 하지 마라 — 히트스톱·이펙트·사운드가 먼저다

### G4. 2D / 어중간한 3D 금지

**반복 지적**: "3D 같은데 어중간해서 별로다. 차라리 2D 가 낫다."

- 리그·부품 조립 방식은 **부품이 따로 노는 순간 2D 도 3D 도 아닌 룩**이 된다.
  관절 겹침·외곽선 연속성·경계 그림자로 **하나의 실루엣**으로 읽히게 하라
- **원근 과장을 억제**하라. 깊이 표현이 필요해도 룩은 명확한 2D 를 목표로
- 애매하면 **2D 로 확실히 가라.** 어중간한 입체감보다 잘 그린 2D 가 낫다
- 상호작용 순간(탑승·잡기·줍기)이 가장 자주 깨진다 — 전수 점검

### G5. 모바일이 1순위 타겟이다 (2026-08-24 전면 개편)

**반복 지적 — 5회 이상.** "모바일에서 캐릭터가 크고 맵이 확대돼 게임을 못 즐길 정도"가
50여 종에서 **한결같이** 나온다. 원인은 게임마다의 실수가 아니라 **이 표준의 구조**였다:
완성의 정의(품질 게이트·검증 프로토콜)가 100% 데스크톱이었고 모바일은 "완성 선언 뒤"
통합 절차에만 있었다. 그래서 클린룸 세션은 **구조적으로** 모바일을 못 보고 끝냈다.

> **웹이 아니라 모바일이 기준선이다.** 데스크톱에서 좋고 모바일에서 나쁘면 그 게임은
> 실패다. 반대는 허용된다. 판정 순서도 모바일이 먼저다.

#### G5-1. 두 방향을 다 검수한다 (세로 + 가로)

| 방향 | 뷰포트 | 언제 필수인가 |
|---|---|---|
| 세로 | **390 × 844** | 전부. 사용자가 링크를 눌러 처음 닿는 화면이다 |
| 가로(전체화면) | **844 × 390** | 전부. 몰입 버튼(`⛶ 크게`)이 모든 게임에 붙어 있다 |

CDP 레시피 — 데스크톱 검증과 **같은 세션에서 이어서** 한다:
```js
await send('Emulation.setDeviceMetricsOverride',
  { width: 390, height: 844, deviceScaleFactor: 3, mobile: true });
await send('Emulation.setTouchEmulationEnabled', { enabled: true, maxTouchPoints: 5 });
await send('Emulation.setEmitTouchEventsForMouse', { enabled: true, configuration: 'mobile' });
// 가로는 width/height 를 바꿔 같은 절차를 반복한다
```
- **`pointer: coarse` 가 잡혀야 한다** — `matchMedia('(pointer: coarse)').matches` 로 확인.
  이게 false 면 공용 가상패드(`lib/touch.js`)가 아예 안 켜져 "패드가 없다"로 오진한다
- 스크린샷은 **두 방향 각각** 남긴다. 한 방향만 찍고 통과시키면 회전 시 레이아웃이 무너지는
  결함이 그대로 배포된다

#### G5-2. 기기 공간(CSS px)으로 다시 재라 — G1 비율 통과와 별개다

**G1 의 비율은 기기 무관이다.** 그런데 16:9 가로 캔버스(2560×1440)를 390px 폭 세로 화면에
레터박스하면 **390 × 219 CSS px** 가 된다. G1 을 통과한 1/19 캐릭터가 실제로는 **11 CSS px**,
즉 손톱만 하다. 이것이 "모바일에서 못 즐긴다"의 정확한 산수다.

| 항목 | 하한 (390×844 세로 기준) |
|---|---|
| 터치 타깃(버튼·카드·타일) | **≥ 44 CSS px** (한 변) |
| 조작 대상(주인공·내가 움직이는 말) | **≥ 28 CSS px** 높이 |
| 읽어야 하는 숫자·라벨 | **≥ 11 CSS px** |
| 구분해야 하는 적·아이템 | **≥ 16 CSS px** |

- **재는 방법**: `el.getBoundingClientRect()` 또는 캔버스면
  `rect.width / canvas.width × 게임좌표크기`. **논리 좌표로 재지 마라** — 레터박스 배율이
  빠지면 전부 통과처럼 보인다 (G1 의 "그려지는 픽셀로 재라"와 같은 함정, 한 단계 더 아래)
- **16:9 이상 가로 캔버스를 세로 화면에 그대로 두면 자동 실패다.** 셋 중 하나를 골라라:
  ① 세로 전용 캔버스로 설계(1080×1440 계열 — 프리셋 대부분이 이미 이쪽)
  ② 세로용 레이아웃을 따로 제공(카메라 줌·HUD 재배치)
  ③ **가로 전용으로 선언**하고 진입 시 자동 가로 전환 (`orientation=LANDSCAPE` 시드 + 아래 G5-5)

#### G5-3. 조작 방식은 둘 중 하나를 **골라서** 정당화한다

| 게임 성격 | 조작 | 근거 |
|---|---|---|
| 탭·드래그·그리기·퍼즐·배치 (카드/타워/보드/드로잉) | **네이티브 터치. 가상패드 금지** | 패드가 판을 가린다. 실측 판례 7종(`sum-trail` `hoop-order` `pixel-logic` `bee-guard` `random-card-defense` `random-tower-defense` `marble-race`) |
| 캐릭터를 직접 움직임 (액션·플랫포머·슈팅) | **가상패드** (`lib/touch.js`) | 방향 입력이 연속값이라 탭으로 대체 불가 |

- **"둘 다 안 한다"는 선택지가 아니다.** 어느 쪽인지와 그 근거를 게임의 `DESIGN.md` 와
  `game/CLAUDE.md` 행에 **한 줄로** 남긴다 (지금까지 이 결정이 암묵이라 매번 다시 논쟁했다)
- 네이티브 터치를 고르면 **모든 조작이 탭/드래그로 실제 도달 가능**한지 전수 확인한다.
  키보드 전용 동작이 하나라도 남으면 그건 미완성이다
- 패드를 고르면 **액션 5개 이하**, 라벨은 **한글 1~3자**(`code:아이콘:라벨` 3-part 형식).
  아이콘만 있으면 무슨 버튼인지 아무도 모른다

#### G5-4. 정보 패널 — 모바일에서 게임을 가리면 실패

웹에서 유용한 큰 정보 패널이 폰에서는 **게임 요소를 덮어 플레이 자체를 막는다.**

- **접기/펼치기 필수. 모바일 기본값은 접힘.** 접힌 상태에서도 지금 판단에 꼭 필요한 값
  (자원·체력·웨이브)은 한 줄로 보여야 한다
- **캔버스에 그린 HUD 도 같은 기준이다.** DOM 패널만 규칙을 지키고 캔버스 HUD 는 방치하는 일이
  실제로 벌어졌다(인피니티 타워·랜덤 카드/타워 디펜스는 UI 가 전부 캔버스 안이라 모바일 처리가 0이었다)
- **가려지는 면적 상한: 세로에서 게임 화면의 25%.** 넘으면 접거나 다른 자리로 옮긴다
- 분기는 **`v.w > v.h` + `pointer: coarse`** 로 한다. **기기 이름·폭 구간으로 분기하지 마라**
  (`docs/conventions/game-input-standard.md` §모바일 화면 배치와 같은 규칙 — 두 문서가 어긋나면 안 된다)
- 협동 게임에서 **다른 플레이어의 화면을 크게 보여줄 필요는 없다** — 미니맵 표식과 상태 요약이면 충분하다

#### G5-5. 가상패드 규격 — 세로는 비율로 고정한다

게임마다 패드 위치·크기가 제각각이라 "어디 있는지 매번 찾는다"는 지적이 나왔다.
**세로모드에서는 뷰포트 기준 비율로 고정한다** (가로는 캔버스를 덮으므로 별도).

| 요소 | 규격 (세로 — 뷰포트·밴드 기준) | 390×844 에서 |
|---|---|---|
| 패드 밴드 높이 | 뷰포트 높이 × **0.28** (하한 `기준지름+28px`, 상한 300px) | 236px |
| 조이스틱 반경 | 밴드 높이 × **0.271** (하한 46, 상한 84) | 64px |
| 노브 반경 | 베이스 반경 × **0.453** | 29px |
| 조이스틱 중심 | 좌: `safe.l + 뷰포트폭 × 0.051 + 반경` · 상: `밴드상단 + 밴드높이 × 0.653` | (84, 762) |
| 주 액션 지름 | 밴드 높이 × **0.322** (하한 58, 상한 96) | 76px |
| 액션 2·3 / 보조 1·2 | 주 지름 × **0.82** / **0.71** | 62 / 54px |
| 슬롯 간격 | 주 지름 × 1.13 · 1.18 · 0.92 · 1.74 | 86 · 90 · 70 · 132px |
| 우측·하단 여백 | `safe + 뷰포트폭 × 0.036` · `safe + 뷰포트높이 × 0.021` | 14 · 18px |

> 계수는 **390×844 실측에서 역산**했다 — 기준 기기에서는 기존 배치가 그대로 재현되고,
> 더 크거나 작은 화면에서만 따라 움직인다. 실측: 360×640 → 반경 49·버튼 58,
> 430×932 → 71·84, 폴드 접음 344×882 → 67·80. **전부 터치 타깃 하한 44 CSS px 이상.**

수치의 집은 `docs/conventions/game-input-standard.md` 이고 구현은 `lib/touch.js` 다 —
**세 곳이 어긋나면 안 된다.**

- **가로 전용 게임은 진입 시 자동 가로 전환**한다. 카탈로그의 `orientation` 필드
  (`LANDSCAPE|PORTRAIT|BOTH`)를 **반드시 시드에 채운다** — 지금은 이 필드가 채워지고도
  아무도 안 읽는 죽은 필드다. 자동 전환의 FE 구현은 후속 큐(맨 아래 절)
- 패드가 필요 없는 게임은 이 절 전체가 해당 없음이다 — 빈 밴드를 만들지 마라

#### G5-6. **화면 가장자리는 게임 것이 아니다** (2026-08-29 신설 — 실제 사고 2건)

게임은 iframe 안에서 돌고, **바깥에 두 겹의 남의 UI 가 있다.** 그 자리에 게임이 버튼을 두면
눌리지 않거나, 브라우저가 먼저 가져간다. 둘 다 "게임이 고장 났다"로 보인다.

| 자리 | 누구 것 | 게임이 지킬 것 |
|---|---|---|
| **우상단** `right 0~96` × `top 0~(safe.t+46)` | 플랫폼 셸 — 닫기 ✕ · 전체화면 ⛶ (`portal-fe` `.game-stage-bar`) | 여기에 **누를 수 있는 것을 두지 않는다** |
| **하단 가장자리** 아래 24px | 브라우저 — 주소창 되살리기(안드로이드) · 탭 바 끌어올리기(iOS) | 조작부를 이 위로 올린다 |
| 좌상단 | `lib/hud.js` 의 「정보 보기/접기」 칩 | 겹치면 `data-pos` 로 칩을 옮긴다 |
| 우하단 | `lib/platform.js` 랭킹 🏆 · `lib/touch.js` 액션 버튼 | 그대로 둔다 |

- **우상단**: 셸 칩은 iframe **바깥** 문서라 항상 위에 뜬다. z-index 로 이길 수 없다.
  실제 사고 — 궁수 키우기의 강화창 「닫기」가 정확히 그 자리에 있어 **한 번도 눌리지 않았다**.
  치수는 `lib/touch.js` 가 CSS 변수와 전역으로 내보낸다:
  ```css
  .my-close-btn { top: calc(var(--kgd-chrome-top, 46px) + 8px); right: 10px; }
  ```
  ```js
  var top = (window.GameChrome && GameChrome.top) || 46;   // 캔버스 HUD
  ```
  Unity 게임은 `Kgd.KgdDevice.ChromeTopCss` 를 읽는다.
- **하단 가장자리**: 페이지가 이 제스처를 막을 방법은 **없다.** 유일하게 확실한 해법은
  전체화면(셸의 ⛶)이고, 그 밖에서는 손가락이 그 띠에 닿지 않게 하는 것이 최선이다.
  `lib/touch.js` 가 세로에서 조작부 전체를 24px 올려 둔다(`EDGE_GUARD`) — 게임이 자기 조작부를
  직접 그린다면 같은 값을 지킨다. 가로는 브라우저 크롬이 좌우로 비켜서 해당 없음.
- **새 게임은 이 표를 지키고 나온다.** 기존 게임을 고칠 때도 같이 본다.

### G6. 벤치마크의 **규모**를 지킨다 (2026-08-28 신설 — 반복 지적)

**반복 지적.** "벤치마크로 준 게임의 맵 범위·해상도·플레이타임을 꼭 지키라고 했는데 매번 누락된다."
구조적 원인이 있었다: 아래 품질 게이트의 "벤치마크는 하한선" 이 **그래픽·애니메이션·해상도·
이펙트·조작감·연출 6축뿐**이라, 맵 범위와 플레이타임은 애초에 판정 대상이 아니었다.
콘텐츠 깊이(C)도 "지역 3개 이상" 같은 **절대 하한**이지 벤치마크 대비가 아니다.

> **품질만 맞추고 규모를 줄이면 "장르가 같은 다른 게임"이 된다.** 사용자는 그것을 미완성으로 본다.

**규모 4축 — 벤치마크작의 수치를 조사해 슬롯으로 싣고, 완성 판정에 넣는다**

| 축 | 무엇을 적나 | 미달이면 |
|---|---|---|
| **맵 범위** | 월드 크기(월드 유닛) · 구역/스테이지 수 · 한 화면이 보는 비율 | 개선 반복 |
| **해상도** | 논리 캔버스 크기 · 한 화면에 담기는 월드 범위 | 개선 반복 |
| **플레이타임** | **1회차 클리어까지 걸리는 시간** | 개선 반복 |
| **진행 깊이** | 강화 단계 수 · 해금 수 · 적/보스 종류 · 콘텐츠 양 | 개선 반복 |

- 벤치마크가 정해지면 **먼저 이 넷을 조사해 수치로 적는다.** 모르면 사용자에게 묻는다.
  "그 장르 최고작 정도" 같은 말은 규모를 말해 주지 않는다.
- **플레이타임이 시간 단위면 이어하기(런 저장·복원)가 자동으로 필수**가 된다. 한 세션에 못 끝내는
  길이를 저장 없이 내면 아무도 끝을 못 본다 — 그 순간 플레이타임 수치가 거짓이 된다.
- **맵이 커지면 청크 스트리밍이 전제다.** 전부 한 번에 만들면 부팅에서 죽는다
  (`deadline` 의 "구역이 곧 청크" 가 이 레포의 선례).
- 규모를 줄여야 할 이유가 생기면 **줄이기 전에 사용자에게 알린다.** 조용히 줄이면
  다 만든 뒤에 반려된다 — 그때는 지형·진행·저장을 전부 다시 짜야 한다.

**실측 사례**: 「궁수 키우기」(벤치마크 = 마린 키우기 계열 유즈맵) 1차본은 맵 88×88 · 구역 5 ·
플레이타임 20분 · 이어하기 없음으로 나와 반려. 원작은 **여러 시간짜리**이고 그래서 원작에도
중간 저장에 해당하는 장치가 있다. 2차에서 맵 300×300 · 구역 18 · 이어하기로 다시 만들었다.

## 기술 도입 게이트 (WASM · WebGL · Worker 등)

**원칙: 측정 없이 도입하지 않는다.** 새 런타임 기술은 "빠를 것 같아서" 가 아니라
**병목을 수치로 특정한 뒤** 그 병목에 맞는 것만 넣는다.

> **왜 이 게이트가 필요한가** (2026-08-18 실측)
> "좀비 생존물에 WASM 을 넣을까" 를 검토하며 실제 코드·수치를 열어보니:
> `ashen-warband` 는 프레임 코스트가 **0.4~1.2ms / 예산 16.7ms**(3~7%)로 CPU 여유가 93% 였고,
> `rustline-hold` 는 경로 탐색이 **이미 플로우 필드**(개체별 A* 가 아님)라 WASM 이 노릴 루프가
> 없었으며, 자기 문서가 정의한 최악 조건이 **"밤 = 조명 합성 + 날씨 + 비네트"**, 즉 전체 화면
> 채우기 비용이었다. fps 가 좀비 수와 **역상관**으로 나온 이상한 측정도 이걸로 설명된다.
> **도입했다면 병목이 아닌 곳을 최적화하면서 빌드 스텝만 얻었을 것이다.**

### 0. 깨지면 안 되는 전제
**빌드 스텝 없음**이 이 생산 체제의 근간이다 — 게임이 폴더째 드롭인으로 배포되고, 클린룸
세션이 툴체인 없이 만들어낸다. 이걸 깨는 결정은 **게임 하나가 아니라 생산 라인 전체**에
비용을 지운다. 예외를 만들려면 아래 게이트를 통과해야 한다.

### 1. 측정 프로토콜 (게이트 진입 조건)
- **`sim`(그리기 제외) / `draw` / `composite`(전체 화면 패스) 를 분리해서 재라.**
  합산 프레임 코스트 하나로는 어떤 기술이 맞는지 고를 수 없다
- **목표 규모에서 재라.** 도달해본 적 없는 규모(예: "좀비 100기") 를 근거로 판단하지 않는다.
  최대 실측치를 명시하고, 목표에 못 미쳤으면 **먼저 그 규모를 만들어라**
- 지표가 **직관과 어긋나면**(개체 수와 fps 가 역상관 등) 측정이 오염된 것이다.
  결론을 내지 말고 측정을 고쳐라

### 2. 사다리 — 싼 것부터. 아랫단을 건너뛰고 윗단으로 가지 않는다
| 단 | 조치 | 비용 |
|---|---|---|
| 1 | **확인된 낭비 제거** — 프레임당 할당(그라디언트·배열·객체), 매 프레임 재계산 | 0 |
| 2 | **자료구조** — 오브젝트 풀, 공간 해시, 필드 1회 계산 후 샘플링(플로우 필드) | 0 |
| 3 | **렌더 비용** — 조명 버퍼 저해상도 + 업스케일, 전체 화면 패스 병합, 오프스크린 캐시 | 0 |
| 4 | **OffscreenCanvas + Worker** — 시뮬레이션을 메인 스레드에서 분리 | **빌드 스텝 0** |
| 5 | **WebGL** — 드로우콜 배칭 | 중 (빌드 스텝 없이 가능) |
| 6 | **WASM** — 덩어리 연산만 | 큼 (**빌드 스텝 도입**) |

### 3. 수치 게이트
- **WebGL 로 간다**: `draw + composite ≥ 8ms`(예산의 절반) **그리고** 1~3 단을 마쳤고
  **그리고** 드로우콜 수 또는 fill rate 가 병목임을 확인했을 때
- **WASM 으로 간다**: `sim ≥ 8ms` **그리고** 1~4 단을 마쳤고 **그리고** 대상이
  **JS↔WASM 경계를 자주 넘지 않는 덩어리 연산**일 때.
  경계를 자주 넘는 작업(개체마다 Canvas 를 그리는 류)은 **오히려 느려진다**
- **게임 전체를 옮기지 않는다. 그 덩어리 하나만 옮긴다**

### 4. WASM 이 값을 하는 작업 / 하지 않는 작업
| 값을 한다 | 하지 않는다 |
|---|---|
| 구조물 파괴 전파·구조 안정성 계산 | Canvas 2D 그리기 (네이티브가 한다) |
| 유체·화재 확산 시뮬 | 조명 합성·전체 화면 채우기 |
| 대규모 물리·충돌 해석 | 이미 플로우 필드로 amortize 된 경로 탐색 |
| 월드/절차 생성 (큰 배열 한 번에) | 개체마다 JS 를 호출해야 하는 로직 |

### 5. 금지
- **코드 보호를 이유로 한 단독 도입.** `wasm2wat`·디컴파일러가 있어 난독화가 **한 단계**
  올라갈 뿐이다. sitelock · frame-ancestors · minify · private 레포 위에 얹기엔 비용이 크다
- **체감으로 이어지지 않는 최적화.** 예산의 7% 를 쓰는 게임을 3% 로 만드는 일은 하지 않는다

### 6. 도구 선택 (도입이 확정된 경우)
**AssemblyScript 우선** — TS 문법이라 클린룸 세션이 그대로 다룰 수 있고, 툴체인이 npm 패키지
하나에 산출물도 `.wasm` 하나라 드롭인 배포에 가장 가깝다. Rust/Emscripten 은 산출물과 CI 가
무거워지므로, AssemblyScript 로 표현이 안 되는 경우에만 고려한다.

### 7. 기록 의무
도입했다면 **전/후 수치(sim·draw·composite 분리)** 를 그 게임의 `DESIGN.md` 에 남긴다.
개선이 없었으면 **되돌린다** — 남겨두면 다음 사람이 근거 없이 따라 한다.

### 8. 엔진 선택 — 유니티는 언제 쓰는가 (2026-08-24 신설)

> **제작 절차는 별도 문서다 — `docs/standards/unity-game-pipeline.md`.**
> 배치·플랫폼 통합(.jslib)·용량 예산·파일럿 절차가 거기 있다. 이 절은 **판정 게이트**만 다룬다.

위 사다리는 **캔버스 게임의 최적화** 이야기다. 이건 **애초에 무엇으로 만들 것인가** 의 문제라
층이 다르다. 판단은 장르로 먼저 갈린다.

| 장르 | 기본 선택 | 근거 |
|---|---|---|

```

프로젝트로, 아래 요구만을 근거로 게임을 완성하라. 디자인 판단은 질문하지 말고 스스로

묻지 말고 끝까지 완성하라."⟩

## 과제

## ★ 벤치마크의 규모 — 품질과 **따로** 판정한다 (전역 가드레일 G6)
⟨맵 범위 — 월드 크기 · 구역/스테이지 수. 예: "월드 300×300, 구역 18곳 6티어"⟩
⟨화면 축척 — **세 수치로**(전역 가드레일 G1-2): 시야 폭(화면 짧은 변이 담는 월드 유닛) ·
 주인공 화면 비율 1/N · 주인공 CSS px. 예: "시야 폭 25, 주인공 1/28, 21 CSS px(표식으로 완화)".
 벤치마크가 RTS·유즈맵이면 **1/22~1/30** 이다 — 이보다 크게 만들면 반려된다⟩
⟨플레이타임 — **1회차 클리어까지**. 예: "10시간 이상"⟩
⟨진행 깊이 — 강화 단계 수 · 해금 수 · 적/보스 종류. 예: "위력 강화 상한 없음, 구역 18, 보스 7"⟩
이 넷은 그래픽 6축과 **별개로** 완성 판정에 들어간다. 미달이면 "미완 명시"가 아니라 개선 반복이다.
**플레이타임이 시간 단위면 이어하기(런 저장·복원)를 반드시 넣는다.** 맵이 크면 청크 스트리밍이 전제다.
줄여야 할 이유가 생기면 **줄이기 전에 사용자에게 알린다.**
⟨타겟 방향 — 디폴트: "세로(1080×1440 계열). 가로가 꼭 필요한 장르면 가로 전용으로 선언하고 그 근거를 적어라."⟩
테마·세계관·이름은 자유롭게 창작하되 slug 는 ⟨slug — 영문 kebab-case, 미정이면 "직접 정하고 보고"⟩ 를 쓴다.

## ★★ 모바일이 1순위 타겟이다 — 이 프로젝트에서 가장 자주 실패한 축
데스크톱에서 좋고 **모바일에서 나쁘면 그 게임은 실패**다. 반대는 허용된다.
- **완성 선언 전에** CDP 디바이스 에뮬레이션으로 **세로 390×844 와 가로 844×390 을 둘 다** 실측하라
  (`Emulation.setDeviceMetricsOverride` + `setTouchEmulationEnabled` — `pointer: coarse` 가 잡혀야 한다)
- **크기는 레터박스 배율을 포함한 CSS px 로 재라.** 논리 좌표로 재면 전부 통과처럼 보인다.
  하한: 터치 타깃 ≥44 · 조작 대상 ≥28 · 라벨 ≥11 · 구분 대상 ≥16 (390×844 기준)
- **16:9 가로 캔버스를 세로 화면에 그대로 두면 자동 실패**다. 세로 캔버스로 설계하거나,
  세로 전용 레이아웃을 주거나, 가로 전용으로 선언하라
- **조작 방식을 골라서 근거를 적어라**: 탭·드래그·그리기·퍼즐·배치 → **네이티브 터치**
  (가상패드 금지 — 판을 가린다) / 캐릭터를 직접 움직임 → **가상패드 전제**로 설계(액션 5개 이하)
- **정보 패널은 접기/펼치기**를 갖고 모바일 기본값은 접힘. 캔버스에 그린 HUD 도 같은 기준.
  가리는 면적은 세로에서 게임 화면의 25% 이하
- **최대 축소에서 맵 전모(또는 구조)가 읽혀야 한다.** 안 되면 미니맵이 그 역할을 해야 한다 —
  "맵이 어떻게 생겼는지 모르겠다"는 웹에서도 실패다

## ★ 품질 게이트 — 이 과제의 핵심. 미달이면 "완성" 선언 금지
이 프로젝트에서 품질은 협상 대상이 아니다. 아래 게이트를 **전부** 넘어야 완성이다.
"동작한다" 와 "완성했다" 를 구분하라.

**⟨벤치마크⟩는 참고가 아니라 하한선이다.** 벤치마크작과 나란히 놓고 아래 축을 비교표로
만들어, 전 축 "동급 이상" 판정이 나와야 완성이다:
①그래픽(스프라이트 밀도·디테일) ②애니메이션(주인공 프레임 수·보간 부드러움)
③해상도·화면 활용 ④이펙트 밀도(피격/폭발/궤적) ⑤조작감(입력 반응·프레임 데이터)
⑥연출(보스 등장·화면 전환·스테이지 도입).
미달 축이 있으면 "미완 명시 후 종료"가 아니라 **개선을 반복**한다. 반복해도 물리적으로
불가능하다고 판단되면 그 시점에 멈추고 사용자에게 갭과 대안을 보고하라 — 미달 상태의
자체 완성 선언은 금지다.

### A. 아트 (가장 자주 미달하는 축 — 최우선 투자)
- **오리지널 디자인 의무 (IP 세이프)**: 벤치마크는 품질·연출의 기준일 뿐이다. 캐릭터·로고·
  고유 디자인을 원작과 유사하게 만들지 않는다 — 마스코트의 실루엣+컬러웨이 조합(예: 파란
  원형 헬멧+얼굴 노출 안드로이드 = 메가맨), 고유 명칭, 트레이드마크 요소 재현 금지.
  "누가 봐도 그 게임 캐릭터" 면 실패. 장르 문법(대시/차지샷 등 메커닉)은 자유
- 해상도: ⟨기본 "1440p급 캔버스 또는 그에 준하는 픽셀 밀도"⟩. 저해상 캔버스를 늘려
  뭉개는 것 금지 (픽셀아트라면 정수 배율)
- **아트 디렉션 일관성**: 팔레트를 정하고 전 요소(캐릭터/배경/VFX/UI)가 같은 문법을 쓴다.
  "에셋 짜깁기 느낌" 이 나면 미달
- **게이트가 막으면 다시 만든다 — 임계값을 낮춰 통과시키지 않는다.**
  기준에 걸렸다는 것은 산출물이 기준에서 벗어났다는 뜻이지 기준이 틀렸다는 뜻이 아니다.
  통과시키려고 상한을 올리거나 후처리로 덮으면, 그 뒤로는 그 축을 아무도 못 잰다.
  기준을 바꿔야 한다고 판단했다면 **그 판단을 따로 적고 승인을 받은 뒤** 바꾼다 —
  통과시키는 김에 슬쩍 올리는 것과는 다르다. (출처: `agent-sprite-forge` 의
  "A failed gate is a regeneration signal", 우리 `no-fallback-workarounds` 규율과 같은 결)
- 개체 렌더 최저선: 3톤 이상 명암 + 외곽선/림라이트 + 접지(그림자). 단색 도형은 개체가 아니다
- 배경은 **레이어 3장 이상** (하늘/원경/근경 급) + 깊이 연출(파랄랙스·비네트·광원 중 2개 이상)
- 애니메이션: 주인공 기준 대기/이동/공격/피격 최소 4클립, 클립당 프레임이 "끊겨 보이지 않을 것"
- 캐릭터 존재감: 주인공이 화면 높이의 1/5 이상이거나, 그 이하라면 실루엣·발광으로
  어떤 순간에도 즉시 식별될 것
- 에셋: 상용 무료(CC0/OFL 등) 리서치 권장 — **라이선스 원문 검증** 후 CREDITS.md 에
  출처·라이선스·검증 근거 기재. 부족분은 절차 생성(리그 베이크·벡터 등)으로

### B. 게임필 (타격감 불변식)
- 히트스톱 + 화면 흔들림 + 데미지 팝업 + KO/클리어 슬로모 — 전부, 예외 없이
- 플레이어 행동에 응답성 문법: 입력 버퍼, (장르에 맞게) 캔슬/무적 프레임/코요테 타임
- 적 공격에는 반드시 예고(텔레그래프) — 회피가 성립해야 난이도를 올릴 자격이 생긴다
- 60fps 유지 (자체 측정해 보고에 수치 기재)

### C. 콘텐츠 깊이
- 런/스테이지 단위 선택·성장 시스템 ⟨장르에 맞게: 빌드 20종+ / 커맨드 기술표 / 스킬트리 등⟩
- 지역(스테이지) 3개 이상 — 배경·지형·기믹이 **실제로** 달라야 한다 (색만 바꾼 재탕 금지)
- 보스: 지역마다 1기, 패턴 2개 이상 + 페이즈 전환
- 숨김 요소 3종 이상, 메타 진행(죽어도 남는 화폐/해금, localStorage)

### D. 사운드 · UI
- 효과음 + BGM (WebAudio 자체 신스 허용, 외부 오디오 파일 없이 가능). 무음 게임은 미완
- 큼직하고 읽기 좋은 **한국어 UI** — 대형 체력바, 카드/목록형 선택 UI, 폰트는 본문에서
  뭉개지지 않을 것 (한글 웹폰트 자체 번들 권장, 라이선스 검증 포함)

### E. 조작
- PC 키보드 우선. 마우스 조준 금지 — 바라보는 방향 + 조준 보정
- 양손 배치 지원: 방향키+ZXC 와 WASD+JKL 를 모두 받는다

- **클린룸 세션이 직접 잰다** — `lib/` 열람은 금지지만 **CDP 디바이스 에뮬레이션은 가능**하다.
  390×844(세로) · 844×390(가로) 두 방향에서 부팅·조작·패널·가독을 실측하고 수치를 보고에 적는다
- **네이티브 터치 게임은 클린룸에서 완결된다** (패드가 없으므로). 가상패드 게임은
  클린룸에서 **터치로 조작 가능한 형태**까지 만들고, 패드 배선·재실측은 통합 세션이 이어받는다
- 판정은 G5-2 의 CSS px 표와 G5-4 의 패널 규칙으로 한다 — "잘 보인다" 는 판정이 아니다

**아래는 공용 가상패드가 붙을 수 있게 하는 최소 계약이다 (어기면 배선 자체가 불가능해진다)**
- **모든 메뉴·선택·결과 화면은 DOM 버튼 탭으로도 조작 가능**해야 한다. "Z 를 눌러 시작"
  같은 키보드 전용 진입을 두지 마라 (키보드 조작을 겸하는 것은 좋다)
- **`.panel` 클래스는 화면 전체를 덮는 메뉴/결과 패널에만** 쓴다. 플레이 중 상시 HUD 에
  쓰면 (통합 후) 가상패드가 영영 숨는다 — HUD 카드에는 다른 클래스명을 써라
- **캔버스 스케일은 비율 유지(레터박스)만.** `width/height:100%` 스트레치 금지 —
  전체화면·가로모드에서 비율이 깨진다
- **액션 키는 5개 이하로 설계**하라 (주공격 / 점프·결정 / 대시·특수 / 보조 2) —
  가상패드 슬롯 상한이다. 순서 의미는 키보드 표준(C/X/Z/A/S)과 같다
- **캔버스 좌표 상호작용**(배치·조준·선택 등)이 있으면 **터치 탭/드래그로도 같은 일**이
  되게 만들어라. 마우스 hover 에만 의존하는 정보는 탭으로도 닿아야 한다
- **로컬 랭킹 입력 UI(이니셜 3자 등)를 만들지 마라** — 닉네임 기반 공통 랭킹 레이어가
  통합 단계에서 붙는다. 게임 자체 입력을 만들면 이중 입력이 된다 (aero-vendetta 실측)
- **텍스트 입력은 DOM input 으로** — 캔버스 가짜 입력창은 모바일 키보드·한글 조합이 깨진다

## 공용 레이어 호출 규약 (클린룸은 `lib/` 를 못 보므로 여기 적는다)
- 런 종료: `window.PlatformAdapter && PlatformAdapter.runEnd({ score, detail, board })`
  — `score` 는 정수, `detail` 은 **문자열**(객체를 넣으면 `[object Object]` 가 그대로 랭킹에 뜬다),
  `board` 는 모드를 나눈 게임만(없으면 생략). **자체 점수 이벤트를 새로 만들지 마라**
- 캔버스를 **flex/grid 아이템으로 두지 마라** — `body { display:block }` + `canvas { margin:0 auto }`.
  flex 로 두면 `fitCanvas` 와 서로 물려 캔버스가 계속 줄어든다 (2026-08-25 실측)
- 정보 패널: `GameHud.expanded()` 가 false 면 그리지 않는다
- 닉네임·순위표 UI 를 만들지 마라 — `lib/rank.js` 가 이미 한다

## 예외를 쓰는 법 (전 가드레일 공통)

가드레일에는 예외가 필요할 때가 있다 — 가로 전용 선언, G5-2 하한과 충돌할 때 표식으로
축척을 지키는 것 같은. 예외 자체는 문제가 아니고, **예외가 조용히 기본값이 되는 것**이 문제다.

1. **이름을 불러 선언한다.** 대화 흐름에서 슬쩍 넘어가지 않는다. 무슨 예외를 쓰는지 적는다.
2. **다른 게이트가 전부 녹색일 때만.** 예외는 한 축을 면제하는 것이지 검사를 건너뛰는 것이 아니다.
3. **그 건에만 적용한다 — 기본값으로 승격하지 않는다.**

그리고 **그 예외가 여전히 사 주지 않는 것을 함께 적는다.** 예: "RTS 축척이라 주인공이
21 CSS px 이다(G5-2 하한 미달). 표식으로 식별을 산다 — **다만 조작 대상 버튼 크기는
여전히 44 px 을 지킨다.**" 범위를 안 적으면 다음 사람이 예외를 넓게 읽는다.

**같은 방법으로 다시 시도해서 통과시키지 않는다.** 임계값을 낮추는 것과 될 때까지 다시
굴리는 것은 둘 다 회피다. 두 번 실패하면 접근을 바꿀 자리고, 무엇으로 바꿀 수 있는지는
프리셋과 함정 목록이 이름으로 적어 둔다.
