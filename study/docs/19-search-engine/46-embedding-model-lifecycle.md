# 46. 임베딩 모델의 생애주기 — 고르기 · 학습 · 서빙 · 교체

> §08·§41 이 **인덱스**를, §34·§45 가 **메트릭**을 다뤘다면 §46 은 그 사이에 있는 **모델 자체**를 다룬다 —
> 무엇을 고르고, 어떻게 학습시키고, 실시간 경로에 어떻게 얹고, 바뀔 때 무엇이 깨지는가.
> 학습 시간 예상: ~3h · 자가평가 입구 레벨: B+

---

## 1. 한 줄 핵심

> **임베딩 모델은 라이브러리가 아니라 데이터베이스 스키마에 가깝다** — 한 번 정하면 색인 전체가 그 벡터 공간에 묶이고,
> 바꾸는 순간 **전량 재임베딩**이다. 그래서 선정은 리더보드가 아니라 **자기 판정 세트**로 하고, 서빙은
> **문서 타워를 오프라인으로 밀어내고 질의 타워만 실시간에 남기는**(two-tower) 비대칭 구조로 하며,
> 교체는 **모델 스탬프로 두 벡터 공간을 격리한 blue-green** 으로 한다.

---

## 2. 왜 §08·§34 만으로는 부족한가

| 이미 배운 것 | 남는 질문 |
|---|---|
| §08 HNSW 로 근사 최근접을 빠르게 찾는다 | **그 벡터를 만드는 모델은 무엇으로 고르나** |
| §34 nDCG 로 순위 품질을 잰다 | **판정 세트 자체가 편향돼 있으면 어떻게 아나** |
| §09 RRF 로 BM25 와 벡터를 섞는다 | **질의 벡터를 요청 경로에서 만들 여유가 있나** |
| §45 3-tier 로 offline→online 을 잇는다 | **모델을 바꾸면 그 파이프라인의 무엇이 무효가 되나** |

이 넷이 이 챕터의 목차다.

---

## 3. 두 개의 타워 — 비용이 비대칭이라는 것이 설계의 출발점

임베딩 검색의 표준 구조는 **two-tower(dual-encoder)** 다. 질의 타워와 문서 타워가 같은 벡터 공간으로
따로 인코딩하고, 유사도는 내적/코사인 한 번으로 끝난다.

```
문서 타워  →  [배치 인코딩]  →  ANN 색인      ← 오프라인. 몇 시간 걸려도 된다
질의 타워  →  [단건 인코딩]  →  kNN 질의      ← 온라인. 수십 ms 안에 끝나야 한다
```

**cross-encoder 와의 차이가 여기 있다.** cross-encoder 는 (질의, 문서) 쌍을 함께 넣어야 점수가 나오므로
후보 수만큼 순전파가 필요하다 — 5만 문서를 훑을 수 없다. 그래서 표준 배치는:

| 단계 | 모델 | 비용 | 역할 |
|---|---|---|---|
| 후보 생성(retrieval) | two-tower | 질의당 1회 인코딩 + ANN | 5만 → 수백 |
| 재순위(ranking) | cross-encoder / LTR | 후보 수만큼 | 수백 → 10 (§10) |

Google Cloud 의 two-tower 문서가 정리한 핵심도 같다 — **후보 임베딩을 전부 미리 계산해 두면
서빙 계산이 「질의를 벡터로 바꾸기」와 「유사 벡터 찾기」 둘로 줄어든다.**

> [!tip] 이 비대칭이 자원 제약을 푸는 손잡이다
> 문서 타워는 언제 돌려도 되므로 **모델 크기 제약이 없다**. 제약은 질의 타워에만 걸린다.
> 자원이 부족하면 「작은 모델 하나」가 아니라 **「질의 타워를 어떻게 싸게 만드나」**를 먼저 묻는다.

---

## 4. 고르기 — 리더보드는 순위를 정해주지 않는다

### 4.1 종합 점수와 도메인 검색은 다른 것을 잰다

MTEB(Massive Text Embedding Benchmark) 다국어 종합 점수는 분류·클러스터링·STS(문장 유사도)를 섞은
평균이다. 검색만 보면 순위가 달라지고, **언어를 좁히면 또 달라진다.**

자체 실측(관광지 44,924건 · 판정 24질의)에서 나온 역전 예:

| 모델 | ko 벡터 단독 | ko 하이브리드 | en 벡터 단독 | en 하이브리드 |
|---|---|---|---|---|
| BM25 (기준) | 0.6802 | — | 0.6271 | — |
| Qwen3-Embedding-4B | **0.7764** | **0.7343** | 0.7158 | **0.6890** |
| arctic-embed-l-v2.0-ko | 0.7313 | 0.7199 | 0.7053 | 0.6801 |
| harrier-oss-270m | 0.7127 | 0.7137 | **0.7208** | 0.6810 |
| multilingual-e5-small | 0.7018 | 0.7119 | 0.6036 | 0.6574 |

**영어 벡터 단독 1위(harrier)와 영어 하이브리드 1위(Qwen3)가 다르다.** 배포하는 것이 하이브리드라면
벡터 단독 표로 고르면 틀린 답이 나온다. **배포 형태와 같은 조건으로 재야 한다**는 것이 첫 규칙이다.

### 4.2 판정 기준이 아닌 것으로 후보를 떨어뜨리지 않는다

자체 사례: 처음에 큰 모델을 「인코딩이 느리다」로 배제했다. 그런데 그 설계에서 인코딩은
**오프라인 문서 타워**에서만 일어나 사용자 요청 경로에 없었다. 판정 기준이 아닌 축으로 후보를
지운 것이고, 다시 재자 nDCG 가 0.7313 → 0.7764 로 갈렸다.

> **체크리스트 — 후보를 지우기 전에 그 축이 실제로 요청 경로에 있는지 확인한다.**
> 인코딩 속도는 질의 타워에서만 비용이고, 문서 타워에서는 배치 시간일 뿐이다.

### 4.3 먼저 지우는 것 — 기술이 아니라 계약

| 지우는 이유 | 예 | 확인 방법 |
|---|---|---|
| 비상업 라이선스 | CC BY-NC 계열 | `cardData.license` |
| 다중 벡터(late-interaction) | ColBERT 류 | 단일 벡터 k-NN 필드에 안 들어간다 |
| 커스텀 코드 요구 | `auto_map` / `modeling_*.py` | `trust_remote_code=True` 가 필요하면 상주 후보에서 제외 |
| pickle 전용 배포 | safetensors 없음 | 역직렬화가 곧 코드 실행 |
| gated 저장소 | 라이선스 수동 승인 | 자동 이미지 빌드가 막힌다 |

### 4.4 지시문(instruction)은 계약이다

Qwen3·Harrier·E5 계열은 **질의에 접두어를 붙이는** 모델이다(`query: ` / `Instruct: … Query: `).
색인과 질의가 같은 함수를 타지 않으면 **예외 없이 조용히 틀린 벡터**가 나온다.
접두어를 한 곳에서만 만들고 양쪽이 그 함수를 부르게 강제한다.

## 5. 학습 — 로그가 라벨이 되는 지점

오픈 모델을 그대로 쓰는 것과 자기 로그로 파인튜닝하는 것 사이가 이 절이다.

### 5.1 클릭·전환이 학습 쌍이 된다

Airbnb 의 EBR(Embedding-Based Retrieval) 사례는 **검색 상호작용 이력에서 학습 쌍을 만든다** —
클릭과 예약(booking)을 관련성 라벨로 쓴다. Etsy 의 unified embedding, Walmart 의 semantic retrieval,
Uber Eats 의 다국어 시맨틱 검색도 같은 골격이다.

```
(질의 q, 클릭/전환된 문서 d⁺)          → positive
(질의 q, 노출됐지만 안 눌린 문서 d⁻)   → hard negative
(질의 q, 무작위 문서 d⁻⁻)              → easy negative
```

### 5.2 hard negative 가 품질을 정한다

무작위 음성만 쓰면 모델이 「관련 있음 vs 완전히 무관함」만 배운다. 실제 검색은
**비슷한 것들 중에서 고르는** 문제라, 같은 분류·같은 지역처럼 **가깝지만 틀린** 것을 음성으로 넣어야
경계가 학습된다. 비율을 너무 올리면 학습이 불안정해지므로 easy 와 섞는다.

> [!warning] 학습이 편향을 그대로 상속한다
> 로그는 이미 현행 랭커가 노출한 것만 담고 있다(§45 exposure bias). 그대로 학습하면
> **현행 시스템을 모사하는 모델**이 된다. §45 의 처방(IPS 가중, 5% random exploration)이
> 랭킹뿐 아니라 **임베딩 학습 데이터에도 그대로 적용된다.**

### 5.3 언제 파인튜닝하지 않는가

| 상황 | 판단 |
|---|---|
| 클릭 로그가 없거나 브라우즈뿐 | 파인튜닝 불가 — 오픈 모델 + 사람 판정으로 시작 |
| 도메인 어휘가 일반 웹과 크게 다름 | 파인튜닝 이득이 큼 |
| 다국어이고 한쪽 언어 로그만 많음 | 그 언어만 좋아지고 다른 쪽이 퇴행할 수 있다 — 언어별로 따로 잰다 |
| 코퍼스가 수만 건 규모 | 오픈 모델 선정 이득(0.05~0.1 nDCG)이 파인튜닝 이득보다 클 수 있다 |

## 6. 재기 — 판정 세트가 편향되는 방식

§34 가 메트릭 수식이라면 여기는 **그 메트릭에 넣을 판정을 어떻게 모으나**다.

### 6.1 풀링(pooling)과 그 편향

TREC 이래의 표준은 **여러 시스템의 상위 k 를 합집합으로 모아 사람이 판정**하는 것이다(pooling).
판정되지 않은 문서는 대개 비관련으로 처리되므로, **풀에 안 들어간 시스템은 손해를 본다.**

자체 사례가 교과서적이었다. BM25 후보만으로 판정 세트를 만든 뒤 벡터 모델을 재자:

```
BGE-M3 nDCG@10 = 0.4811   (BM25 0.6802 보다 낮음)
그런데 결과를 눈으로 보면 멀쩡했다.
원인: BGE-M3 상위 10 중 판정된 것이 57.5% 뿐 — 나머지는 "판정 없음"으로 0점
```

각 후보의 벡터 상위 10 을 풀에 병합하고 새 후보 249건을 추가 판정하자 값이 뒤집혔다.

> **판정 세트는 그것을 만든 시스템에만 공정하다.**
> 새 시스템을 비교표에 올리기 전에 **그 시스템의 후보를 풀에 병합**하고, 비교표에는
> 항상 **커버리지(판정된 비율)를 함께 적는다.** 커버리지 없는 비교표는 믿지 않는다.

**같은 함정이 즉시 재발했다.** 위 교훈을 적은 사흘 뒤 새 후보(granite-97m)를 같은 판정 세트로
재자 ko 0.3693 / en 0.3938 — BM25(0.6802 / 0.6271)보다 한참 낮게 나왔다. 커버리지를 재 보니:

| | 상위 10 중 판정된 것 |
|---|---|
| ko | 106 / 240 = **44.2%** |
| en | 119 / 240 = **49.6%** |

「비 오는 날 갈만한 곳」·「서울 근교 드라이브」·`beach near busan` 은 **10개 전부 판정 없음**이었다.
즉 이 숫자는 품질이 아니라 **그 모델이 판정 풀에 없었다는 사실**을 재고 있다.

> **운영 규칙**: 새 모델을 비교표에 올리는 절차는 두 단계다 — ① 상위 k 를 풀에 병합하고 판정,
> ② 그 다음에 재측정. ①을 건너뛴 숫자는 **표에 적지 않는다.** 적어 두면 나중에 누군가
> 그 모델을 근거 없이 배제한다.

### 6.2 질의 수가 곧 분해능이다

질의 6개로 재면 **한 질의가 결과의 17%**다. 우연히 잘 맞는 질의 하나가 순위를 뒤집는다.
자체 사례에서 영어를 6 → 24 질의로 늘리자 실제로 모델 순위가 바뀌었다.

| 질의 수 | 질의 1개의 비중 | 용도 |
|---|---|---|
| 5~10 | 10~20% | 스모크 — 「완전히 틀리지 않았나」 |
| 20~30 | 3~5% | 후보 선별 |
| 100+ | ~1% | 근소한 차이 판정 · 회귀 감시 |

### 6.3 판정 없이 시작하는 법

노출·클릭 로깅이 없으면 로그에서 부트스트랩할 수 없다. 그때는 사람이 20~30 질의의 상위 5를 판정해
파일로 두고, **사용자와 같은 공개 API** 를 호출해 그 파일을 기대값으로 쓴다.
LLM 초안 판정 + 사람 검수 혼합도 실무 표준에 들어왔고, **항목마다 출처(`by:`)를 남겨** 나중에
사람 판정만으로 다시 계산할 수 있게 한다.

### 6.4 그리고 offline 은 proxy 다

여기서 §45 로 넘어간다. offline nDCG 가 올라도 online 이 안 오르는 일은 흔하다.
Airbnb 는 이것을 **3단계 절차**로 처리한다 — 먼저 offline nDCG 로 랭커를 거르고,
통과한 것만 **interleaving** 으로 온라인 검증하고, 거기서 유망한 것만 **A/B** 로 보낸다.
interleaving 은 A/B 보다 빠르고 offline 보다 정확한 중간 단계다.

```
offline nDCG (분 단위, 위험 0)
   ↓ 통과한 것만
interleaving  (일 단위, 노출 위험 낮음)
   ↓ 유망한 것만
A/B 테스트    (주 단위, 비즈니스 지표)
```

## 7. 서빙 — 질의 타워를 어디에 두나

문서 타워는 배치라 문제가 아니다. 실시간 경로는 질의 타워 하나다.

### 7.1 네 자리

| 자리 | 지연 | 운영 비용 | 언제 |
|---|---|---|---|
| **전용 추론 서버**(TEI · Triton) | GPU 수 ms | 서버 상시 | 트래픽 크고 자원 있음 |
| **애플리케이션 내장**(ONNX Runtime) | CPU 수십 ms | 배포 단위에 묶임 | 작은 모델 · 파드 추가 불가 |
| **사이드카** | CPU 수십 ms | 파드 +1 | 언어가 다를 때(JVM ↔ Python) |
| **질의 사전**(미리 계산) | 조회 1회 | 상주 0 | 자원이 없고 질의가 head-heavy |

HuggingFace TEI(Text Embeddings Inference) 같은 전용 서버는 dynamic batching·Flash Attention·
텐서 병렬을 제공한다. 운영 지침으로 자주 언급되는 것은 **온라인 질의 인코딩은 배치 토큰 상한을
낮게(4k~16k) 잡아 지연을 줄인다** — 처리량과 지연의 손잡이가 반대 방향이기 때문이다.

### 7.2 지연 예산을 나눠 적는다

```
검색 P99 300ms
├─ 질의 이해(분석·정규화)      ~5ms
├─ 질의 인코딩                 ← 여기가 모델 크기가 들어오는 자리
├─ ANN + BM25 병렬 실행        ~10~30ms
├─ 융합(RRF)                   ~1ms
└─ 재순위(cross-encoder, 선택) ~20~50ms
```

**질의 인코딩에 얼마를 줄 수 있는지가 모델 크기의 상한을 정한다.** 반대로 모델을 먼저 고르고
지연을 나중에 재면 되돌릴 수 없다(색인이 이미 그 공간에 묶여 있다).

### 7.3 캐시가 실제로 듣는가

질의 벡터 캐시(또는 사전)의 이득은 **적중률에 정비례**한다. 미적중은 이득이 0 이다.
그래서 「캐시하면 되지」는 답이 아니고, **질의 분포가 head-heavy 한지**가 답이다.

라이브 인코딩과 사전 방식의 우열은 나눗셈 한 줄로 갈린다.

```
사전(큰 모델) 기대 이득 = 적중률 × Δ_큰모델
라이브(작은 모델) 이득  =            Δ_작은모델

라이브가 이기는 적중률 = Δ_작은모델 / Δ_큰모델
```

자체 실측 대입(ko, BM25 기준): 작은 모델 +0.0317 / 큰 모델 +0.0541 → **적중률 58.6% 미만이면
라이브가 이긴다.** 자동완성에서 고른 검색이 많으면 넘기 쉽고, 자유 입력이 매번 새로우면 못 넘는다.
**적중률을 재기 전에는 사전 방식을 채택할 근거가 없다.**

### 7.4 제약 노드의 눈금 (자체 실측, Ampere A1 · Neoverse-N1 4코어)

| 모델 | 파라미터 | 1코어 p50 | RSS | 비고 |
|---|---|---|---|---|
| granite-embedding-97m-r2 | 97M | 36.5ms | 753MB | fp32 강제 필요 |
| multilingual-e5-small | 118M | 43.8ms | 529MB | 체크포인트가 이미 fp32 |
| harrier-oss-270m | 270M | 123.7ms | 1,605MB | fp32 강제 필요 |
| (외삽) 4B 급 | 4,020M | ~1,800ms | fp16 8GB | 상주 불가 |

두 가지가 교과서에 없는 실무 지식이다.

> [!warning] 작은 모델은 코어를 더 줘도 안 빨라진다
> e5-small 은 1스레드 43.8ms, 2스레드 45.1ms 로 사실상 같았다. 단건 인코딩은 병렬화 이득이
> 거의 없다 — **질의 타워 사이드카에 1코어면 충분하다**는 뜻이고, 자원 산정이 크게 달라진다.

> [!warning] 체크포인트 dtype 이 하드웨어와 맞는지 본다
> 2025년 이후 모델은 대부분 **bf16 저장**인데, ARM Neoverse-N1 에는 bf16 명령이 없다(N2/V1부터).
> 그대로 적재하면 `mkldnn_matmul bf16 path needs a cpu with bf16 support` 로 BLAS 폴백에 떨어져
> 쓸 수 없을 만큼 느려진다. **fp32 로 강제 적재하면 정상 속도로 돈다** — 하드웨어 한계가 아니라
> 적재 옵션 문제다. 파라미터 수만 보고 후보를 지우면 이걸 놓친다.

## 8. 교체 — 벡터 공간이 바뀐다는 뜻

### 8.1 모델을 바꾸면 색인이 무효가 된다

임베딩 모델이 다르면 **좌표계가 다르다.** 옛 벡터와 새 질의 벡터 사이의 코사인 거리는
숫자는 나오지만 뜻이 없다. 그래서 모델 교체는 설정 변경이 아니라 **전량 재임베딩 + 재색인**이다.
같은 모델의 양자화본(int8)으로 바꾸는 것도 좌표가 이동하므로 같은 취급이다(§41).

### 8.2 모델 스탬프로 두 공간을 격리한다

문서마다 **어느 공간의 벡터인지**를 필드로 박고, 벡터 레그 질의에 그 필드 필터를 건다.

```
model_ref = "{hf_id}@{commit_sha7}#d{dim}"      예: Qwen/Qwen3-Embedding-4B@5cf2132#d1024
```

- 재색인이 아직 옛 스탬프 문서를 갖고 있으면 그 문서는 **벡터 레그에서 빠지고 키워드 레그로만** 올라온다.
- 필터는 **두 레그에 각각** 건다 — 하이브리드는 레그별로 후보를 뽑아 합치므로 한쪽만 걸면 다른 쪽이 샌다.
- 커밋 sha 를 넣는 이유는 **같은 이름의 저장소가 나중에 바뀔 수 있어서**다. 재현성과 보안이 같은 이유로 묶인다.

### 8.3 무중단 전환의 모양

```
1. 새 스탬프로 문서 벡터 생성        (오프라인, 며칠 걸려도 무방)
2. 새 인덱스에 색인 + alias 는 아직 옛 것
3. 판정 세트로 새 인덱스 nDCG 측정   ← offline 게이트
4. interleaving 으로 온라인 비교      ← §45
5. alias swap
6. 옛 인덱스 보관 기간 후 삭제
```

**3번을 건너뛰면 되돌릴 근거가 없다.** 새 모델이 리더보드에서 더 좋다는 것은 내 코퍼스에서
더 좋다는 뜻이 아니다(§4.1).

### 8.4 텍스트 규칙도 스탬프의 일부다

문서를 어떤 문자열로 조립해 인코딩했는지(제목만? 본문 포함? 주소 포함?)가 바뀌면
벡터도 바뀐다. 그래서 **임베딩 텍스트의 해시**를 함께 저장해 멱등성을 만든다.

```
text_hash = sha256(model_ref + "\n" + embedding_text)
```

바뀌지 않은 문서는 다시 인코딩하지 않고 **touch 만** 한다. 이 한 줄이 일일 배치의 비용을
「전체」에서 「변경분」으로 바꾼다.

자체 실측에서 텍스트 규칙 6종을 비교한 결과, **제목·분류·주소·개요를 모두 넣은 v1 이 1위**였고
이름만 쓰면 0.7939 → 0.6379 로 급락했다 — **개요 본문이 이 도메인의 실제 재료**라는 뜻이다.
규칙 후보는 첫 채움 전에 닫아야 한다. 뒤에 바꾸면 전량 재임베딩이다.

## 9. 자원이 무한할 때 vs 제약이 있을 때

같은 파이프라인이 자원에 따라 어디까지 접히는지가 이 절이다.

| 단계 | 자원 무제한 (엔터프라이즈) | 제약 노드 (단일 무료 인스턴스) |
|---|---|---|
| 모델 | 자체 학습 two-tower + 주기 재학습 | 오픈 모델, 자기 판정 세트로 선정 |
| 학습 데이터 | 클릭·전환 로그 + hard negative 마이닝 | 로그 없음 → 사람 + LLM 초안 판정 |
| 문서 인코딩 | GPU 클러스터 배치, 시간 단위 | 노트북/노드 CPU, 시간~일 단위 |
| 질의 인코딩 | GPU 추론 서버(TEI/Triton), 수 ms | CPU 1코어 사이드카 수십 ms, 또는 사전 |
| 색인 | 샤딩 + 복제 + IVF-PQ/BBQ 양자화 | 단일 인덱스 HNSW, 차원으로 메모리 조절 |
| 평가 | offline → interleaving → A/B → ramp | offline nDCG 만 (트래픽 부족) |
| 재순위 | cross-encoder / LLM 랭커 | 없음 — 융합(RRF)까지 |
| 교체 | blue-green + 자동 롤백 | alias swap 수동 |

> [!tip] 접는 순서가 정해져 있다
> 자원이 줄면 **재순위 → 파인튜닝 → 온라인 평가 → 질의 타워 상주** 순으로 접힌다.
> 마지막까지 남는 것은 **문서 벡터 + ANN + 융합** 이고, 그것만으로도 BM25 대비 이득이 나온다
> (자체 실측 +0.03~0.05 nDCG). 제일 먼저 접히는 재순위가 제일 비싼 것도 우연이 아니다.

| 함정 | 증상 | 처방 |
|---|---|---|
| 판정 세트가 한 시스템에서만 나옴 | 새 모델이 BM25 보다 낮게 나옴 | 풀 병합 + 커버리지 병기 (§6.1) — **두 번 겪었다** |

| 질의/문서 접두어 불일치 | 예외 없이 품질만 떨어짐 | 접두어를 한 함수에 (§4.4) |
| 모델 교체를 설정 변경으로 취급 | 거리가 뜻을 잃음 | 스탬프 + 필터 + 재색인 (§8.2) |
| bf16 체크포인트를 그대로 적재 | ARM 에서 수십 배 느려짐 | fp32 강제 (§7.4) |
| 큰 모델을 캐시로 감당하려 함 | 미적중 질의는 이득 0 | 손익분기 계산 (§7.3) |
| 인코딩 결과를 평가 뒤에 저장 | 평가에서 죽으면 몇 시간 소실 | 인코딩 직후 저장 |

## 11. 자가 점검

1. two-tower 구조에서 **질의 타워만** 실시간 제약을 받는 이유를 한 줄로 설명하라.
2. 판정 세트에 새 모델의 후보를 병합하지 않으면 그 모델의 nDCG 는 어느 방향으로 편향되는가.
3. `라이브가 이기는 적중률 = Δ작은모델 / Δ큰모델` 이 성립하는 전제는 무엇인가.
4. 모델 스탬프에 커밋 sha 를 넣는 이유를 **재현성**과 **보안** 두 관점에서 각각 답하라.
5. offline nDCG 가 올랐는데 A/B 가 안 오르는 대표적 원인 셋(§45)을 들고, 그중 임베딩 **학습**에도
   그대로 적용되는 것을 골라라.
6. 자원이 줄어들 때 파이프라인이 접히는 순서와, 마지막까지 남는 구성 요소를 답하라.
